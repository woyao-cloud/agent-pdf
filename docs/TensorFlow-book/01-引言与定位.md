# 第 1 章 引言与定位

> **本章导读**：理解 TensorFlow 想解决什么问题、它的历史脉络与整个生态地图。读完后你能回答：什么时候应该用 TF？它的强项在哪里？这一章是地图，后续章节是城市的具体街区。

## 1. 基础层：TensorFlow 解决什么问题

### 1.1 现实痛点

如果你尝试用裸 NumPy 训练一个稍大点的神经网络，会立刻撞上几堵墙：

1. **没有自动微分**：你必须手推每一层的反向传播公式
2. **没有 GPU 加速**：CPU 上几小时的训练在 GPU 上只要几分钟
3. **没有分布式抽象**：多卡多机训练需要自己写参数同步
4. **没有部署方案**：训练完的模型怎么放到手机、浏览器、生产服务里？

TensorFlow 把这四件事打包成一个工程化体系：

| 痛点 | TF 提供的能力 |
|------|--------------|
| 反向传播复杂 | `tf.GradientTape` 自动微分 |
| 异构硬件 | 同一份代码自动跑 CPU/GPU/TPU |
| 大规模训练 | `tf.distribute` 分布式策略 |
| 部署碎片化 | SavedModel 一份模型、Serving/TFLite/TFJS 多端推理 |

### 1.2 一个最小例子

```python
# requires: tensorflow>=2.15
import tensorflow as tf

# 数据
x = tf.random.normal([1000, 10])
y = tf.random.normal([1000, 1])

# 模型
model = tf.keras.Sequential([
    tf.keras.layers.Dense(64, activation="relu"),
    tf.keras.layers.Dense(1),
])

# 编译 + 训练 + 预测
model.compile(optimizer="adam", loss="mse")
model.fit(x, y, epochs=3, batch_size=32, verbose=0)
print(model.predict(x[:1]))
```

七行核心代码完成"数据→模型→训练→推理"的全链路。这是 TF 2.x 时代的常态：高层 API 把繁琐的样板隐藏起来，但下面藏着的是一个工业级的引擎。

## 2. 进阶层：TensorFlow 的历史脉络

### 2.1 关键节点

```
2015-11  TF 1.0 开源（Google Brain 团队，DistBelief 继任者）
         |  特征：静态计算图、Session.run、Placeholder
         |  痛点：调试难、API 凌乱
2017-02  Keras 加入 tf.keras
2017-11  Eager Execution 首次亮相（实验特性）
2019-09  TF 2.0 GA
         |  默认 Eager + tf.function 装饰器
         |  Keras 提升为官方高层 API
         |  API 大量重命名 / 合并
2020-05  TFLite Micro（MCU 端推理）
2021-04  TF 2.5 起稳定支持 mixed_float16
2022    TFX 完整 ML 流水线方案成熟
2023+   生态稳定：与 PyTorch 形成"研究 PT、生产 TF"分工
2024+   Keras 3 多后端（同时支持 TF/JAX/PyTorch）
```

### 2.2 1.x → 2.x 的核心转变

TF 1.x 的心智模型是**先定义图，后执行**：

```python
# TF 1.x 风格（仅作对照，不要再写新代码）
x = tf.placeholder(tf.float32, [None, 784])
W = tf.Variable(tf.zeros([784, 10]))
b = tf.Variable(tf.zeros([10]))
y = tf.nn.softmax(tf.matmul(x, W) + b)

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    sess.run(y, feed_dict={x: batch})
```

TF 2.x 的心智模型是**算子立即求值**，需要静态图优化时再用 `@tf.function` 包起来：

```python
@tf.function  # 此装饰器把函数体转成图
def step(x, W, b):
    return tf.nn.softmax(x @ W + b)
```

这一转变直接对标 PyTorch 的动态图体验，但保留了图模式的部署与性能优势。第 2 章会深入讲清这件事是怎么做到的。

> 💡 阅读官方迁移指南：`https://www.tensorflow.org/guide/migrate` 仍然是 1.x → 2.x 项目最权威的资料。

## 3. 生态全景

TF 不是一个库，而是一组围绕 SavedModel 这个"通用货币"运转的工具链。

```
                ┌──────────────────────────────────────┐
                │           你的训练代码                │
                │     (Python + tf.keras + tf.data)    │
                └─────────────────┬────────────────────┘
                                  │
                          训练 ↓ 检查点
                                  │
                ┌─────────────────▼────────────────────┐
                │          SavedModel 标准格式          │
                │   (graph + weights + signatures)     │
                └──┬───────────┬────────────┬──────────┘
                   │           │            │
            服务端 ↓     移动/IoT ↓    浏览器/Node ↓
        ┌──────────┐  ┌──────────┐   ┌───────────┐
        │TF Serving│  │  TFLite  │   │   TFJS    │
        │(gRPC/REST│  │(Android, │   │(浏览器、  │
        │  在线推理)│  │ iOS, MCU)│   │ Node.js)  │
        └──────────┘  └──────────┘   └───────────┘
```

主要子项目快览：

| 子项目 | 定位 | 你什么时候会用到 |
|--------|------|----------------|
| **Keras** | 高层 API（已成为 TF 官方前端） | 99% 的训练代码 |
| **tf.data** | 输入管道 | 数据加载/预处理永远不掉队 |
| **tf.distribute** | 分布式训练 | 多 GPU / 多机 / TPU |
| **TFX** | 端到端 ML 流水线 | 生产化、可复现训练 |
| **TF Serving** | 在线推理服务 | gRPC/REST 模型服务 |
| **TFLite** | 端侧推理 | Android / iOS / 嵌入式 |
| **TFJS** | JavaScript 运行时 | 浏览器、Node.js 推理 |
| **TF-Agents** | 强化学习 | RL 算法库 |
| **TFRS** | 推荐系统 | 检索 + 排序两塔模型 |
| **TFP** | 概率编程 | 贝叶斯模型 / 不确定性估计 |
| **TF Quantum** | 量子机器学习 | 与 Cirq 集成 |
| **TensorBoard** | 可视化 | 训练监控 / Profiler |
| **MLIR + XLA** | 编译栈 | 你不直接调用，但它决定性能 |

## 4. 何时该用 TF、何时不用

### 4.1 倾向使用 TF 的场景

- ✅ **需要规模化生产部署**：移动端、IoT、浏览器、TPU 多端推理
- ✅ **需要稳定的端到端流水线**：TFX 是最成熟的 ML pipeline 方案之一
- ✅ **使用 TPU**：TPU 是 Google 一等公民，对 TF 支持远好于其他框架
- ✅ **大型组织的工程化诉求**：版本兼容承诺、签名校验、监控接入完整

### 4.2 倾向不用 TF 的场景

- ⚠️ **学术研究、快速原型**：PyTorch 在论文社区已成事实标准
- ⚠️ **小团队、追求开发体验**：PyTorch 调试、错误信息更友好
- ⚠️ **需要最新模型实现**：Hugging Face 的最新模型先在 PyTorch 落地
- ⚠️ **超大规模 LLM 训练**：JAX + Flax + GSPMD 在前沿训练栈中势头更猛

### 4.3 一个判断 checklist

回答下面 5 个问题，3 个以上"是"则倾向选 TF：

- [ ] 模型最终要部署到移动端 / 浏览器 / IoT？
- [ ] 团队需要严格的版本兼容、签名 SavedModel 校验？
- [ ] 公司基础设施已经投入 TFX / TFServing / TPU？
- [ ] 训练数据规模 > 10TB，需要稳定的 tf.data 管道？
- [ ] 维护周期长达数年，希望避免框架替换风险？

## 5. 小结与延伸阅读

**关键回顾**：

- TF 解决的核心问题是 **自动微分 + 异构硬件 + 分布式 + 跨端部署** 的工程化打包
- TF 2.x 用 Eager + `tf.function` 同时拿到了"调试友好"和"生产高效"
- TF 不是一个库，是以 SavedModel 为核心的工具链生态
- 选 TF 还是 PyTorch 取决于场景：研究偏 PT，生产偏 TF（不绝对，第 10 章详细对比）
