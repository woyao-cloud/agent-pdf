# 第9章 企业微调实践与工作流

## 9.1 企业微调成熟度模型

企业在将大模型微调落地到生产环境时，通常会经历五个成熟度等级。理解当前所处阶段，有助于规划合理的投入节奏。

**L1: 仅提示工程** — 团队仅使用 Prompt Engineering 满足业务需求，零微调投入。适用于验证阶段，但无法深度定制模型行为。

**L2: 即兴微调实验** — 工程师在个人笔记本或单机 GPU 上运行微调脚本，缺乏标准化流程。实验结果难以复现，代码和数据集散落在个人目录中。常见于技术验证期。

**L3: 标准化微调流水线** — 建立了基于脚本或工作流引擎的固定管道。数据清洗、训练、评估步骤被标准化。实验结果通过实验管理工具（如 MLflow、Weights & Biases）记录。团队开始使用统一的 base model 和超参数模板。

**L4: 自动化 MLOps 流水线** — 微调流水线与 CI/CD 集成。数据变更自动触发重新训练，模型自动评估并与基线对比。部署流程包含 A/B 测试和渐进式发布。监控系统捕获生产环境中的模型退化信号。

**L5: 持续学习与模型治理** — 建立模型生命周期管理机制。定期用新数据增量训练，自动检测数据漂移和概念漂移。完整的模型治理框架覆盖审计、合规、偏见检测和模型退役流程。

> **案例**: 某金融科技公司从 L1 起步，6 个月内推进到 L3。关键转折点发生在一次"上周能复现的结果今天跑不出来了"的事件后，团队强制推行了实验记录和随机种子固定制度，随后逐步建立了标准化评估集和自动评测流水线。

## 9.2 企业级微调工作流（12步）

### 步骤1：业务需求分析与任务界定

与业务方共同明确：目标任务是什么？衡量标准是什么？当前方案（人工规则或 Prompt）的瓶颈在哪里？常见误区是试图用一个模型解决所有问题。建议将复杂任务拆解为多个子任务，每个子任务由专门的模型或策略处理。

### 步骤2：基线评估

在微调之前，必须先建立基线。分别使用纯 Prompt 和 RAG（检索增强生成）方案评估目标任务。记录准确率、延迟、成本等关键指标。基线评估回答一个关键问题：**微调带来的提升是否值得投入**？如果 Prompt + RAG 已经满足业务需求，微调可能不是当前优先事项。

### 步骤3：数据收集、整理与质量保证

收集真实业务场景中的输入输出对。数据来源包括：人工标注、用户反馈日志、专家总结、历史工单。建立数据质量检查清单：

- 每条数据是否有明确的输入和期望输出
- 标注一致性是否经过校验（建议使用 Cohen's Kappa 系数）
- 是否存在偏见或有害内容
- 数据分布是否覆盖了所有边缘场景

### 步骤4：数据隐私与合规审查

在训练之前，必须对数据进行脱敏处理。常见的 PII（Personally Identifiable Information）包括：姓名、电话、邮箱、身份证号、IP 地址。使用正则匹配或 NER 模型识别并替换敏感信息。建议形成数据合规 checklist，并由法务部门会签。

### 步骤5：基座模型选择

选择 base model 的核心考量维度有三：**参数量级**（7B、13B、70B 等直接影响推理成本和部署难度）、**许可证**（如 Llama 2 Community License 允许商用但有限制，Mistral 使用 Apache 2.0 更宽松）、**能力基线**（推荐先在小规模代表性数据集上横向对比多个模型的 zero-shot 性能）。经验法则：能用小模型解决就不用大模型，7B 模型经过充分微调在特定任务上往往能超越未微调的 70B 模型。

### 步骤6：微调方案选择

根据数据量和任务类型选择微调策略：

- **数据量 < 1000 条**: 优先考虑 Prompt Engineering 或 Few-shot 方法。若必须微调，推荐 LoRA（Low-Rank Adaptation），rank=8~16。
- **数据量 1000~10000 条**: LoRA / QLoRA 是主流选择。可尝试 DoRA（Weight-Decomposed Low-Rank Adaptation）以获得更好的训练稳定性。
- **数据量 > 10000 条**: 可以考虑 Full Fine-tuning，但需要评估灾难性遗忘（Catastrophic Forgetting）的风险，通常需要混合通用数据共同训练。

### 步骤7：训练基础设施

选择训练基础设施时需综合考虑预算、数据安全要求和团队运维能力：

- **云服务**: AWS SageMaker、GCP Vertex AI、Azure ML 提供了托管训练环境，降低运维负担。按需付费，适合初期探索。
- **自建集群**: 数据安全要求高的企业（如金融、医疗）倾向于自建。常用方案包括 Slurm 集群管理 + NVIDIA A100/H100 GPU。
- **成本优化**: 在云上使用 Spot Instance 可以降低 60~70% 的训练成本。建议使用 checkpoint 自动保存和恢复机制，应对 Spot 实例被回收的场景。

### 步骤8：实验跟踪与版本管理

使用 MLflow 或 W&B 记录每次实验的完整上下文：超参数、数据版本、base model 版本、训练损失曲线、评估指标。**随机种子必须固定**（推荐 seed=42），确保结果可复现。建议为每个实验生成唯一的 Run ID，并在模型名称中编码关键参数信息。

### 步骤9：模型评估与验收测试

评估不应只看单一指标。企业级评估体系应包含：

- **自动评估**: 在标准化测试集上的准确率、ROUGE/BLEU（生成类任务）、回答完整性等自动指标。
- **人工评估**: 由领域专家对模型输出进行 1~5 分打分，重点关注事实准确性、安全性和格式规范。
- **场景测试**: 构造针对性的 adversarial examples，测试模型的鲁棒性。
- **回归测试**: 确保模型在新任务上的提升不会导致已有旧任务上的退化。

### 步骤10：模型部署与服务化

模型上线前需进行量化和性能测试。常用部署方案：

- vLLM 或 TensorRT-LLM 作为推理引擎，支持 PagedAttention 和 Continuous Batching
- FP16 或 INT8 量化，将 70B 模型从 ~140GB 压缩到 ~70GB（FP16）或 ~35GB（INT8）
- 设置合理的推理超时和重试策略
- 部署多个模型副本实现高可用

### 步骤11：监控与维护

生产环境的模型并非一劳永逸。需要持续监控：

- **输入监控**: 数据分布是否发生变化（Data Drift）
- **输出监控**: 输出质量指标是否下降，用户反馈的负面率
- **性能监控**: 推理延迟 P50/P99、GPU 利用率、内存使用

### 步骤12：模型治理与合规

建立模型审批流程：训练完成 → 内部评审 → 安全测试 → 合规审查 → 灰度发布 → 全量上线。每次部署需生成模型卡片（Model Card），记录模型用途、训练数据、评估结果和已知限制。

> **案例**: 某银行信用卡客服场景。团队在步骤1-2发现纯 Prompt 方案意图识别准确率仅 72%，RAG 提升到 81%，而微调后达到 94%。步骤4的数据审查发现 12% 的训练样本含客户身份证号，经脱敏处理后重新标注。最终使用 LoRA 微调 Qwen-7B，部署在私有云上，推理延迟控制在 800ms 以内。

## 9.3 团队角色与技能

微调项目成功的关键因素之一是跨职能团队的协作：

- **数据工程师**: 负责数据采集、清洗、脱敏管道建设。技能要求：Python、SQL、Spark、数据质量监控。
- **机器学习工程师**: 负责微调实验、模型评估、部署优化。技能要求：PyTorch、Hugging Face Transformers、LoRA/QLoRA、MLflow。
- **领域专家**: 提供业务知识，审核训练数据质量，参与人工评估。他们是最容易被低估的角色，但恰恰是决定模型"好不好用"的关键。
- **评估员/标注团队**: 执行人工标注和模型输出评分。需要有清晰的标注规范和质检机制，建议每两周轮换标注任务以保持一致性。

> **建议**: 在项目启动初期就建立"三明治协作模式"——ML 工程师与领域专家结对工作，数据工程师处理管道，所有人每周同步一次评估结果。

## 9.4 基础设施深度分析

### 云平台选型

| 平台 | 优势 | 适用场景 |
|------|------|----------|
| AWS SageMaker | 与 S3、IAM 深度集成，生态完善 | 已有 AWS 基础设施的团队 |
| GCP Vertex AI | TPU 支持，BigQuery 集成 | 需要 TPU 训练的大规模项目 |
| Azure ML | 与 Office 365、Azure AD 集成 | 微软技术栈的企业用户 |

### 成本分析：训练 vs 推理

许多团队只关注训练成本，却忽视了推理成本才是长期最大的开支。以一个日活 10 万用户的应用为例：

- **训练成本**: 使用 4×A100 微调 7B 模型约 3 天，按云上 $3~4/GPU-h 计算，约 $864~1,152
- **推理成本**: 同样 7B 模型，FP16 部署在单张 A100 上，假设平均 300 token/请求，每日推理成本约 $80~120
- **结论**: 训练是一次性投入，推理是持续性支出。优化推理（量化、batch、模型蒸馏）往往比优化训练带来更大的长期回报。

### Spot Instance 策略

在 AWS 上使用 Spot Instance 训练可以大幅降低成本。最佳实践：

1. 使用自动 checkpoint 保存（每 5~10 分钟）
2. 选择中断概率较低的实例类型（p4d/p4de 优于 g5）
3. 设置 Spot 多元化策略，跨多个可用区
4. 使用 AWS Health Dashboard 监控 Spot 中断事件
5. 训练脚本需支持从 checkpoint 自动恢复

## 9.5 模型版本控制

### 模型注册表

MLflow Model Registry 和 Hugging Face Hub 是两种主流方案。前者适合企业内部管理，后者更适合开源协作。

**企业级模型标签规范**:
```
{project_name}-{model_type}-{base_model}-{date}-v{version}
# 示例: customer-service-lora-qwen7b-20250315-v2
```

### 数据集版本控制

使用 DVC（Data Version Control）或 Hugging Face Datasets 的版本管理功能。每条数据记录变更历史：谁在什么时间修改了哪条数据，修改原因是什么。

### 可复现性保障

确保复现的三要素：**环境锁死**（Docker 镜像或 Conda env export）、**随机种子固定**、**配置管理**（使用 YAML 配置文件而非硬编码参数）。建议在每次实验结束后自动生成一份"复现报告"，包含所有上下文信息。

## 9.6 模型治理

### 审批工作流

典型的企业模型部署审批流程：

```
模型训练完成 → 内部技术评审 → 安全扫描 → 偏见审计 → 
法务合规审查 → 灰度 5% → 逐步放量 → 全量上线
```

### 偏见与公平性审计

定期检查模型在不同群体（性别、地域、年龄段等）上的表现差异。使用工具如 AI Fairness 360 或 Fairlearn 辅助检测。如果发现某一群体上的表现显著低于平均水平，需要检查训练数据在该群体上的代表性和标注质量。

### 模型卡片

每次模型发布必须附带模型卡片（Model Card），包含：

- 模型用途和预期应用场景
- 训练数据的来源、规模和覆盖范围
- 评估结果（包括不同细分群体上的表现）
- 已知限制和潜在风险
- 联系人和维护者信息

### 法规合规

欧盟 AI Act 将 AI 系统分为不可接受风险、高风险、有限风险和最低风险四级。微调后的模型如果用于高风险场景（如招聘、信用评估），需满足更严格的透明度、人工监督和文档记录要求。中国《生成式人工智能服务管理暂行办法》要求提供者履行内容审核主体责任，不得生成违法信息。

## 9.7 ROI 分析：微调何时真正值得

微调并非万能药。在决策前，可以通过以下框架评估 ROI：

```
微调年化收益 = (微调后质量提升带来的业务增益) - 
              (训练成本 + 额外推理成本 + 维护人力成本)
```

**微调更有优势的场景**:
- 任务有明确的输入输出映射（如分类、抽取、格式转换）
- 需要学习特定的写作风格或术语体系
- 需要对输出格式有严格的结构化要求
- 数据量 3000+ 条高质量标注样本

**非微调的更优选择**:
- 任务过于开放或创意性过高
- 标注成本远超微调收益
- 可用的高质量数据不足 500 条
- 任务可以通过 RAG 或 Prompt 工程以 90% 以上的质量满足需求

> **真实案例**: 某电商公司投入 $50,000 微调客服模型，召回率从 78% 提升至 93%，每年节省人工客服费用约 $200,000，投资回报周期为 3 个月。

本章总结了企业微调的全生命周期实践。核心原则是：**先基线、再微调；先小模型、再大模型；先验证、再规模化**。将这些方法论融入团队的日常工作流中，才能让微调从"工程师的实验"进化为"企业的工程能力"。
