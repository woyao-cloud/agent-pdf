# 第10章 典型问题处理方法

微调过程中的问题千变万化，但大多数可以归纳为有限几类。本章逐一剖析常见问题的根因与解决方案，并提供一个系统化的调试框架。

## 10.1 训练 Loss 问题

### Loss 不下降

**现象**: 训练数个 epoch 后，loss 在较高位置震荡或停滞。

**可能原因与解决方案**:

1. **学习率过小或过大** — 学习率是首要检查项。对于 LoRA 微调，建议初始学习率设置在 1e-4 到 5e-4 之间；Full Fine-tuning 则从 1e-5 到 5e-5 开始。使用学习率预热（Warmup）和余弦衰减调度（Cosine Schedule）。**调试技巧**：在第一个 batch 后打印 loss 值，如果相比随机初始化没有明显下降，检查学习率是否有效。

2. **数据质量问题** — 训练数据中存在大量噪声或 label 错误。建议抽样 100~200 条数据人工检查，计算标注一致性。使用 loss 分布分析找出 loss 异常高的样本，往往能发现错误标注。

3. **基座模型与任务不匹配** — 例如用代码模型做文本分类。切换到更适合目标任务的 base model。

4. **优化器选择不当** — LoRA 微调推荐使用 AdamW（betas=(0.9, 0.999), weight_decay=0.01），而非 SGD。

### Loss 突刺

**现象**: 训练过程中 loss 突然出现尖峰，之后可能恢复也可能持续发散。

**根因与对策**:

- **梯度爆炸**（Gradient Explosion）：梯度范数突然增大到正常值的 100x 以上。解决方案：使用梯度裁剪（Gradient Clipping），设置 `max_grad_norm=1.0`。
- **学习率过高**：遇到 loss 突刺时立即降低学习率 50%，观察是否稳定。
- **数据批次异常**：某个 batch 中包含了异常长的序列或格式错误的样本。在 DataLoader 中加入异常检测逻辑。

> **案例**: 某团队在微调 70B 模型时，loss 每 200 步出现一次尖峰。排查发现训练数据中存在一条 32K token 的超长文本，导致该 batch 的 loss 计算异常。过滤后训练恢复稳定。

### NaN Loss

**现象**: Loss 突然变为 NaN（Not a Number），训练无法继续。

**原因与排查顺序**:

1. **混合精度训练问题** — FP16 训练时梯度下溢或溢出是最常见的原因。解决方案：使用 BF16（如果在 A100/H100 上）替代 FP16；对 loss 使用 `scale` 机制或在 `Trainer` 中开启 `fp16_opt_level="O2"`。
2. **学习率过高** — 降低学习率至当前值的 1/10，重启训练。
3. **数据中包含 NaN 值** — 检查输入数据的每个字段，确保没有 NaN 或 Inf。在数据加载后加入 `torch.isnan()` 断言。
4. **模型权重初始化问题** — 某些层的参数初始化不稳定。尝试加载 base model 的不同 checkpoint。
5. **自定义 loss 函数中的除零错误** — 检查 loss 函数中是否有除法操作，添加 epsilon（如 1e-8）。

### Loss 震荡

**现象**: Loss 在训练过程中持续上下波动，没有明确的下降趋势。

**解决方案**:

- 增大 batch size（如果 GPU 内存允许），减小梯度估计的方差
- 降低学习率，尤其是在使用 AdamW 时
- 检查数据是否按相似长度分桶（Bucket Sampling），减少 padding 带来的噪声
- 增加梯度累积步数（Gradient Accumulation Steps），模拟更大的有效 batch size

### 训练 Loss 下降但评估 Loss 上升（过拟合）

**现象**: 典型的过拟合（Overfitting）信号。

**解决方案**:

- 增加数据量，尤其是目标领域的高质量数据
- 增加 dropout 比例（LoRA 中默认无 dropout，可设置 `lora_dropout=0.1`）
- 降低 LoRA rank 值（从 rank=32 降到 rank=8）以减少可训练参数
- 提前停止（Early Stopping）：监控 eval loss，连续 N 轮不下降则停止训练
- 加入通用数据混合训练：按 7:3 比例混合领域数据与通用数据，保持模型的通用能力

## 10.2 GPU 显存问题

### CUDA Out of Memory

**现象**: 训练或推理时抛出 `CUDA out of memory` 错误。

**系统化诊断流程**:

1. `torch.cuda.memory_summary()` 打印详细显存分配画像
2. 计算理论显存需求：模型参数(FP16) + 优化器状态 + 梯度 + 激活值
3. 检查是否有其他进程占用 GPU：`nvidia-smi` 查看所有进程

**解决方案（按成本从低到高）**:

- 减小 batch size（最直接）
- 使用 Gradient Checkpointing：以计算换显存，可减少 40~60% 激活值占用
- 切换到 QLoRA（4-bit NormalFloat 量化）：将 70B 模型从 ~140GB 压缩到 ~35GB
- 使用 DeepSpeed ZeRO Stage 2 或 3 进行显存优化
- 缩短序列长度（max_seq_length）
- 使用 Paged Optimizer（来自 unsloth 库）减少优化器状态占用

### 显存碎片化

**现象**: `nvidia-smi` 显示有充足显存，但分配大 tensor 时仍然 OOM。

**解决方案**:

- 设置 `PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:128` 减少碎片
- 训练前清空缓存：`torch.cuda.empty_cache()`
- 重启训练进程（长期运行的训练进程中碎片化会逐渐加剧）
- 使用 `torch.cuda.memory_snapshot()` 生成可视化火焰图分析碎片模式

## 10.3 收敛问题

### 模型未学到领域知识

**现象**: 在领域特定问题上的表现没有显著提升，模型仍然依赖通用知识回答。

**根因**: 训练数据中的领域知识密度不够。如果 80% 的训练样本是格式转换或简单问答，模型学到的只是"格式"而非"知识"。

**解决方案**: 重写训练数据，确保每条样本都包含至少一个需要领域知识才能回答的信息点。知识密集型样本占比不低于 60%。

### 灾难性遗忘

**现象**: 模型在目标任务上表现提升，但在通用能力（推理、常识、安全性）上明显下降。

**解决方案**:

- **数据混合训练**: 在训练数据中混入 20~30% 的通用数据（如 Alpaca、ShareGPT 的子集）
- **EWC（Elastic Weight Consolidation）**: 对重要参数施加正则化惩罚，限制其大幅变化
- **LoRA 优于 Full Fine-tuning**: LoRA 的可训练参数少，天生具有更强的抗遗忘特性
- **多阶段训练**: 先在小规模领域数据上粗调，再在混合数据上精调

### 模型只学格式不学内容

**现象**: 输出格式完美符合要求（JSON、Markdown 等），但内容空洞或错误。

**根因**: 训练数据中"简单格式转换"类样本占比过高，模型学会了套壳但没学会填充核心内容。

**解决方案**: 在数据集中增加需要复杂推理的样本，减少格式脚手架样本的比例。每个 batch 中确保有一定比例的"内容密集型"样本。

### 模型输出重复

**现象**: 模型生成的内容不断重复同一个词或句子。

**方案**: 降低 repetition_penalty（默认 1.0 可调至 1.1~1.2），增加 top_k 或 top_p 采样参数，检查训练数据中是否存在大量重复序列。

## 10.4 数据问题

### 标签噪声

**检测方法**: 训练一个初步模型，找出 loss 最高的 5% 的训练样本，人工审查。这通常能发现标注错误、答案不一致或格式混乱的样本。

**处理**: 错误标注的样本重新标注或删除；边界模糊的样本需要制定更明确的标注规范。

### 数据不平衡

**现象**: 模型在某些类别的预测准确率远低于其他类别。

**解决方案**: 计算类别分布，对少数类进行过采样（Oversampling）；使用加权 loss（`weighted cross-entropy`）；收集更多少数类样本。

### 格式不一致

**现象**: 训练数据中的 prompt 格式不统一，导致模型对格式变化敏感。

**解决方案**: 建立严格的模板系统，所有训练数据使用统一的 Chat Template。微调后使用与训练时完全相同的模板进行推理。

### Tokenization 不匹配

**现象**: base model 的词表（Vocabulary）中没有覆盖目标领域的专业术语，导致一个术语被拆成多个 subword token。

**解决方案**: 在微调前检查领域术语的 tokenization 效率。如果某个术语的 token 数超过 3 个，考虑在词表中添加新 token 并扩展 embedding 矩阵。

## 10.5 评估问题

### 高指标低质量

**现象**: ROUGE/BLEU 分数很高，但人工评估发现生成内容质量差。

**根因**: 自动指标只捕捉 n-gram 重叠，无法衡量语义正确性。当训练数据和测试数据高度同分布时，模型容易 "背" 出高分但无意义的回复。

**解决方案**: 引入基于 LLM 的评估（如 GPT-4 作为 judge），使用 G-Eval 或 BLEURT 等语义评估指标，固定比例的人工抽检。

### 评估指标与人类判断不相关

**现象**: 指标上升但人类评分没有改善，甚至下降。

**解决方案**: 调整评估策略，让领域专家参与制定评分标准，使用 pairwise 比较（A vs B）替代绝对评分，计算指标与人类判断的 Spearman 相关系数，只保留相关系数 > 0.5 的指标。

### 测试集污染

**现象**: 模型在测试集上表现极好但实际场景表现差。

**根因**: 测试集数据与训练数据高度相似或存在重叠，或 base model 已在预训练阶段"见过"测试样本。

**解决方案**: 构建测试集时使用时间分割（time-based split），确保测试数据的时间在训练数据之后；使用 n-gram 重叠检测排除训练集和测试集之间的重复样本；定期更新测试集。

## 10.6 部署问题

### 模型体积过大

对于 70B+ 模型，INT4 量化是生产部署的标准做法。使用 GPTQ 或 AWQ 量化算法，可以在保持 ~99% 性能的前提下将模型压缩至原来的 1/4。如果精度损失不可接受，考虑模型蒸馏（Distillation）：用大模型生成大量训练数据，训练一个小模型。

### 推理延迟过高

使用 vLLM 的 Continuous Batching 可以将吞吐量提升 10~20 倍。Flash Attention 2 减少注意力计算的显存读写。KV Cache 量化减少显存占用。如果延迟仍不达标，考虑模型蒸馏或切换到更小的 base model。

### 量化精度下降

Perplexity 上升 0.5~1.0 是可接受范围。如果量化后质量下降过大，尝试使用 AWQ 替代 GPTQ（AWQ 在低比特下通常表现更好），或使用 SmoothQuant 进行权重和激活值的联合量化。

## 10.7 系统化调试工作流

面对一个微调问题时，按以下顺序排查：

1. **检查数据**: 随机抽 50 条人工审查，计算标注一致性，检查格式是否统一
2. **检查 loss 曲线**: 区分是"不收敛"还是"收敛到错误值"
3. **缩小范围**: 在 100 条数据的子集上过拟合测试，验证模型是否具备学习能力
4. **检查梯度**: 打印梯度范数，查看是否存在梯度爆炸或消失
5. **消融实验**: 逐个关闭可能的影响因素（dropout、数据增强等），定位根因
6. **对比基线**: 用同样的数据和代码跑一个已知可工作的配置，排除环境问题

## 10.8 常见报错对照表

| 错误信息 | 常见原因 | 解决方案 |
|----------|----------|----------|
| `CUDA out of memory` | 显存不足 | 见 10.2 节 |
| `KeyError: 'llama'` | 模型配置不匹配 | 检查 base model 类型与代码中的 model class 是否一致 |
| `RuntimeError: expected scalar type Half but found Float` | 混合精度类型不匹配 | 检查模型的 dtype 设置，确保输入与模型精度一致 |
| `ValueError: Token indices sequence length is longer than the specified maximum sequence length` | 输入超长 | 截断或调整 max_length 参数 |
| `AssertionError: No training data found` | 数据加载路径错误或空数据集 | 检查数据路径和文件格式 |
| `AttributeError: 'LoraModel' object has no attribute 'merge_and_unload'` | PEFT 版本兼容性 | 升级 peft >= 0.7.0 |
| `RuntimeError: one of the variables needed for gradient computation has been modified` | 反向传播时参数被意外修改 | 检查是否有 in-place 操作修改了需要求梯度的参数 |

本章覆盖了微调过程中最常见的七大类问题。遇到问题时，建议按照调试工作流系统化排查，而非随机尝试各种"偏方"。记住一条原则：**大多数问题的根因最终都指向数据质量、超参数或模型选择**——排查时从这三个方向入手，往往能最快定位问题。
