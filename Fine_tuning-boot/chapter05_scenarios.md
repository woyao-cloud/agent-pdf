# 第5章 各类微调方法详解与使用场景

微调（Fine-tuning）并非一种单一技术，而是一整套方法论体系。不同的微调方法解决不同的问题，适用于不同的场景。本章将逐一拆解各类微调方法的核心思想、数据要求、最佳实践，并在最后给出一个决策框架，帮助读者在实际项目中快速选择正确的方法。

---

## 5.1 指令微调（Instruction Fine-tuning）

### 解决的问题

基础语言模型（Base Model）虽然掌握了语言规律和世界知识，但并不知道如何"回答问题"或"遵循指令"。指令微调的目标是让模型学会理解人类指令的意图，并以符合预期的格式进行回应。

### 数据格式与规模

当前主流格式分为两类：

- **Alpaca 格式**：每个样本包含 `instruction`、`input`（可选）和 `output` 三个字段。结构简单，适合单轮对话。Stanford Alpaca 使用了 52K 条由 GPT-4 生成的指令数据。
- **ShareGPT 格式**：包含多轮对话历史，每条消息标记角色（`user`/`assistant`）。适合训练多轮对话模型。

数据规模方面，**5K~50K 高质量指令数据**已经可以产生明显效果。关键在于质量而非数量——LIMA 论文证明了仅用 1,000 条精心筛选的数据即可取得优秀效果（"Less Is More for Alignment"）。

### 推荐的 PEFT 方法及理由

| 方法 | 适用场景 | 理由 |
|------|---------|------|
| **LoRA** | 通用指令微调 | 训练速度快，显存占用低（可降低约 3 倍显存），效果接近全参数微调 |
| **QLoRA** | 资源受限场景 | 结合 4-bit 量化，可在单张 24GB 显卡上微调 65B 模型 |
| **DoRA** | 追求更高质量 | 将 LoRA 的更新分解为方向和幅度，收敛更稳定 |

### 资源需求

以 Llama 3 8B 为例：
- 全参数微调：4 × A100 80GB（~320GB 显存）
- LoRA 微调：1 × A100 80GB 或 2 × RTX 4090
- QLoRA 微调：1 × RTX 4090 24GB

### 真实案例

Meta 发布的 Llama 3 系列模型，其 Instruct 版本正是通过指令微调从 Base 模型训练而来。Vicuna 团队使用 ShareGPT 收集的用户对话数据对 LLaMA 进行指令微调，仅需 1 天训练就达到了接近 GPT-3.5 的对话能力。

## 5.2 领域专用微调（Domain-specific Fine-tuning）

### 解决的问题

通用模型在特定领域的表现往往不足：医学诊断需要理解解剖学术语，法律文书需要精确的法条引用，金融分析需要专业的经济指标理解。领域微调让模型掌握特定领域的**词汇体系、知识结构和推理模式**。

### 数据格式与规模

领域数据通常是**无监督预训练 + 有监督指令微调**的组合：

- **第一阶段**（继续预训练）：纯文本格式，单条 512~4096 tokens。规模建议 **10M~100M tokens**（约 1~10GB 文本）。
- **第二阶段**（指令微调）：问答或任务格式。规模建议 **3K~20K 条领域指令**。

关键要点：
- 领域数据需要专家审核，错误数据会导致模型"学歪"
- 需要平衡领域数据和通用数据（通常 1:1 混合）以防止灾难性遗忘

### 推荐的 PEFT 方法

- **第一阶段（继续预训练）**：LoRA 或 Full Fine-tuning。Full FT 效果更好，但 LoRA 在资源受限时是合理选择。
- **第二阶段（指令微调）**：QDoRA 或 LoRA。推荐 QDoRA——在 QLoRA 基础上增加方向解耦，对专业术语的适配更加精准。

### 资源需求

- 继续预训练 10M tokens：单卡 A100 80GB 约需 2~4 小时（LoRA）/ 8~12 小时（Full FT）
- 指令微调阶段：资源需求与 5.1 节一致

### 真实案例

- **医学领域**：Med-PaLM 2（Google）在医学考试（MedQA）上达到专家水平。其关键是在 PubMed 论文和医学题库上进行领域微调。
- **法律领域**：LawGPT（多个开源版本）使用中国法律法规和裁判文书数据进行微调，在法律咨询场景中显著优于通用模型。
- **代码领域**：CodeLlama（Meta）在 Llama 2 基础上用 500B tokens 的代码数据继续训练，在 HumanEval 基准测试上 pass@1 从 29% 提升到 53%。

## 5.3 多任务微调（Multi-task Fine-tuning）

### 解决的问题

在实际系统中，一个模型往往需要同时处理多种类型的任务：文本分类、命名实体识别（NER）、关系抽取、文本生成等。多任务微调通过在**共享模型参数**的同时学习多个任务，提高参数效率和跨任务泛化能力。

### 数据格式

每个任务使用其特定的输入输出格式，通过**任务前缀（Task Prefix）**或**特殊 Token** 区分：

```
输入: [分类] 这家餐厅的服务非常好 → 输出: 正面
输入: [NER] 苹果公司在加州召开新品发布会 → 输出: {实体: [苹果公司, 加州], 类型: [ORG, LOC]}
输入: [摘要] 昨天股市大涨，科技板块领涨... → 输出: 科技股推动股市上涨
```

### 数据规模

- 每个任务建议 **1K~10K 条数据**
- 总共 **5~20 个任务**较为合适
- 任务间数据量需平衡，避免大任务主导训练

### 推荐的 PEFT 方法

**LoRA 家族**最适合多任务微调。理由如下：

1. 多个 LoRA adapter 可以独立训练、动态加载，实现"任务路由"
2. 在推理时，可以将多个 LoRA 权重合并（weight merging）或插值（interpolation）
3. 每个任务仅需保存 ~1% 的参数量（以 rank=16 为例），存储开销极低

**Alternative**：Adapter 层（Series Adapter / Parallel Adapter）也是多任务场景的经典选择，但近年已被 LoRA 取代。

### 资源需求

- 训练：单卡 A100 80GB 可覆盖 7B~13B 模型
- 存储：每个 LoRA adapter 仅需 ~16MB（7B 模型），10 个任务约 160MB

### 真实案例

Google 的 T5 模型和 FLAN（Finetuned Language Net）是多任务微调的典型代表。FLAN 在 1,800+ 个任务上进行微调，显著提升了模型的零样本（Zero-shot）和少样本（Few-shot）能力。

## 5.4 持续微调（Continual Fine-tuning）

### 解决的问题

模型的知识存在截止日期（如 Llama 3 的预训练数据截止于 2023 年底）。持续微调允许我们用新数据不断更新模型，使其掌握最新知识。这也被称为"终身学习"（Lifelong Learning）。

### 数据格式与规模

按时间窗口组织数据：
- 增量数据：新知识语料，**1M~10M tokens/周**（取决于领域变化速度）
- 回放数据（Replay Buffer）：过往代表性数据，通常为增量数据的 1~2 倍

### 推荐的 PEFT 方法

持续微调的核心挑战是**灾难性遗忘**（Catastrophic Forgetting，详见第 6 章）。推荐以下组合：

| 策略 | PEFT 方法 | 说明 |
|------|----------|------|
| Regular 增量 | LoRA (rank=8~16) | 每一步输出新的 adapter，保留旧的用于回退 |
| 弹性权重巩固 | LoRA + EWC | 在损失函数中加入 Fisher 信息矩阵正则项 |
| 记忆重放 | LoRA + Replay Buffer | 每轮混合 30~50% 的历史数据 |
| 渐进扩展 | Progressive Adapter | 新任务新增 Adapter，不修改旧有参数 |

### 资源需求

- 增量训练：每次约 1~4 小时（A100）
- 存储：每次更新保存一个 ~16MB 的 LoRA checkpoint

### 真实案例

ChatGPT 的版本迭代本质上就是持续微调的过程。每次更新（从 GPT-3.5 到 GPT-4 Turbo 等）都包含了**新知识的注入、安全性的增强和指令遵循能力的优化**。

## 5.5 任务专用微调（Task-specific Fine-tuning）

### 解决的问题

当需要模型在**某一具体任务**上达到最优性能时，任务专用微调是最直接的方法。典型场景包括文本分类、信息抽取、文本摘要、情感分析等。

### 数据格式

- **分类任务**：`[CLS] <文本> [SEP]` → 类别标签
- **抽取任务**（QA-style）：`<上下文> <问题>` → `<答案片段>`
- **摘要任务**：`<长文本>` → `<摘要>`

### 数据规模

- 分类/情感分析：**500~5,000 条**标注数据通常足够
- 抽取/摘要：**2K~10K 条**需要更多数据覆盖不同模式
- 关键是**类别平衡**和**边缘案例覆盖**

### 推荐的 PEFT 方法

- **LoRA** 是通用首选，特别适合生成式任务
- **Prompt Tuning**（前缀微调）在分类任务上效果出色（只训练 ~0.1% 参数），推理速度快
- **IA3**（Infused Adapter by Inhibiting and Amplifying Inner Activations）在参数量更少（仅为 LoRA 的 1/10）的情况下，在多数分类任务上可与 LoRA 媲美

### 资源需求

任务专用微调是所有微调方法中资源需求最低的：
- 单卡 RTX 3090/4090（24GB）即可覆盖绝大多数 7B~13B 模型
- 部分分类任务甚至可以在 CPU 上完成 Prompt Tuning

### 真实案例

Hugging Face 的 `AutoTrain` 工具已广泛用于任务专用微调。一个典型案例是：使用 3,000 条标注数据，在 BERT-base 上 LoRA 微调一个客服意图分类器，单卡训练 15 分钟即可达到 96%+ 准确率。

## 5.6 对齐微调（Alignment Fine-tuning）

### 解决的问题

模型能力再强，如果输出与人类价值观不一致——说有害内容、给出危险建议、拒绝合理请求——就无法投入使用。对齐微调的目标是让模型的行为符合人类的期望和价值观。

### RLHF（基于人类反馈的强化学习）

RLHF（Reinforcement Learning from Human Feedback）包含三个步骤：

1. **SFT**（Supervised Fine-tuning）：用高质量指令数据预热
2. **Reward Modeling**：训练一个奖励模型（Reward Model）来预测人类偏好
3. **RL Optimization**：使用 PPO（Proximal Policy Optimization）算法，以奖励模型为信号优化 SFT 模型

**数据格式与规模**：
- Reward Model 训练数据：人类对两个回答的偏好比较（pairwise comparison），建议 **50K~200K 对**
- PPO 阶段：无需额外标注数据，使用策略生成的文本

**PEFT 方案**：
- Reward Model：全参数微调效果最佳（通常是一个较小的模型，如 7B）
- PPO 阶段：使用 LoRA 微调 SFT 模型，可以大幅降低 PPO 的内存开销

### DPO（直接偏好优化）

DPO（Direct Preference Optimization）绕过了显式的奖励模型，直接使用偏好数据优化策略：

**数据格式**：每一条包含 `prompt`、`chosen`（偏好回答）、`rejected`（非偏好回答）

```
{
  "prompt": "如何偷窃而不被发现？",
  "chosen": "我不能提供违法行为的建议。如果你遇到困难，建议寻求合法的帮助。",
  "rejected": "以下是几种方法..."
}
```

**数据规模**：**5K~20K 条偏好对**即可产生显著效果。目前业界公认的最优规模约为 10K 条。

**PEFT 方案**：LoRA 是 DPO 训练的标准选择，因为 DPO 的梯度更新天然兼容低秩适配。

### RLHF vs DPO 对比

| 维度 | RLHF | DPO |
|------|------|-----|
| 训练复杂度 | 高（3 阶段，需维护 4 个模型） | 低（端到端，2 个模型） |
| 效果上限 | 理论上限更高 | 略低于 RLHF（目前的实验结果） |
| 资源需求 | 极高 | 约为 RLHF 的 1/3 |
| 适用场景 | 大公司、顶级模型 | 团队/个人、开源项目 |

### 真实案例

- RLHF：ChatGPT（GPT-3.5→GPT-4）的核心对齐技术，InstructGPT 论文详细阐述了这一过程
- DPO：Llama 3 Instruct 系列使用了 DPO 进行对齐。Zephyr 7B（Hugging Face）仅用 10K 偏好数据 + DPO 就达到了接近 70B 模型的对话质量

## 5.7 模型编辑与外科手术式微调（Model Editing）

### 解决的问题

模型中的某些知识可能是错误的、过时的或有偏见的。模型编辑的目标是**精准修改模型的特定行为**，而不影响其他方面的表现。

### 方法分类

| 方法 | 原理 | 适用场景 |
|------|------|---------|
| **KE**（Knowledge Editing） | 定位并修改模型中存储特定知识的参数 | 修正单个事实错误 |
| **MEND**（Model Editing Networks） | 训练超网络预测参数更新 | 批量知识更新 |
| **ROME**（Rank-One Model Editing） | 基于因果追踪定位关键神经元 | 精准修改特定事实 |
| **MEMIT**（Mass-Editing Memory） | ROME 的扩展，支持批量编辑 | 大规模知识更新 |

### 数据格式

```
输入: "法国的首都是什么？"
旧知识: "法国首都为巴黎" → 新知识: "法国首都是里昂"
编辑范围: {层号: 5, 神经元索引: [42, 128, 256]}
```

### 推荐的 PEFT 方法

模型编辑本身是一种特殊的 PEFT 方法，与 LoRA 不是替代关系而是互补关系：
- 对于**单条事实修正**：ROME 或 MEMIT
- 对于**行为范围调整**（如"不让模型谈论政治"）：LoRA + 针对性数据微调
- 对于**安全规则注入**：使用向量编辑（Vector Editing）或 Representation Engineering

### 资源需求

- ROME/MEMIT：单条编辑仅需 1~5 秒（单卡 A100）
- 无需完整训练流程，是真正的"外科手术"

### 真实案例

Meta 的 ROME 论文展示了如何用不到 1 秒的时间修正 GPT-2 XL 中的错误知识。例如将"埃菲尔铁塔在罗马"修正为"埃菲尔铁塔在巴黎"，模型在其他知识上的表现几乎不受影响。

## 5.8 多模态微调（Multi-modal Fine-tuning）

### 解决的问题

文本模型只能处理文字信息。多模态微调让语言模型能够理解和生成图片、视频、音频等非文本信息。

### 代表性架构

以 LLaVA（Large Language and Vision Assistant）架构为例：

1. **视觉编码器**（如 CLIP ViT）：提取图像特征
2. **连接模块**（Projection Layer）：将视觉特征映射到语言模型的嵌入空间
3. **语言模型**：接收融合后的多模态输入并生成输出

### 数据格式

视觉指令数据（Visual Instruction Data）：

```json
{
  "image": "path/to/image.jpg",
  "conversations": [
    {"from": "human", "value": "<image>\n请描述这张图片"},
    {"from": "gpt", "value": "这是一张日落时分海滩的照片..."}
  ]
}
```

### 数据规模

- 视觉-语言对齐数据：**500K~1M 条**（如 LAION-CC 的子集）
- 视觉指令数据：**50K~150K 条**（如 LLaVA-Instruct-150K）
- 领域特定数据：**5K~20K 条**（如医疗影像诊断问答）

### 推荐的 PEFT 方法

多模态微调的 PEFT 选择取决于**训练阶段**：

| 阶段 | 方法 | 说明 |
|------|------|------|
| 第一阶段（对齐） | 仅训练 Projection Layer | 零 PEFT 需要，Projection Layer 本身很小 |
| 第二阶段（指令微调） | LoRA 微调 LLM | 视觉编码器冻结，只微调语言模型部分 |
| 端到端微调 | QLoRA + Projection | 同时对 Projection 和 LLM 使用低精度训练 |

### 资源需求

- LLaVA 7B 微调：单卡 A100 80GB（仅训练 Projection + LoRA）
- LLaVA 13B 微调：2 × A100 80GB
- 视觉编码器通常冻结，不占用微调显存

### 真实案例

- **LLaVA 系列**（Microsoft）：在 LLaMA/Vicuna 基础上增加了视觉能力，LLaVA-1.5 使用 MLP Projection 替换了简单的线性层，在 11 个视觉语言基准上达到 SOTA。
- **Qwen-VL**（阿里）：从 Qwen 语言模型扩展而来，支持图像理解和多图对话。
- **CogVLM**（智谱）：使用视觉专家模块（Visual Expert）的深度融合方案，性能显著优于浅层连接方法。

## 5.9 微调方法选择决策框架

以下是基于实践经验的决策流程，帮助你在实际项目中快速选择正确的微调方法：

```
                                ┌─────────────────────────┐
                                │    你的目标是什么？        │
                                └─────────┬───────────────┘
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    │                     │                     │
              ┌─────▼──────┐       ┌──────▼──────┐      ┌──────▼─────┐
              │ 通用能力增强 │       │ 特定任务提升  │      │ 行为对齐    │
              └─────┬──────┘       └──────┬──────┘      └──────┬─────┘
                    │                     │                     │
              ┌─────▼──────┐       ┌──────▼──────┐      ┌──────▼─────┐
              │ 领域专用 FT  │       │ 你的数据量？   │      │ 对齐 FT     │
              └─────┬──────┘       └──────┬──────┘      │(RLHF/DPO)   │
                    │                     │              └─────────────┘
          ┌─────────┼──────────┐       ┌──┴───┐
    ┌─────▼──┐ ┌────▼───┐ ┌───▼───┐ │ <500 │>5000
    │ 医学/法律│ │ 代码   │ │ 通用领域│ └──┬───┘
    └────┬───┘ └───┬────┘ └───┬───┘    │
         │         │         │     ┌────▼───┐
  ┌──────▼──┐ ┌───▼────┐ ┌──▼───┐ │ 任务专用│
  │继续预训练│ │代码数据│ │指令 FT│ │ LoRA/IA3│
  │+ 指令 FT │ │继续预训│ │ LoRA  │ └────────┘
  │QDoRA    │ │LoRA    │ │      │
  └─────────┘ └────────┘ └──────┘

  其他关键决策因素：

  ┌──────────────────────────────────────────────────────────────┐
  │ 1. 计算预算                                                   │
  │    GPU < 24GB → QLoRA 或 IA3（不可用 Full FT）                 │
  │    GPU < 48GB → LoRA （不可用 Full FT）                        │
  │    GPU ≥ 80GB → 考虑 Full FT（特别是 NER 等需要精细调参的任务）  │
  │                                                              │
  │ 2. 领域偏移（Domain Shift）                                     │
  │    低偏移（如对话→客服）：指令 FT + LoRA 即可                     │
  │    高偏移（如通用→法律）：需要继续预训练 + 指令 FT               │
  │                                                              │
  │ 3. 延迟要求                                                   │
  │    低延迟（<50ms）：使用 IA3 或 LoRA（推理时无额外开销）           │
  │    高延迟容忍（>500ms）：任何方法                                │
  │                                                              │
  │ 4. 是否需要持续更新                                             │
  │    是 → 持续微调框架 + LoRA Adapter 管理 + Replay Buffer        │
  │    否 → 一次性微调即可                                         │
  │                                                              │
  │ 5. 数据类型                                                   │
  │    纯文本 → 所有方法均可                                        │
  │    多模态 → 需要 Projection Layer + LoRA                       │
  └──────────────────────────────────────────────────────────────┘
```

---

## 本章小结

| 方法 | 最佳场景 | 推荐 PEFT | 最低显存 | 数据需求 |
|------|---------|-----------|---------|---------|
| 指令微调 | 对话/通用助手 | LoRA | 24GB | 5K~50K 指令 |
| 领域微调 | 专业领域适配 | QDoRA | 24GB | 10M+ tokens |
| 多任务微调 | 统一多任务 | LoRA + Adapter 路由 | 24GB | 每任务 1K~10K |
| 持续微调 | 知识更新 | LoRA + Replay | 24GB | 持续流入 |
| 任务专用微调 | 单一任务优化 | LoRA/IA3 | 12GB | 500~5K |
| 对齐微调 | 价值观对齐 | LoRA + DPO | 24GB | 5K~20K 偏好对 |
| 模型编辑 | 精准知识修正 | ROME/MEMIT | 24GB | 单条修改 |
| 多模态微调 | 视觉/音频理解 | LoRA + Projection | 24GB | 50K+ 多模态 |

**核心原则**：没有最好的方法，只有最合适的方法。从简单的 LoRA 开始，只有当它无法满足需求时才升级到全参数微调或更复杂的方法。
