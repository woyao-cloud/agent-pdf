## 1. 使用场景

### 1.1 编译期计算

编译期计算是 Bun Macros 最基础也是最强大的应用场景之一。在传统的 JavaScript 和 TypeScript 开发中，许多计算工作是在运行时完成的，这意味着每次运行程序时都需要重复执行相同的计算逻辑，造成不必要的 CPU 开销。Bun Macros 允许开发者将这些计算提前到编译阶段执行，从而显著提升运行时性能。

**数值计算与常量折叠**

在实际开发中，我们经常需要定义一些基于复杂计算得出的常量值。例如，一个游戏应用中可能需要计算经验值曲线、伤害计算公式或者资源消耗表。这些计算涉及大量数学运算，如果放在运行时执行，每次启动应用都需要重新计算一遍。通过 Bun Macros，这些计算可以在编译时一次性完成，计算结果的常量值直接内联到代码中。

一个典型的例子是配置常量的编译期计算。假设我们有一个需要根据多个环境变量计算得出的超时时间配置，这个计算涉及字符串解析、数学运算和条件判断。如果放在运行时执行，每次请求都需要重新计算；而如果使用宏，这个计算在编译时完成，运行时直接使用计算结果。

**数据转换与预处理**

编译期计算的另一大用途是数据预处理。在 Web 开发中，我们经常需要将某些数据格式在运行时进行转换，例如将日期字符串解析为时间戳、将配置文件中的相对路径转换为绝对路径、或者根据某些规则生成排序后的数组。这些转换如果放在运行时执行，不仅增加启动时间，还可能导致运行时错误。使用宏，这些转换在编译时完成，生成的数据直接以 JavaScript 对象的形式内联到代码中。

**代码生成与模板编译**

编译期代码生成是宏系统的高级应用。通过宏，开发者可以编写在编译时执行的代码生成逻辑，根据输入参数生成优化的运行时代码。这在模板引擎、状态机生成、ORM 查询构建等场景中特别有用。

例如，一个 HTML 模板引擎可以通过宏在编译时将模板字符串编译为优化的渲染函数。编译过程包括解析模板结构、提取插值表达式、生成转义代码等步骤。编译后的渲染函数是一个纯 JavaScript 函数，运行时不再需要模板解析和编译的开销。

### 1.2 静态资源内联

静态资源内联是 Bun Macros 在生产环境中最重要的应用之一。传统的 Web 应用通常将 CSS、图片、JSON 配置文件等静态资源作为外部文件加载，运行时需要通过文件系统读取或通过 HTTP 请求获取这些资源。这不仅增加了运行时 I/O 开销，还可能导致文件丢失、路径错误等运行时问题。

**文件内容内联**

通过 Bun Macros，开发者可以在编译时将静态文件的内容直接读取并内联到 JavaScript 代码中。常见的应用包括：

SQL 查询文件的内联是一个典型场景。在大型应用中，SQL 查询通常保存在独立的 .sql 文件中以方便管理和维护。传统做法是在运行时使用 fs.readFileSync 读取这些文件，或者在代码中以字符串模板的形式硬编码。前者引入运行时 I/O 开销，后者破坏代码的可维护性。通过宏，SQL 文件在编译时被读取，查询字符串直接内联到代码中，既保持了文件独立管理的优势，又消除了运行时 I/O 开销。

JSON 配置文件的内联同样重要。应用配置通常以 JSON 格式保存在独立的配置文件中，运行时解析并加载。使用宏后，JSON 文件在编译时被读取并解析为 JavaScript 对象，直接内联到代码中。这意味着配置文件的格式错误在编译时就能被发现，而不是等到运行时才暴露。

Markdown 文档的内联是另一个有价值的应用。对于文档网站、博客系统或者帮助文档功能，Markdown 文件需要在运行时被读取并渲染为 HTML。通过宏，Markdown 文件在编译时就被读取、解析并转换为 HTML 字符串，运行时直接输出 HTML，省去了 Markdown 解析的性能开销。

**二进制资源内联**

对于图片、字体等二进制资源，Bun Macros 可以将其读取为 Base64 编码的字符串并内联到代码中。这对于小图标、小图片特别有用，可以减少 HTTP 请求次数，提升页面加载速度。需要注意的是，大文件的 Base64 内联会导致代码体积显著增加，应根据实际情况权衡。

### 1.3 代码生成

代码生成是 Bun Macros 最有创造力的应用领域。通过宏，开发者可以编写在编译时执行的高级抽象，生成高效且类型安全的运行时代码。

**类型安全的查询构建**

在数据库访问层，我们可以通过宏在编译时构建类型安全的 SQL 查询。宏接收表名和查询条件作为输入，在编译时验证表名和字段名的合法性，生成优化的查询函数。这样做的优势是查询错误在编译时就能被发现，而不是等到运行时才暴露为 SQL 语法错误。

**API 客户端生成**

对于微服务架构中的应用，API 客户端代码通常是重复且容易出错的。通过宏，可以根据 OpenAPI 规范或 GraphQL Schema 在编译时生成类型安全的 API 客户端代码。宏解析 API 定义文件，为每个端点生成对应的调用函数，包括请求序列化、响应反序列化和错误处理逻辑。

**状态机生成**

状态机是一种常见的编程模式，用于管理具有明确状态转换逻辑的系统。通过宏，可以用简洁的 DSL 定义状态机，在编译时生成完整的状态转换代码。宏负责验证状态转换的合法性、生成状态转换表、以及生成错误处理代码。

**数据验证规则编译**

在表单验证、数据清洗等场景中，验证规则通常在运行时被解释执行。通过宏，验证规则可以在编译时被编译为高效的检查函数。宏解析规则定义，生成针对性的验证代码，消除了运行时的规则解释开销。

### 1.4 配置注入

配置注入是 Bun Macros 在 CI/CD 和生产部署中最常用的功能。现代应用通常需要根据不同环境（开发、测试、生产）使用不同的配置，传统做法是在运行时读取环境变量或配置文件。

**环境变量内联**

通过宏，环境变量在构建时被读取并内联到代码中。这带来了几个重要优势：

构建时环境变量的值被固化到代码中，运行时不再依赖环境变量的存在。这意味着部署时只需要关注构建产物，不需要额外配置环境变量，简化了部署流程。同时，环境变量在构建时就被读取，如果缺少必要配置，构建过程会直接失败，避免了运行时才发现配置缺失的问题。

**特性开关编译**

特性开关（Feature Toggle）是现代应用开发的常见模式。通过宏，特性开关可以在编译时确定，未启用的特性对应的代码在编译时就被排除。这比运行时的特性开关更高效，因为未使用的代码根本不会包含在构建产物中。

**构建时元信息注入**

应用通常需要记录构建时间、Git 提交哈希、构建版本等元信息。通过宏，这些信息在编译时自动收集并注入到代码中。应用运行时可以直接获取这些信息，用于日志记录、错误报告和调试。

**敏感信息处理**

对于 API 密钥、数据库密码等敏感信息，宏提供了比运行时环境变量更安全的处理方式。敏感信息在构建时从安全的密钥管理系统读取并内联，构建产物中的敏感信息可以通过代码混淆进一步保护。不过需要注意的是，编译后的代码仍然包含这些敏感信息，因此构建产物的安全存储同样重要。

## 2. 实现原理

### 2.1 宏导入语法

Bun Macros 的实现基于 JavaScript 和 TypeScript 的导入断言（Import Assertions）语法。当开发者使用 `with { type: "macro" }` 导入一个模块时，Bun 的编译器会识别这个特殊的导入类型，并对该模块进行特殊的编译处理。

**导入断言的工作原理**

在标准的 JavaScript 中，`import` 语句用于在运行时加载模块。当添加 `with { type: "macro" }` 断言后，Bun 的编译器会改变这个导入的语义：

第一，被导入的模块不会被打包到最终的构建产物中。宏模块是纯编译时的，它们的代码不会出现在运行时环境中。这意味着宏模块可以包含仅在编译时需要的依赖，这些依赖不会增加运行时代码的体积。

第二，导入的绑定在运行时不是普通的函数或变量引用，而是宏调用的结果。每次在代码中使用这些绑定，Bun 的编译器都会执行对应的宏函数，并将返回值内联到调用位置。

第三，宏模块的执行环境是 Bun 的编译时运行时，这个环境提供了完整的 Node.js API 和 Bun API 访问权限。这意味着宏模块可以使用文件系统、网络请求、加密等功能，这些功能在正常的浏览器运行时中可能不可用。

**导入断言的语法细节**

Bun Macros 的导入语法需要精确遵循以下格式：

```typescript
import { functionName } from "./module.macro" with { type: "macro" }
```

这里有几个关键点需要注意：

文件路径必须是相对路径或绝对路径，不能是裸模块名（bare specifier）。这意味着你不能从 npm 包中导入宏，宏必须是本地模块。这是出于安全考虑，防止恶意 npm 包滥用宏的能力。

宏模块的文件名可以任意，但按照惯例使用 `.macro.ts` 或 `.macro.js` 后缀，以便于代码审查和工具识别。

导入断言的 `with { type: "macro" }` 必须精确匹配。Bun 会检查这个断言来决定是否进行宏处理。

**编译时 vs 运行时导入**

理解宏导入与普通导入的区别至关重要。普通导入在运行时解析模块依赖、执行模块代码、返回导出值。宏导入在编译时执行模块代码，获取返回值，然后将返回值内联到编译后的代码中，替换原始的导入使用。

这意味着宏模块中不能包含任何运行时逻辑。如果宏模块的代码依赖于运行时的 DOM API、浏览器全局对象或者动态数据，这些依赖在编译时不可用，会导致宏执行失败。

### 2.2 编译时 JavaScript 执行

Bun Macros 的编译时执行机制是 Bun 运行时最独特的功能之一。理解这个机制对于正确使用宏至关重要。

**编译流水线中的宏处理阶段**

Bun 的编译流水线包含多个阶段，宏处理发生在解析（Parsing）和代码生成（Code Generation）之间。具体流程如下：

第一阶段是词法分析和语法分析。Bun 的解析器扫描源代码，生成抽象语法树（AST）。在解析过程中，解析器会识别所有的 import 语句，包括带有 `type: "macro"` 断言的导入。

第二阶段是依赖解析。Bun 解析所有导入的模块，确定模块之间的依赖关系。对于普通模块，这个阶段仅建立模块映射；对于宏模块，Bun 会额外标记这些模块需要特殊处理。

第三阶段是宏执行。Bun 遇到标记为宏的导入使用时，会执行对应的宏函数。这个执行发生在 Bun 内置的编译时 JavaScript 运行时中。这个运行时支持完整的 ES2022 语法和大部分 Node.js API。

第四阶段是结果内联。宏函数的返回值被序列化为 JavaScript 代码，直接替换原始调用表达式。这个过程是递归的：宏的返回值本身可以包含对其他宏的调用，Bun 会继续处理这些内嵌的宏调用。

第五阶段是代码生成。处理完所有宏调用后，Bun 生成最终的 JavaScript 代码。此时，所有宏调用都已被替换为它们的编译时计算结果。

**编译时运行时的能力**

Bun 的编译时运行时是一个受限但功能完整的 JavaScript 执行环境。它提供了以下能力：

文件系统访问：宏可以读写文件系统中的文件。这使得静态资源内联成为可能。文件系统操作使用标准的 Node.js `fs` API 或 Bun 的 `Bun.file()` API。

网络请求：宏可以发起 HTTP 请求，从远程服务获取数据。这在需要从配置中心或服务发现系统获取构建时配置时非常有用。

加密和哈希：宏可以使用 Node.js 的 `crypto` 模块或 Bun 的 `Bun.CryptoHasher` API。这使得在编译时生成安全的随机值、哈希和加密密钥成为可能。

第三方依赖：宏可以导入和使用编译时运行时中可用的第三方库。但需要注意，这些依赖必须在编译时环境中可用，它们不会被打包到最终的运行时代码中。

**编译时运行时的限制**

理解编译时运行时的限制同样重要：

没有 DOM API：编译时运行时没有浏览器环境，因此 `window`、`document`、`navigator` 等浏览器 API 不可用。宏不能依赖这些 API。

没有事件循环保证：虽然宏可以使用异步 API，但编译时执行是同步的。宏函数的返回值必须同步返回，不能依赖未完成的事件循环回调。

有限的全局对象：编译时运行时的全局对象集合不同于浏览器和 Node.js 运行时。一些 Node.js 特定的全局对象可能不可用。

### 2.3 结果内联机制

结果内联是 Bun Macros 的核心机制，它决定了宏返回值如何被嵌入到编译后的代码中。

**序列化策略**

宏函数的返回值可以是多种类型，Bun 会根据值的类型采用不同的序列化策略：

对于原始类型（字符串、数字、布尔值、null、undefined），Bun 直接生成对应的字面量表达式。例如，字符串值被生成为字符串字面量，数字值被生成为数字字面量。

对于对象和数组，Bun 生成对象字面量和数组字面量。这个过程是递归的：嵌套的对象和数组也会被正确序列化。需要注意，对象中的函数、Symbol 等不可序列化的值会被忽略或抛出错误。

对于函数，Bun 的序列化策略比较特殊。如果宏返回一个函数，Bun 会尝试将函数体序列化为字符串，然后生成一个新的函数表达式。这意味着函数体内的闭包捕获的变量会被丢失，因此宏返回的函数应该是不依赖外部变量的纯函数。

对于类实例，Bun 会尝试将实例的属性序列化为普通对象。类的方法不会被序列化，因为方法依赖类的原型链，而原型链在编译时上下文中不可用。

**内联位置的语法**

宏调用的结果可以内联到多种语法位置：

变量声明初始化：`const value = macroCall()` — 宏的结果成为变量的初始值。

表达式中的子表达式：`console.log(macroCall())` — 宏的结果成为函数调用的参数。

默认值：`function fn(value = macroCall())` — 宏的结果成为参数的默认值。

属性值：`const obj = { key: macroCall() }` — 宏的结果成为对象的属性值。

**内联后的代码结构**

理解宏内联后的代码结构对于调试和优化非常重要。假设我们有以下的宏定义和调用：

宏定义：
```typescript
// config.macro.ts
export function getConfig() {
  return {
    apiUrl: "https://api.example.com",
    timeout: 5000,
    retries: 3
  }
}
```

宏调用：
```typescript
import { getConfig } from "./config.macro" with { type: "macro" }
const config = getConfig()
```

编译后的代码：
```typescript
const config = {
  apiUrl: "https://api.example.com",
  timeout: 5000,
  retries: 3
}
```

注意，编译后的代码中不再包含宏导入语句和宏调用，宏函数 `getConfig` 的执行结果直接替换了原始调用。

### 2.4 宏与 TypeScript 的类型安全

Bun Macros 与 TypeScript 的类型系统完美集成，这是它优于许多其他宏系统的重要特性。

**类型推断**

当宏函数的返回值被内联后，TypeScript 的类型推断仍然有效。宏函数的返回类型被用于推断调用位置的变量类型。这意味着开发者可以获得完整的类型检查和代码补全支持。

例如，如果宏函数返回一个具有精确类型的对象，TypeScript 可以推断出内联后变量的精确类型，包括可选属性、只读属性和字面量类型。

**类型安全的宏接口**

设计良好的宏应该提供精确的类型签名。宏函数的参数和返回类型应该尽可能精确，以便 TypeScript 在编译时进行类型检查。这包括使用泛型、条件类型和模板字面量类型等高级 TypeScript 特性。

例如，一个读取配置文件的宏可以这样定义类型：

```typescript
export function readJSON<T = Record<string, unknown>>(filePath: string): T {
  const fs = require("fs")
  const content = fs.readFileSync(filePath, "utf-8")
  return JSON.parse(content) as T
}
```

使用时可以指定泛型参数来获得精确的类型：

```typescript
interface AppConfig {
  apiUrl: string
  timeout: number
  features: string[]
}

const config = readJSON<AppConfig>("./config.json")
// config 的类型为 AppConfig，可以获得完整的类型检查
```

### 2.5 宏的缓存策略

Bun 对宏的执行结果实施了智能缓存策略，这既提升了开发体验，也引入了一些需要注意的问题。

**基于文件哈希的缓存**

Bun 会计算宏模块文件的哈希值，当宏模块文件内容没有变化时，Bun 会复用之前的宏执行结果。这个缓存机制避免了在每次构建时都重新执行宏，显著提升了增量构建的速度。

缓存的粒度是宏模块级别的。只要宏模块的代码没有变化，该模块中所有导出的宏函数的调用结果都会被缓存。这意味着如果宏模块的代码没有变化，即使调用参数不同，Bun 也可能返回缓存的结果。

**缓存失效**

缓存会在以下情况下失效：宏模块文件被修改，宏模块依赖的文件被修改，或者构建配置发生变化。Bun 通过跟踪宏模块及其依赖的文件系统的修改时间来检测缓存是否有效。

对于读取外部文件的宏，缓存失效的检测尤为重要。如果宏读取了一个 JSON 配置文件，而这个文件被修改了，Bun 应该检测到这种变化并重新执行宏。但在某些复杂场景下，如果宏通过动态计算的文件路径读取文件，Bun 可能无法正确跟踪所有依赖。

**强制刷新缓存**

在开发过程中，有时需要强制刷新宏的缓存。这可以通过以下几种方式实现：修改宏模块文件的内容，删除 Bun 的缓存目录，或者使用 `bun run --no-cache` 标志禁用缓存。

## 3. 风险与优化

### 3.1 副作用问题

宏在编译时执行，这意味着宏中的副作用（Side Effects）行为与普通运行时函数完全不同。理解这些差异对于正确使用宏至关重要。

**副作用的定义**

在编程中，副作用是指函数在执行过程中除了返回值之外还对外部状态产生的影响。常见的副作用包括：

文件系统操作：读取或写入文件、创建或删除目录。宏中的文件读取是预期的行为，用于实现静态资源内联。但文件写入则需要特别谨慎，因为宏在编译时执行，写入操作会影响开发环境的文件系统。

网络请求：发送 HTTP 请求、建立 WebSocket 连接。宏中的网络请求应该在编译时执行，但需要注意网络请求的延迟和失败风险。如果宏依赖的外部服务不可用，整个构建过程都会失败。

修改全局状态：修改全局变量、设置环境变量。宏中的全局状态修改会影响编译时环境，但不应该影响运行时环境。因为宏在独立的编译时上下文中执行，其全局状态修改不会泄漏到运行时。

**可重复性问题**

宏应该是可重复执行的：在相同的输入条件下，宏应该返回相同的结果。这听起来简单，但在实际中可能因为以下原因导致不可重复：

依赖当前时间：如果宏使用 `new Date()` 或 `Date.now()` 获取当前时间，每次执行都会得到不同的结果。这在某些场景下是预期的（如注入构建时间），但在其他场景下可能导致不可预测的构建行为。

依赖随机数：如果宏使用 `Math.random()` 或 `crypto.randomUUID()` 生成随机值，每次执行都会得到不同的结果。这在生成唯一标识符时是预期的，但可能导致每次构建产生不同的代码。

依赖外部状态：如果宏的返回值依赖于环境变量、文件系统状态或网络服务状态，当这些外部状态变化时，宏的返回值也会变化。这可能导致在不同环境中构建出不同的代码。

**副作用管理策略**

管理宏的副作用需要遵循以下原则：

宏应该优先使用纯函数模式。纯函数是指给定相同输入总是返回相同输出的函数，且不产生任何副作用。纯函数模式的宏最容易理解和调试。

对于不可避免的副作用（如读取配置文件），应该显式声明这些依赖。Bun 会自动跟踪宏模块的文件系统依赖，但依赖外部服务（如网络 API）的宏需要额外的注意。

宏不应该执行非预期的副作用。例如，宏不应该修改文件系统、发送邮件、或者修改构建环境。这些操作应该在构建脚本中完成，而不是在宏中。

测试宏的可重复性很重要。可以在开发过程中多次构建项目，检查每次构建产物的差异。如果构建产物在不应该变化的时候发生了变化，说明宏存在不可重复性问题。

### 3.2 调试困难

宏的调试比普通代码更加困难，因为宏在编译时执行，传统运行时调试工具无法用于宏的调试。这给开发和问题排查带来了独特的挑战。

**调试工具的限制**

传统的 JavaScript 调试工具（如 Chrome DevTools、VS Code 调试器）是为运行时调试设计的。它们无法介入编译时执行的过程，因此无法在宏执行时设置断点、检查变量值或单步执行。

这意味着宏开发者在很大程度上依赖传统调试技术：日志输出、代码审查和单元测试。理解宏的执行环境与运行时环境的差异对于有效调试至关重要。

**日志调试技术**

最常用的宏调试技术是在宏代码中添加日志输出。由于宏在编译时执行，日志输出会在构建过程中显示在控制台中。

在宏函数中添加 `console.log` 语句可以在构建过程中输出调试信息。这些信息可以帮助开发者理解宏的执行流程、参数值和返回值。与运行时日志不同，编译时日志只在构建过程中可见，不会出现在运行时的日志输出中。

为了更有效地使用日志调试，可以定义一个调试工具函数：

```typescript
// debug-utils.macro.ts
const DEBUG = process.env.MACRO_DEBUG === "true"

export function debugLog(...args: unknown[]): void {
  if (DEBUG) {
    console.log("[Macro Debug]", ...args)
  }
}
```

这个工具函数允许开发者在需要时启用宏的调试日志，而不会在生产构建中产生额外的输出。

**错误处理与堆栈跟踪**

宏执行时的错误处理与普通代码不同。当宏抛出错误时，Bun 会在构建过程中输出错误信息，并指向宏模块中的错误位置。但是，由于宏的调用栈与普通代码不同，错误信息可能不够直观。

宏开发者应该在宏代码中添加详细的错误处理逻辑。对于可能失败的宏（如文件读取、网络请求），应该提供清晰的错误信息，包括失败的原因和可能的解决方法。

使用 TypeScript 的类型系统可以在编译时捕获一些错误，但运行时错误的处理仍然需要完善的错误处理代码。

**单元测试宏**

虽然宏在编译时执行，但宏函数本身是普通的 JavaScript 或 TypeScript 函数。这意味着宏函数可以在测试环境中被直接调用和测试。

单元测试宏的主要方法是直接调用宏函数并断言其返回值。测试应该覆盖正常输入、边界情况和错误输入。对于读取外部文件的宏，测试可以使用模拟文件系统或临时文件。

单元测试宏需要注意宏函数可能依赖编译时环境中的全局对象。在测试环境中，这些全局对象可能不可用，因此测试代码可能需要设置模拟的全局环境。

### 3.3 缓存问题

Bun 的宏缓存机制虽然提升了构建性能，但也引入了一些需要注意的问题。

**缓存不一致**

缓存不一致是指宏缓存中的结果与当前源文件状态不匹配的情况。这种情况可能发生在以下场景：

当宏模块或其依赖的文件被修改时，Bun 应该检测到变化并重新执行宏。但在某些复杂场景下，如果宏通过动态计算的文件路径读取文件，或者通过间接的依赖关系引用其他文件，Bun 的依赖跟踪可能不够完整，导致缓存未能正确失效。

宏模块的依赖关系越复杂，缓存不一致的风险就越高。为了降低这种风险，宏应该尽可能简化其依赖关系，优先使用直接的文件路径引用，而不是动态计算的路径。

**增量构建中的缓存行为**

在增量构建中，Bun 会复用上次构建的缓存结果，只重新处理有变化的模块。对于宏来说，增量构建的缓存行为可能导致以下问题：

如果宏的输入没有变化但宏依赖的外部状态发生了变化（如环境变量被修改），Bun 可能无法检测到这种变化，从而返回过时的缓存结果。

如果宏读取的配置文件被修改但宏模块本身没有变化，Bun 应该检测到配置文件的修改时间变化并重新执行宏。但这个过程依赖于文件系统的修改时间戳，在某些情况下（如版本控制系统切换分支）可能出现时间戳不一致的问题。

**缓存清理策略**

为了解决缓存问题，开发者需要了解如何强制清理宏的缓存。以下是一些常用的策略：

删除 Bun 的缓存目录是最直接的方法。Bun 的缓存通常存储在操作系统的临时目录中，删除这些缓存文件可以强制 Bun 重新执行所有宏。

使用 `--no-cache` 标志运行 Bun 可以禁用所有缓存，包括宏缓存。这在调试宏相关问题时特别有用。

在开发过程中，当怀疑宏缓存可能导致问题时，可以手动触发宏的重新执行。这通常通过修改宏模块文件的内容来实现，例如添加一个空格然后保存。

### 3.4 构建速度影响

宏虽然在运行时提升了性能，但在编译时增加了额外的计算开销。理解宏对构建速度的影响对于大型项目的构建优化很重要。

**宏执行时间**

宏在编译时执行，因此宏函数的执行时间直接增加了总构建时间。每个宏调用都需要在编译时执行对应的函数，宏函数的执行时间、宏调用的次数和宏的复杂度共同决定了宏对构建速度的影响。

对于简单的宏（如读取和解析 JSON 文件），执行时间通常在毫秒级别，对构建速度的影响可以忽略不计。但对于复杂的宏（如编译模板引擎、生成大量代码），执行时间可能达到数百毫秒甚至数秒。

**宏的数量与构建时间的关系**

宏调用的数量与构建时间的关系并不是简单的线性关系。Bun 的宏执行引擎会并行处理独立的宏调用，因此增加宏调用的数量不一定会线性增加构建时间。

但是，宏模块之间的依赖关系会影响并行处理的效果。如果多个宏调用都依赖同一个宏模块，这些宏调用需要等待该模块执行完成后才能执行。因此，合理设计宏模块的依赖关系对于优化构建速度很重要。

**大型项目中的宏优化策略**

在大型项目中，宏的使用需要更加谨慎的优化策略：

宏应该只用于那些确实有明确性能收益的场景。对于简单的常量定义，直接使用字面量通常比使用宏更高效。

宏的复杂度应该与收益平衡。一个在运行时节省几毫秒的宏，如果在编译时需要几百毫秒的执行时间，其整体价值需要仔细评估。

宏应该设计为可缓存的。使用纯函数模式的宏可以充分利用 Bun 的缓存机制，在增量构建中几乎不增加额外时间。

## 4. 典型问题处理

### 4.1 宏未执行

宏未执行是最常见的问题之一。开发者导入宏模块并调用宏函数，但预期中的编译时执行并未发生，宏函数在运行时被当作普通函数执行。

**问题原因分析**

宏未执行通常由以下几个原因导致：

导入语法错误是最常见的原因。`with { type: "macro" }` 断言必须精确匹配，任何拼写错误、大小写不一致或者语法错误都会导致 Bun 无法识别宏导入。特别是 `"macro"` 这个值必须是字符串字面量，不能是变量。

文件路径错误是另一个常见原因。宏导入必须使用相对路径或绝对路径，不能使用裸模块名。如果使用了 npm 包名或省略了文件后缀，Bun 可能无法正确解析宏模块。

Bun 版本兼容性问题也可能导致宏未执行。早期版本的 Bun 可能不支持宏功能，或者某些语法在特定版本中有不同的行为。确保使用最新稳定版本的 Bun 可以避免这类问题。

**诊断方法**

诊断宏未执行问题需要系统性的排查方法：

第一步，检查导入语法。确认导入语句中包含了 `with { type: "macro" }` 断言，并且语法完全正确。

第二步，检查文件路径。确认宏模块的文件路径是正确的，文件存在且可读。尝试使用绝对路径导入以排除路径解析问题。

第三步，在宏函数中添加 `console.log` 语句。如果宏在编译时执行，日志会在构建过程中输出。如果日志没有出现，说明宏确实没有在编译时执行。

第四步，检查构建输出。使用 `bun build` 命令而不是 `bun run` 来构建项目，检查构建产物中是否包含了宏模块的代码。如果宏模块的代码出现在构建产物中，说明宏没有被正确处理。

**解决方案**

根据问题原因采取相应的解决方案：

修复导入语法：确保 `with { type: "macro" }` 断言完全正确，包括空格和引号的使用。

修复文件路径：使用正确的相对路径或绝对路径，确保文件扩展名正确。

升级 Bun 版本：使用 `bun upgrade` 升级到最新版本，确保宏功能可用。

使用正确的运行方式：某些 Bun 命令可能不支持宏，确保使用 `bun run` 或 `bun build` 命令。

### 4.2 结果不正确

宏返回的结果与预期不符是另一个常见问题。宏在编译时执行，其行为可能因为编译时环境与运行时环境的差异而出现异常。

**问题原因分析**

编译时环境与运行时环境的差异是导致结果不正确的主要原因。宏在编译时执行时，其执行环境可能缺少某些运行时才有的全局对象、环境变量或文件系统状态。

环境变量差异是一个典型的例子。宏在编译时读取环境变量，但构建时的环境变量可能与运行时的环境变量不同。这可能导致宏返回的值在运行时环境中不正确。

时间相关的值也可能导致问题。宏中使用 `new Date()` 获取当前时间，这个时间是构建时间而非运行时间。在某些场景下（如缓存键的生成），这可能导致预期之外的行为。

宏的可重复性问题也可能导致结果不正确。如果宏依赖随机数或外部服务，每次执行可能得到不同的结果。

**诊断方法**

诊断宏结果不正确的问题需要以下方法：

对比宏在编译时和运行时的执行环境。检查环境变量、文件系统状态和可用 API 的差异。

在宏函数中添加详细的调试日志，输出宏接收的参数、中间计算步骤和最终返回值。

使用单元测试验证宏函数在受控环境中的行为。单元测试可以帮助排除运行时环境差异导致的问题。

检查构建产物中宏内联后的代码，确认宏的返回值确实如预期。

**解决方案**

根据问题原因采取相应的解决方案：

确保宏函数是纯函数，不依赖运行时环境的状态。将宏的依赖作为参数传递，而不是在宏内部读取全局状态。

对于必须依赖外部状态的宏，明确记录宏的依赖项，并在文档中说明宏的构建时行为。

使用固定的种子值替代随机数，确保宏的可重复性。如果必须使用随机值，考虑在构建时生成一次并在整个构建过程中复用。

### 4.3 构建速度显著下降

宏使用不当可能导致构建速度显著下降，特别是在大型项目中。

**问题原因分析**

宏的执行时间过长是导致构建速度下降的主要原因。复杂的宏函数可能涉及大量计算、多次文件读取或者网络请求，这些操作在宏调用时执行，直接增加了构建时间。

宏调用次数过多也是常见原因。如果项目中大量使用了宏，每个宏调用都需要在编译时执行，总的宏执行时间可能非常可观。

宏的缓存失效频繁也会影响构建速度。如果宏模块或其依赖频繁变化，Bun 无法有效利用缓存，每次构建都需要重新执行所有宏。

**诊断方法**

诊断构建速度问题需要以下方法：

使用 `bun build --trace` 命令查看构建过程的详细时间分布，识别宏执行阶段的耗时。

逐个注释宏调用，测量每次注释后的构建时间变化，定位耗时最长的宏。

检查宏模块的依赖关系，识别可能导致缓存频繁失效的原因。

**优化策略**

优化宏的构建性能需要以下策略：

简化宏函数的实现，减少不必要的计算和 I/O 操作。对于文件读取的宏，考虑只读取必要的文件内容，避免读取整个目录。

使用缓存友好的宏设计。确保宏函数是纯函数，输入相同的情况下返回相同的输出。避免在宏中使用随机数、当前时间等每次执行都会变化的值。

对于确实需要复杂计算的宏，考虑将计算结果缓存到文件中，避免每次构建都重新计算。

将不经常变化的宏结果预先计算并提交到版本控制中，避免每次构建都执行相同的计算。

### 4.4 宏执行环境问题

宏在 Bun 的编译时运行时中执行，这个环境与 Node.js 和浏览器环境存在差异，可能导致一些意想不到的问题。

**API 兼容性问题**

编译时运行时的 API 支持情况可能与 Node.js 或浏览器环境不同。以下是一些常见的 API 兼容性问题：

文件系统 API 的差异：编译时运行时支持大部分 Node.js 的 `fs` API，但某些特定 API（如 `fs.watch`）可能不可用或不稳定。

网络 API 的差异：编译时运行时支持 `fetch` API，但可能不支持某些高级特性（如流式处理、WebSocket）。

加密 API 的差异：编译时运行时支持 `crypto` 模块，但某些算法的实现可能与 Node.js 不同。

**全局对象差异**

编译时运行时的全局对象集合与标准 Node.js 环境不同：

`process` 对象可用，但某些属性（如 `process.argv`）的行为可能与 Node.js 不同。

`Buffer` 类可用，但某些方法的实现可能与 Node.js 不同。

`global` 对象可用，但某些 Node.js 特有的全局函数可能不可用。

**解决方案**

解决宏执行环境问题需要以下策略：

在宏代码中避免使用特定于运行时的 API。优先使用跨运行时的标准 API。

在宏代码中添加环境检测，针对不同环境使用不同的实现。

使用 try-catch 包裹可能不兼容的 API 调用，在 API 不可用时提供降级方案。

在项目文档中明确记录宏的编译时依赖和限制。

### 4.5 宏与模块系统的交互问题

宏与 JavaScript 模块系统的交互可能产生一些微妙的问题，特别是在处理循环依赖、动态导入和条件导入时。

**循环依赖问题**

宏模块和普通模块之间可能出现循环依赖。由于宏在编译时执行，循环依赖可能导致宏模块无法正确加载。

例如，如果宏模块导入了普通模块，而普通模块又导入了宏模块，就形成了循环依赖。Bun 在处理循环依赖时可能返回未完全初始化的模块对象，导致宏函数中的导入值不正确。

**解决方案**是避免宏模块和普通模块之间的循环依赖。宏模块应该只依赖纯工具模块，不应该依赖包含宏调用的模块。

**动态导入问题**

宏不支持动态导入（dynamic import）。`import()` 表达式在宏模块中无法正常工作，因为动态导入是运行时行为，而宏在编译时执行。

如果宏需要根据条件加载不同的模块，应该在编译时使用条件判断，而不是运行时动态导入。

**条件导入问题**

宏模块中的条件导入（conditional import）行为可能与预期不同。由于宏在编译时执行，条件导入的条件判断发生在编译时，而非运行时。

这意味着宏模块中的条件导入不能依赖于运行时变量。如果条件导入的条件是编译时可以确定的常量，条件导入可以正常工作。但如果条件依赖于运行时数据，条件导入的行为将不可预测。

## 5. 必备知识

### 5.1 AST 概念

抽象语法树（Abstract Syntax Tree，AST）是计算机科学中的一个核心概念，也是理解 Bun Macros 工作原理的基础。AST 是源代码的树状结构表示，其中每个节点代表代码中的一个语法结构。

**AST 的基本结构**

AST 将源代码解析为层次化的树结构。树的根节点代表整个程序，子节点代表程序中的各个语法结构，如函数声明、变量定义、表达式等。

例如，一个简单的变量声明 `const x = 42` 在 AST 中的表示形式如下：

根节点是一个 VariableDeclaration 节点，它包含一个 VariableDeclarator 节点。VariableDeclarator 节点又包含两个子节点：Identifier 节点（代表变量名 `x`）和 NumericLiteral 节点（代表值 `42`）。

每个 AST 节点都包含以下信息：

节点类型：标识节点代表的语法结构类型，如 `VariableDeclaration`、`FunctionDeclaration`、`CallExpression` 等。

节点位置：节点在源代码中的起始和结束位置，包括行号和列号。这些信息对于错误报告和代码生成非常重要。

节点属性：不同类型的节点有不同的属性。例如，`FunctionDeclaration` 节点有 `id`（函数名）、`params`（参数列表）、`body`（函数体）等属性。

**AST 与宏的关系**

Bun Macros 的工作原理与 AST 密切相关。当 Bun 编译源代码时，它首先将代码解析为 AST，然后在 AST 上执行宏处理。

具体来说，Bun 在 AST 中识别带有 `type: "macro"` 断言的导入语句。对于这些导入，Bun 会进一步解析宏模块的 AST，并在 AST 级别执行宏函数的调用。

宏调用的执行结果是新的 AST 节点。Bun 将原始调用表达式对应的 AST 节点替换为宏返回值的 AST 节点，这个过程称为 AST 变换。

理解 AST 的概念有助于开发者更好地理解宏的能力边界。宏只能在编译时操作 AST，不能在运行时操作。宏的输入和输出都是 AST 节点，而不是运行时值。

**AST 节点类型**

JavaScript 和 TypeScript 的 AST 包含多种节点类型，常见的包括：

程序节点（Program）：代表整个程序，是所有其他节点的根节点。

语句节点：包括 VariableDeclaration（变量声明）、FunctionDeclaration（函数声明）、ExpressionStatement（表达式语句）、IfStatement（if 语句）、ForStatement（for 语句）等。

表达式节点：包括 CallExpression（函数调用表达式）、MemberExpression（属性访问表达式）、BinaryExpression（二元表达式）、UnaryExpression（一元表达式）等。

字面量节点：包括 StringLiteral（字符串字面量）、NumericLiteral（数字字面量）、BooleanLiteral（布尔字面量）、NullLiteral（null 字面量）等。

标识符节点（Identifier）：代表变量名、函数名等标识符。

模板节点：包括 TemplateLiteral（模板字符串）、TaggedTemplateExpression（标签模板字符串）等。

### 5.2 元编程

元编程（Metaprogramming）是指编写能够操作其他程序（或自身）的程序。Bun Macros 是元编程的一种实现形式，它允许开发者在编译时操作和生成代码。

**元编程的基本概念**

元编程的核心思想是将程序的一部分作为数据来操作。在 JavaScript 中，元编程的常见形式包括：

反射（Reflection）：程序在运行时检查和修改自身结构的能力。JavaScript 的 `Reflect` API 和 `Proxy` 对象是反射的典型实现。

代码生成：程序生成其他程序代码的能力。`eval()` 函数和 `new Function()` 构造函数是 JavaScript 中代码生成的简单形式。

宏：在编译时操作和生成代码的能力。Bun Macros 是这种形式的实现。

**元编程的优势**

元编程可以带来以下优势：

减少样板代码：通过生成重复的代码模式，元编程可以显著减少手动编写的工作量。

提高抽象层次：元编程允许开发者创建更高层次的抽象，将复杂的实现细节隐藏在简洁的接口后面。

提升性能：编译时元编程（如宏）可以将计算从运行时移到编译时，提升运行时性能。

增强类型安全：通过生成类型安全的代码，元编程可以减少运行时类型错误。

**元编程的风险**

元编程也带来了一些风险：

代码可读性下降：元编程生成的代码可能难以理解和调试，特别是对于不熟悉元编程的开发者。

调试困难：元编程增加了代码的间接层次，使得问题定位更加困难。

过度抽象：元编程可能导致过度抽象，使得简单的任务变得复杂。

性能陷阱：如果元编程使用不当，可能导致运行时性能下降而非提升。

**Bun Macros 中的元编程**

Bun Macros 是编译时元编程的一种实现。与运行时的元编程（如 `eval`、`Proxy`）不同，Bun Macros 在编译时执行，生成高效的运行时代码。

在 Bun Macros 中，元编程的典型模式包括：

代码生成宏：在编译时生成运行时代码。例如，模板编译宏在编译时将模板字符串转换为渲染函数。

代码变换宏：在编译时变换代码结构。例如，日志宏可以在编译时注入日志记录代码。

代码分析宏：在编译时分析代码结构并生成元数据。例如，参数校验宏可以在编译时分析函数参数并生成校验代码。

### 5.3 JavaScript 运行时模型

理解 JavaScript 的运行时模型对于正确使用 Bun Macros 很重要。

**执行上下文**

JavaScript 代码在特定的执行上下文中运行。执行上下文包含代码执行所需的所有信息，包括变量环境、词法环境、this 绑定等。

在 Bun Macros 中，存在两个独立的执行上下文：编译时执行上下文和运行时执行上下文。宏在编译时执行上下文中运行，普通代码在运行时执行上下文中运行。

这两个执行上下文是隔离的：编译时上下文中的变量、函数和状态不会泄漏到运行时上下文中。这意味着宏不能直接操作运行时上下文中的变量，也不能访问运行时上下文中的 DOM API。

**事件循环**

JavaScript 的事件循环（Event Loop）是 JavaScript 运行时处理异步操作的核心机制。事件循环负责协调同步代码执行、微任务队列和宏任务队列。

在 Bun Macros 中，编译时执行上下文的事件循环与运行时执行上下文的事件循环是独立的。宏在编译时执行时，其事件循环行为可能与运行时不同。

特别需要注意的是，宏函数必须是同步的。宏函数不能依赖异步操作的结果，因为编译时执行上下文在宏函数返回后就结束了。如果宏函数启动了异步操作但没有等待其结果，这个异步操作可能无法完成。

**内存模型**

JavaScript 的内存模型包括栈（Stack）和堆（Heap）。栈用于存储基本类型值和函数调用帧，堆用于存储对象和数组等引用类型值。

在 Bun Macros 中，编译时执行上下文有自己的栈和堆。宏函数执行期间分配的内存，在宏函数返回后会被垃圾回收。如果宏函数中创建了大型对象，这些对象在宏函数返回后会被回收，不会增加运行时内存占用。

但是，宏返回的值会被序列化为 JavaScript 代码。如果宏返回大型对象（如大型配置文件的内容），这个对象会在运行时重新创建，占用运行时内存。因此，开发者需要在编译时计算和运行时内存占用之间做出权衡。

### 5.4 TypeScript 类型系统与宏

TypeScript 的类型系统与 Bun Macros 的集成是 Bun 的一大优势。理解这种集成可以帮助开发者编写更类型安全的宏。

**类型推断与宏**

TypeScript 的类型推断可以正确处理宏的返回值。当宏函数返回一个具有精确类型的值时，TypeScript 可以推断出宏调用位置的变量类型。

例如，如果一个宏函数返回类型为 `{ name: string; age: number }` 的对象，TypeScript 可以正确推断出接收这个返回值的变量的类型。这保证了使用宏的代码可以获得完整的类型检查和代码补全支持。

**泛型宏**

宏函数可以使用 TypeScript 的泛型来增强类型安全性。通过泛型，宏函数的输入和输出类型可以精确关联。

例如，一个读取 JSON 配置文件的宏可以使用泛型来指定返回值的类型：

```typescript
export function readJSON<T>(filePath: string): T {
  // 编译时读取并解析 JSON
}
```

使用时可以指定类型参数，获得精确的类型推断。

**类型安全的宏设计**

设计类型安全的宏需要遵循以下原则：

为宏函数提供精确的输入类型。使用字面量类型、联合类型和条件类型来约束宏函数的参数。

为宏函数提供精确的输出类型。使用泛型、映射类型和模板字面量类型来描述宏函数的返回值。

在宏函数内部使用类型断言，确保 TypeScript 的编译时类型检查与宏的编译时执行逻辑一致。

### 5.5 构建工具与宏的集成

Bun Macros 作为 Bun 运行时的一部分，与其他构建工具和开发工具的集成是一个重要的考虑因素。

**Bun 作为构建工具**

Bun 内置了构建工具，可以替代 Webpack、Rollup 等传统构建工具。Bun 的构建工具原生支持宏，无需额外的配置。

使用 `bun build` 命令时，宏会自动被识别和处理。构建产物中不会包含宏模块的代码，宏调用被替换为编译时计算结果。

**与其他构建工具的兼容性**

Bun Macros 是 Bun 特有的功能，其他构建工具（如 Webpack、Rollup、esbuild）不支持宏语法。这意味着如果项目使用了其他构建工具，宏功能不可用。

对于需要在多个构建工具之间共享代码的项目，可以考虑将宏的逻辑抽象为普通的编译时工具函数，然后根据使用的构建工具选择是否启用宏优化。

**开发工具支持**

Bun Macros 的开发工具支持正在逐步完善。目前，Bun 提供了以下开发工具支持：

Bun 的运行时原生支持宏，无需额外的插件或配置。

Bun 的 TypeScript 支持包括宏的类型检查。

Bun 的热重载（Hot Reload）功能支持宏的增量更新。

### 5.6 编译原理基础

理解编译原理的基本概念对于深入掌握 Bun Macros 非常重要。虽然不需要成为编译器专家，但了解编译器的工作流程可以帮助开发者更好地理解宏的能力边界。

**编译器的工作阶段**

现代编译器通常将源代码的处理分为多个阶段。每个阶段负责特定的转换任务，前一阶段的输出作为后一阶段的输入。

词法分析是编译器的第一个阶段。词法分析器（Lexer）将源代码的字符序列转换为标记（Token）序列。标记是源代码的最小语法单元，包括关键字、标识符、运算符、字面量等。例如，`const x = 42` 被转换为 `const`、`x`、`=`、`42` 四个标记。

语法分析是编译器的第二个阶段。语法分析器（Parser）将标记序列转换为抽象语法树（AST）。语法分析器根据语言的语法规则确定标记之间的关系，构建树状结构。例如，`const x = 42` 被转换为以 VariableDeclaration 为根节点的子树。

语义分析是编译器的第三个阶段。语义分析器检查 AST 的语义正确性，包括类型检查、变量绑定和作用域分析。在 TypeScript 中，语义分析还负责类型推断和类型检查。

中间代码生成是编译器的第四个阶段。编译器将 AST 转换为中间表示（IR），这种表示更适合后续的优化和代码生成。

优化是编译器的第五个阶段。编译器在中间表示上执行各种优化变换，包括常量折叠、死代码消除、循环优化等。

代码生成是编译器的最后一个阶段。编译器将优化后的中间表示转换为目标代码，可以是机器码、字节码或其他高级语言的代码。

**Bun 编译器的工作流程**

Bun 的编译器基于 JavaScriptCore 引擎，其工作流程与标准编译器类似，但加入了宏处理的特殊阶段。

Bun 的编译器在语法分析和语义分析之间插入了宏处理阶段。在这个阶段，编译器识别宏导入语句，执行宏函数，并将宏调用的结果内联到 AST 中。

宏处理阶段的输入是包含宏调用表达式的 AST，输出是宏调用已被替换为编译时计算结果的 AST。这个阶段是 Bun Macros 的核心，也是 Bun 编译器最独特的功能。

**编译时与运行时的分界线**

理解编译时与运行时的分界线对于正确使用宏至关重要。编译时是源代码被编译器处理的阶段，运行时是编译后的代码被执行的阶段。

在编译时，编译器可以访问源代码的全部信息，包括代码结构、类型信息、导入关系等。编译器可以执行代码生成、代码变换和代码分析等操作。

在运行时，执行环境只能访问编译后的代码和数据。运行时环境没有源代码的结构信息，不能重新编译或修改代码结构。

宏位于编译时和运行时的分界线上。宏在编译时执行，但其执行结果影响运行时代码的行为。宏的输入是编译时可用的信息（如源代码、文件系统、环境变量），宏的输出是运行时可用的代码和数据。

### 5.7 JavaScript 模块系统

JavaScript 模块系统是理解 Bun Macros 的重要基础。宏的导入和导出机制建立在 JavaScript 模块系统之上，理解模块系统的工作原理有助于正确使用宏。

**CommonJS 模块系统**

CommonJS 是 Node.js 原生支持的模块系统。在 CommonJS 中，使用 `require()` 函数导入模块，使用 `module.exports` 导出模块的值。

CommonJS 模块是同步加载的。当 `require()` 被调用时，Node.js 会同步读取并执行模块文件，返回模块的导出值。这意味着 CommonJS 模块在导入时就会执行模块代码。

CommonJS 模块的加载是动态的。`require()` 可以在任何位置调用，可以接收变量作为参数。这使得条件加载和动态加载成为可能。

**ES Modules 模块系统**

ES Modules（ESM）是 JavaScript 语言标准中定义的模块系统。在 ESM 中，使用 `import` 关键字导入模块，使用 `export` 关键字导出模块的值。

ES Modules 是异步加载的。浏览器和 Node.js 会异步加载和解析模块，然后按依赖顺序执行模块代码。这使得 ESM 可以支持循环依赖和延迟加载。

ES Modules 的导入是静态的。`import` 语句必须在模块的顶层，不能嵌套在条件语句或函数中。导入的模块名必须是静态字符串，不能是变量。这种静态结构使得编译器可以分析和优化模块依赖关系。

**Bun Macros 的模块模型**

Bun Macros 基于 ES Modules 的导入断言语法。宏模块是普通的 ES Module，但使用 `with { type: "macro" }` 断言标记为宏。

宏模块的导入和导出遵循 ES Modules 的规则。宏模块使用 `export` 导出宏函数，使用 `import` 导入其他模块。

但是，宏模块的执行时机与普通模块不同。宏模块在编译时执行，普通模块在运行时执行。这种执行时机的差异是宏模块与普通模块最根本的区别。

宏模块的导入也有限制。宏模块不能使用动态导入（`import()`），因为动态导入是运行时行为。宏模块只能导入编译时可用的模块，不能导入只在运行时才存在的模块。

### 5.8 函数式编程与纯函数

函数式编程的概念对于正确设计和使用 Bun Macros 非常重要。宏的最佳实践与函数式编程的原则高度一致。

**纯函数的定义**

纯函数是函数式编程的核心概念。一个函数被称为纯函数，当且仅当它满足以下两个条件：

给定相同的输入，总是返回相同的输出。这意味着纯函数不能依赖任何可变状态，包括全局变量、文件系统状态、网络响应等。

函数执行不产生任何副作用。这意味着纯函数不能修改外部状态，包括修改全局变量、写入文件、发送网络请求等。

纯函数的这些特性使得它们易于理解、测试和推理。纯函数的行为是完全可预测的，不受外部环境的影响。

**纯函数与宏的关系**

Bun Macros 的最佳实践是设计为纯函数。纯函数模式的宏具有以下优势：

可预测性：纯函数宏在相同输入下总是产生相同的输出。这意味着每次构建都会产生相同的结果，构建产物是可重现的。

可测试性：纯函数宏可以在测试环境中直接调用，无需设置复杂的全局环境。

可缓存性：纯函数宏的缓存行为是可预测的，Bun 可以安全地缓存纯函数宏的执行结果。

可组合性：纯函数宏可以安全地组合使用，一个宏的输出可以作为另一个宏的输入。

**函数组合与宏**

函数组合是函数式编程中的重要概念。函数组合是指将多个函数组合成一个新函数，新函数的行为是依次执行组合中的函数。

在 Bun Macros 中，函数组合同样适用。多个宏可以组合使用，一个宏的输出作为另一个宏的输入。例如，一个读取配置文件的宏和一个验证配置的宏可以组合使用：

```typescript
// 编译时：读取配置 -> 验证配置 -> 内联配置
const config = validateConfig(readJSON("./config.json"))
```

这种组合方式保持了每个宏的单一职责，同时通过组合实现复杂的功能。

**不可变性与宏**

不可变性是函数式编程的另一个重要概念。不可变性意味着数据一旦创建就不能被修改，任何修改都会创建新的数据副本。

在 Bun Macros 中，不可变性同样重要。宏函数的输入应该是不可变的，宏函数不应该修改输入参数。宏函数的输出也应该是不可变的，不应该在后续的宏调用中被修改。

保持不可变性可以避免许多微妙的错误，特别是在宏的组合使用中。如果一个宏修改了另一个宏的输入，可能导致不可预测的行为。

### 5.9 测试驱动开发与宏

测试驱动开发（TDD）是一种软件开发方法论，强调先编写测试再编写实现代码。对于 Bun Macros，测试驱动开发尤为重要，因为宏在编译时执行，传统运行时调试工具不可用。

**宏的单元测试**

宏函数是普通的 JavaScript 或 TypeScript 函数，可以在测试环境中直接调用。这为宏的单元测试提供了基础。

宏的单元测试应该覆盖以下场景：

正常输入：测试宏在正常输入下的行为，验证返回值是否符合预期。

边界输入：测试宏在边界输入下的行为，如空字符串、极大数值、特殊字符等。

错误输入：测试宏在错误输入下的行为，验证错误处理是否符合预期。

**测试环境设置**

宏的测试环境需要模拟编译时执行环境。具体来说，测试环境需要提供以下能力：

模拟文件系统：对于读取文件的宏，测试环境需要设置模拟的文件系统，提供测试所需的文件。

模拟环境变量：对于读取环境变量的宏，测试环境需要设置模拟的环境变量。

模拟全局对象：对于依赖编译时全局对象的宏，测试环境需要提供相应的模拟对象。

**宏的集成测试**

除了单元测试，宏还需要集成测试。集成测试验证宏在 Bun 编译器中的实际行为。

集成测试可以通过以下方式进行：

构建测试：使用 `bun build` 构建包含宏的项目，验证构建产物中宏的调用是否被正确替换。

运行时测试：运行包含宏的应用，验证宏在运行时的行为是否符合预期。

快照测试：对比构建产物的快照，验证宏的修改是否产生预期的影响。

### 5.10 设计模式与宏

设计模式是软件工程中经过验证的解决方案模板。在 Bun Macros 的开发中，一些设计模式特别适用。

**工厂模式**

工厂模式是一种创建型设计模式，用于封装对象的创建逻辑。在 Bun Macros 中，工厂模式可以用于在编译时生成对象创建代码。

例如，一个配置对象的工厂宏可以在编译时根据环境变量创建配置对象。工厂宏封装了配置对象的创建逻辑，应用代码只需要调用工厂宏即可获得配置对象。

**策略模式**

策略模式是一种行为型设计模式，用于在运行时选择算法。在 Bun Macros 中，策略模式可以用于在编译时选择最优算法。

例如，一个排序宏可以在编译时根据数据特征选择最优的排序算法。宏在编译时分析数据的规模和特征，选择适合的排序算法并生成对应的排序代码。

**模板方法模式**

模板方法模式是一种行为型设计模式，用于定义算法的骨架，将具体步骤延迟到子类实现。在 Bun Macros 中，模板方法模式可以用于在编译时生成代码骨架。

例如，一个 API 客户端生成宏可以定义 API 调用的骨架（请求构建、发送请求、处理响应），具体的 API 端点信息通过参数传入，宏在编译时生成完整的 API 客户端代码。

**单例模式**

单例模式是一种创建型设计模式，确保一个类只有一个实例。在 Bun Macros 中，单例模式可以用于在编译时创建全局唯一的对象。

例如，一个配置管理器的单例宏可以在编译时创建配置对象的唯一实例，应用代码中的每次调用都返回同一个实例。这与运行时单例模式的区别在于，单例实例在编译时创建，运行时直接使用。

**适配器模式**

适配器模式是一种结构型设计模式，用于将不兼容的接口转换为兼容的接口。在 Bun Macros 中，适配器模式可以用于在编译时适配不同格式的数据。

例如，一个数据格式适配宏可以在编译时将不同格式的配置文件（YAML、TOML、JSON）转换为统一的 JavaScript 对象格式。宏在编译时读取配置文件，解析为目标格式，返回统一的 JavaScript 对象。

## 6. 示例代码详解

### 6.1 基础示例：HTML 模板宏

基础示例展示了 Bun Macros 最核心的功能：编译期代码生成。`html.macro.ts` 文件定义了一个编译期 HTML 模板编译宏，`macro-basics.ts` 文件演示了如何使用这个宏。

**html.macro.ts 详解**

`html.macro.ts` 文件定义了一个名为 `html` 的宏函数。这个函数接收一个标签模板字符串（Tagged Template）作为输入，在编译时将模板编译为优化的渲染函数。

宏函数的第一部分处理模板字符串的静态部分。对于模板字符串中的静态 HTML 内容，函数会转义 HTML 特殊字符以防止跨站脚本攻击（XSS）。转义包括将 `&`、`<`、`>`、`"` 和 `'` 替换为对应的 HTML 实体。

宏函数的第二部分处理模板字符串的插值部分。对于每个插值表达式，函数生成对应的 HTML 转义代码。这意味着在运行时，插值的值会自动被转义，进一步增强了安全性。

宏函数的返回值是一个渲染函数的代码字符串。这个字符串不是直接内联的 HTML，而是一个 JavaScript 函数的源代码。Bun 会将这些函数代码字符串内联到调用位置，使其成为运行时可以直接调用的函数。

**macro-basics.ts 详解**

`macro-basics.ts` 文件演示了 `html` 宏的使用方法。文件的第一部分使用宏导入语法导入 `html` 函数：

```typescript
import { html } from "./html.macro" with { type: "macro" }
```

这个导入语句告诉 Bun：`html` 函数来自宏模块，需要在编译时执行。

在文件中，`html` 标签模板被用于创建用户卡片模板：

```typescript
const renderUserCard = html`
  <div class="user-card">
    <h2>${"name"}</h2>
    <p>邮箱: ${"email"}</p>
    <p>角色: ${"role"}</p>
  </div>
`
```

在编译时，`html` 函数接收模板字符串和插值键名，生成预编译的渲染函数。编译后的代码相当于：

```typescript
const renderUserCard = function(data) {
  // 编译时生成的渲染逻辑
  return '<div class="user-card">\n  <h2>' + escapeHTML(data.name) + '</h2>\n  ...'
}
```

在运行时，`renderUserCard` 是一个普通的 JavaScript 函数，可以直接调用并传入数据对象。由于模板编译已经在编译时完成，运行时没有模板解析的开销。

文件还演示了 `constant` 宏的使用：

```typescript
const appName = constant("Bun Macros Demo")
const version = constant("1.0.0")
```

`constant` 宏在编译时直接返回传入的值，相当于在编译时将字面量内联到变量声明中。编译后的代码等价于：

```typescript
const appName = "Bun Macros Demo"
const version = "1.0.0"
```

### 6.2 进阶示例：Markdown 转换宏

进阶示例展示了 Bun Macros 在静态资源内联和编译时数据转换方面的能力。`markdown.macro.ts` 文件定义了一个编译期 Markdown 转换宏，`markdown-macro.ts` 文件演示了如何使用这个宏。

**markdown.macro.ts 详解**

`markdown.macro.ts` 文件定义了三个宏函数：`readMarkdown`、`readFile` 和 `readJSON`。

`readMarkdown` 函数接收一个 Markdown 文件的路径，在编译时读取文件内容，将其转换为 HTML，并返回 HTML 字符串。这个函数在编译时执行以下操作：

第一步，使用 Node.js 的 `fs` 模块读取 Markdown 文件的内容。文件路径相对于项目根目录解析，确保路径在不同环境中一致。

第二步，调用内部的 `convertMarkdownToHtml` 函数将 Markdown 文本转换为 HTML。这个函数实现了一个简单的 Markdown 解析器，支持标题、粗体、斜体、代码块、列表、链接和图片等常见 Markdown 语法。

第三步，返回转换后的 HTML 字符串。这个字符串在编译时被内联到调用位置，运行时直接使用预转换的 HTML。

`readFile` 函数更为通用，它在编译时读取文件内容并返回字符串。这个函数适用于读取 SQL 查询文件、配置文件等文本文件。

`readJSON` 函数在编译时读取并解析 JSON 文件，返回解析后的 JavaScript 对象。这个函数适用于读取配置文件、国际化翻译文件等 JSON 格式的数据。

**markdown-macro.ts 详解**

`markdown-macro.ts` 文件演示了三个宏函数的使用方法。

`readMarkdown` 宏的使用：

```typescript
const readmeHTML = readMarkdown("./content/readme.md")
```

在编译时，`readMarkdown` 函数读取 `./content/readme.md` 文件，将其转换为 HTML，并将 HTML 字符串内联到 `readmeHTML` 变量中。运行时，`readmeHTML` 是一个已经包含完整 HTML 内容的字符串。

`readFile` 宏的使用：

```typescript
const getUserQuery = readFile("./sql/getUser.sql")
```

在编译时，`readFile` 函数读取 SQL 文件的内容，将 SQL 查询字符串内联到变量中。运行时，SQL 查询已经可用，无需读取文件系统。

`readJSON` 宏的使用：

```typescript
const appConfig = readJSON("./config/app.json")
```

在编译时，`readJSON` 函数读取 JSON 配置文件，解析为 JavaScript 对象，并将对象字面量内联到变量中。运行时，配置对象已经可用，无需解析 JSON。

### 6.3 生产示例：构建时配置注入

生产示例展示了 Bun Macros 在 CI/CD 和部署流程中的应用。`config.macro.ts` 文件定义了一个编译期配置注入宏，`app.ts` 文件演示了如何使用这个宏。

**config.macro.ts 详解**

`config.macro.ts` 文件定义了三个宏函数：`env`、`buildConfig` 和 `dbConfig`。

`env` 函数是环境变量读取宏。它在编译时从 `process.env` 中读取环境变量的值，并将值内联到代码中。如果环境变量不存在，使用默认值。

```typescript
export function env(key: string, defaultValue?: string): string {
  return process.env[key] ?? defaultValue ?? ""
}
```

这个函数的关键在于，它在编译时读取环境变量。这意味着构建时环境变量的值被固化到代码中，运行时不再依赖环境变量。

`buildConfig` 函数生成完整的应用配置对象。它读取多个环境变量，构建一个包含构建时间、API 配置、功能开关和日志配置的配置对象。

```typescript
export function buildConfig(): Record<string, unknown> {
  return {
    buildTime: new Date().toISOString(),
    buildVersion: process.env.BUILD_VERSION || "0.0.0",
    // ...
  }
}
```

这个函数在编译时执行，生成完整的配置对象。构建时间在编译时确定，功能开关在编译时根据环境变量值确定。

`dbConfig` 函数生成数据库连接配置。它从环境变量中读取数据库连接信息，返回一个包含主机、端口、数据库名、用户名和密码的配置对象。

**app.ts 详解**

`app.ts` 文件演示了配置注入宏在生产环境中的使用。

文件开头使用宏导入语法导入三个宏函数：

```typescript
import { env, buildConfig, dbConfig } from "./config.macro" with { type: "macro" }
```

在编译时，这三个宏函数被执行，它们的返回值被内联到代码中。

`env` 宏用于获取基本的运行时配置：

```typescript
const nodeEnv = env("NODE_ENV", "development")
const appPort = env("APP_PORT", "3000")
```

在编译时，这些环境变量的值被内联到代码中。如果构建时设置了 `NODE_ENV=production`，编译后的代码中 `nodeEnv` 的值就是 `"production"`。

`buildConfig` 宏生成完整的配置对象：

```typescript
const config = buildConfig()
```

编译后的代码中，`config` 变量被替换为编译时生成的配置对象字面量。

`dbConfig` 宏生成数据库配置：

```typescript
const db = dbConfig()
```

编译后的代码中，`db` 变量被替换为编译时生成的数据库配置对象字面量。

文件的其他部分使用这些编译时注入的配置值启动应用。由于所有配置值在编译时已经确定，运行时启动速度更快，且不会因为缺少环境变量而失败。

### 6.5 示例代码的扩展思路

示例代码提供了 Bun Macros 的基础用法，实际项目中可以根据需求进行扩展。

**扩展 HTML 模板宏**

`html.macro.ts` 中的模板编译器可以扩展支持以下功能：

条件渲染：在模板中支持 `if` 条件语句，根据数据条件决定是否渲染特定部分。

组件系统：在模板中支持组件嵌套，允许在模板中引用其他模板组件。

异步数据：在模板中支持异步数据加载，在编译时预取数据并内联到模板中。

**扩展 Markdown 转换宏**

`markdown.macro.ts` 中的 Markdown 转换器可以扩展支持以下功能：

自定义渲染器：支持自定义 HTML 渲染器，允许开发者自定义 Markdown 元素的渲染方式。

代码高亮：在编译时为代码块添加语法高亮，生成包含高亮样式的 HTML。

数学公式：支持 LaTeX 数学公式的渲染，在编译时转换为 MathML 或 SVG。

**扩展配置注入宏**

`config.macro.ts` 中的配置注入宏可以扩展支持以下功能：

加密配置解密：在编译时从加密的配置文件中读取配置，解密后内联到代码中。

远程配置获取：在编译时从远程配置中心获取配置，将配置值内联到代码中。

配置验证：在编译时验证配置的完整性和合法性，确保构建时配置正确。

配置合并：支持多个配置源的合并，允许分层配置的编译时合并。

**自定义宏的开发指南**

开发自定义宏需要遵循以下步骤：

第一步，定义宏函数的接口。确定宏函数的输入参数和返回值类型，使用 TypeScript 的类型系统确保类型安全。

第二步，实现宏函数的逻辑。宏函数的实现与普通函数类似，但需要注意编译时执行环境的限制。

第三步，编写宏的单元测试。宏函数可以在测试环境中直接调用和测试。

第四步，在应用代码中使用宏。使用 `with { type: "macro" }` 导入宏模块，在需要的地方调用宏函数。

第五步，验证宏的行为。通过构建项目并检查构建产物来验证宏是否正确工作。

开发宏时需要注意以下最佳实践：

宏函数应该是纯函数，不依赖运行时环境的状态。宏函数的输入应该通过参数传递，而不是通过全局状态。

宏函数的返回值应该是可序列化的。不支持序列化的值（如函数、Symbol）可能导致宏返回不正确的值。

宏函数的执行时间应该尽可能短。宏在编译时执行，过长的执行时间会影响构建速度。

宏函数应该提供详细的错误信息。宏在编译时执行，清晰的错误信息有助于快速定位问题。

宏模块应该遵循单一职责原则。一个宏模块只负责一个领域的功能，避免宏模块过于复杂。

## 总结

Bun Macros 是 Bun 运行时提供的一个强大而独特的编译时元编程功能。通过宏，开发者可以在编译时执行代码，将计算结果、文件内容或生成的代码直接内联到运行时代码中。这带来了以下主要优势：

运行时性能提升：将计算从运行时转移到编译时，减少运行时的 CPU 和 I/O 开销。

静态资源内联：在编译时将文件内容内联到代码中，消除运行时的文件系统依赖。

配置注入：在构建时将环境变量和配置信息注入代码中，简化部署流程。

代码生成：在编译时生成高效的运行时代码，消除运行时的模板解析和编译开销。

同时，使用 Bun Macros 也需要注意以下事项：

副作用管理：宏中的副作用需要在编译时环境中正确管理。

调试困难：宏在编译时执行，传统运行时调试工具不可用。

构建速度：复杂的宏会增加构建时间，需要在运行时收益和编译时开销之间做出权衡。

缓存问题：宏的缓存机制需要在特定场景下特别注意。

通过合理使用 Bun Macros，开发者可以在不牺牲开发体验的前提下，显著提升应用的运行时性能和部署效率。宏的设计应该遵循纯函数原则，确保可预测的行为和良好的可测试性。在大型项目中，宏的使用应该经过仔细的评估和优化，确保编译时开销与运行时收益的合理平衡。

**学习路径建议**

对于刚开始学习 Bun Macros 的开发者，建议按照以下路径循序渐进地掌握宏的使用：

第一步，理解宏的基本概念和导入语法。尝试运行本章的基础示例，观察宏在编译时的执行行为。理解 `with { type: "macro" }` 导入断言的语法和语义。

第二步，掌握宏的常见使用场景。从简单的常量内联和文件读取开始，逐步过渡到模板编译和配置注入等高级应用。

第三步，学习宏的设计原则和最佳实践。理解纯函数、副作用管理和错误处理在宏开发中的重要性。

第四步，在实际项目中应用宏。选择适合宏优化的场景，评估宏的性能收益和编译时开销。
