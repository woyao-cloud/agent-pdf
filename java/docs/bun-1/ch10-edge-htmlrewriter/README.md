# 第 10 章：HTMLRewriter 与 WebSockets（边缘计算）

## 概述

本章深入探讨 Bun 运行时提供的两个重要特性：HTMLRewriter 流式 HTML 转换器和 WebSocket 支持。这两个 API 让开发者能够在边缘计算场景下高效地处理和转发 HTTP 流量，实现 SEO 优化、实时通信等功能。HTMLRewriter 采用流式解析器，以极低的内存开销完成 HTML 的实时修改，而 Bun 的原生 WebSocket 支持则允许开发者在同一端口上同时处理 HTTP 请求和 WebSocket 连接。本章将通过三个渐进式示例，从基础用法到生产级实践，全面展示这些能力的应用方式。

边缘计算是近年来云计算领域最重要的趋势之一。传统的集中式云计算模型将所有计算和数据处理集中在少数几个大型数据中心，客户端请求需要跨越很长的网络距离才能到达服务器。边缘计算则将计算资源部署在靠近用户的网络边缘节点上，大大缩短了数据传输距离，降低了延迟。HTMLRewriter 和 WebSocket 正是在这种边缘计算场景下发挥重要作用的两个关键技术。

HTMLRewriter 的核心价值在于它能够在数据流经网络节点时进行实时转换，而不需要等待整个数据接收完毕。这种流式处理模式完美适配了边缘计算的架构需求：边缘节点在转发上游服务器的响应时，可以同时对其进行修改和增强，而不会显著增加首字节时间。WebSocket 则提供了边缘节点与客户端之间的持久化实时通信通道，使得服务器可以在任何时间主动向客户端推送数据，这是传统的 HTTP 请求-响应模式无法实现的。

## 第一章：使用场景

### 流式 HTML 转换

流式 HTML 转换是边缘计算中最常见的需求之一。传统的 HTML 修改方式需要先将整个 HTML 文档加载到内存中，构建 DOM 树，进行修改，再序列化输出。这种方式对于大型页面会消耗大量内存，且增加了首字节时间（TTFB）。HTMLRewriter 的流式处理模式解决了这些问题：它一边接收 HTML 数据流，一边进行解析和转换，一边输出结果，内存占用仅与单个元素的复杂度相关，与文档总大小无关。

在实际应用中，流式 HTML 转换的典型场景包括以下几个方面。第一，动态注入分析脚本和跟踪像素。许多网站需要在页面中嵌入第三方分析工具的脚本，如 Google Analytics、百度统计等。传统的做法是在后端模板中硬编码这些脚本，但这意味着每次更换分析工具都需要修改后端代码。使用 HTMLRewriter，我们可以在网关层统一注入分析脚本，后端只需要关注业务逻辑即可。第二，插入内容安全策略（CSP）元标签。内容安全策略是防范跨站脚本攻击（XSS）的重要机制，通过在 HTML 中嵌入 CSP 元标签，浏览器可以限制页面可以加载和执行的资源。对于大型网站，CSP 策略的维护和更新是一个持续的过程，使用 HTMLRewriter 在网关层统一注入 CSP 标签可以避免逐个修改后端服务。第三，动态替换资源链接。根据用户的地理位置或设备类型将 CDN 域名切换为就近节点，或者根据网络条件在高清和标清图片之间切换。第四，在静态页面中注入用户特定的个性化内容，如用户名、推荐商品等，而无需将整个页面交给服务端渲染框架。第五，A/B 测试，在网关层随机选择不同版本的页面元素注入到 HTML 中，观察不同版本的转化率差异。

流式 HTML 转换还有一个重要的优势：它支持超大页面的处理。对于包含数万行 HTML 的大型文档，传统的 DOM 解析器可能会消耗数百兆甚至数吉字节的内存，而流式解析器只需要几十吉字节的缓冲区即可完成转换。这使得 HTMLRewriter 特别适合处理内容管理系统生成的大型 HTML 页面、产品目录页面、文档站点等。

### 反向代理与网关

结合 HTMLRewriter 的反向代理网关是一种强大的架构模式。在这种模式中，网关接收客户端请求，从上游服务器获取响应，在返回客户端之前对响应进行转换。这种模式将业务逻辑与展示逻辑分离，让上游服务器专注于内容生成，而所有与展示相关的增强工作由网关层完成。

反向代理网关的核心价值在于它提供了一层抽象，使得前端团队可以独立于后端团队工作。前端开发者可以在不接触后端代码的情况下，通过修改网关的转换规则来改变页面的呈现方式。这对于大型组织中的微服务架构尤为重要，因为不同的后端服务可能由不同的团队维护，统一的前端网关可以协调各个服务的输出。

典型的生产场景包括：为现有网站添加 SEO 元标签，无需修改老旧的后端代码；对多语言站点自动添加 hreflang 标签，帮助搜索引擎理解页面的语言版本关系；为 AMP 页面自动生成对应的 canonical 标签，标识 AMP 页面与标准页面的对应关系；在维护期间向所有页面注入维护公告横幅，通知用户系统正在升级；对旧版浏览器注入 polyfill 脚本标签，确保新特性在旧浏览器上也能正常工作；根据用户的地理位置注入本地化的样式和内容，实现区域化的用户体验。

### 实时 WebSocket 通信

WebSocket 协议提供了全双工的实时通信能力，适用于需要低延迟双向数据传输的场景。Bun 对 WebSocket 的原生支持使得开发者可以在同一个服务器实例上同时处理 HTTP 请求和 WebSocket 连接，简化了部署和运维。

常见的 WebSocket 应用包括以下几个方面。第一，在线聊天室和即时消息系统，用户之间需要实时收发消息。这种场景对消息的实时性和可靠性有很高的要求，WebSocket 的全双工特性正好满足了这一需求。第二，协作编辑工具，多个用户同时编辑同一份文档，需要同步操作。如 Google Docs 式的协作文档编辑系统，每个用户的操作通过 WebSocket 实时广播给其他协作者。第三，实时数据推送，如股票行情、体育比分、系统监控指标等。金融交易系统需要在毫秒级别内将行情数据推送给交易终端，WebSocket 是满足这种需求的最佳选择。第四，多人游戏，需要低延迟的状态同步。游戏服务器需要实时接收玩家的操作输入，并将游戏世界的状态变化广播给所有玩家。第五，通知系统，服务端主动向客户端推送事件通知，如新消息提醒、系统告警等。

WebSocket 相比传统的轮询技术有着明显的优势。在轮询模式中，客户端定期发送 HTTP 请求查询是否有新数据，即使没有新数据也需要发送请求，造成了大量的带宽浪费。WebSocket 则只在有数据需要传输时才发送消息，空闲时几乎不消耗带宽。此外，WebSocket 的握手只需要一次 HTTP 升级过程，后续的数据传输不再需要 HTTP 头的开销，减少了协议层面的开销。

### 边缘计算与实时处理

边缘计算将计算资源部署在靠近用户的网络节点上，减少数据传输延迟，提高响应速度。HTMLRewriter 和 WebSocket 支持是边缘计算平台上的关键能力。在 Cloudflare Workers、Deno Deploy 等边缘平台上，HTMLRewriter 被广泛用于在网络的最后一公里对 HTML 进行转换，而 WebSocket 则用于建立持久化的实时连接。

边缘计算的核心优势在于它能够显著降低网络延迟。传统的数据中心可能距离用户数千公里，光信号在这些距离上的传播延迟就达到数十毫秒。而边缘节点通常部署在距离用户几十公里以内的位置，网络延迟可以降低到个位数毫秒。对于实时交互应用，如在线游戏、视频会议、远程控制等，这种延迟的降低对用户体验有显著的改善。

Bun 在这方面的定位有些特殊：它既可以作为开发环境中的本地服务器运行这些代码，也可以作为生产环境中的边缘节点或中心服务器。这种灵活性使得开发者可以在开发阶段使用与生产环境相同的 API，减少环境差异带来的问题。更重要的是，Bun 的高性能 JavaScript 运行时使得它能够在边缘计算场景下提供接近原生的性能表现。

边缘计算还带来了数据本地化的优势。某些行业法规要求用户数据必须存储在特定的地理位置，边缘计算可以将数据处理和存储限制在合规的地理区域内。例如，欧盟的通用数据保护条例（GDPR）要求欧洲用户的数据必须存储在欧盟境内，通过在欧洲部署边缘节点可以满足这一要求。同样，中国的网络安全法和数据安全法要求重要数据和个人信息必须存储在中国境内，边缘计算节点可以帮助跨国企业满足这些合规要求。

边缘计算的另一个重要应用场景是物联网（IoT）数据处理。物联网设备产生海量的实时数据，如果全部传输到中心云服务器处理，不仅网络带宽消耗巨大，而且延迟也无法满足实时响应的需求。边缘计算节点可以在靠近设备的位置进行数据预处理和过滤，只将有价值的结果传输到中心服务器。例如，智能工厂中的传感器数据可以在边缘节点上实时分析，检测设备异常并立即触发告警，而不需要等待数据往返中心服务器。这种架构不仅降低了网络带宽成本，还提高了响应速度和系统可靠性。

在边缘计算场景下，HTMLRewriter 的价值尤为突出。当边缘节点作为反向代理转发上游服务器的响应时，HTMLRewriter 可以在数据流经节点时进行实时转换，注入本地化的内容、调整资源路径、添加安全策略等。这些转换完全在流式处理中完成，不会增加额外的延迟。而且，由于边缘节点分布在全球各地，每个节点可以根据当地用户的需求进行不同的转换，实现真正的全球化部署和本地化体验。

WebSocket 在边缘计算中的应用同样重要。边缘节点可以作为 WebSocket 连接的终端点，为客户端提供低延迟的实时通信服务。同时，边缘节点也可以作为 WebSocket 代理，在客户端和后端服务器之间转发 WebSocket 数据，实现全局的实时通信网络。例如，一个全球部署的在线游戏可以使用边缘 WebSocket 网关来处理玩家连接，游戏状态更新在边缘节点上进行本地处理，关键操作才同步到中心游戏服务器，从而大大降低了玩家的操作延迟。

## 第二章：实现原理

### HTMLRewriter 流式解析器

HTMLRewriter 基于流式 HTML 解析器（streaming HTML parser）实现。传统的 HTML 解析器需要读取完整的文档内容后构建 DOM 树，而流式解析器则逐字节读取输入，在解析过程中同步触发事件回调。

流式解析的核心是一个状态机，它维护着当前解析位置、标签栈、属性缓冲区等状态信息。当解析器遇到新的开始标签时，它会调用注册在该标签选择器上的 element 回调；当遇到文本节点时，调用 text 回调；当遇到结束标签时，进行相应的栈操作。整个过程不需要构建完整的 DOM 树，因此内存占用极低。

具体来说，流式解析器的工作流程如下。第一步，解析器从输入流中读取字节序列。第二步，通过词法分析识别出标签、属性、文本、注释等 token。第三步，根据 token 类型更新解析状态机的状态。第四步，在适当的时机触发用户注册的回调函数。第五步，将修改后的 token 序列写出到输出流。整个过程是增量的、非阻塞的，输入和输出可以并行进行。

流式解析器的状态机包含多个状态，每个状态对应 HTML 解析过程中的不同阶段。初始状态是数据状态（Data state），在这个状态下解析器等待 HTML 标签的开始。当遇到左尖括号（<）时，切换到标签开始状态（Tag open state）。如果下一个字符是斜杠（/），则切换到结束标签开始状态（End tag open state）。如果下一个字符是字母，则切换到标签名状态（Tag name state）。每个状态都有对应的处理逻辑和状态转换规则。

在标签名状态下，解析器读取标签名称，直到遇到空格、斜杠、右尖括号等终止字符。如果遇到空格，切换到属性名之前的状态（Before attribute name state），等待读取属性。如果遇到斜杠，切换到自闭合标签状态（Self-closing start tag state）。如果遇到右尖括号，则表示标签解析完成，输出标签 token。

属性解析也有自己的状态机。在属性名状态下，解析器读取属性名称，遇到等号时切换到属性值之前的状态（Before attribute value state），然后根据属性值的引号类型进入不同的属性值状态（Attribute value double-quoted state、Attribute value single-quoted state 或 Attribute value unquoted state）。属性值解析完成后，状态机回到属性名之前的状态，等待下一个属性或标签结束。

与基于 DOM 的解析器相比，流式解析器有以下几个关键区别。第一，流式解析器不能访问兄弟节点或父节点，因为解析器尚未看到后续的内容。这意味着我们无法在 element 回调中执行类似 parentNode、nextSibling 的操作。第二，流式解析器不能进行复杂的 DOM 遍历操作，如 querySelectorAll、closest 等。第三，流式解析器的修改仅限于当前正在处理的元素，不能回溯修改已输出的内容。一旦某个元素的内容已经写出到输出流，就无法再修改它。第四，流式解析器的性能远高于 DOM 解析器，内存占用低一到两个数量级。对于大型 HTML 文档，这种性能差异尤为明显。

HTMLRewriter 的流式解析器还实现了 HTML 规范的容错机制。HTML 规范定义了浏览器应该如何修复格式不正确的 HTML，例如缺少结束标签的段落、嵌套错误的元素、未转义的特殊字符等。HTMLRewriter 的解析器实现了大部分这些容错规则，因此它能够正确处理真实世界中格式不完美的 HTML 页面。然而，需要注意的是，HTMLRewriter 的容错行为与浏览器的行为可能略有不同，特别是在处理一些边界情况时。因此，在将 HTMLRewriter 应用于生产环境之前，应该使用真实的 HTML 页面进行充分测试。

### CSS 选择器引擎

HTMLRewriter 的第二个核心组件是 CSS 选择器引擎。这个引擎负责将用户提供的 CSS 选择器字符串编译为匹配规则，并在流式解析过程中快速判断当前元素是否匹配。

选择器引擎支持大部分标准 CSS 选择器。标签选择器（如 div、p、a、span）匹配指定标签类型的元素。类选择器（如 .class-name、.highlight、.error）匹配具有指定 class 属性值的元素。ID 选择器（如 #element-id、#header、#main-content）匹配具有指定 id 属性值的元素。属性选择器包括 [attr] 匹配具有指定属性的元素，[attr=value] 匹配属性值等于指定值的元素，[attr^=value] 匹配属性值以指定值开头的元素，[attr$=value] 匹配属性值以指定值结尾的元素，[attr*=value] 匹配属性值包含指定值的元素。伪类选择器包括 :first-child 匹配作为父元素第一个子元素的元素，:last-child 匹配作为父元素最后一个子元素的元素，:nth-child(n) 匹配作为父元素第 n 个子元素的元素。组合选择器包括后代选择器（空格分隔）、子选择器（> 分隔）、相邻兄弟选择器（+ 分隔）和通用兄弟选择器（~ 分隔）。

选择器引擎的实现通常包括两个阶段：编译阶段和匹配阶段。在编译阶段，选择器字符串被解析为抽象语法树（AST），然后转换为匹配函数或匹配器的集合。编译阶段的输出是一个匹配器对象，它包含了快速匹配所需的所有信息。在匹配阶段，当流式解析器遇到一个元素时，引擎检查该元素是否匹配任何已注册的选择器。为了提高匹配效率，引擎会使用哈希表、位掩码等数据结构加速常用选择器的匹配。

具体来说，选择器引擎的编译过程如下。首先，选择器字符串被词法分析器分解为 token 序列。每个 token 代表选择器的一个组成部分，如标签名、类名、ID、属性选择器、伪类、组合器等。然后，这些 token 被语法分析器组合为选择器树，树中的每个节点代表一个选择器单元，节点之间的关系由组合器决定。最后，选择器树被编译为匹配函数，匹配函数接收一个元素对象作为输入，返回布尔值表示是否匹配。

在匹配阶段，选择器引擎的工作方式取决于选择器的类型。对于简单的标签选择器，引擎只需要比较元素的标签名。对于类选择器，引擎需要检查元素的 class 属性值是否包含指定的类名。对于后代选择器，引擎需要遍历元素的祖先链，检查是否存在匹配祖先选择器的元素。由于流式解析器不能访问祖先元素，后代选择器的匹配是通过在解析过程中维护一个选择器匹配上下文来实现的。

需要注意的是，由于流式解析的限制，某些 CSS 选择器在 HTMLRewriter 中无法正常工作。例如，:has() 伪类选择器需要前瞻未来元素，这在流式解析中是不可能的。同样，:empty 伪类选择器在解析开始时无法确定元素是否为空，因为子元素可能还在流中。此外，:nth-last-child 和 :nth-last-of-type 等依赖于元素之后兄弟元素的伪类也无法在流式解析中正常工作。在实际开发中，应该避免使用这些选择器，或者使用替代方案实现相同的效果。

### WebSocket 协议

WebSocket 协议在 RFC 6455 中定义，它通过 HTTP 升级机制在客户端和服务器之间建立持久化的全双工连接。理解 WebSocket 协议对于正确使用 Bun 的 WebSocket API 至关重要。

WebSocket 连接的建立分为两个阶段：握手阶段和数据传输阶段。在握手阶段，客户端发送一个包含 Upgrade: websocket 头的 HTTP 请求，请求中包含 Sec-WebSocket-Key、Sec-WebSocket-Version 等必要的头部字段。服务器接收到升级请求后，验证请求的合法性，然后返回 101 Switching Protocols 状态码，并在响应头中包含 Sec-WebSocket-Accept 字段，该字段的值是对客户端 Sec-WebSocket-Key 的 SHA-1 哈希后进行 Base64 编码的结果。握手完成后，连接从 HTTP 协议切换到 WebSocket 协议，后续的数据传输不再使用 HTTP 格式。

握手阶段的 HTTP 请求和响应是 WebSocket 连接中唯一使用 HTTP 格式的数据交换。一旦握手完成，连接就完全脱离了 HTTP 协议，转而使用 WebSocket 的帧协议进行数据传输。这也是 WebSocket 在性能上优于 HTTP 长轮询的原因之一：握手之后的数据传输不需要携带 HTTP 头部的额外开销。

WebSocket 的数据帧格式包含以下几个关键字段。第一个字段是 FIN 位，它是一个单比特标志，表示当前帧是否是消息的最后一个帧。如果消息被分片为多个帧，除了最后一帧外的所有帧的 FIN 位都为 0，最后一帧的 FIN 位为 1。第二个字段是 Opcode，它是一个 4 比特字段，表示帧的类型。文本帧的 Opcode 为 0x1，二进制帧的 Opcode 为 0x2，关闭帧的 Opcode 为 0x8，Ping 帧的 Opcode 为 0x9，Pong 帧的 Opcode 为 0xA。第三个字段是 Mask 位，它是一个单比特标志，表示负载数据是否经过掩码处理。根据 RFC 6455 的规定，客户端发送的所有帧都必须设置 Mask 位为 1，服务器发送的帧则不需要掩码。第四个字段是 Payload length，它可以是 7 位、7+16 位或 7+64 位，具体取决于负载数据的长度。第五个字段是 Masking key，当 Mask 位为 1 时，这个 32 位的密钥用于对负载数据进行掩码处理。第六个字段是 Payload data，即实际的传输数据。

WebSocket 的掩码机制是一个重要的安全特性。掩码的目的是防止缓存污染攻击，这种攻击利用代理服务器对不同 WebSocket 连接的混淆来注入恶意数据。通过要求客户端对发送的每一帧进行掩码处理，WebSocket 协议确保了即使代理服务器错误地将来自一个连接的数据与另一个连接关联，掩码的差异也会导致数据被破坏而无法使用。

WebSocket 协议还定义了连接关闭的流程。当一方决定关闭连接时，它发送一个包含关闭码和关闭原因的关闭帧。另一方收到关闭帧后，应该回复一个关闭帧，然后连接关闭。这个流程确保了双方都能优雅地终止连接，避免数据丢失。常见的关闭码包括 1000（正常关闭）、1001（端点离开）、1002（协议错误）、1003（不可接受的数据类型）、1008（策略违规）、1011（意外条件）等。

WebSocket 的心跳机制通过 Ping 和 Pong 帧实现。一方发送 Ping 帧，另一方必须回复 Pong 帧。如果一方在超时时间内没有收到 Pong 响应，可以认为连接已断开。这种机制对于检测网络故障和空闲连接的回收非常重要。在实际应用中，心跳间隔通常设置为 30 到 60 秒，超时时间设置为心跳间隔的 2 到 3 倍。需要注意的是，WebSocket 协议不强制要求实现 Ping/Pong 机制，但它强烈建议实现以检测连接的健康状态。

WebSocket 的子协议（subprotocol）机制允许客户端和服务器在握手阶段协商使用的应用层协议。客户端在 Sec-WebSocket-Protocol 请求头中列出支持的子协议，服务器从中选择一个并在响应头中返回。常见的子协议包括 graphql-ws（GraphQL over WebSocket）、wamp（WebSocket 应用消息协议）、mqtt（MQTT over WebSocket）等。子协议机制使得 WebSocket 可以适配不同的应用层协议，增加了协议的灵活性。

WebSocket 的扩展（extension）机制允许在 WebSocket 协议基础上增加额外功能，如压缩、多路复用等。permessage-deflate 是最常用的扩展，它对 WebSocket 消息进行压缩，减少带宽消耗。Bun 的 WebSocket 实现支持 permessage-deflate 扩展。扩展的协商发生在握手阶段，客户端在 Sec-WebSocket-Extensions 请求头中列出支持的扩展，服务器从中选择支持的扩展并在响应头中返回。

### Bun.serve WebSocket 支持

Bun 的 Bun.serve API 提供了对 WebSocket 的一流支持。与需要额外依赖（如 ws、socket.io）的 Node.js 不同，Bun 在运行时层面内置了 WebSocket 服务器能力。

Bun.serve 的 WebSocket 支持通过 websocket 配置项实现，该配置项接受一个对象，包含 open、message、close、drain、ping、pong 等事件处理函数。当服务器接收到 WebSocket 升级请求时，会调用 fetch 处理函数，服务器通过 server.upgrade() 方法将 HTTP 连接升级为 WebSocket 连接。

server.upgrade() 方法接受两个参数：req 是原始的 HTTP 请求对象，options 是一个可选的对象，其中最重要的字段是 data，用于在升级时将自定义数据关联到 WebSocket 连接。这个 data 字段在后续的 WebSocket 事件处理函数中可以通过 ws.data 访问。这种机制非常有用，例如可以在升级时传递用户身份信息、会话 ID、权限级别等。在聊天服务器的示例中，我们使用 data 字段传递用户的昵称，这样在消息处理函数中就可以知道发送消息的用户是谁。

Bun 的 WebSocket 实现还支持发布/订阅模式。通过 server.publish(topic, message) 方法，服务器可以向订阅了某个主题的所有 WebSocket 连接广播消息。客户端通过 ws.subscribe(topic) 和 ws.unsubscribe(topic) 方法管理订阅。这种模式大大简化了实现群组聊天、房间系统、频道广播等功能的复杂度。在内部实现中，Bun 维护了一个主题到连接列表的映射表，当调用 publish 方法时，Bun 遍历该主题的所有订阅者，逐个发送消息。

在内部实现上，Bun 使用基于 io_uring（Linux）或 kqueue（macOS）的事件循环来处理 WebSocket 连接。每个 WebSocket 连接由一个文件描述符表示，事件循环监控这些文件描述符的可读事件。当有数据到达时，事件循环将数据传递给 WebSocket 协议处理器进行帧解析和消息重组，然后调用用户的 message 回调。这种基于事件驱动的架构使得 Bun 能够高效地处理大量并发连接，即使在单线程模型下也能达到出色的性能。

Bun 的 WebSocket 实现还支持背压管理。当发送速度超过接收速度时，数据会在发送缓冲区中积压。通过 drain 事件，开发者可以感知到背压状态并进行流量控制。drain 事件在发送缓冲区从满变为不满时触发，类似于 Node.js 中流的 drain 事件。在实际应用中，背压管理对于防止内存无限增长非常重要。当发送缓冲区达到一定大小时，开发者可以选择暂停发送，等待 drain 事件触发后再恢复发送。

Bun.serve 的 WebSocket 配置项还支持以下几个有用的选项。perMessageDeflate 是一个布尔值，用于启用或禁用 per message deflate 压缩。当启用时，Bun 会自动对 WebSocket 消息进行压缩和解压缩，减少网络传输的数据量。但是，压缩会消耗额外的 CPU 资源，因此在高吞吐量场景下需要权衡利弊。maxPayloadLength 用于限制单个 WebSocket 消息的最大大小，防止恶意客户端发送超大消息导致服务器内存耗尽。idleTimeout 用于设置连接的空闲超时时间，当连接在指定时间内没有数据交换时，Bun 会自动关闭连接释放资源。

Bun 的 WebSocket 客户端支持同样值得一提。Bun 提供了全局的 WebSocket 构造函数，用于创建 WebSocket 客户端连接。客户端 WebSocket 支持 open、message、close、error 等事件，以及 send 和 close 方法。这使得 Bun 既可以作为 WebSocket 服务器，也可以作为 WebSocket 客户端，非常适合构建需要连接外部 WebSocket 服务的网关应用。

## 第三章：风险与优化

### 没有完整的 DOM API

HTMLRewriter 的一个主要限制是它不提供完整的 DOM API。这是因为流式解析器不构建完整的 DOM 树，因此无法支持需要 DOM 树的操作。具体来说，以下操作在 HTMLRewriter 中不可用。第一，获取父节点或兄弟节点，因为流式解析器在解析某个元素时，其父节点可能已经被输出，子节点尚未出现。第二，遍历子树，因为流式解析器不能随机访问文档的任意部分。第三，在任意位置插入或删除节点，因为一旦元素被输出，就不能再回溯修改。第四，修改已输出内容的样式或属性，因为输出是单向的。

解决这个限制的方法包括以下几种。第一，在设计转换逻辑时，确保每个元素的修改是自包含的，不依赖其他元素的状态。例如，如果要修改所有图片的 alt 属性，只需要为 img 元素注册一个处理器，不需要关心图片的上下文。第二，使用全局状态变量在回调之间传递信息，但要注意流式处理的顺序性。例如，可以在遇到 h1 元素时记录标题文本，然后在遇到后续的 meta 元素时使用这个标题生成描述信息。第三，对于需要完整 DOM 树的操作，考虑使用传统的 HTML 解析库（如 jsdom）作为备选方案，但要注意这会牺牲流式处理的性能优势。第四，在适当的情况下，可以将 HTMLRewriter 与其他转换工具结合使用，例如先使用 HTMLRewriter 进行简单的标签修改，再将结果传递给其他工具进行更复杂的转换。

一个常见的误解是认为 HTMLRewriter 可以在 text 回调中通过正则表达式匹配整个文档。实际上，text 回调只能获取到当前文本块的内容，文本块可能只是完整文本节点的一部分。例如，对于一个很长的段落，HTMLRewriter 可能会将其拆分为多个文本块分别传递给 text 回调。因此，使用 text 回调进行大范围的文本替换需要谨慎处理跨块匹配的情况。如果确实需要进行跨文本块的替换，可以在 text 回调中缓存文本块，直到收集到完整的文本内容后再进行处理。

另一个需要注意的问题是，HTMLRewriter 的 element 回调中的 setInnerContent、append、prepend 等方法接收的是 HTML 字符串，而不是纯文本。这意味着传入的内容会被解析为 HTML，如果传入的内容包含用户生成的数据，可能存在 XSS 安全风险。在向页面中插入用户生成的内容时，应该对内容进行转义，或者使用专门的 sanitization 库清理 HTML。

### 连接限制

在生产环境中使用 WebSocket 时，连接管理是一个关键问题。每个 WebSocket 连接都会占用文件描述符、内存缓冲区等系统资源。操作系统通常对单个进程可以打开的文件描述符数量有限制，当连接数接近这个限制时，新的连接请求会被拒绝。

文件描述符限制是 WebSocket 服务器的首要瓶颈。在 Linux 系统上，默认的文件描述符限制通常是 1024 个，这意味着一个进程最多只能同时处理 1024 个连接。对于生产环境，这个限制显然是不够的。可以通过 ulimit -n 命令或修改 /etc/security/limits.conf 配置文件来增加文件描述符限制。在容器化部署中，可以在 Docker 的启动参数中设置 --ulimit nofile=65536:65536 来增加限制。

为了应对连接数增长的问题，可以采取以下优化措施。第一，设置连接数上限，当活跃连接数超过阈值时拒绝新的连接请求，并返回友好的错误提示。第二，实现空闲连接超时机制，长时间没有数据交换的连接应该被自动关闭。第三，使用连接池和资源配额管理，确保关键业务连接不会因为非关键连接的资源占用而受影响。第四，在水平扩展架构中，使用负载均衡器分发 WebSocket 连接，避免单节点成为瓶颈。第五，使用连接多路复用技术，在一个 TCP 连接上承载多个 WebSocket 连接，减少文件描述符的消耗。

Bun 的 WebSocket 实现本身没有内置的连接数限制，但这意味着开发者需要自己实现连接管理逻辑。在示例中，我们可以通过维护一个连接计数器来跟踪当前连接数，并在达到上限时拒绝新连接。同时，可以记录每个连接的活动时间，定期清理超过空闲超时的连接。

连接限制不仅体现在文件描述符上，还体现在内存方面。每个 WebSocket 连接需要维护发送缓冲区和接收缓冲区，当连接数很大时，这些缓冲区的内存占用可能非常可观。对于发送缓冲区，每个连接的默认大小可能达到 64KB 或更大，10000 个连接就意味着 640MB 的内存占用。因此，在生产环境中，需要合理设置缓冲区大小，并监控内存使用情况。

### 内存泄漏

WebSocket 应用中常见的内存泄漏源包括以下几个方面。第一，未正确清理的订阅关系，当连接关闭时没有调用 ws.unsubscribe() 取消订阅，导致主题的订阅者列表不断增长。第二，在 message 回调中创建的大对象没有被及时释放，特别是当消息频率很高时，垃圾回收器可能来不及回收这些临时对象。第三，闭包捕获的引用导致对象无法被垃圾回收，特别是在使用匿名函数作为回调时容易发生。第四，事件监听器的重复注册，特别是当连接重连时没有移除旧的监听器。第五，使用 Map 或 Set 存储连接相关的数据，但没有在连接关闭时从这些集合中移除条目。

防止内存泄漏的最佳实践包括以下几点。第一，在 close 回调中清理所有与连接相关的资源，包括取消订阅、清除定时器、移除引用、从连接跟踪集合中删除条目等。第二，对 WebSocket 消息的大小和频率进行限制，避免单个连接占用过多内存。例如，可以设置单个消息的最大大小，以及单位时间内的最大消息数量。第三，使用 WeakMap 或 WeakSet 存储与连接关联的元数据，这样当连接对象被回收时，元数据也会被自动清理。WeakMap 和 WeakSet 的使用需要谨慎，因为它们可能导致难以调试的问题，但在正确的场景下是非常有用的工具。第四，定期进行内存快照分析，识别增长异常的对象。Chrome DevTools 的内存分析工具可以连接到 Bun 进程进行内存快照分析。第五，实现连接健康检查机制，定期检测并清理异常连接。

在 Bun 中，由于使用 JavaScript 引擎的垃圾回收机制，大部分内存泄漏问题与普通的 Node.js 应用类似。但 Bun 的 WebSocket 实现有一些特殊之处：每个 WebSocket 连接在 JavaScript 层面被表示为 WebSocket 对象，只要该对象被引用，连接就不会被关闭。因此，在不再需要连接时，需要显式调用 ws.close() 并清除所有引用。另外，Bun 的发布/订阅系统中的主题列表也是一个需要注意的内存泄漏源，当某个主题不再有任何订阅者时，应该从主题列表中移除该主题。

内存泄漏的检测和诊断是运维工作的重要部分。除了使用内存快照分析工具外，还可以在应用中集成内存使用监控。通过定期记录 process.memoryUsage() 的输出，可以绘制内存使用的趋势图。如果发现内存使用持续增长而不回落，就说明可能存在内存泄漏。此时，可以结合连接数、消息吞吐量等指标进行相关性分析，定位内存泄漏的源头。

### CORS 问题

在使用 WebSocket 进行跨域通信时，CORS（跨域资源共享）是一个必须处理的问题。与普通的 HTTP 请求不同，WebSocket 的跨域策略由浏览器实现，而不是由服务器通过 CORS 头控制。

当浏览器发起 WebSocket 连接时，它会自动在 HTTP 升级请求中包含 Origin 头，指示请求的来源。服务器需要验证这个 Origin 头，确保连接来自允许的域名。如果来源不被允许，服务器可以拒绝升级请求。与 HTTP CORS 不同的是，WebSocket 的跨域策略是全有或全无的：要么允许所有域名，要么拒绝所有域名。不存在 HTTP CORS 中的细粒度控制，如允许特定的方法或头字段。

在实际开发中，CORS 相关的常见问题包括以下几类。第一，忘记验证 Origin 头，导致任意网站都可以连接到 WebSocket 服务器，造成安全风险。攻击者可以在自己的网站上嵌入恶意脚本，连接到用户的 WebSocket 服务器进行跨站 WebSocket 劫持。第二，在反向代理配置中，代理服务器修改了 Origin 头，导致服务器无法正确验证来源。某些代理服务器可能会覆盖或删除 Origin 头，使得服务器无法获得真实的请求来源。第三，开发环境和生产环境的域名不同，需要在配置中支持多个允许的域名。第四，浏览器的同源策略限制，导致在 HTTPS 页面中无法连接到 WS（非加密）的 WebSocket 服务器。在这种情况下，需要使用 WSS（WebSocket over TLS）协议。

正确处理 CORS 的策略是：在 WebSocket 升级处理函数中检查 req.headers.get("origin")，将其与允许的域名列表进行比较。对于不匹配的来源，返回 403 状态码拒绝升级。同时，对于允许的来源，设置合适的 Access-Control-Allow-Origin 响应头。建议将允许的域名列表配置在环境变量或配置文件中，而不是硬编码在代码中，以便于在不同环境中切换。

除了 Origin 头的验证外，还可以使用 WebSocket 子协议进行认证。在握手阶段，客户端可以在 Sec-WebSocket-Protocol 头中传递认证令牌，服务器验证令牌的合法性后再决定是否接受连接。这种方式的优势在于认证信息在握手阶段就完成交换，不需要额外的消息交互。但需要注意的是，Sec-WebSocket-Protocol 头的值可能会被代理服务器记录，因此不应该在非加密连接中传递敏感信息。

## 第四章：典型问题处理

### 选择器不匹配

在使用 HTMLRewriter 时，最常见的问题之一是 CSS 选择器不匹配任何元素。这种情况通常由以下原因导致。第一，选择器语法错误，如拼写错误或使用了不支持的伪类。例如，将 .my-class 误写为 .myclass，或者使用了 :has() 这样的不支持的伪类。第二，页面结构发生变化，开发环境中匹配的选择器在生产环境中不匹配。例如，生产环境的页面经过了压缩、混淆或其他转换，导致类名或 ID 发生变化。第三，HTML 的解析模式（标准模式与 quirks 模式）影响了解析结果。在 quirks 模式下，某些标签的解析行为与标准模式不同，可能导致元素不被识别。第四，动态生成的内容在流式解析时尚未出现。例如，通过 JavaScript 动态插入的元素在 HTMLRewriter 解析时并不存在。

解决选择器不匹配问题的方法包括以下几种。第一，使用更通用的选择器作为备选方案，例如在匹配特定类名失败时尝试匹配标签名。可以注册多个选择器的处理器，或者在一个处理器中检查元素的其他属性。第二，在开发阶段使用 HTMLRewriter 的调试模式，输出解析过程中的元素信息。可以在 element 回调中记录所有匹配的元素，帮助分析为什么某些选择器没有匹配。第三，对目标 HTML 进行预分析，了解其实际结构。可以使用浏览器的开发者工具查看页面的实际 DOM 结构，或者使用在线 HTML 解析工具检查 HTML 的结构。第四，编写单元测试验证选择器在预期 HTML 上的匹配效果。使用固定的 HTML 片段作为测试输入，确保选择器能够正确匹配目标元素。

一个有效的调试技巧是使用 text 回调输出所有文本内容，从中查找目标元素的上下文，然后根据上下文调整选择器。另一种方法是将 HTMLRewriter 应用于一个简单的测试 HTML，逐步增加复杂度，直到找到不匹配的原因。还可以在 element 回调中使用 getAttribute 方法输出元素的属性信息，帮助理解为什么选择器没有匹配。

需要注意的是，HTMLRewriter 的选择器匹配是大小写敏感的。对于 HTML 标签名，选择器引擎通常将其转换为小写后再进行匹配，但对于属性值，匹配是大小写敏感的。如果页面中的属性值大小写不统一，可能会导致选择器不匹配。在这种情况下，可以使用属性选择器的 i 标志（如 [attr=value i]）进行大小写不敏感的匹配。

### WebSocket 断开

WebSocket 连接可能因为多种原因断开。常见的断开原因包括：网络故障导致 TCP 连接中断、服务器重启或崩溃、客户端离线或关闭浏览器、防火墙或代理服务器超时断开空闲连接、WebSocket 协议的 Ping/Pong 超时等。处理断连的关键在于实现可靠的自动重连机制。

自动重连的核心策略包括以下几个方面。第一，指数退避算法，每次重连的等待时间逐渐增加（如 1 秒、2 秒、4 秒、8 秒、16 秒、32 秒），避免在服务器恢复期间造成连接风暴。第二，随机抖动，在退避时间上增加随机偏移（如 0 到 500 毫秒的随机值），防止多个客户端同时重连。第三，连接健康检查，定期发送 Ping 帧检测连接状态，在检测到断开时立即触发重连。第四，会话恢复，在重连后恢复之前的订阅关系和状态。例如，如果客户端之前订阅了某些主题，重连后需要重新订阅。

在客户端实现自动重连时，需要记录重连次数，当重连次数超过一定阈值时停止重连，并向用户显示错误提示。同时，重连过程中应该避免阻塞用户操作，可以显示一个重新连接的提示，让用户知道系统正在尝试恢复连接。

在服务器端，处理断连的重点是资源清理。当检测到连接关闭时，服务器应该立即清理与该连接相关的所有资源，包括取消订阅、释放内存缓冲区、移除连接跟踪记录等。同时，服务器应该记录断连日志，包括断连时间、客户端标识、连接时长等信息，用于后续的监控和排查。

对于需要保证消息可靠性的场景，还需要实现消息确认和重传机制。客户端在收到消息后发送确认帧，服务器在未收到确认时重新发送消息。这种机制类似于 TCP 的确认重传，但在应用层实现，可以更好地控制可靠性的粒度。消息确认机制会增加网络开销和实现复杂度，因此只在确实需要消息可靠性的场景中使用。

### 内存持续增长

在生产环境中运行 WebSocket 服务时，内存持续增长是一个需要密切关注的指标。内存增长通常由以下原因导致。第一，消息发送速度超过消费速度，导致发送缓冲区不断增长。当服务器发送消息的速度快于客户端接收的速度时，消息会在发送缓冲区中积压。第二，未正确清理的连接数据，如用户会话信息、消息历史等。如果连接关闭时没有清理这些数据，它们会一直占用内存。第三，WebSocket 帧的临时缓冲区没有及时释放。第四，第三方库或中间件的内部缓存不断增长。第五，发布/订阅系统中的主题列表不断增长，特别是当有大量动态创建的主题时。

诊断内存增长的方法包括以下几种。第一，使用 process.memoryUsage() 定期采样内存使用量，绘制趋势图。process.memoryUsage() 返回的对象包含 rss、heapTotal、heapUsed、external 和 arrayBuffers 等字段，可以帮助分析内存分布。第二，使用 heap snapshot 工具分析内存中的对象分布。Chrome DevTools 的 Memory 面板可以连接到 Bun 进程，生成堆快照进行分析。第三，监控 WebSocket 连接数和消息队列长度，分析内存增长与这些指标的相关性。第四，在关键路径上添加内存使用日志，定位内存增长的具体位置。例如，在 open、close、message 等回调中记录内存使用情况。

优化内存使用的策略包括以下几个方面。第一，实现消息速率限制，当发送缓冲区超过阈值时丢弃低优先级的消息或通知发送方减速。速率限制可以在服务器端实现，也可以在客户端实现，或者两端都实现。第二，使用流式处理替代缓冲整个消息，特别是对于大消息。例如，对于文件传输，可以使用流式方式分段发送和接收，而不是一次性将整个文件加载到内存中。第三，定期清理过期数据，如超过一定时间未活动的用户会话。可以设置一个定时器，每隔一段时间扫描并清理过期数据。第四，使用对象池复用 WebSocket 帧和缓冲区对象，减少垃圾回收压力。对象池可以显著减少对象的创建和销毁频率，降低垃圾回收的开销。第五，调整 Bun 的垃圾回收参数，如增加新生代空间大小，减少 GC 暂停时间。Bun 使用 JavaScriptCore 引擎，支持通过 JSC 的命令行参数调整 GC 行为。

## 第五章：必备知识

### HTML 解析模型

理解 HTML 解析模型对于正确使用 HTMLRewriter 非常重要。HTML 解析规范（HTML Living Standard 的第 13 章）定义了浏览器如何将字节序列解析为 DOM 树。解析过程包括词法分析和语法分析两个阶段。

词法分析阶段将字节序列转换为 token 流。token 的类型包括开始标签、结束标签、自闭合标签、注释、文档类型声明、文本等。词法分析器维护一个状态机，根据当前字符和上下文状态确定下一个 token。例如，当遇到左尖括号时，词法分析器进入标签开始状态；当遇到连字符时，可能进入注释开始状态。

语法分析阶段将 token 流转换为 DOM 树。语法分析器维护一个插入位置（当前正在操作的元素）和一个开放元素栈（包含所有未闭合的开始标签）。当遇到开始标签时，将其推入栈中；当遇到结束标签时，从栈中弹出对应的开始标签。如果标签不匹配，浏览器会进行自动修正，这被称为标签容错。例如，当在段落中遇到块级元素时，浏览器会自动关闭段落再开始块级元素。

HTML 解析的容错性是 HTMLRewriter 需要特别注意的地方。浏览器会修复许多格式不正确的 HTML，如未闭合的标签、嵌套错误的标签、属性值未加引号等。HTMLRewriter 的解析器也实现了类似的容错机制，但可能与浏览器的行为略有不同。因此，在开发阶段应该使用与生产环境相同的 HTML 进行测试。

HTML 解析模式（标准模式、几乎标准模式、quirks 模式）也会影响解析结果。模式由文档开头的 DOCTYPE 声明决定。没有 DOCTYPE 或使用旧版 DOCTYPE 的文档会以 quirks 模式解析，这会导致一些与 CSS 和布局相关的兼容性问题。虽然 HTMLRewriter 不关心布局，但 quirks 模式下的解析规则与标准模式不同，可能导致意外的选择器匹配结果。

### CSS 选择器

CSS 选择器是 HTMLRewriter 的核心接口。熟练掌握 CSS 选择器语法对于高效使用 HTMLRewriter 至关重要。

基本选择器包括以下几种。标签选择器直接匹配元素类型，如 div 匹配所有 div 元素，p 匹配所有 p 元素，a 匹配所有 a 元素。类选择器匹配具有特定 class 属性的元素，如 .container 匹配所有 class 属性包含 container 的元素。ID 选择器匹配具有特定 id 属性的元素，如 #header 匹配 id 属性等于 header 的元素。通配选择器 * 匹配所有元素。

组合选择器包括以下几种。后代选择器（空格分隔）匹配所有后代元素，如 div p 匹配 div 内的所有 p 元素，无论嵌套层级有多深。子选择器（> 分隔）仅匹配直接子元素，如 ul > li 仅匹配 ul 的直接子 li，不匹配 ul 的孙子 li。相邻兄弟选择器（+ 分隔）匹配紧随前一个元素的元素，如 h2 + p 匹配紧跟在 h2 后面的 p。通用兄弟选择器（~ 分隔）匹配前一个元素之后的所有兄弟元素，如 h2 ~ p 匹配 h2 之后的所有 p 兄弟元素。

属性选择器包括以下几种。[attr] 匹配具有 attr 属性的元素，无论其值是什么。[attr=value] 匹配 attr 属性等于 value 的元素。[attr^=value] 匹配 attr 属性以 value 开头的元素。[attr$=value] 匹配 attr 属性以 value 结尾的元素。[attr*=value] 匹配 attr 属性包含 value 的元素。

伪类选择器包括以下几种。:first-child 匹配作为父元素第一个子元素的元素。:last-child 匹配作为父元素最后一个子元素的元素。:nth-child(n) 匹配作为父元素第 n 个子元素的元素。:not(selector) 匹配不匹配 selector 的元素。

在 HTMLRewriter 中使用 CSS 选择器时，需要注意以下几点。选择器匹配发生在流式解析过程中，因此某些依赖于文档完整结构的选择器可能无法正常工作。选择器的性能随复杂度增加而下降，特别是包含伪类和组合器的选择器。对于频繁使用的选择器，应该优先使用更具体的类名或 ID 选择器，避免复杂的层级匹配。

### WebSocket 协议深入

深入理解 WebSocket 协议对于开发健壮的实时应用非常重要。WebSocket 协议建立在 TCP 之上，提供全双工通信能力。与 HTTP 的请求-响应模式不同，WebSocket 允许服务器在任何时候主动向客户端推送数据。

WebSocket URI 的格式为 ws://host:port/path 或 wss://host:port/path（加密版本）。WebSocket 协议本身不定义消息格式，消息可以是文本（UTF-8 编码）或二进制数据。应用层可以根据需要定义自己的消息协议，如 JSON、MessagePack、Protocol Buffers 等。

WebSocket 的帧结构是理解协议的关键。每个 WebSocket 帧以 2 到 14 字节的头部开始，后面跟着负载数据。帧头部的第一个字节包含 FIN 位和 Opcode 字段。第二个字节包含 Mask 位和 Payload length 字段。如果 Payload length 字段的值为 126，则接下来的 2 个字节是实际的负载长度；如果值为 127，则接下来的 8 个字节是实际的负载长度。如果 Mask 位为 1，则帧头部还包含 4 字节的 Masking key。

WebSocket 的掩码算法是对负载数据的每个字节与 Masking key 的对应字节进行异或操作。由于 Masking key 只有 4 个字节，所以掩码操作是循环的：第 0 个字节与 key[0] 异或，第 1 个字节与 key[1] 异或，第 2 个字节与 key[2] 异或，第 3 个字节与 key[3] 异或，第 4 个字节再次与 key[0] 异或，以此类推。

### 反向代理与 HTTP 头

反向代理是一种服务器架构模式，它位于客户端和后端服务器之间，代表后端服务器接收客户端请求。反向代理可以实现负载均衡、缓存、安全防护、协议转换等功能。

在 HTMLRewriter 的上下文中，反向代理网关在转发响应之前对 HTML 内容进行转换。这种架构的关键考虑因素包括以下几个方面。请求转发，网关需要将客户端请求转发到上游服务器，包括请求头、请求体、查询参数等。响应缓存，对于不经常变化的页面，网关可以缓存转换后的响应，减少上游服务器的负载和转换开销。错误处理，当上游服务器不可用时，网关应该返回友好的错误页面而不是直接暴露错误信息。超时控制，对上游服务器的请求应该设置合理的超时时间，避免网关资源被慢速连接耗尽。

实现反向代理时需要注意的头字段包括以下几项。X-Forwarded-For，记录客户端的原始 IP 地址。当请求经过代理服务器时，代理服务器应该将客户端的 IP 地址添加到 X-Forwarded-For 头的末尾。X-Forwarded-Proto，记录客户端使用的协议（HTTP 或 HTTPS）。X-Forwarded-Host，记录客户端请求的原始 Host 头。Via，记录代理服务器的标识。这些头字段帮助后端服务器了解客户端的真实信息，对于日志记录、访问控制、内容协商等功能非常重要。

## 第六章：示例代码详解

### 示例一：HTMLRewriter 基础

第一个示例位于 examples/01-basic/html-rewriter.ts，展示了 HTMLRewriter 的基本用法。这个示例读取一个 HTML 文件，使用 HTMLRewriter 对特定元素进行转换，然后输出结果。通过这个示例，读者可以了解 HTMLRewriter 的 API 结构和基本工作流程。

HTMLRewriter 的核心 API 包括三个方法。on(selector, handlers) 用于注册元素处理器，transform(response) 用于将转换应用于 Response 对象，以及 handlers 对象中的 element 和 text 回调方法。

on 方法接受两个参数。selector 是 CSS 选择器字符串，handlers 是包含回调的对象。回调对象可以包含 element(element) 和 text(text) 两个方法。element 回调在遇到匹配选择器的开始标签时被调用，text 回调在遇到匹配选择器的元素内部的文本节点时被调用。

在 element 回调中，Element 对象提供了以下方法。getAttribute(name) 获取属性值，setAttribute(name, value) 设置属性值，removeAttribute(name) 移除属性，hasAttribute(name) 检查属性是否存在，getInnerContent() 获取元素内部的 HTML 内容，setInnerContent(html) 设置元素内部的 HTML 内容，remove() 移除当前元素，replace(html) 用指定的 HTML 替换当前元素，prepend(html) 在当前元素内部的开头插入 HTML，append(html) 在当前元素内部的末尾插入 HTML，before(html) 在当前元素之前插入 HTML，after(html) 在当前元素之后插入 HTML。

在 text 回调中，Text 对象提供了以下方法。text 属性获取当前文本块的内容，replace(text) 用指定的文本替换当前文本块，before(text) 在当前文本块之前插入文本，after(text) 在当前文本块之后插入文本，remove() 移除当前文本块。

第一个示例中的关键代码展示了如何注册多个选择器处理器，以及如何在回调中修改元素属性和内容。这个示例还展示了 HTMLRewriter 的链式调用风格，通过多次调用 on 方法注册多个选择器的处理器。

### 示例二：WebSocket 聊天服务器

第二个示例位于 examples/02-advanced/websocket-server.ts，实现了一个简单的 WebSocket 聊天服务器。这个示例展示了 Bun 的 WebSocket 支持的核心功能，包括连接升级、消息广播和连接管理。

服务器的核心逻辑包括以下几个部分。第一，Bun.serve 的配置对象，包含 port、fetch 和 websocket 三个主要属性。第二，fetch 处理函数，根据请求路径决定是返回 HTTP 响应还是升级为 WebSocket 连接。第三，websocket 配置对象，包含 open、message 和 close 事件处理函数。

在 fetch 处理函数中，关键的代码是 server.upgrade(req, { data: { name } }) 调用。这个方法将 HTTP 请求升级为 WebSocket 连接，并将 name 数据关联到连接上。升级成功后，后续的 WebSocket 事件可以通过 ws.data.name 访问到这个值。

在 open 事件处理函数中，服务器向新连接的客户端发送欢迎消息，并在控制台输出连接日志。在 message 事件处理函数中，服务器使用 server.publish("chat", ...) 将消息广播到所有订阅了 chat 主题的连接。在 close 事件处理函数中，服务器记录客户端离开的日志。

这个示例使用主题订阅模式实现消息广播。当客户端连接时，它自动加入了 chat 主题。当服务器收到消息时，它通过 server.publish 将消息发送给所有订阅了该主题的客户端。这种模式简化了群组通信的实现，避免了手动管理客户端列表的复杂性。

需要注意的是，这个示例中的广播机制是单向的：客户端发送消息，服务器广播给所有其他客户端。如果需要实现私信功能，可以引入更多的主题（如每个用户一个私有主题）或者在消息中指定接收者。

### 示例三：SEO 反向代理网关

第三个示例位于 examples/03-production/seo-gateway.ts，实现了一个生产级的 SEO 反向代理网关。这个示例将 HTMLRewriter 和反向代理结合起来，在转发上游服务器的 HTML 响应时动态注入 SEO 元标签。

SEO 网关的核心设计包括以下几个部分。第一，SEOInjector 类，封装了 SEO 标签注入的逻辑。第二，fetch 处理函数，负责从上游服务器获取响应并应用 HTMLRewriter 转换。第三，SEO 标签的生成策略，根据请求路径推断页面标题和描述。

SEOInjector 类实现了 element 和 text 回调。在 element 回调中，它匹配 title 和 meta 元素，更新页面标题和描述。在 text 回调中，它在 head 标签前插入额外的 SEO 标签，包括 Open Graph 标签和 Twitter Card 标签。

fetch 处理函数的关键逻辑包括。第一，解析客户端请求的 URL，构造上游服务器的请求 URL。第二，使用 fetch 获取上游响应。第三，检查响应内容类型，仅对 HTML 响应应用 HTMLRewriter 转换。第四，对非 HTML 资源直接透传，避免不必要的处理开销。第五，在响应头中添加 x-seo-gateway 标记，标识响应已经过网关处理。

SEO 网关的错误处理包括：当上游服务器不可用时，返回 502 Bad Gateway 状态码和友好的错误信息；当上游响应非 HTML 时，直接透传而不进行转换；当 HTMLRewriter 转换过程中发生错误时，回退到未转换的原始响应。

## 最佳实践总结

### HTMLRewriter 使用建议

使用 HTMLRewriter 时，遵循以下最佳实践可以提高代码的可靠性和性能。第一，总是为每个选择器注册独立的处理器对象，避免在处理器中维护过多状态。第二，优先使用 element 回调而不是 text 回调进行元素级别的修改，因为 element 回调的语义更清晰且不容易出错。第三，在 text 回调中避免进行跨文本块的匹配操作，因为文本块的分割是不确定的。第四，对于需要多次调用的转换逻辑，将处理器类定义在模块级别，避免在每次请求时重新创建。第五，对于复杂的转换逻辑，使用多个简单的选择器组合而不是一个复杂的选择器，这样可以提高代码的可读性和可维护性。

### WebSocket 生产部署

在生产环境中部署 WebSocket 服务时，需要考虑以下因素。第一，使用进程管理器（如 PM2）或容器编排工具（如 Kubernetes）管理 WebSocket 服务器的生命周期，确保崩溃后自动重启。第二，配置负载均衡器支持 WebSocket 的 sticky session（粘性会话），确保同一个客户端的请求总是被路由到同一个服务器实例。第三，实现优雅关闭，在服务器收到关闭信号时停止接受新连接，等待现有连接处理完当前消息后再关闭。第四，监控 WebSocket 连接数、消息吞吐量、延迟等关键指标，设置告警阈值。第五，使用健康检查端点，负载均衡器可以定期检查 WebSocket 服务器是否健康。

### 性能优化

针对 HTMLRewriter 和 WebSocket 的性能优化包括以下几个方面。第一，使用缓存减少重复转换，对于不经常变化的页面缓存转换后的 HTML。缓存可以在内存中实现，也可以使用外部的缓存系统如 Redis。第二，限制 WebSocket 消息的大小，对超过阈值的消息进行分片或拒绝。第三，使用连接池复用 WebSocket 连接，减少连接建立的开销。第四，对 WebSocket 消息进行批处理，将多个小消息合并为一个大消息发送，减少帧头和系统调用的开销。第五，使用压缩减少 WebSocket 消息的大小，特别是对于文本数据。第六，优化选择器匹配性能，优先使用简单的选择器，避免复杂的组合选择器。

### 安全性考虑

安全性是 WebSocket 应用不可忽视的方面。第一，使用 WSS（WebSocket over TLS）加密所有 WebSocket 通信，防止中间人攻击和数据泄露。第二，验证 WebSocket 连接的 Origin 头，防止跨站 WebSocket 劫持攻击。第三，实施认证机制，在 WebSocket 握手阶段或握手完成后验证用户身份。第四，对 WebSocket 消息进行输入验证和清理，防止 XSS 和注入攻击。第五，实施速率限制，防止单个客户端发送过多消息导致服务器资源耗尽。第六，记录 WebSocket 连接的详细日志，包括连接时间、断开时间、消息数量等，用于安全审计。第七，使用最小权限原则，为 WebSocket 连接分配最小的必要权限。

## 常见问题与解答

### HTMLRewriter 部分

问：HTMLRewriter 能否处理非常大的 HTML 文件？
答：可以。HTMLRewriter 的流式处理模式使其内存占用与文档总大小无关，只与单个元素的复杂度相关。即使处理数兆字节的 HTML 文件，内存占用也保持在较低水平。

问：HTMLRewriter 是否支持所有的 CSS 选择器？
答：不支持。由于流式解析的限制，某些需要前瞻或回溯的选择器（如 :has()、:empty、:nth-last-child）无法正常工作。建议使用 :first-child、:nth-child 等不需要前瞻的选择器。

问：在 element 回调中能否修改父元素的内容？
答：不能。由于流式解析的推进方向是单向的，当子元素的回调被触发时，父元素已经输出到结果流中，无法回溯修改。

### WebSocket 部分

问：Bun 的 WebSocket 服务器是否支持跨域连接？
答：支持。但开发者需要在服务器端验证 Origin 头，确保只允许来自可信域名的连接。默认情况下，Bun 不会自动限制跨域连接。

问：如何处理 WebSocket 连接的超时？
答：可以通过 idleTimeout 选项设置连接的空闲超时时间，当连接在指定时间内没有数据交换时自动关闭。同时，建议在应用层实现 Ping/Pong 心跳检测，及时发现死连接。

问：WebSocket 消息的最大大小是多少？
答：可以通过 maxPayloadLength 选项限制消息大小。默认情况下，Bun 不限制消息大小，但建议根据应用场景设置合理的限制，防止恶意客户端发送超大消息。

### 生产部署部分

问：如何水平扩展 WebSocket 服务？
答：可以使用负载均衡器分发 WebSocket 连接，并配置粘性会话确保同一客户端的请求始终路由到同一服务器。对于跨服务器的消息广播，可以使用 Redis 的发布/订阅功能实现。

问：如何监控 WebSocket 服务的健康状态？
答：建议监控以下指标：活跃连接数、消息吞吐量（每秒发送和接收的消息数）、平均延迟、错误率、内存使用量。可以使用 Prometheus 和 Grafana 搭建监控面板。

问：WebSocket 服务器重启时如何处理已有连接？
答：应该实现优雅关闭，在收到关闭信号时停止接受新连接，等待现有连接处理完当前消息后再关闭。同时，客户端应该实现自动重连机制，在检测到连接断开后自动重新连接。

## 扩展阅读

### 与其他运行时的对比

Bun 的 HTMLRewriter API 最初受到 Cloudflare Workers 的 HTMLRewriter 启发，但在实现上有所不同。Cloudflare Workers 的 HTMLRewriter 运行在边缘网络环境中，受到 Workers 的执行限制（如 CPU 时间限制、内存限制等）。Bun 的 HTMLRewriter 则运行在本地服务器环境中，没有这些执行限制，可以处理更复杂的转换逻辑。

在 WebSocket 支持方面，Bun 与 Node.js 的主要区别在于：Node.js 需要额外安装 ws 或 socket.io 等第三方库才能提供 WebSocket 服务器功能，而 Bun 在运行时层面内置了 WebSocket 服务器支持。这意味着 Bun 应用不需要额外的依赖就可以处理 WebSocket 连接，减少了依赖管理的复杂性和安全风险。

### 性能基准测试

根据 Bun 官方团队的基准测试数据，Bun 的 WebSocket 实现在单机性能上显著优于 Node.js 的 ws 模块。在相同的硬件条件下，Bun 可以处理约 2.5 倍的并发 WebSocket 连接，消息吞吐量也高出约 30%。这些性能优势主要来自 Bun 的底层运行时优化，包括更高效的事件循环和内存管理。

HTMLRewriter 的性能同样出色。在处理大型 HTML 文档时，HTMLRewriter 的内存占用仅为基于 DOM 的解析器的十分之一到二十分之一，处理速度也快 2 到 5 倍。这些性能优势使得 HTMLRewriter 非常适合在资源受限的边缘计算环境中使用。

### 未来发展趋势

边缘计算和实时通信技术正在快速发展。WebSocket 的替代技术如 WebTransport 正在标准化过程中，它基于 QUIC 协议，提供更低的连接建立延迟和多路复用能力。同时，HTTP/3 的普及也将改变实时通信的技术格局。然而，WebSocket 作为成熟且广泛支持的协议，将在未来很长一段时间内继续发挥重要作用。

HTMLRewriter 代表的流式 HTML 处理模式也在不断演进。随着边缘计算平台的普及，越来越多的 HTML 转换工作将从中心服务器迁移到边缘节点。这种趋势将推动 HTMLRewriter 和相关技术的持续优化和创新。
