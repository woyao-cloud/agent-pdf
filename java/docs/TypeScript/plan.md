# 《深入理解 TypeScript：类型系统原理、工程化实战与架构进阶》

## 第一部分：解密 TypeScript —— 编译器原理与类型系统基石
*本部分带您潜入 `tsc` 编译器底层，理解 TS 是如何“看懂”你的代码的，以及它在运行时究竟做了什么。*

### 第1章 TS 编译器（tsc）内幕与 AST 抽象语法树
* **1.1 编译的五个阶段**：扫描器（Scanner） -> 解析器（Parser） -> 绑定器（Binder） -> 检查器（Checker） -> 发射器（Emitter）。
* **1.2 AST（抽象语法树）探秘**：代码是如何被转化为树状结构的？（利用 AST Explorer 可视化分析）。
* **1.3 类型擦除（Type Erasure）的本质**：为什么 TS 类型在运行时不存在？`enum`、`namespace` 和 `装饰器` 为什么是“非纯类型”特性？
* **1.4 为什么 TS 不能做运行时校验？**：从设计哲学看 TS 的“静态契约”与运行时数据的“不可信”之间的矛盾。

### 第2章 类型推导（Type Inference）与控制流分析
* **2.1 双向类型推导机制**：自底向上（表达式推导）与自顶向下（上下文类型推导 Contextual Typing）的博弈。
* **2.2 控制流分析（Control Flow Analysis, CFA）**：
  * TS 如何在 `if/else`、`switch`、`throw` 甚至 `&&`/`||` 中自动收窄（Narrowing）类型。
  * **痛点**：为什么在闭包或 `setTimeout` 中，TS 会“遗忘”变量的类型收窄？（别名与可变性分析）。
* **2.3 判别联合类型（Discriminated Unions）与 `never` 的防御性编程**：利用 `never` 实现穷尽性检查（Exhaustiveness Checking），确保业务分支无遗漏。

### 第3章 结构类型系统（Structural Typing）的陷阱
* **3.1 鸭子类型（Duck Typing）哲学**：为什么 `interface A` 和 `interface B` 字段一样，就可以互相赋值？
* **3.2 潜在风险：弱类型检测与多余属性检查**：对象字面量赋值时的“严格模式”与变量赋值时的“宽松模式”差异。
* **3.3 品牌化类型（Branded Types / Nominal Typing）**：
  * **实战**：如何通过交叉类型与 `unique symbol` 模拟标称类型，防止将 `UserId` (string) 错误赋值给 `OrderId` (string)。

## 第二部分：高级类型系统与“类型体操”实战
*本部分深入 TS 图灵完备的类型系统，掌握构建复杂类型逻辑的核心武器。*

### 第4章 泛型（Generics）与类型约束
* **4.1 泛型的本质**：类型的函数（参数化类型）。
* **4.2 约束（`extends`）与默认值**：如何限制泛型必须具备某些属性。
* **4.3 泛型的作用域与逆变/协变（Variance）**：
  * 为什么 `Dog[]` 可以赋值给 `Animal[]`（协变），但 `(dog: Dog) => void` 不能赋值给 `(animal: Animal) => void`（逆变）？（深度解析函数参数的类型安全）。

### 第5章 条件类型（Conditional Types）与 `infer` 关键字
* **5.1 条件类型的分布式特性（Distributive Conditional Types）**：当泛型参数是联合类型时，条件类型如何自动展开（这是实现 `Exclude` / `Extract` 的底层原理）。
* **5.2 `infer` 模式匹配**：在类型层面进行“解构赋值”。
* **5.3 实战示例**：提取函数的返回值类型、提取 Promise 内部的解析类型、提取数组的第一个元素与剩余元素。

### 第6章 映射类型（Mapped Types）与模板字面量类型
* **6.1 映射类型**：遍历联合类型或 `keyof` 生成新对象类型（`Partial`, `Required`, `Readonly` 的底层实现）。
* **6.2 键值重映射（Key Remapping via `as`）**：在映射过程中过滤或修改键名。
* **6.3 模板字面量类型（Template Literal Types）**：
  * **实战**：将 CSS 驼峰命名自动转换为短横线命名。
  * **实战**：实现类型安全的事件总线（EventBus）或路由参数解析。

## 第三部分：核心业务场景实战（原理、风险、优化与代码）
*本部分针对 4 大核心开发场景，展示 TS 如何提升工程质量并规避重构灾难。*

### 第7章 场景一：React/Vue 复杂组件与 Hooks 的类型安全
* **7.1 潜在风险**：组件 Props 类型推导丢失，泛型组件在 JSX 中无法正确推导。
* **7.2 优化与实战**：使用 `ComponentProps` 提取复用类型；高阶组件（HOC）与自定义 Hooks 的泛型推导技巧。

### 第8章 场景二：Node.js 后端与全栈类型共享（端到端类型安全）
* **8.1 潜在风险**：前后端分离导致 API 接口变更时，前端无法在编译期感知。
* **8.2 优化与实战**：Monorepo 共享 Schema；使用 **tRPC** 实现 100% 类型推导的 RPC 调用；Prisma ORM 复杂查询的类型推导陷阱。

### 第9章 场景三：开源库 / SDK 的 `.d.ts` 声明文件编写
* **9.1 潜在风险**：导出的类型过于宽泛，内部实现细节被意外暴露。
* **9.2 优化与实战**：掌握 `declare module` 与声明合并；编写**重载（Overloads）** 实现精准推导；配置 `tsup` 自动生成干净的 `.d.ts`。

### 第10章 场景四：复杂业务状态机与领域模型（DDD）建模
* **10.1 潜在风险**：非法状态组合（如 `status: 'success'` 时却带有 `error` 字段）。
* **10.2 优化与实战**：利用**判别联合类型**对业务状态进行互斥建模；结合 XState 利用 TS 泛型约束状态流转的合法性。

## 第五部分：典型问题排查与“老中医”排坑指南
*直击生产环境与日常开发中最头疼的类型疑难杂症。*

### 第14章 生产环境“四大类型灾难”排查
* **14.1 `any` 与 `unknown` 的滥用与传染**：掌握 `unknown` 配合类型守卫进行安全收窄。
* **14.2 第三方库类型冲突（Duplicate Identifier）**：依赖树排查与 `patch-package` 修复有缺陷的 `.d.ts`。
* **14.3 泛型推导失败退化为 `unknown`**：使用“虚拟参数”或 `NoInfer<T>` (TS 5.4+) 阻断不期望的推导。
* **14.4 `this` 指向类型丢失**：显式声明 `this: Context` 参数。

### 第15章 类型守卫与断言的高级玩法
* **15.1 自定义类型守卫**：`obj is User` 的底层逻辑。
* **15.2 断言函数（Assertion Functions）**：`asserts condition` 如何在函数内部抛出异常以收窄外部作用域。
* **15.3 `satisfies` 操作符**：既享受精确推导，又确保符合接口约束（彻底替代部分 `as const` 场景）。

## 第六部分：TypeScript 开发者核心素养与必备技能图谱（🌟 核心新增）
*本部分专门针对“开发人员必须熟练掌握的相关知识与技能”进行系统化梳理，帮助开发者建立正确的“类型思维”和工程素养。*

### 第16章 技能一：类型驱动的 API 设计能力 (Type-Driven Design)
* **16.1 调用者体验优先**：如何写出对调用者友好的类型？（避免让调用者手动传入复杂的泛型参数，利用函数签名自动推导）。
* **16.2 避免“类型体操”滥用**：区分“必要的类型抽象”与“炫技式的类型推导”。（原则：如果一个类型推导需要超过 3 层 `infer` 且严重影响 IDE 性能，请果断放弃，改用显式声明）。
* **16.3 防御性 API 设计**：利用 `readonly`、`Omit` 和私有品牌类型，限制外部对内部状态的非法篡改。

### 第17章 技能二：TS 报错信息的“阅读理解”与调试技能
* **17.1 破解“天书”报错**：如何阅读长达几十行的“类型不兼容”报错？（技巧：从报错信息的**最底部**或**差异点**开始看，寻找 `Type 'X' is not assignable to type 'Y'` 的核心冲突）。
* **17.2 IDE 高级调试技巧**：
  * 熟练使用 VSCode 的“悬停（Hover）”查看推断类型。
  * 使用 `// @ts-expect-error` 替代 `// @ts-ignore`（前者会在错误消失时报警，防止遗留技术债）。
  * 使用 TS 官方提供的 [TypeScript Playground](https://www.typescriptlang.org/play) 隔离并复现类型问题。

### 第18章 技能三：代码审查（Code Review）中的 TS 规范与反模式识别
* **18.1 识别常见的 TS 反模式（Anti-Patterns）**：
  * **反模式 1**：滥用 `interface` 继承代替交叉类型（`&`）。（*规范：组合对象类型时优先使用 `type A = B & C`，避免多重继承带来的属性冲突盲区*）。
  * **反模式 2**：在不需要多态的场景下强行使用泛型。（*规范：如果泛型参数 `T` 在函数签名中只出现了一次，通常应该直接用具体类型或 `unknown`*）。
  * **反模式 3**：用 `as any` 掩盖类型错误。（*规范：必须使用 `as unknown as TargetType` 进行双重断言，强迫开发者意识到类型的不安全性*）。
* **18.2 制定团队的 TS 编码规范**：Do's and Don'ts 清单与 ESLint 强制约束。

### 第19章 技能四：跨越静态与运行时的鸿沟（运行时校验技能）
* **19.1 核心认知**：深刻理解“TS 类型在边界处（网络请求、用户输入、本地存储）一定会失效”。
* **19.2 必备工具链**：熟练掌握 **Zod / Valibot / TypeBox** 等运行时校验库。
* **19.3 实战技能**：
  * 编写一次 Schema，同时生成 TS 静态类型（`z.infer`）与运行时校验逻辑。
  * 在 API 网关层或 BFF 层，强制对所有外部流入数据进行 Schema 校验，将“运行时的 `undefined` 灾难”转化为“可控的业务异常”。

### 第20章 技能五：类型级测试（Type-Level Testing）
* **20.1 为什么需要类型测试？**：当你编写了复杂的工具类型（如 `DeepPartial`）或 SDK 声明文件时，如何确保重构后类型推导依然正确？
* **20.2 必备工具**：掌握 `tsd` 或 `expect-type` 库。
* **20.3 实战示例**：编写测试用例，断言某个函数的返回值类型是否严格等于预期的接口（在编译期执行测试，不产生运行时代码）。
