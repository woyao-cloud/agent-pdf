## 🌟 第六篇：架构演进篇 —— 突破单机瓶颈的分库分表实战
*本篇目标：当单表数据量突破千万或单库并发达到瓶颈时，如何科学地进行分库分表？重点解决拆分策略、衍生难题以及平滑迁移方案。*

* **第18章：分库分表的破局与重构（何时拆？怎么拆？）**
  * **18.1 触发分库分表的“临界点”**
    * *解决什么问题：* 避免“为了拆而拆”，明确单表容量瓶颈（如2000万行/50GB）与并发瓶颈（如单机QPS上限）。
    * *白话原理：* 把“一个大仓库”拆成“多个小仓库”，解决的是“找货慢（容量）”和“门口排队挤（并发）”的问题。
  * **18.2 垂直拆分：业务解耦与冷热分离**
    * *实战示例：* 将大字段（如文章内容、商品详情）剥离到扩展表；将核心交易库与用户基础库拆分。
    * *避坑指南：* 垂直拆分后跨库JOIN的代价评估。
  * **18.3 水平拆分：分片键（Sharding Key）的抉择**
    * *解决什么问题：* 数据如何均匀打散？如何避免数据倾斜（热点数据问题）？
    * *实战方案：* 常用分片算法对比（Hash取模、Range范围、时间轮转）。
    * *白话原理：* 分片键就是“快递分拣的条码”，选错条码会导致某个分拣口永远爆满（数据热点）。

* **第19章：分库分表后的“疑难杂症”与解决方案**
  * **19.1 全局唯一ID生成方案**
    * *解决什么问题：* 分表后自增主键失效，如何生成全局唯一且趋势递增的ID？
    * *实战方案：* 雪花算法（Snowflake）的时钟回拨问题、号段模式（Leaf）、UUID的致命缺陷（B+树频繁页分裂）。
  * **19.2 跨库查询的痛：JOIN、分页、排序与聚合**
    * *解决什么问题：* 数据分散在多个库，无法直接进行复杂查询和内存排序。
    * *实战方案：* 
      * 基因法：将分片键冗余到关联表中，避免跨库JOIN。
      * 应用层组装：拆分大JOIN为多次单表查询。
      * 异构索引：将复杂查询（多维度检索、深分页）同步至 Elasticsearch。
  * **19.3 分布式事务的妥协与落地**
    * *解决什么问题：* 跨库操作如何保证数据一致性？
    * *实战方案：* 放弃强一致性，拥抱最终一致性。2PC/3PC的局限性、可靠消息最终一致性（RocketMQ事务消息）、Seata AT模式的原理与性能损耗。

* **第20章：平滑演进：数据迁移与不停机扩容**
  * **20.1 历史数据迁移方案（不停机双写）**
    * *解决什么问题：* 线上业务不能停，如何把老库的数据平滑搬到新库？
    * *实战方案：* “双写方案”标准流程（开启双写 -> 历史数据全量同步 -> 增量数据Binlog追平 -> 数据校验 -> 灰度切读 -> 停写老库）。
  * **20.2 扩容与缩容的痛点：数据重分布**
    * *解决什么问题：* 分片数量（如4库16表）固定后，数据量再次翻倍如何扩容？
    * *实战方案：* 翻倍扩容法（4库扩8库，原有数据不动，只迁移Hash冲突的数据），最小化数据搬迁量。
  * **20.3 主流中间件选型与接入指南**
    * *实战对比：* ShardingSphere-JDBC（轻量级、无中间代理、性能高） vs ShardingSphere-Proxy（独立进程、支持多语言、运维方便） vs MyCat。
    * *开发建议：* 根据团队技术栈和运维能力选择最合适的中间件。

### 💡 针对新增“分库分表”篇章的编写建议：
1. **强调“克制”：** 在开篇一定要向开发者传递一个理念：**“分库分表是架构上的妥协，而不是银弹”**。能靠加索引、读写分离、缓存解决的问题，绝不要上分库分表。
2. **图解数据流转：** 在讲解“双写迁移”和“翻倍扩容”时，强烈建议配上**时序图**和**数据流转图**，因为纯文字描述数据同步过程非常容易绕晕读者。
3. **结合真实踩坑经验：** 在“跨库查询”和“分布式事务”章节，多分享一些真实的线上血泪史（例如：因为用了UUID导致索引失效、因为跨库JOIN导致内存OOM、因为分布式事务导致数据不一致等），这会让开发人员产生强烈共鸣。
