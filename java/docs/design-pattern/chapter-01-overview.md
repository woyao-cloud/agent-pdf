# 第1章 设计模式概述

软件设计是一个复杂的过程，需要考虑代码的可维护性、可扩展性、可复用性和可读性。在长期的软件开发实践中，前人总结出了许多经过验证的解决方案，这些解决方案就是**设计模式**。

## 1.1 设计模式定义与价值

### 1.1.1 什么是设计模式

**设计模式**（Design Pattern）是一套被反复使用、经过分类编目的代码设计经验的总结。它描述了在软件设计中反复出现的核心问题，以及该问题的核心解决方案。

设计模式具有以下特征：

- **系统性**：设计模式是一套完整的解决方案，不是零散的技巧
- **可复用性**：设计模式可以在不同的项目中重复使用
- **经过验证**：设计模式是经过大量项目验证的有效实践
- **上下文相关**：每种设计模式都有其适用场景和限制条件

### 1.1.2 设计模式的价值

设计模式的价值体现在以下几个方面：

**1. 提高代码质量**

- 增强代码的可读性和可维护性
- 促进代码的模块化和解耦
- 降低代码的复杂性

**2. 促进团队协作**

- 提供共同的设计 vocabulary
- 降低团队成员之间的沟通成本
- 便于代码审查和知识传递

**3. 提升开发效率**

- 避免重复造轮子
- 使用经过验证的解决方案减少试错成本
- 加速新成员的上手速度

**4. 应对变化**

- 使代码更易于扩展
- 降低修改代码时的风险
- 支持敏捷开发和持续迭代

### 1.1.3 设计模式与面向对象

设计模式的核心基础是**面向对象编程**（OOP）。设计模式的成功运用依赖于面向对象的三大特性：

- **封装**：将数据和行为封装在一起，隐藏实现细节
- **继承**：通过继承实现代码复用和类型层次
- **多态**：同一接口的不同实现，增强代码的灵活性

> **注意**：设计模式并非面向对象的专利，但在面向对象语言中应用最为广泛。

## 1.2 设计模式分类（GoF）

1994年，Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides 四位学者合著了《Design Patterns: Elements of Reusable Object-Oriented Software》一书，书中收录了23种设计模式，被称为**GoF设计模式**（Gang of Four，四人帮）。

GoF设计模式按照目的分为三类：

### 1.2.1 创建型模式（Creational Patterns）

创建型模式关注对象的创建机制，旨在解决对象创建过程中的问题：

| 模式 | 目的 |
|------|------|
| 单例模式 | 确保一个类只有一个实例 |
| 工厂方法模式 | 定义创建对象的接口，由子类决定实例化哪个类 |
| 抽象工厂模式 | 创建一系列相关对象的接口 |
| 建造者模式 | 分离复杂对象的构建和表示 |
| 原型模式 | 通过复制现有对象创建新对象 |

### 1.2.2 结构型模式（Structural Patterns）

结构型模式关注对象之间的组合关系，旨在解决系统结构问题：

| 模式 | 目的 |
|------|------|
| 适配器模式 | 转换接口以兼容不兼容的类 |
| 桥接模式 | 分离抽象部分和实现部分 |
| 组合模式 | 将对象组合成树形结构 |
| 装饰器模式 | 动态添加额外职责 |
| 外观模式 | 提供统一的接口访问子系统 |
| 代理模式 | 为对象提供代理以控制访问 |
| 享元模式 | 共享大量细粒度对象 |

### 1.2.3 行为型模式（Behavioral Patterns）

行为型模式关注对象之间的通信和职责分配：

| 模式 | 目的 |
|------|------|
| 责任链模式 | 将请求沿着处理者链传递 |
| 命令模式 | 将请求封装为对象 |
| 迭代器模式 | 顺序访问集合元素 |
| 中介者模式 | 用中介对象封装对象交互 |
| 备忘录模式 | 捕获对象状态并保存 |
| 观察者模式 | 定义对象间的一对多依赖 |
| 状态模式 | 对象状态改变时改变其行为 |
| 策略模式 | 定义一系列算法并互换使用 |
| 模板方法模式 | 定义算法骨架，部分步骤由子类实现 |
| 访问者模式 | 表示一个作用于对象结构中的元素的操作 |
| 解释器模式 | 定义语言的语法表示和解释器 |

### 1.2.4 模式分类图

```

```

## 1.3 设计模式与软件架构

### 1.3.1 设计模式与架构的关系

设计模式和软件架构是不同层次的设计工具：

- **架构**关注系统的整体结构和组件关系，通常在项目早期确定
- **设计模式**是具体的解决方案，可应用于架构的各个部分

两者相辅相成：
- 设计模式是架构实现的基础构件
- 架构为设计模式的选择提供上下文
- 良好的架构由多个合理的设计模式组合而成

典型的Java企业应用分层架构中，设计模式的应用位置：

### 1.3.3 框架中的设计模式

主流Java框架大量使用了设计模式：

**Spring Framework**

- 工厂模式：BeanFactory、ApplicationContext
- 单例模式：默认Scope为Singleton
- 代理模式：AOP、事务管理
- 模板方法模式：JdbcTemplate、HibernateTemplate
- 观察者模式：ApplicationEvent、Listener
- 策略模式：Resource、Environment

**MyBatis**

- 工厂模式：SqlSessionFactory
- 装饰器模式：Plugins
- 迭代器模式：ResultSetHandler
- 代理模式：Mapper代理

**JDK核心类库**

- 迭代器模式：Iterator、ListIterator
- 装饰器模式：InputStream/OutputStream系列
- 责任链模式：FilterChain
- 策略模式：Comparator
- 观察者模式：Observer、Observable

## 1.4 如何学习设计模式

### 1.4.1 学习路径

学习设计模式建议遵循以下路径：

```
第一阶段：理解基础
│
├── 掌握面向对象编程（OOP）基础
├── 理解七大设计原则
└── 了解UML类图基础
│
第二阶段：学习模式
│
├── 每种模式按照"问题→原理→实现→应用"学习
├── 重点理解每种模式解决的特定问题
└── 动手实现每种模式
│
第三阶段：实践应用
│
├── 阅读开源框架源码，识别设计模式
├── 在实际项目中尝试应用设计模式
└── 学习分析和重构现有代码
│
第四阶段：融会贯通
│
├── 理解模式之间的联系和组合
├── 建立模式选择的能力
└── 形成自己的设计思维
```

### 1.4.2 每种模式的学习方法

针对每种设计模式，建议按照以下结构学习：

1. **明确问题**：这个模式要解决什么问题？
2. **理解原理**：核心思想是什么？
3. **UML分析**：类图结构是怎样的？角色有哪些？
4. **代码实现**：如何用Java实现？
5. **源码解析**：JDK或框架中是如何应用的？
6. **使用场景**：什么情况下应该使用？
7. **注意事项**：有什么缺点和限制？

### 1.4.3 实践建议

- **不要过度使用**：设计模式不是越多越好，滥用会导致过度设计
- **理解本质**：学习模式背后的思想，而不是死记硬背代码
- **活学活用**：根据实际场景选择合适的模式，而非强行套用
- **持续积累**：通过阅读源码和优秀开源项目不断加深理解

### 1.4.4 常见误区

| 误区 | 正确认识 |
|------|----------|
| 设计模式是银弹 | 设计模式是工具，不是万能解决方案 |
| 必须使用设计模式 | 简单方案优于复杂模式 |
| 设计模式是固定的 | 根据实际情况灵活调整 |
| 记住所有模式就能写好代码 | 理解思想比记住实现更重要 |

## 本章小结

本章介绍了设计模式的基本概念：

1. **设计模式定义**：经过验证的代码设计经验总结
2. **设计模式价值**：提高代码质量、促进团队协作、提升开发效率、应对变化
3. **GoF分类**：创建型（5种）、结构型（7种）、行为型（11种）
4. **与架构关系**：设计模式是架构实现的基础构件
5. **学习方法**：理解基础→学习模式→实践应用→融会贯通
