# 第8章 数据转换（Transformations）：前端 ETL 利器

## 8.1 为什么需要 Transformations？

### 数据源能力不足

并非所有数据源都支持复杂计算。例如：
- Prometheus 不支持跨数据源 JOIN
- Loki 不支持多维聚合
- JSON API 只返回原始数据

Transformations 在浏览器端对 Data Frame 进行二次加工，弥补数据源的能力不足。

> **比喻：Transformations = 浏览器端的"瑞士军刀"**
>
> 想象你从超市买了食材（数据源查询结果），但食材不能直接吃——需要切、煮、调味。Transformations 就是你的厨房工具。Prometheus 提供的是"已切好的肉片"，MySQL 提供的是"蔬菜拼盘"，你要把它们做成一道菜（一张图表），就需要厨房里的"瑞士军刀"来完成合并、切片、重组。
>
> 关键区别：传统的 ETL 在服务器端做数据加工，Transformations 在浏览器（客户端）做——这意味着你不需要改数据源配置，不用写后端代码，直接在 Dashboard 界面上"拖拽式"完成数据加工。

### 使用场景

**场景 1：多源数据合并**
- Prometheus 查询 CPU 使用率 + MySQL 查询订单量 → Join by time → 展示在一张图上

**场景 2：字段计算**
- 从已有的 `error_count` 和 `total_count` 计算出 `error_rate = error / total * 100`

**场景 3：数据降维**
- 10 条时间序列 → 聚合成 1 条平均值 → 显示在 Stat 面板

**场景 4：格式转换**
- 宽表 → 长表（或反之）
- 时间序列 → 表格

### 数据流转

```
查询 A (Prometheus)  ──▶  Data Frame A ──┐
                                         ├──▶ Transformations ──▶ Data Frame ──▶ Panel
查询 B (MySQL)       ──▶  Data Frame B ──┘
                                              │
                                        ┌─────┴─────┐
                                        │ Join       │
                                        │ Reduce     │
                                        │ Add field  │
                                        │ Group by   │
                                        │ ...        │
                                        └───────────┘
```

> **注意**：Transformations 的输入是前一步的输出。如果你添加了 3 个 Transformation，步骤 2 的输入是步骤 1 的输出，步骤 3 的输入是步骤 2 的输出。顺序很重要！

## 8.2 核心操作实战

### Join by field（按字段合并）

将两个不同数据源的查询结果按时间戳或 Label 合并为一张宽表。

> **故事：没有 JOIN 的数据库？我帮你 JOIN**
>
> 某电商团队用 Prometheus 监控 CPU 使用率，用 MySQL 记录订单量。他们想在同一个图表上看到"CPU 飙升时订单量是否下降"，但 Prometheus 和 MySQL 是两个完全不同的系统，没有共同的查询接口。
>
> 过去的方法：运维人员打开两个浏览器标签页，一边看 CPU 图表，一边看订单图表，来回切换对比。不仅累，而且经常看错时间轴。
>
> Transformations 的 `Join by field` 解决了这个问题：在浏览器端把两个查询结果按时间戳合并成一张表，然后用 Time Series 面板同时展示 CPU 和订单量两条曲线。一张图，一目了然。

> **代码旁白**：Join 的匹配逻辑
>
> Join by field 的工作原理是"精确匹配"——两个 Data Frame 中字段值完全一致的行会被合并到同一行。如果时间戳精度不同（一个精确到秒，一个精确到毫秒），Join 后会出现大量空值行。例如：
>
> ```
> Data Frame A 时间戳: 10:00:00.000
> Data Frame B 时间戳: 10:00:00.123
> ```
>
> 这两行不会被 Join 到同一行，因为毫秒数不同。解决方法：在查询层面统一时间戳精度。

**配置方式：**
1. 在面板中添加查询 A（Prometheus）和查询 B（MySQL）
2. 添加 Transformation → Join by field
3. 选择字段：Time

### Reduce（降维）

将时序数据缩减为单行统计值（适用于 Stat 面板）。

> **比喻：把一部电影浓缩成一张海报**
>
> 时序数据就像一部 2 小时的电影——有很多帧画面。Reduce 操作相当于从电影中提取"最精彩的一幕"：最大值（最高潮的瞬间）、平均值（整部电影的基调）、最小值（最平淡的部分）。Stat 面板只需要一个数字，Reduce 就是那个"摘取关键帧"的操作。

```
输入（时间序列）:
┌──────────┬──────┐
│ Time     │ CPU  │
├──────────┼──────┤
│ 10:00:00 │ 45   │
│ 10:01:00 │ 60   │
│ 10:02:00 │ 55   │
│ 10:03:00 │ 70   │
└──────────┴──────┘

输出（Reduce → Max）:
┌──────┐
│ CPU  │
├──────┤
│ 70   │  ← 最大值
└──────┘
```

**支持的 Reduce 计算：**
- `Max` / `Min` / `Mean` / `Last` / `First`
- `Count` / `Sum` / `Delta` / `Difference`
- `All values`（保持原始值）

> **选择 Reduce 策略的原则**：
> - **Max**：关注峰值（如 CPU 峰值、延迟 P99 的尖刺）
> - **Mean**：关注平均水平（如平均响应时间）
> - **Last**：关注最新状态（如当前连接数、当前磁盘使用率）
> - **Delta**：关注变化量（如从开始到现在的增长量）
> - **Count**：关注数据点数量（如检测数据采集是否正常）

### Add field from calculation（字段计算）

通过数学公式动态创建新字段。

> **比喻：厨师调酱汁**
>
> 你手头有盐和糖两种原料（已有的字段），按比例混合就能得到一种新的调味汁（计算字段）。`Add field from calculation` 就是这个"混合配方"——不需要重新去数据源取数据，直接用已有数据算出新值。

```
输入:
┌──────────┬──────────┬───────────┐
│ Time     │ Errors   │ Total     │
├──────────┼──────────┼───────────┤
│ 10:00:00 │ 5        │ 100       │
│ 10:01:00 │ 8        │ 120       │
└──────────┴──────────┴───────────┘

Add field from calculation:
  Formula: Errors / Total * 100
  Alias: Error Rate (%)

输出:
┌──────────┬──────────┬───────────┬────────────┐
│ Time     │ Errors   │ Total     │ Error Rate │
├──────────┼──────────┼───────────┼────────────┤
│ 10:00:00 │ 5        │ 100       │ 5.0        │
│ 10:01:00 │ 8        │ 120       │ 6.7        │
└──────────┴──────────┴───────────┴────────────┘
```

**支持的计算类型：**
- Binary operations: `+`, `-`, `*`, `/`
- Unary operations: `abs()`, `log()`, `sqrt()`
- Aggregations: `sum()`, `mean()`, `min()`, `max()`
- Conditional: `if()`, `ifelse()`

> **代码旁白：公式中的字段引用**
>
> 在公式中引用字段时，你可能会看到两种写法：
> - `#A` — 引用第一个查询的结果（按查询顺序编号）
> - `$field_name` — 按字段名引用
>
> 建议使用字段名引用，因为它更直观。但要注意：字段名必须完全匹配（包括大小写和空格）。如果字段名包含空格（如 `Error Rate`），需要用引号包裹：`$"Error Rate"`。

### Group by（分组聚合）

按指定字段分组，并对其他字段进行聚合计算。

> **比喻：把水果按颜色分类**
>
> 你有一篮子水果（原始数据），有苹果、香蕉、葡萄。按颜色分组：红色水果放在一起，黄色水果放在一起，紫色水果放在一起。然后计算每组的总重量（聚合）。这就是 Group by 的核心思想——把数据按某个维度分组，然后对每组做统计。

```
输入（长表）:
┌──────────┬──────┬─────────┐
│ Time     │ host │ cpu     │
├──────────┼──────┼─────────┤
│ 10:00:00 │ web1 │ 45      │
│ 10:00:00 │ web2 │ 60      │
│ 10:01:00 │ web1 │ 50      │
│ 10:01:00 │ web2 │ 55      │
└──────────┴──────┴─────────┘

Group by → Field: host → Calculation: Mean
输出（宽表）:
┌──────────┬──────┬──────┐
│ host     │ cpu  │      │
├──────────┼──────┼──────┤
│ web1     │ 47.5 │      │
│ web2     │ 57.5 │      │
└──────────┴──────┴──────┘
```

> **代码旁白：长表 vs 宽表**
>
> - **长表（Long format）**：每一行是一个观测值，有多个标识列（如 time、host）和一个值列（如 cpu）。这种格式适合大多数数据库存储。
> - **宽表（Wide format）**：每个分组一行，每个类别一列。这种格式更适合人眼阅读和表格展示。
>
> Transformations 可以在两种格式之间自由转换。长表→宽表用 Group by，宽表→长表用 Convert field type + 其他 Transformation 组合。

### Convert field type（字段类型转换）

改变字段的数据类型：

| 原始类型 | 目标类型 | 示例 |
|---------|---------|------|
| String → Number | `"123"` → `123` | 解析数字字符串 |
| Number → String | `123` → `"123"` | 格式化显示 |
| String → Time | `"2024-01-01"` → timestamp | 解析时间字符串 |

> **常见陷阱**：JSON API 返回的字段经常是字符串类型，即使内容是数字（如 `"cpu_usage": "45.5"`）。如果不做类型转换，Grafana 会把它当作文本而不是数值，无法进行排序、计算或画图。

### Merge（合并）

将多个查询结果的序列合并到同一张表中（与 Join 的区别：不要求时间轴对齐）。

```
查询 A: web1 CPU  ──┐
                     ├── Merge ──▶ 同一张图显示所有序列
查询 B: web2 CPU  ──┘
```

> **Merge vs Join 的区别**：
> - **Merge**：把多个数据序列"堆叠"到一张图上，不要求时间轴对齐。A 有 100 个数据点，B 有 80 个数据点，Merge 后还是 180 个数据点（各自独立的时间轴）。
> - **Join**：按时间戳精确匹配，要求时间轴对齐。A 有 100 个数据点，B 有 80 个数据点，Join 后最多 80 个数据点（只有时间匹配的行才保留）。

## 8.3 实战：多数据源聚合 Dashboard

### 场景：同时查看 CPU、订单量、错误日志

**Step 1：添加三个查询**

```
查询 A: Prometheus → avg(rate(node_cpu_seconds_total{mode!="idle"}[5m])) * 100
查询 B: MySQL → SELECT $__timeGroupAlias(created_at, $__interval), count(*) FROM orders GROUP BY 1
查询 C: Loki → rate({job="api"} |= "error"[1m])
```

> **代码旁白：为什么每个查询返回不同格式的数据？**
>
> - 查询 A（Prometheus）返回时间序列——每行有时间戳和 CPU 值
> - 查询 B（MySQL）返回表格——每行有时间戳和订单计数
> - 查询 C（Loki）返回日志流计数——每行有时间戳和错误率
>
> 三个查询的"形状"不同，但都包含时间戳列。这就是 Join by field 可以工作的基础——只要所有 Data Frame 都有一个共同的字段（Time），就能按它对齐。

**Step 2：添加 Transformation**

```
1. Join by field (Time)
   - 将 A、B、C 的结果按时间轴合并
   
2. Add field from calculation
   - Name: Error Rate (%)
   - Formula: Errors / (CPU / 100) * 100
   
3. Rename fields
   - CPU → CPU Usage (%)
   - count(*) → Orders
```

> **代码旁白：Transformation 的"流水线"思维**
>
> 每个 Transformation 的输出是下一个的输入。理解这个流水线对调试至关重要：
>
> ```
> 原始查询结果                  Join 之后              计算字段之后           重命名之后
> ┌──────┬──────┐            ┌──────┬──────┬──────┐  ┌──────┬──────┬──────┬──────┐  ┌──────┬──────┬──────┬──────┐
> │ Time │ CPU  │     Join   │ Time │ CPU  │ Err  │  │ Time │ CPU  │ Err  │ E%   │  │ Time │ CPU%│ Ord  │ E%   │
> ├──────┼──────┤    ─────▶  ├──────┼──────┼──────┤  ├──────┼──────┼──────┼──────┤  ├──────┼──────┼──────┼──────┤
> │ 10:00│ 45   │            │ 10:00│ 45   │ 5    │  │ 10:00│ 45   │ 5    │ 11.1 │  │ 10:00│ 45   │ 120  │ 11.1 │
> │ 10:01│ 60   │            │ 10:01│ 60   │ 8    │  │ 10:01│ 60   │ 8    │ 13.3 │  │ 10:01│ 60   │ 150  │ 13.3 │
> └──────┴──────┘            └──────┴──────┴──────┘  └──────┴──────┴──────┴──────┘  └──────┴──────┴──────┴──────┘
> ```
>
> 如果在某一步发现数据不对，可以逐个禁用 Transformation 来定位问题步骤。

**Step 3：配置面板**

```
类型: Time Series
单位: 各自配置
图例: 显示字段名
```

## 8.4 潜在风险与优化

### 风险 1：浏览器内存溢出

**问题**：Transformations 在浏览器端执行，如果输入数据量很大（数万行），浏览器可能 OOM。

> **真实案例**：某团队在 Dashboard 中配置了一个不加任何过滤条件的 Prometheus 查询，返回了 50 万行时序数据。然后在这个查询上应用了 4 层 Transformation（Merge → Group by → Add field → Rename）。用户在打开 Dashboard 时，Chrome 直接崩溃，弹出"Aw, Snap!"错误页面。
>
> **根因分析**：50 万行数据在浏览器端被复制了 4 次（每层 Transformation 都会生成新的 Data Frame），内存占用从原始的 50MB 飙升到 200MB+。加上其他面板的数据，Chrome 标签页内存占用超过 1GB，导致 OOM。
>
> **教训**：Transformations 不是万能的。大数据量的聚合应该在数据源侧完成，Transformations 只做"轻量级"的后处理。

**优化：**
1. 在查询层面先做聚合（PromQL 的 `avg by`、SQL 的 `GROUP BY`）
2. 限制时间范围，减少数据量
3. 使用 Recording Rule 预计算

### 风险 2：Join 时时间轴未对齐

**问题**：两个数据源的时间戳精度不同（ms vs s），Join 后大量空值。

**解决：** 在查询中将时间戳统一到相同精度。

> **调试技巧**：如果你发现 Join 后大部分行的值为 `null`，先检查时间戳格式。在 Explore 中分别查看两个查询的原始结果，对比时间戳列：
> - Prometheus 返回的是秒级时间戳（如 `1700000000`）
> - MySQL 返回的是毫秒级时间戳（如 `1700000000000`）
>
> 解决方法：在 PromQL 中用 `... * 1000` 转为毫秒，或在 SQL 中用 `UNIX_TIMESTAMP(time) * 1000` 转为毫秒。

### 风险 3：过多的 Transformation 步骤

**问题**：超过 5 步的 Transformation 链不仅难以调试，而且性能下降明显。

**建议：** 尽量在数据源侧完成计算，Transformations 只做最后的"粘合"。

> **黄金法则**：Transformations 做"形状转换"（宽转长、合并、重命名），不做"重量级计算"（复杂聚合、多层计算）。如果某个计算能在 PromQL 或 SQL 中完成，就在数据源侧完成。

### 风险 4：Transformation 顺序错误

**问题**：Transformations 的执行顺序对结果有决定性影响，顺序错了结果完全不对。

> **案例**：某用户先做 `Reduce`（降维为单行），再做 `Add field from calculation`。由于 Reduce 后只剩一行数据，`Add field` 只能算出一个值，完全失去了时序意义。正确的顺序是先 `Add field` 计算新字段，再 `Reduce` 取最大值。

## 8.5 典型问题处理

### 问题 1：Transformation 后数据丢失

**排查：**
1. 逐个禁用 Transformation，确认是哪一步导致的问题
2. 检查 Join 的字段名是否完全匹配（大小写、空格）
3. 检查 Reduce 的计算方式是否正确

> **快速定位"哪一步出问题"**：在 Transformation 列表的右上角，每个步骤都有一个"眼睛"图标（Toggle visibility）。点击可以临时禁用该步骤，观察数据变化。从最后一步开始向前禁用，能快速定位问题步骤。

### 问题 2：计算字段显示为 0

**原因**：字段名引用错误。

**解决**：在 Add field from calculation 中检查字段引用名是否与输入字段名完全一致。

> **排查步骤**：
> 1. 在 Transformation 面板中，点击上一步的输出预览，确认字段的准确名称
> 2. 检查字段名中是否有隐藏字符（如前后空格）
> 3. 如果字段名包含特殊字符，尝试用反引号包裹：`` `my-field` ``

### 问题 3：Merge 后线条太多

**原因**：Merge 把所有序列合并到一张图上，如果序列数过多（>20），图表难以阅读。

**解决**：在查询中使用 `topk()` 或 `LIMIT` 限制序列数。

### 问题 4：Group by 后时间轴消失

**问题**：Group by 操作默认会移除时间戳列，因为分组后的数据不再是时间序列。

**解决**：如果需要保留时间维度，考虑使用其他 Transformation 或在查询层面做聚合。

## 8.6 开发者必须掌握的技能

- **7 种核心 Transformation**：Join / Reduce / Add field / Group by / Merge / Convert / Rename
- **计算公式语法**：`$field_A + $field_B`、`sum($field) / count($field)`
- **数据流转理解**：查询结果 → Transformation → Panel 的完整链路
- **浏览器端性能意识**：大数据量下避免复杂 Transformation

## 本章小结

- Transformations 在浏览器端对 Data Frame 进行二次加工
- Join by field 实现多数据源时间轴对齐合并
- Reduce 将时序数据降维为统计值
- Add field from calculation 动态创建计算字段
- Group by 实现宽表和长表的互相转换
- 大数据量下尽量在数据源侧完成聚合，减少浏览器端负担
