# 第1章 日志架构演进与选型决策

## 本章导读

假设你负责一个 20 个微服务的电商系统，部署在 10 台服务器上。某个客户电话投诉他的订单支付成功了但没看到物流信息。你需要排查这到底发生在"订单服务"还是"支付服务"还是"物流服务"。

在没有集中式日志系统的时代，排查流程是这样的：

```
传统日志排查流程：

  1. 登录订单服务服务器 → tail -f logs/order.log
     → "支付回调处理成功"（看起来没问题）
  2. 登录支付服务服务器 → grep "order_123" logs/payment.log
     → 找到记录，但日志格式不同，看不出具体参数
  3. 登录物流服务服务器 → 发现日志文件太大，被截断了
     → 查不到！因为磁盘满了，最早的日志被删了
  4. 耗时：25 分钟，结果：没找到根因
     → 客户还在等回复
```

在拥有 ELK 集中式日志系统后：

```
集中式日志排查流程：

  1. 打开 Kibana → 搜索 traceId: "abc-def-ghi"
     → 1 秒返回跨 3 个服务的 15 条日志
     → 按时间线排列，自动关联
  2. 看到支付服务参数 "amount: 0.00"（金额为 0 的异常订单）
  3. 再搜索 orderId 确认
  4. 耗时：30 秒
     → 立即回复客户并提供截图
```

这就是日志架构的价值。本章从最原始的 `tail -f` 开始，逐层演进到企业级高可用架构，帮助你理解"为什么需要每一层"。

## 1.1 从 tail -f 到集中式日志

### 微服务时代的日志痛点

在单体应用时代，`tail -f` 或者 `grep` 通常就够用了。但微服务架构带来了三个维度的变化：

```
痛点一：日志分散
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ 订单服务  │    │ 支付服务  │    │ 库存服务  │
  │ 服务器 A  │    │ 服务器 B  │    │ 服务器 C  │
  │ order.log│    │ pay.log  │    │ stock.log│
  └─────────┘    └─────────┘    └─────────┘

  一个请求穿越 3 个服务 → 日志在 3 台服务器上
  grep 只能查一台，做不到跨服务器关联

痛点二：日志格式混乱
  订单服务：2024-01-01 10:00:00 [INFO] 订单创建成功
  支付服务：[2024-01-01 10:00:01] PaymentService.create order_123 success
  库存服务：{"time":"2024-01-01T10:00:02","level":"info","msg":"stock deducted"}
  3 种格式 → 没法用统一脚本分析

痛点三：磁盘容量限制
  一台服务器 500GB 磁盘
  日志每天产生 5GB
  只能保留 100 天的日志 → 旧数据被删除
  但审计要求保留 1 年
```

### 集中式日志的核心目标

```
集中式日志要解决的 4 个问题：

  ┌──────────────────────────────────────────────┐
  │  1. 统一采集                                 │
  │     所有服务器上的日志自动发送到中央存储       │
  │     不需要登录每台服务器                       │
  ├──────────────────────────────────────────────┤
  │  2. 统一解析                               │
  │     不同格式的日志解析为统一结构（JSON）       │
  │     时间戳标准化、字段类型统一                │
  ├──────────────────────────────────────────────┤
  │  3. 统一存储                               │
  │     所有日志存储在可横向扩展的中央存储中       │
  │     支持海量数据的快速检索                    │
  ├──────────────────────────────────────────────┤
  │  4. 统一查询                               │
  │     一个查询界面搜索所有服务的日志            │
  │     支持跨服务关联（TraceId 串联）            │
  └──────────────────────────────────────────────┘
```

## 1.2 ELK vs EFK：深度对比与选型

ELK 和 EFK 的核心思想相同——采集器（Agent）→ 缓冲（可选）→ 处理（Pipeline）→ 存储（ES）→ 可视化（Kibana）。唯一的区别在于"处理层"的组件选择：

```
ELK 架构：

  App ──► Filebeat ──► (Kafka) ──► Logstash ──► Elasticsearch ──► Kibana

  核心处理组件：Logstash
  语言：JRuby（运行在 JVM 上）
  插件生态：200+ 插件，极其丰富
  性能：中等（JVM 启动慢，内存占用高）

EFK 架构：

  App ──► Fluent Bit ──► (Kafka) ──► Fluentd ──► Elasticsearch ──► Kibana

  核心处理组件：Fluentd（聚合层）/ Fluent Bit（边缘层）
  语言：C + Ruby（Fluent Bit 用 C 编写）
  插件生态：100+ 插件
  性能：高（Fluent Bit 内存占用极低）
```

### 组件对比表

| 对比维度 | Logstash | Fluentd | Fluent Bit |
|---------|----------|---------|------------|
| **运行语言** | JRuby（JVM） | Ruby + C | C |
| **内存占用** | 500MB-1GB+ | 100-300MB | **3-50MB** |
| **启动时间** | 30-60 秒 | 5-10 秒 | **< 1 秒** |
| **吞吐量** | 2-5 万事件/秒 | 1-3 万事件/秒 | **5-10 万事件/秒** |
| **插件数量** | 200+（最丰富） | 100+ | 50+ |
| **数据处理能力** | 最强（丰富的 Filter） | 强 | 基础 |
| **适用场景** | 复杂数据处理中心 | 通用日志处理 | 边缘采集 |

### 选型建议

```
选型决策树：

  你的需求是？
  │
  ├── 简单环境（< 10 台服务器，不需要 Kafka）
  │     └── Filebeat + Logstash + ES + Kibana（ELK 最简架构）
  │
  ├── 企业级（需要高可用、削峰填谷）
  │     └── Filebeat + Kafka + Logstash + ES + Kibana
  │                               ↑ Logstash 的 Filter 能力是无价的
  │
  ├── K8s 环境（容器化、资源受限）
  │     └── Fluent Bit + (Kafka) + Fluentd + ES + Kibana
  │         ↑ Fluent Bit 内存 50MB，比 Filebeat 更适合容器
  │
  └── 全云原生（极致资源效率）
        └── Fluent Bit + ES + Kibana
            ↑ 如果不需要复杂的数据清洗
```

> **💡 本书的选择**：本书以 **ELK 架构（Filebeat → Kafka → Logstash → ES）** 为主线，因为这是生产环境中最常见、数据处理能力最强的组合。在第 7 章会单独介绍 Fluent Bit 的云原生方案。

## 1.3 企业级高可用日志架构

### 完整架构图

```
企业级日志架构（6 层模型）：

  应用层                   采集层                缓冲层                 处理层                 存储层                可视化层
  ┌─────────┐            ┌─────────┐          ┌────────────┐          ┌─────────┐          ┌─────────┐          ┌─────────┐
  │ 订单服务  │──日志文件──►│ Filebeat │──JSON──►│            │──事件──►│ Logstash │──Bulk──►│ ES 集群  │◄──查询──►│ Kibana  │
  └─────────┘            └─────────┘          │            │          │ (Pipeline)│          │         │          │         │
  ┌─────────┐            ┌─────────┐          │   Kafka    │          │  过滤/脱敏 │          │ 3 节点  │          │  大屏    │
  │ 支付服务  │──日志文件──►│ Filebeat │──JSON──►│   Cluster  │──事件──►│  路由/转  │──Bulk──►│         │◄──查询──►│  告警    │
  └─────────┘            └─────────┘          │            │          └─────────┘          └─────────┘          └─────────┘
  ┌─────────┐            ┌─────────┐          │            │            DLQ(死信)
  │ 库存服务  │──日志文件──►│ Filebeat │──JSON──►│            │
  └─────────┘            └─────────┘          └────────────┘
```

### 为什么需要 Kafka？

```
|-- 没有 Kafka --|                      |-- 有 Kafka --|

  Filebeat ──► Logstash ──► ES           Filebeat ──► Kafka ──► Logstash ──► ES

  ES 抖动时：                              ES 抖动时：
  Logstash 写 ES 失败 → 重试 → 队列满     Logstash 写 ES 失败 → 重试
  → Logstash 停止消费 Filebeat             → 数据在 Kafka 中安全保留
  → Filebeat 缓冲满 → 停止读日志文件        → ES 恢复后 Logstash 继续消费
  → 磁盘日志文件膨胀 → 磁盘满 → 应用挂掉    → 数据不丢
```

## 本章总结

| 架构方案 | 采集端 | 缓冲层 | 处理层 | 存储层 | 适用场景 |
|---------|-------|-------|-------|--------|---------|
| **最简 ELK** | Filebeat | 无 | Logstash | ES | 小规模、开发测试 |
| **企业级 ELK** | Filebeat | Kafka | Logstash | ES | **生产环境标准方案** |
| **EFK** | Fluent Bit | (Kafka) | Fluentd | ES | K8s、容器环境 |
| **全 Fluent** | Fluent Bit | 内置缓冲 | Fluent Bit | ES | 极致轻量、边缘场景 |

**核心原则**：
1. **日志架构不是一步到位的**——从最简 ELK 开始，当流量上涨后逐步加入 Kafka 缓冲层
2. **Kafka 是缓冲层的标准选择**——它的高吞吐和持久化能力使得 Logstash 即使宕机一段时间也不会丢失数据
3. **理解每一层的职责**——采集层只负责搬数据，处理层负责清洗转换，存储层负责检索。职责分离后，每一层都可以独立替换
