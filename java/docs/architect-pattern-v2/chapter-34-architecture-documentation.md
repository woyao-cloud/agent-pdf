# 第34章 架构文档与沟通

架构文档是架构师最重要的交付物之一。好的架构文档不是"写完了就过时"的形式主义产物，而是团队理解系统、做出决策、传承知识的活工具。

---

## 34.1 架构设计文档

### 34.1.1 架构文档的最小化结构

```
一份有效的架构设计文档应该包含以下部分——每部分都有明确的目的：

1. 背景与目标（1 页）
   为什么需要做这个设计？要解决什么问题？
   不写这段 → 6 个月后没人记得当初为什么这样设计

2. 约束与假设（半页）
   有哪些不可更改的限制？（时间、预算、技术栈、合规）
   有哪些尚待验证的假设？
   不写这段 → 后人可能会在已经被否决的方向上重新讨论

3. 架构决策（2-3 页）
   选择了什么架构模式？为什么？
   关键的架构决策及理由
   不写这段 → 文档就只剩"我们做了什么"，没有"为什么这么做"

4. 系统架构图（1 页）
   一张图说清楚系统由哪些部分组成，它们之间如何连接
   文字描述架构图上的每个部分

5. 关键流程（2-3 页）
   2-3 个最重要的业务流程的序列图/流程图
   写"正常路径"和"异常路径"两条线

6. 数据模型（1-2 页）
   核心实体的 ER 图或描述
   关键的数据流向

7. 非功能需求（1 页）
   性能、可用性、安全性、可扩展性的目标
   不是"系统应该快"，而是"P95 延迟 < 200ms"

8. 风险与缓解（1 页）
   已知的架构风险
   缓解措施
   剩余的"接受"的风险
```

### 34.1.3 文档的生存法则

```
让架构文档"活下来"的策略：

1. 文档放在代码旁边（不是 Confluence / Notion）
   推荐：项目根目录的 docs/arch/ 下
   Git 版本控制 → 文档和代码同步演进
   代码评审时顺便评审相关的文档变更

2. 把文档变"小"
   不要写"完整架构文档"——维护成本太高
   改为写多个小的 ADR + 一张总览图
   小的文档更容易保持更新

3. 接受"文档会过时"
   在每个文档头部写上"最后更新日期"
   代码是唯一不会说谎的权威来源
   文档提供的是"意图"和"原因"，不是"精确的实现细节"

4. 自动化生成能自动化的部分
   - 包依赖图：用 ArchUnit 或 jQAssistant 自动生成
   - API 文档：OpenAPI / Spring REST Docs 自动生成
   - 数据库 Schema：Flyway/Liquibase 的迁移脚本即文档
   只手工编写"为什么"的部分
```

## 34.2 ADR（架构决策记录）

### 34.2.1 ADR 的价值

```
为什么需要 ADR？

场景：
  新人：为什么我们用 MongoDB 而不是 MySQL？
  老员工：我也不记得了，好像是三年前小明提的……
  小明：已经离职了

没有 ADR → 原因丢失 → 换技术时无法判断旧的约束是否还存在
有 ADR → 知道当时为什么选，也知道什么情况下应该重新评估
```

### 34.2.2 ADR 模板与示例

```markdown
# ADR-007: 选择 PostgreSQL 替代 MySQL

| 属性 | 值 |
|------|-----|
| 状态 | Accepted |
| 日期 | 2025-06-01 |
| 决策者 | 张三（架构师） |
| 影响范围 | 所有新建微服务的数据库选型 |

## 上下文

现有系统使用 MySQL 5.7，面临以下问题：
1. 需要 JSON 字段支持——MySQL 5.7 的 JSON 支持不够成熟
2. 需要高级分析查询（窗口函数、CTE）——MySQL 5.7 不支持
3. 地理空间查询需求（查找用户附近的门店）——PostGIS 扩展更成熟
4. 团队已经在 2 个新项目中尝试了 PostgreSQL，反馈良好

## 决策

新服务统一使用 PostgreSQL 15+。已有 MySQL 服务暂不强制迁移。

## 考虑的选项

### 选项 A：升级到 MySQL 8.0
- 好处：团队熟悉，迁移成本低
- 坏处：JSON 和空间查询仍不如 PostgreSQL
- 评估：满足部分需求，但不是最优

### 选项 B：切换到 PostgreSQL（选中）
- 好处：JSON/JSONB 原生支持，PostGIS 业界标准，窗口函数/CTE 成熟
- 坏处：团队需要学习，运维需要调整
- 评估：长期收益 > 短期成本

### 选项 C：MongoDB（JSON 文档 + 空间查询）
- 好处：灵活 Schema，空间查询
- 坏处：不支持 ACID 事务（需要跨集合），与现有 ORM 不兼容
- 评估：不适合需要强事务的订单/支付场景

## 后果

### 正面
- 新服务获得更好的 JSON 和空间查询能力
- 统一新服务的技术选型，减少运维碎片化

### 负面
- 运维需要同时管理 MySQL 和 PostgreSQL 两种数据库
- 团队需要 PostgreSQL 培训

### 风险
- Hibernate/Spring Data JPA 的 PostgreSQL 方言兼容性需要验证
  → 缓解：已在 pilot 项目中验证，无阻塞问题
```

### 34.2.3 ADR 的生命周期

```
ADR 的状态流转：

Proposed → Accepted → Deprecated → Superseded
    │          │            │
    │          │            └── 被新的 ADR 替代
    │          └── 仍然有效，是当前策略
    └── 正在讨论中，尚未被接受，不应被引用

文件命名：docs/arch/adr/0007-use-postgresql.md
编号规则：从 0001 开始，顺序递增

ADR 的组织：
  - 目录中的 README.md 列出所有 ADR 的索引
  - 索引格式：
    | ADR | 日期 | 决策 | 状态 |
    |-----|------|------|------|
    | 0001 | 2025-01-10 | 选择 Kafka 作为消息平台 | Accepted |
    | 0002 | 2025-02-15 | 使用 ArgoCD 做 GitOps | Superseded by 0008 |
```

## 34.3 技术方案评审

### 34.3.1 评审的组织与流程

```
技术方案评审的三个阶段：

阶段 1: 方案准备（架构师）
  - 编写架构设计文档 + ADR
  - 在文档中标注"待评审的决策"
  - 提前 48 小时发出文档给评审人

阶段 2: 评审会议（1-2 小时）
  参会人：
    - 架构师（方案作者）
    - 相关服务的 Tech Lead（2-3 人）
    - 资深工程师（能挑战方案的人，不是凑人数的）
    - 运维/SRE 代表（如果涉及基础设施变更）

  议程：
    1. 背景介绍（5 分钟）
    2. 架构概览（10 分钟）
    3. 关键决策讨论（45 分钟——主要时间花在这里）
    4. 风险和缓解（15 分钟）
    5. 行动项确认（5 分钟）

阶段 3: 评审后续
  - 更新文档（根据评审意见）
  - 将行动项写入 Issue Tracker
  - 方案状态从 Draft → Review → Approved
```

### 34.3.2 评审中的常见陷阱

```
技术方案评审的常见问题：

问题 1: "展示会"而不是"评审会"
  症状：架构师花 50 分钟演示方案，最后 10 分钟问"有什么问题吗？"
  结果：没有人认真审过方案，问题都在实现阶段才暴露
  修复：提前发文档，会议只讨论"有争议的决策"

问题 2: 评审者沉默
  症状：参会的人都不提问，只是"点头"
  原因：文档太复杂、看不懂，或者觉得"这不是我的事"
  修复：明确指定"每位评审人至少提出 1 个问题或建议"

问题 3: 过度追求完美方案
  症状：讨论陷入了"要不要用 XX 模式"的哲学辩论
  修复："这个决策可以推迟吗？如果可以，我们先做能确定的部分"

问题 4: "评审完了就不管了"
  症状：方案评审通过后，实际实现与方案产生偏差
  修复：方案中的关键决策用适应度函数（见 30.4.2）守护
```

## 34.4 团队知识传递

### 34.4.1 知识传递的策略

```
知识的传递方式的效率和成本：

  效率高 ↑
       │  结对编程             架构文档 + 代码评审
       │  (最高效但最贵)        (平衡效率和成本)
       │
       │  团队分享会            Wiki / Notion
       │  (中等)                (写的多，看的少)
       │
       │  视频录制              不传递
       │  (录的人方便、看的人痛苦)  (默认状态)
       │
       └─────────────────────────────────────→ 成本
                                              (时间 + 维护)

推荐组合：
  - 架构决策 → ADR（永久记录，代码旁边）
  - 系统全貌 → 架构文档 + 图（定期更新）
  - 关键实现 → 代码评审 + 结对编程（实时传递）
  - 新人上手 → 结构化阅读清单 + mentor 制度
```

### 34.4.2 新人上手文档

```markdown
# 架构上手指南（给新团队成员）

## 第一步：理解业务（第 1 天）
阅读材料：
  - [产品介绍文档]
  - [核心业务流程说明]
  - 目标：理解"我们为什么存在"和"用户需要什么"

## 第二步：理解系统全貌（第 2-3 天）
阅读顺序（从外到内）：
  1. 系统上下文图 → 理解系统边界和外部交互
  2. 容器图 → 理解有哪些服务和中间件
  3. 架构决策索引 → 浏览 ADR 列表，了解重大决策
  4. 关键流程文档 → 理解 2-3 个核心业务流程

## 第三步：深入一个领域（第 4-5 天）
- 选择一个相对简单的服务（建议从 Gateway 开始）
- 阅读代码：从 Controller → Service → Repository
- 阅读该服务的组件图和 ADR
- 尝试做一个小的代码变更（加一个日志、修复一个文档）

## 第四步：参与团队活动（持续）
- 参加代码评审（先看，再评）
- 参加架构讨论（听比说重要）
- P0：知道哪里找信息 > P1：知道所有信息
```

## 34.5 本章小结

架构文档和沟通的核心原则：

1. **文档是工具，不是目的**——写最少够用的文档，保持更新，放在代码旁边
2. **ADR 是最有价值的架构文档**——记录"为什么"，代码已经记录了"是什么"
3. **评审要提前发文档，会议只讨论争议**——不是展示会，是决策会
4. **知识传递要有结构**——从外到内（系统边界 → 服务 → 组件），而不是随机分享
5. **图要能版本控制**——PlantUML/Mermaid 是纯文本，可以像代码一样 diff

最好的文档是**"下一个接手的人能够理解当初为什么这样设计"**。如果看完文档后可以做出与当初相同的决策，这份文档就是成功的。
