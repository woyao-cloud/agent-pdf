# 第30章 架构模式选择

选择正确的架构模式是软件项目中最关键的早期决策之一。错误的架构选择在项目推进 6-12 个月后会变得非常昂贵。本章提供一套系统化的架构选择方法，帮助你做出理性的、可辩护的技术决策。

---

## 30.1 如何选择架构模式

### 30.1.1 决策的基础框架

```
架构选择的五个维度：

        业务需求             质量属性
       (做什么)            (做到什么程度)
           │                   │
           └───────┬───────────┘
                   │
              ┌────▼────┐
              │ 架构决策  │
              └────┬────┘
                   │
      ┌────────────┼────────────┐
      │            │            │
  团队能力      技术生态      组织约束
 (谁会做)     (用什么做)    (在什么限制下做)
```

选择架构模式不是选"哪个模式最好"，而是选"在这个特定的上下文（业务需求 + 质量属性 + 团队 + 约束）中，哪个模式的收益/代价比最高"。

### 30.1.2 质量属性驱动的选择

回顾第 3 章的质量属性，不同架构模式对各属性的支持程度不同：

```
架构模式的质量属性表现：

                    性能    可用性   可修改性  可扩展性  开发效率  运维复杂度
单体架构            ★★★★   ★★      ★★       ★★       ★★★★★   ★★★★★
三层架构            ★★★    ★★★     ★★★      ★★★      ★★★★    ★★★★
SOA                 ★★     ★★★★    ★★★★     ★★★★     ★★      ★
微服务              ★★★    ★★★★★   ★★★★★    ★★★★★    ★★      ★★
事件驱动            ★★★★★  ★★★★    ★★★★     ★★★★★    ★★★     ★★
空间架构            ★★★★★  ★★★★    ★★★      ★★★★★    ★       ★
管道-过滤器         ★★★    ★★      ★★★★★    ★★★      ★★★★    ★★★★
云原生              ★★★    ★★★★★   ★★★★     ★★★★★    ★★★     ★★
```

### 30.1.3 架构选择决策树

```
架构选择决策树：

问题 1：你的团队是 1-5 人的小团队吗？
  ├── 是 → 问题 1a：未来 12 个月内团队会扩展到 15+ 人吗？
  │         ├── 否 → 选择：模块化单体（Modular Monolith）
  │         └── 是 → 选择：分层架构 + 有准备的模块化（为未来拆分铺路）
  │
  └── 否 → 问题 2：是否需要多个团队独立部署？
            ├── 否 → 问题 2a：数据处理的步骤是否超过 5 个？
            │         ├── 是 → 选择：管道-过滤器模式
            │         └── 否 → 选择：三层/N-Tier
            │
            └── 是 → 问题 3：数据一致性要求是否极其严格？
                      ├── 是 → 选择：SOA（集中式事务管理）
                      └── 否 → 问题 4：是否需要对每个请求亚毫秒级响应？
                                ├── 是 → 选择：空间架构
                                └── 否 → 问题 5：流量波动是否在 10 分钟内从 0 到 10000 TPS？
                                          ├── 是 → 选择：微服务 + 云原生 + 事件驱动
                                          └── 否 → 选择：微服务
```

### 30.1.4 量化决策：架构权衡分析法（ATAM）

```java
// ATAM 的核心思想：不是凭感觉选架构，而是用数据支持决策

// 步骤 1: 定义效用树（Utility Tree）—— 将业务目标转化为可量化的质量属性场景
//
// 业务目标：支持日订单量 100 万单
//   ├── 性能
//   │     ├── P99 延迟 < 200ms
//   │     └── 峰值 TPS = 5000
//   ├── 可用性
//   │     ├── 99.95% uptime
//   │     └── 单点故障恢复 < 30s
//   ├── 可修改性
//   │     ├── 新增支付渠道 < 3 人天
//   │     └── 修改定价规则不影响其他模块
//   └── 安全性
//         ├── PCI-DSS 合规
//         └── 所有 API 需认证

// 步骤 2：对候选架构在每个场景上打分（0-10）
public record ArchitectureEvaluation(
    String scenario,
    int monolithic,
    int microservices,
    int eventDriven,
    int spaceBased
) {}

List<ArchitectureEvaluation> evaluations = List.of(
    new ArchitectureEvaluation("P99延迟<200ms",     8, 5, 7, 10),
    new ArchitectureEvaluation("峰值TPS=5000",       6, 8, 9, 10),
    new ArchitectureEvaluation("99.95%可用性",       5, 9, 7, 8),
    new ArchitectureEvaluation("新增支付渠道<3天",   3, 9, 5, 2),
    new ArchitectureEvaluation("修改定价规则隔离",   3, 8, 6, 3),
    new ArchitectureEvaluation("PCI-DSS合规",        7, 6, 6, 4),
    new ArchitectureEvaluation("团队学习成本",       9, 3, 5, 2)
);

// 步骤 3：加权计算（每个场景有不同的重要性权重）
Map<String, Double> weights = Map.of(
    "P99延迟<200ms",      0.25,
    "峰值TPS=5000",       0.25,
    "99.95%可用性",       0.20,
    "新增支付渠道<3天",   0.05,
    "修改定价规则隔离",   0.05,
    "PCI-DSS合规",        0.10,
    "团队学习成本",       0.10
);

// 根据上面的数据：
// 单体:    8*0.25+6*0.25+5*0.20+3*0.05+3*0.05+7*0.10+9*0.10 = 6.25
// 微服务:  5*0.25+8*0.25+9*0.20+9*0.05+8*0.05+6*0.10+3*0.10 = 6.55
// 事件驱动: 7*0.25+9*0.25+7*0.20+5*0.05+6*0.05+6*0.10+5*0.10 = 7.10
// 空间架构: 10*0.25+10*0.25+8*0.20+2*0.05+3*0.05+4*0.10+2*0.10 = 7.35
//
// 结论：空间架构得分最高，但团队学习成本是硬伤
// 实际选择：事件驱动（综合得分第二，且团队学习成本可控）
```

## 30.2 场景化决策

### 30.2.1 创业公司 / MVP 阶段

```
场景画像：
  - 团队 3-5 人，全栈工程师
  - 需求剧烈变化（每月可能 pivot）
  - 用户量 < 10000
  - 目标：验证产品市场匹配（PMF）

推荐架构：模块化单体
  理由：
    - 开发效率最高——一个 IDE 可以跑全部代码
    - 重构成本最低——功能未定型时，单体最容易调整边界
    - 运维成本最低——一个 JAR、一个数据库

需要做的事：
  - 按包结构做模块隔离（com.example.order / com.example.payment / ...）
  - 模块间通过接口通信（不是直接调用实现类）
  - 用 ArchUnit 在 CI 中强制模块边界
  - 做好拆分准备——但不要过早拆分
```

### 30.2.2 快速增长的业务

```
场景画像：
  - 团队 20-50 人，分成 3-5 个小组
  - 用户量快速增长（10 万 → 100 万）
  - 需要多个团队并行开发、独立发布
  - 核心业务流程已稳定

推荐架构：微服务 + 事件驱动
  理由：
    - 团队独立部署——一个组的发布不阻塞其他组
    - 独立扩展——订单服务和搜索服务的流量模式完全不同
    - 事件驱动解耦——新功能可以通过订阅已有事件实现

关键分阶段策略：
  第 1 阶段（现在）：
    - 从单体中拆出 2-3 个核心服务（订单、支付、用户）
    - 其他功能暂留在单体中
  第 2 阶段（3 个月后）：
    - 引入事件总线（Kafka）
    - 服务间异步通信替代同步调用
  第 3 阶段（6 个月后）：
    - 根据瓶颈数据继续拆分
    - 引入服务网格、完善可观测性
```

### 30.2.3 企业级系统

```
场景画像：
  - 大型组织，多个业务部门
  - 需要与大量遗留系统集成
  - 事务一致性要求极高（财务、合规）
  - 技术栈多样（Java、.NET、大型机）

推荐架构：SOA（轻量级）+ N-Tier
  理由：
    - ESB/API Gateway 统一管理异构系统的集成
    - 集中式事务管理（两阶段提交）
    - 标准化接口契约（WSDL/OpenAPI）
    - 适合"不要大改，但要能集成"的组织文化

关键注意事项：
  - 不要重蹈"重型 ESB"的覆辙
  - ESB 只做路由和协议转换，不写业务逻辑
  - 新功能可以在微服务中构建，通过 API Gateway 与现有系统对接
```

### 30.2.4 高并发 / 低延迟系统

```
场景画像：
  - 每秒钟处理数万甚至十万级请求
  - 响应时间要求 < 10ms
  - 数据可以在内存中放下（尽管可能很大）
  - 典型：广告竞价、秒杀、游戏 Matchmaking

推荐架构：空间架构
  理由：
    - 数据和逻辑在内存中同一位置——零网络 I/O
    - 线性扩展——增加节点 = 增加吞吐量 + 增加数据容量
    - 数据库退化为异步备份，不在请求关键路径上

前提条件（必须全部满足）：
  □ 活跃数据集可以在集群总内存中放下
  □ 可以接受最终一致性（内存数据到数据库有延迟）
  □ 团队有能力管理分布式内存网格（Hazelcast/Apache Ignite）
  □ 已穷尽所有传统优化（缓存、读写分离、分库分表）
```

### 30.2.5 流式数据处理

```
场景画像：
  - 数据持续流入（日志、传感器、用户行为）
  - 需要多步骤处理（清洗 → 聚合 → 分析 → 存储）
  - 步骤可能增减（业务分析需求变化）
  - 典型：日志分析、实时推荐、风控模型

推荐架构：管道-过滤器 + 事件驱动
  理由：
    - 每个处理步骤是独立的 Filter，可以自由编排
    - 消息队列（Kafka）作为步骤间的缓冲——天然支持背压和重放
    - 新增分析维度 = 新增一个 Filter / Consumer，不影响已有流程

技术栈参考：
  - 轻量级：Java Stream API + Spring Reactor
  - 中等规模：Spring Batch + Kafka
  - 大规模：Apache Flink / Spark Streaming + Kafka
```

## 30.3 模式组合使用

### 30.3.1 混合架构的真实世界

真实的生产系统几乎从不使用单一架构模式。以下是常见的组合模式：

```
混合架构示例：电商平台

                    ┌─────────────┐
                    │  CDN + DNS   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  API Gateway │        ← N-Tier 的 Gateway 层
                    └──────┬──────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
   ┌──────▼──────┐  ┌──────▼──────┐  ┌──────▼──────┐
   │ 商品服务     │  │ 订单服务     │  │ 用户服务     │  ← 微服务
   │ (三层架构)   │  │ (事件驱动)   │  │ (模块单体)   │
   └──────────────┘  └──────┬──────┘  └──────────────┘
                            │
                     ┌──────▼──────┐
                     │    Kafka    │            ← 事件驱动总线
                     └──────┬──────┘
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                  │
   ┌──────▼──────┐  ┌──────▼──────┐  ┌──────▼──────┐
   │ 风控引擎     │  │ 推荐引擎     │  │ 数据分析     │
   │ (管道-过滤器)│  │ (空间架构)   │  │ (管道-过滤器) │
   └──────────────┘  └──────────────┘  └──────────────┘
```

**关键原则**：不同的子系统可以使用不同的架构模式——只要子系统之间的接口是明确定义的。

### 30.3.2 组合指南

```java
// 服务内部架构 vs 服务间架构 —— 它们是独立的选择

// 服务内部：选择最合适的内部组织方式
// 订单服务内部：三层架构（Controller → Service → Repository）
// 因为它的业务逻辑是典型的 CRUD + 事务

// 服务间：选择最合适的通信和协作方式
// 订单服务 → 支付服务：异步事件（Kafka）
// 因为订单创建后支付可能延迟，需要解耦

// 组合模式选择指南：
//
// 系统边界         适合的架构模式
// ─────────────────────────────────
// 整个系统         微服务（服务划分）
// 单个服务内部      三层/N-Tier（代码组织）
// 跨服务异步通信    事件驱动（Kafka）
// 跨服务同步通信    REST/gRPC
// 数据密集型服务    空间架构
// 流式处理流程      管道-过滤器
// 基础设施层        云原生（K8s + 服务网格）
```

## 30.4 演进式架构

### 30.4.1 架构不是一次性决策

```
传统思维：选一个架构 → 按这个架构做 → 不变

演进式思维：
  第 1 年：模块化单体（快速验证）
  第 2 年：拆出 3 个核心微服务（独立扩展）
  第 3 年：引入事件驱动（异步解耦）
  第 4 年：引入空间架构（解决极端高并发场景）

架构随系统的规模和复杂度共同演进
```

### 30.4.2 适应度函数（Fitness Function）

```java
// 适应度函数是演进式架构的核心工具
// 定义：自动化测试/检查，持续验证架构是否满足关键质量属性

// 示例 1：模块边界适应度函数
@Test
public void paymentModule_shouldNot_dependOnOrderModule() {
    JavaClasses classes = new ClassFileImporter()
        .importPackages("com.example.payment");

    ArchRule rule = classes()
        .that().resideInAPackage("com.example.payment..")
        .should().onlyDependOnClassesThat()
        .resideOutsideOfPackage("com.example.order..");

    rule.check(classes);
    // 如果有人在 payment 模块中 import 了 order 模块 → CI 失败
}

// 示例 2：性能适应度函数
@Test
public void orderCreation_p99latency_shouldBeUnder_200ms() {
    // 在 CI 中运行性能基准测试
    LatencyResult result = benchmarkRunner.run(
        "OrderCreation", 1000, Duration.ofMinutes(1));

    assertThat(result.getP99())
        .isLessThan(Duration.ofMillis(200));
    // 如果某次提交让 P99 延迟超过了 200ms → CI 失败
}

// 示例 3：架构决策适应度函数
@Test
public void all_services_must_haveHealthEndpoint() {
    // 通过反射检查：所有 @Service 类是否有健康检查
    // 这强制了"每个服务必须可观测"的架构决策
}
```

## 30.5 本章小结

选择架构模式是一个"在约束条件下做多目标优化"的问题。核心方法：

1. **用质量属性驱动，而非跟风**——理解你的系统在性能、可用性、可修改性等维度上的真实需求
2. **用 ATAM 量化决策**——将直觉转化为数据支持的选择
3. **匹配团队和组织阶段**——创业公司选单体，快速增长选微服务，企业选 SOA 改良
4. **组合使用，不追求纯粹**——真实的系统总是混合多种架构模式
5. **演进式思维，不是一次性决策**——架构随系统成长而演化，用适应度函数守护关键属性

最重要的原则：**宁可选择一个"够用但简单"的架构并成功交付，也不要选择一个"完美但复杂"的架构而延期失败。**
