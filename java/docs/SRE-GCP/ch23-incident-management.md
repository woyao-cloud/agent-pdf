# 第 23 章 事件管理：从告警到恢复的标准化流程

## 23.1 为什么需要标准化的事件管理？

### 一个故事：混乱的事件响应

周一下午 2 点，支付服务宕机。5 个工程师几乎同时开始行动——有人在看日志，有人在重启服务，有人在检查数据库配置。

但问题是：**没有人协调。**

30 分钟后，团队发现：
- 两个人在排查同一个问题（重复劳动）
- 一个问题被重启暂时缓解了，但根因没有找到（还会复发）
- 管理层在 Slack 上问"怎么回事？"——没人回答（信息黑洞）
- 没有人记录操作时间线（复盘时无从谈起）

混乱的根源不是技术能力不足，而是**没有标准化的事件响应流程**。

### 标准化事件管理的价值

| 维度 | 混乱响应 | 标准化响应 |
|------|---------|-----------|
| 响应速度 | 慢，各自为政 | 快，各司其职 |
| 信息透明 | 管理层不知道发生了什么 | 实时同步进展 |
| 操作质量 | 可能遗漏根因 | 系统性排查 |
| 复盘价值 | 时间线混乱，无法复盘 | 完整时间线，有价值的复盘 |

## 23.2 事件的类型和级别

### 严重级别定义

| 级别 | 定义 | 响应时间 | 通知方式 | 示例 |
|------|------|---------|---------|------|
| **P0** | 核心服务完全不可用，影响大量用户 | 立即 | 电话/PagerDuty | 支付系统宕机、所有用户无法登录 |
| **P1** | 核心服务部分受损，影响部分用户 | 15 分钟 | Slack 强提醒 | 某个 API 延迟飙升、某功能模块不可用 |
| **P2** | 非核心功能受损，或问题处于早期阶段 | 当天 | 工单系统 | 后台管理页面加载慢、报表生成失败 |
| **P3** | 轻微问题，无用户影响 | 本周内 | 工单系统 | 实验性功能错误率偏高、文档链接失效 |

### 级别升级机制

如果事件在预期时间内没有解决，需要自动升级：

```
P1 事件 → 15 分钟未确认 → 升级到 P0
P2 事件 → 2 小时未开始处理 → 升级到 P1
P0 事件 → 30 分钟未解决 → 升级到值班经理
```

## 23.3 事件响应指挥系统（ICS）

### 角色定义

当面临重大事件时，SRE 团队借鉴了消防和应急管理领域的**事件指挥系统（Incident Command System, ICS）**，为技术事件定义了明确的角色分工。

| 角色 | 职责 | 不做的事 | 类比 |
|------|------|---------|------|
| **事件指挥官** | 协调全局、分配任务、管理资源、宣布事件结束 | 不参与具体排查 | 项目经理 |
| **运营负责人** | 技术排查、实施修复方案 | 不分心做通报 | 技术组长 |
| **沟通负责人** | 对内对外信息通报、管理层沟通 | 不参与技术排查 | 新闻发言人 |
| **记录员** | 记录全过程的操作、观察、决策 | 不做决策 | 书记员 |

### 各角色的具体操作

**事件指挥官的操作清单：**

```
1. 宣布事件开始，指定事件级别
2. 分配 ICS 角色（运营负责人、沟通负责人、记录员）
3. 创建事件沟通频道（如 Slack 专用频道）
4. 设定每 15 分钟同步进展的节奏
5. 定期检查恢复进度
6. 判断是否需要升级事件级别
7. 宣布事件结束
```

**运营负责人的操作清单：**

```
1. 确认服务影响范围
2. 查看相关监控、日志和追踪数据
3. 制定排查计划
4. 分配排查任务给团队成员
5. 实施修复方案
6. 验证修复效果
```

**沟通负责人的操作清单：**

```
1. 在事件频道发布初始通告
2. 每 15 分钟向管理层更新进展
3. 向受影响的用户/业务方通报（如需要）
4. 记录关键决策点
5. 事件结束后发布事件总结
```

### 一个场景：ICS 分工

**事件：** 支付服务 P0 宕机。

**事件指挥官（Alice）：**
- "现在是 14:00，支付服务 P0 宕机，我是事件指挥官。"
- "Bob 负责技术排查，Charlie 负责沟通，David 负责记录。"
- "每 15 分钟同步一次进展。"

**运营负责人（Bob）：**
- "我正在查看支付服务的日志。"
- "发现数据库连接池满了。"
- "我正在重启数据库连接池。"
- "连接池已恢复，支付服务正在恢复。我会继续监控。"

**沟通负责人（Charlie）：**
- "[14:00] 支付服务 P0 宕机，正在排查。"
- "[14:05] 发现数据库连接池问题，正在恢复。"
- "[14:10] 连接池已恢复，服务正在逐步恢复正常。"
- "[14:15] 服务已完全恢复。安排了 15:00 的复盘会议。"

## 23.4 On-call 轮值的最佳实践

### 轮值周期

| 周期 | 优点 | 缺点 |
|------|------|------|
| 1 周 | 疲劳度适中，交接频率合理 | 轮值频率较高 |
| 2 周 | 轮值频率较低 | 疲劳积累较多 |
| 1 个月 | 轮值频率最低 | 疲劳积累严重，不推荐 |

**推荐：** 1 周轮值，团队 5 人以上时每人每 5-6 周轮值一周。

### 主备机制

```
主 On-call → 处理所有告警
备 On-call → 主 On-call 忙时接手
             主 On-call 处理事件时接手新的告警
```

### 疲劳管理

- 夜间被叫醒处理 P0/P1 事件后，第二天补休
- 连续 3 天夜间被叫醒，应安排人替换
- On-call 期间不安排重要会议

### On-call 交接清单

```
[ ] 本周有哪些告警被触发？
[ ] 是否有未解决的 P2/P3 事件？
[ ] 是否有已知的变更计划？
[ ] 是否有需要关注的系统状态？
[ ] 是否有调试中的排查场景？
[ ] 下周是否有已知的大流量事件？
```

## 23.5 事件通知渠道

| 事件级别 | 通知方式 | 说明 |
|---------|---------|------|
| P0 | 电话/PagerDuty | 确保立即被唤醒 |
| P1 | Slack 强提醒 | 实时通知，15 分钟内响应 |
| P2 | 邮件/工单 | 当天处理 |
| P3 | 工单系统 | 本周内处理 |

---

## 23.6 事件响应检查清单

### 启动检查

收到 P0/P1 告警时，按以下顺序操作：

```
[ ] 1. 确认告警真实性——不是误报
[ ] 2. 查看影响范围——多少用户？哪些功能？
[ ] 3. 检查 GCP Status Dashboard——是否是 GCP 自身问题？
[ ] 4. 确认事件级别——P0 还是 P1？
[ ] 5. 启动 ICS——分配角色
[ ] 6. 开始排查——按照 Runbook 推进
[ ] 7. 记录所有操作——时间、操作、结果
```

### 结束检查

宣布事件结束前：

```
[ ] 服务是否完全恢复？SLO 指标回到正常范围？
[ ] 临时修复是否已转换为长期修复或已排期？
[ ] 事件时间线是否完整记录？
[ ] 是否已通知相关方（管理层、业务方、用户）？
[ ] 是否已安排复盘会议？
```
