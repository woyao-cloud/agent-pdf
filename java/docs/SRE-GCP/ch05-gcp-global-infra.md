# 第 5 章 GCP 的全球基础设施布局

## 5.1 为什么理解 GCP 基础设施很重要？

### 一个故事：单区域部署的教训

某创业公司将其全部服务部署在 GCP 的 `us-central1`（美国中部）区域。他们的用户主要在美国，所以这个选择看起来没什么问题。

一天下午，`us-central1` 的一个可用区（Zone）因为电力故障导致部分服务宕机。由于他们的所有实例都集中在这个 Zone 中，整个服务中断了 45 分钟。

事后复盘时，团队发现：如果当初把实例分布到 `us-central1` 的多个 Zone 中，这次故障根本不会影响服务——其他 Zone 的实例会继续运行。

这个教训的代价是：**45 分钟的服务中断 + 数千美元的损失 + 用户信任的下降。**

### 基础设施知识是架构设计的基础

在 GCP 上设计高可用架构之前，你需要先理解 GCP 的物理基础设施是如何组织的。就像盖房子之前要先了解地基一样，设计云架构之前要先了解云平台的基础设施布局。

## 5.2 Region、Zone 和 Edge 节点

GCP 的基础设施分为三个层次，从大到小依次是：**Region（区域）**、**Zone（可用区）** 和 **Edge（边缘节点）**。

### Region（区域）

Region 是 GCP 资源部署的基本地理单位。每个 Region 是一个独立的地理位置，包含一个或多个物理数据中心。

**关键特性：**

- 每个 Region 之间在物理上完全隔离——电力、网络、冷却系统都是独立的
- Region 之间通过 Google 的全球光纤网络连接，延迟低、带宽充裕
- 不同 Region 之间的网络流量会产生数据传输费用

**截至 2025 年，GCP 在全球拥有 40 多个 Region，分布情况：**

| 大洲 | 代表 Region | 数量 |
|------|------------|------|
| 北美洲 | us-central1, us-east1, us-west1 | 10+ |
| 南美洲 | southamerica-east1 | 2 |
| 欧洲 | europe-west1, europe-west4 | 10+ |
| 亚洲 | asia-east1, asia-northeast1 | 10+ |
| 澳洲 | australia-southeast1 | 2 |
| 中东 | me-central1 | 2 |
| 非洲 | africa-south1 | 1 |

**选择 Region 的考虑因素：**

1. **用户位置**：选择离用户最近的 Region，降低延迟
2. **合规要求**：某些行业要求数据必须存储在特定国家或地区
3. **服务可用性**：某些 GCP 服务只在部分 Region 可用
4. **成本**：不同 Region 的资源价格可能不同
5. **冗余需求**：多 Region 部署需要至少 2 个 Region

### Zone（可用区）

Zone 是 Region 内部的细分。每个 Region 包含**至少三个 Zone**，它们是相互独立的物理数据中心。

**关键特性：**

- Zone 之间在电力、网络、冷却系统上完全隔离
- 一个 Zone 的故障不会影响到同 Region 内的其他 Zone
- Zone 之间的网络延迟极低（通常 < 1ms）
- Zone 之间的流量不产生数据传输费用

**Zone 的命名规则：**

```
us-central1-a  # us-central1 区域的 a 可用区
us-central1-b  # us-central1 区域的 b 可用区
us-central1-c  # us-central1 区域的 c 可用区
us-central1-f  # us-central1 区域的 f 可用区
```

**注意：** Zone 的字母标识（a、b、c 等）在不同的 GCP 项目中可能对应不同的物理数据中心。这是 GCP 的设计——防止某个 Zone 故障时，所有项目都同时受到影响。

### Edge（边缘节点）

Edge 节点是 GCP 分布在全球的 PoP（Point of Presence，接入点），数量超过 **200 个**。

**关键特性：**

- 边缘节点的作用是把用户的流量从最近的位置接入 Google 的网络
- Cloud CDN、Cloud Load Balancing 等服务都会利用边缘节点来加速用户的访问
- 边缘节点不运行你的应用代码，只负责网络加速和缓存

**边缘节点的工作方式：**

```
用户 → 最近的 Edge 节点 → Google 骨干网 → 目标 Region → 后端服务
```

## 5.3 GCP 的网络连接优势

### Google 的私有光纤网络

GCP 的一个关键优势是其网络基础设施。Google 拥有世界上最大的私有光纤网络之一，连接着全球的数据中心。

**这意味着什么？**

当你通过 Cloud Load Balancing 对外提供服务时，用户的请求会从离他最近的边缘节点进入 Google 网络，然后通过 Google 的高速骨干网传输到你的后端服务所在的 Region。

**你的用户并不会直接通过公共互联网访问你的服务——他们走的是 Google 的"私有高速公路"。**

### 网络延迟对比

| 连接方式 | 延迟（纽约到伦敦） | 说明 |
|---------|-----------------|------|
| 公共互联网 | ~80ms | 经过多个 ISP 网络 |
| Google 骨干网 | ~50ms | 全程在 Google 私有网络内 |
| 专线（Cloud Interconnect） | ~45ms | 物理专线直连 |

### 对 SRE 的实际意义

1. **全球用户体验更一致**：无论用户在哪里，都能通过最近的边缘节点快速接入
2. **延迟更可预测**：Google 骨干网的延迟波动远小于公共互联网
3. **故障隔离更好**：边缘节点故障不会影响后端服务，流量会自动路由到其他边缘节点

## 5.4 "跨区域"思维的重要性

### 一个常见的架构陷阱

很多团队在起步时因为成本原因只在单个 Region 部署。这种做法本身没有问题——但问题在于，他们往往把架构设计成了"只能单 Region 运行"的形式。

当业务增长需要扩展到多区域时，发现架构不支持，需要重新设计。这种"重来"的成本远高于一开始就做好规划。

### 好的做法：预留跨区域能力

即使只在单个 Region 部署，也在架构上预留跨区域的能力：

| 架构决策 | 单 Region 做法 | 预留跨区域能力的做法 |
|---------|--------------|-------------------|
| 负载均衡 | 区域负载均衡器 | 全局负载均衡器（即使只配一个 Region） |
| 存储 | 区域级存储 | 多区域/双区域存储 |
| 数据库 | 单实例 | 配置好只读副本的扩展路径 |
| DNS | 简单 A 记录 | Cloud DNS 托管区域 |
| 网络 | 默认 VPC | 规划好 IP 地址空间，预留扩展 |

### 多区域部署的典型架构

```
                    ┌──────────────────┐
                    │  Global Load     │
                    │  Balancer        │
                    └────────┬─────────┘
                            │
            ┌───────────────┼───────────────┐
            │               │               │
    ┌───────┴───────┐ ┌─────┴───────┐ ┌─────┴───────┐
    │  us-central1  │ │ europe-west1│ │asia-east1   │
    │  (Primary)    │ │ (Secondary) │ │(Secondary)  │
    └───────┬───────┘ └─────┬───────┘ └─────┬───────┘
            │               │               │
    ┌───────┴───────┐ ┌─────┴───────┐ ┌─────┴───────┐
    │ Zone a,b,c    │ │ Zone a,b,c  │ │ Zone a,b,c  │
    │ GKE Cluster   │ │ GKE Cluster │ │ GKE Cluster │
    │ Cloud SQL     │ │ Cloud SQL   │ │ Cloud SQL   │
    │ (Primary)     │ │ (Replica)   │ │ (Replica)   │
    └───────────────┘ └─────────────┘ └─────────────┘
```

## 5.5 一个场景：全球部署的延迟优化

### 背景

某游戏公司为全球用户提供在线游戏服务。用户分布在美国、欧洲和亚洲。最初，所有服务都部署在 `us-west1`（美国西部）。

### 问题

欧洲玩家反馈游戏延迟很高，平均在 200ms 以上。亚洲玩家的延迟更高，达到 300ms。

### 分析

```
用户位置 → 最近的 Edge → 骨干网 → us-west1 → 总延迟
美国西海岸: 5ms + 2ms = 7ms
美国东海岸: 30ms + 60ms = 90ms
欧洲: 5ms + 140ms = 145ms
亚洲: 10ms + 160ms = 170ms
```

问题在于：所有流量都要传输到 `us-west1`，距离越远的用户延迟越高。

### 解决方案

团队决定采用多区域部署：

1. 在 `us-west1`（美洲）、`europe-west1`（欧洲）、`asia-east1`（亚洲）各部署一套服务
2. 使用全局 HTTP(S) 负载均衡器，将用户流量路由到最近的 Region
3. 使用 Cloud Spanner 实现全球数据一致性

### 优化后

```
用户位置 → 最近的 Region → 总延迟
美国西海岸: us-west1 = 7ms
美国东海岸: us-west1 = 90ms
欧洲: europe-west1 = 20ms
亚洲: asia-east1 = 15ms
```

欧洲玩家延迟从 200ms+ 降到了 20ms，亚洲玩家从 300ms+ 降到了 15ms。

### 成本

多区域部署的成本比单区域高出约 2.5 倍，但换来了全球用户的一致体验。对于面向全球用户的业务来说，这笔投入是值得的。

## 5.6 反模式：基础设施布局中的常见错误

### 反模式一：所有资源放在一个 Zone

**表现**：所有虚拟机、数据库、缓存都放在同一个 Zone 中。

**后果**：该 Zone 发生故障时，整个服务中断。虽然 Zone 故障的概率不高，但一旦发生就是灾难性的。

**正确的做法**：至少将资源分布到同一个 Region 的 2-3 个 Zone 中。对于关键服务，考虑多 Region 部署。

### 反模式二：选择 Region 只看价格

**表现**：选择最便宜的 Region 部署所有服务，不考虑用户位置和延迟。

**后果**：远离用户的 Region 导致高延迟，用户体验差。

**正确的做法**：选择离用户最近的 Region。如果用户分布在全球，考虑多 Region 部署。

### 反模式三：忽略 Region 的服务可用性

**表现**：选择了一个 Region，但发现需要的 GCP 服务在该 Region 不可用。

**后果**：无法使用某些 GCP 服务，或者需要使用替代方案，增加复杂度。

**正确的做法**：在选择 Region 之前，先确认你需要的 GCP 服务在该 Region 是否可用。GCP 官方文档提供了各 Region 的服务可用性列表。

### 反模式四：没有考虑数据引力

**表现**：计算资源和数据存储分布在不同的 Region 中。

**后果**：每次数据访问都要跨 Region 传输，延迟高、成本高。

**正确的做法**：将计算资源和数据存储在同一个 Region 中。如果必须跨 Region，使用缓存或 CDN 来减少跨 Region 的数据传输。

## 5.7 速查总结

### GCP 基础设施层次速查

| 层次 | 范围 | 故障隔离 | 延迟 | 用途 |
|------|------|---------|------|------|
| Edge | 全球 200+ 节点 | 独立 | 最低 | 网络加速、CDN 缓存 |
| Region | 地理区域 | 独立 | 低 | 资源部署的基本单位 |
| Zone | Region 内 | 独立 | 极低 | 高可用部署 |

### Region 选择检查清单

- [ ] 用户主要分布在哪些地区？
- [ ] 是否有数据驻留的合规要求？
- [ ] 需要的 GCP 服务在该 Region 是否可用？
- [ ] 该 Region 的资源价格是否在预算范围内？
- [ ] 是否需要多 Region 部署？
- [ ] 数据存储和计算资源是否在同一个 Region？

### 跨区域架构设计原则

| 原则 | 说明 |
|------|------|
| 从单区域开始，但预留跨区域能力 | 使用全局负载均衡器、多区域存储 |
| 至少跨 2-3 个 Zone | 防止单 Zone 故障导致服务中断 |
| 计算和存储放在同一 Region | 避免跨 Region 数据传输的延迟和成本 |
| 关键服务考虑多 Region | 核心业务至少部署在 2 个 Region |
| 使用全局负载均衡器 | 即使只配一个 Region，也为未来扩展预留 |
