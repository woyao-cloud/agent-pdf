# 第 3 章 错误预算：风险管理的艺术

## 3.1 错误预算的概念

### 一个类比：孩子的零花钱

想象一下，你每周给孩子 100 元零花钱。这笔钱他可以自由支配——买零食、买玩具、打游戏。但有一个规则：**花完就没有了**，不会提前预支下周的。

如果孩子这周只花了 30 元，那剩下的 70 元他可以存起来，下周有更多的钱可以花。但如果他在周一就把 100 元全花光了，那这周剩下的几天他就没钱了——只能省着点。

**错误预算（Error Budget）** 的逻辑完全一样。

### 错误预算的定义

你设定了一个 SLO，比如 99.9% 的可用性。这意味着你允许有 **0.1% 的不可用时间**。这 0.1% 就是你拥有的"错误预算"。

**计算公式：**

```
错误预算 = 总时间 × (1 - SLO)
```

**具体计算：**

| SLO | 月错误预算（30 天） | 年错误预算 |
|-----|-------------------|-----------|
| 99% | 7.2 小时 | 87.6 小时 |
| 99.9% | 43.2 分钟 | 8.76 小时 |
| 99.99% | 4.3 分钟 | 52.6 分钟 |
| 99.999% | 25.9 秒 | 5.26 分钟 |

**一个具体的例子：**

你的服务 SLO 是 99.9%（月可用性）。一个月有 43,200 分钟（30 天 × 24 小时 × 60 分钟）。

```
错误预算 = 43,200 × (1 - 0.999) = 43,200 × 0.001 = 43.2 分钟
```

这意味着，在这个月内，你的服务最多可以不可用 43.2 分钟。超过这个时间，你就违反了 SLO。

### 错误预算的消耗

错误预算的消耗不是简单地按故障时长计算的。你需要跟踪的是**所有导致 SLI 下降的事件**的累积效果：

- 服务完全不可用 5 分钟 → 消耗 5 分钟预算
- 服务延迟超过 SLO 阈值，虽然没宕机但体验下降 → 按比例消耗预算
- 部分用户受到某个区域故障影响 → 按受影响用户比例消耗预算
- 单个功能模块出错 → 按功能重要性比例消耗预算

**在 Cloud Monitoring 中**，错误预算的消耗是自动计算的。你只需要配置好 SLO，系统会实时跟踪消耗情况。

---

## 3.2 错误预算的两种用途

错误预算最聪明的地方在于：它把**可靠性**和**创新速度**统一到了一个框架中。

### 当错误预算充足时

**说明系统运行得很稳定，几乎没有消耗预算。**

这时候团队应该**加大创新力度**：
- 发布新功能
- 做架构升级
- 进行实验性操作
- 尝试新的技术方案

因为即使这些操作带来一些风险，你也有足够的预算来承受。

### 当错误预算即将耗尽时

**说明系统已经出了问题，消耗了大量预算。**

这时候团队应该**优先处理可靠性问题**：
- 冻结新功能发布
- 排查根本原因
- 加固系统薄弱环节
- 回滚有风险的变更

你的首要任务不再是推出新功能，而是防止错误预算耗尽。

### 这个机制解决了什么矛盾？

SRE 团队和开发团队之间有一个长期存在的矛盾：

- **开发团队**：想快速上线新功能
- **SRE 团队**：担心新功能会破坏系统稳定性

在没有错误预算机制的组织中，这种矛盾往往演变成"SRE 说不能上线，开发和产品说必须上线"的拉锯战。决策取决于"谁嗓门大"或者"谁的级别高"。

有了错误预算，决策变得简单：

> **预算还有吗？有，那就上线。没有了，那就先不上了。**

这个决策不再依赖于"SRE 不信任开发"或者"开发不理会 SRE"的情绪化判断，而是基于一个**客观、透明的数字**。

## 3.3 一个完整场景：错误预算指导上线决策

### 背景

某社交平台，SLO 为 99.9%（月可用性），月错误预算为 43.2 分钟。

### 时间线

**6 月 1 日**：月初，错误预算重置为 43.2 分钟。团队按计划发布了新版本，一切正常。

**6 月 10 日**：错误预算消耗了 5 分钟（约 12%），剩余 38.2 分钟。消耗速度正常。

**6 月 15 日**：数据库迁移导致了一次 15 分钟的服务降级。错误预算消耗了 20 分钟（累计 46%），剩余 23.2 分钟。

**6 月 18 日**：开发团队说新功能已经测试完了，这个功能对业务很重要，需要本周上线。

### 决策过程

SRE 团队查看错误预算仪表盘：

```
当前日期：6 月 18 日
本月错误预算：43.2 分钟
已消耗：20 分钟（46%）
剩余：23.2 分钟（54%）
距离月底还有：12 天
当前消耗速度：约 1.1 分钟/天
```

**方案一：正常上线**

如果按当前的消耗速度（1.1 分钟/天），到月底还会消耗约 13 分钟。加上已消耗的 20 分钟，总计 33 分钟。剩余预算 10.2 分钟——在 SLO 范围内。

但新功能上线可能带来额外的风险。如果上线后导致额外的 10 分钟故障，总消耗将达到 43 分钟——几乎耗尽全部预算。

**方案二：暂缓上线**

暂缓上线，先用两周时间进行额外的压力测试和代码审查。等 7 月 1 日预算重置后再上线。

**决策结果：**

团队决定暂缓上线。不是因为"SRE 不信任开发"，而是因为数据表明：在当前预算消耗速度下，新功能带来的额外风险可能导致 SLO 违反。

这个决策被记录在案，并通知了产品经理。产品经理虽然有些失望，但理解了决策的依据——**不是"不能上"，而是"现在不是最好的时机"**。

### 后续

7 月 1 日，错误预算重置。团队在 7 月 3 日成功上线了新功能，没有出现任何问题。

## 3.4 在 Cloud Monitoring 中配置错误预算告警

### 第一步：创建 SLO

在 Cloud Monitoring 中，你可以为每个服务创建 SLO：

```
1. 进入 Cloud Monitoring → SLO
2. 点击 "Create SLO"
3. 选择服务（GKE、Compute Engine 或自定义服务）
4. 选择 SLI 类型（可用性、延迟等）
5. 设定目标值（如 99.9%）
6. 选择时间窗口（如 30 天滚动窗口）
```

### 第二步：配置错误预算燃烧率告警

Google SRE 团队推荐使用**燃烧率告警**（Burn Rate Alert）而不是传统的阈值告警。燃烧率告警关注的是"错误预算消耗的速度"，而不是"当前指标是否超过阈值"。

**燃烧率的概念：**

```
燃烧率 = 实际消耗速度 / 预期消耗速度
```

- 燃烧率 = 1：消耗速度与预期一致
- 燃烧率 > 1：消耗速度比预期快
- 燃烧率 < 1：消耗速度比预期慢

**告警配置示例：**

```yaml
# Cloud Monitoring 告警策略配置
# 快速燃烧告警：2 小时内消耗 10% 的错误预算
alert:
  name: "error-budget-burn-rate-fast"
  condition:
    type: "burn_rate"
    threshold: 10  # 燃烧率 > 10
    window: 2h     # 2 小时窗口
    budget_percent: 10  # 消耗了 10% 的预算
  notification:
    channel: "pagerduty"
    severity: "P1"

# 慢速燃烧告警：6 小时内消耗 10% 的错误预算
alert:
  name: "error-budget-burn-rate-slow"
  condition:
    type: "burn_rate"
    threshold: 3.3  # 燃烧率 > 3.3
    window: 6h      # 6 小时窗口
    budget_percent: 10  # 消耗了 10% 的预算
  notification:
    channel: "slack"
    severity: "P2"
```

**为什么用燃烧率告警？**

传统的阈值告警（如"CPU > 80%"）的问题是：你不知道这个告警有多紧急。CPU 80% 可能意味着系统即将崩溃，也可能只是正常的波动。

燃烧率告警直接告诉你：**错误预算正在以危险的速度消耗。** 即使当前指标还没有超过阈值，但如果消耗速度很快，说明问题正在发生，需要立即关注。

### 第三步：创建错误预算仪表盘

在 Cloud Monitoring 中创建一个错误预算仪表盘，包含以下信息：

```
┌─────────────────────────────────────────────┐
│  错误预算仪表盘 - 支付服务                   │
├─────────────────────────────────────────────┤
│  SLO: 99.9% 可用性                          │
│  时间窗口: 30 天滚动                         │
│                                              │
│  剩余预算: 23.2 分钟 (54%)  ████████░░░░    │
│  已消耗: 20 分钟 (46%)                       │
│                                              │
│  燃烧率 (1h): 1.2  ✅ 正常                   │
│  燃烧率 (6h): 0.8  ✅ 正常                   │
│  燃烧率 (24h): 1.1  ✅ 正常                  │
│                                              │
│  预计耗尽时间: 7 月 2 日                     │
│  当前日期: 6 月 18 日                        │
└─────────────────────────────────────────────┘
```

## 3.5 错误预算耗尽后的行动

当错误预算耗尽时，SRE 团队需要启动一系列行动：

### 行动一：发布冻结

停止所有非关键的新功能发布。只有以下类型的变更可以继续：
- 安全补丁
- 紧急故障修复
- 与恢复可靠性直接相关的变更

### 行动二：根因分析

找出消耗错误预算的根本原因：
- 是哪个服务或组件消耗了最多的预算？
- 是什么类型的故障导致的？
- 是代码问题、配置问题还是基础设施问题？

### 行动三：优先级调整

将团队精力从"开发新功能"转向"提高系统可靠性"：
- 修复已知的 bug 和性能问题
- 加固系统薄弱环节
- 增加自动化测试覆盖
- 改进监控和告警

### 行动四：资源投入

评估是否需要增加资源投入来改善服务稳定性：
- 是否需要增加冗余？
- 是否需要升级硬件？
- 是否需要增加人力？

### 行动五：复盘

在服务恢复稳定后，进行一次完整的复盘：
- 为什么错误预算会耗尽？
- 哪些措施有效？哪些无效？
- 如何防止类似情况再次发生？

## 3.6 反模式：错误预算实践中的常见错误

### 反模式一：错误预算耗尽后无视

**表现**：错误预算已经耗尽了，但团队仍然继续发布新功能。"这个功能很重要，不能等"、"就这一次，不会有问题的"。

**后果**：错误预算机制失去了意义。团队回到了"凭感觉做决策"的模式。下一次故障发生时，没有预算可以承受。

**正确的做法**：严格执行错误预算规则。如果确实有紧急功能需要上线，走例外审批流程——让更高层级的管理者来承担这个风险决策。

### 反模式二：错误预算永远用不完

**表现**：SLO 定得太低（比如 99%），错误预算非常充裕（每月 7.2 小时），团队几乎永远不会触发发布冻结。

**后果**：错误预算失去了约束力。团队没有动力去改进系统可靠性，因为"反正预算用不完"。

**正确的做法**：SLO 应该有一定的挑战性。如果错误预算从来没有被消耗超过 50%，说明 SLO 可能定得太低了。

### 反模式三：把错误预算当作惩罚工具

**表现**：当错误预算耗尽时，管理层不是去分析根因、改进系统，而是追究责任——"是谁导致了预算耗尽？扣绩效！"

**后果**：团队开始隐瞒问题、不报告故障、不记录事件。错误预算数据变得不准确，失去了指导意义。

**正确的做法**：错误预算是一种风险管理工具，不是惩罚机制。它的目的是帮助团队做出正确的优先级判断，而不是用来追责。

### 反模式四：只关注一个时间窗口

**表现**：团队只关注 30 天滚动窗口的错误预算，忽略了更长时间的趋势。

**后果**：可能错过一些慢性的可靠性问题——比如错误预算每个月都在缓慢消耗，但从来没有在 30 天内耗尽。长期来看，系统的可靠性在持续下降。

**正确的做法**：同时关注多个时间窗口——7 天、30 天、90 天。短窗口用于发现急性问题，长窗口用于发现慢性问题。

## 3.7 速查总结

### 错误预算速查表

| SLO | 月预算 | 年预算 | 适合场景 |
|-----|-------|-------|---------|
| 99% | 7.2 小时 | 87.6 小时 | 内部工具 |
| 99.9% | 43.2 分钟 | 8.76 小时 | 大多数 Web 应用 |
| 99.99% | 4.3 分钟 | 52.6 分钟 | 金融交易 |
| 99.999% | 25.9 秒 | 5.26 分钟 | 关键基础设施 |

### 剩余预算 → 行动决策表

| 剩余预算 | 状态 | 建议行动 |
|---------|------|---------|
| > 80% | 充裕 | 正常发布新功能，可进行实验性操作 |
| 50% - 80% | 正常 | 正常发布，但关注消耗趋势 |
| 20% - 50% | 关注 | 控制发布节奏，优先修复已知问题 |
| < 20% | 危险 | 考虑发布冻结，全力处理可靠性问题 |
| 0% | 耗尽 | 发布冻结，根因分析，全面加固 |

### 燃烧率告警配置参考

| 告警级别 | 燃烧率阈值 | 时间窗口 | 通知方式 | 响应时间 |
|---------|-----------|---------|---------|---------|
| P1 | > 10 | 2 小时 | 电话/PagerDuty | 立即 |
| P2 | > 3.3 | 6 小时 | Slack/即时消息 | 15 分钟 |
| P3 | > 1.5 | 24 小时 | 邮件/工单 | 工作时间 |

### 每周错误预算检查清单

- [ ] 所有核心服务的错误预算剩余量是多少？
- [ ] 是否有服务的燃烧率异常？
- [ ] 本周是否有服务触发了发布冻结？
- [ ] 错误预算消耗的趋势是否正常？
- [ ] 是否需要调整 SLO 或告警配置？
