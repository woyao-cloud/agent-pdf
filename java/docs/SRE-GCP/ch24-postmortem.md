# 第 24 章 无指责事后复盘（Blameless Postmortem）

## 24.1 为什么复盘很重要？

### 一个故事："不是我的错"

一次数据库连接池耗尽导致服务宕机。事后，开发团队说是"SRE 的监控没发现"，SRE 团队说是"开发写的代码有连接泄漏"。

双方互相指责，却没有人问真正重要的问题：
- **为什么代码审查没有发现连接泄露？**
- **为什么没有监控连接池使用率？**
- **为什么连接耗尽时没有自动熔断机制？**

**复盘的核心理念是：** 人是会犯错的，好的系统应该能容忍人的错误。如果一次故障是因为某人执行了一条错误的命令导致的，那么真正的问题是：**为什么系统允许一条错误的命令造成如此严重的后果？**

### 复盘的目的

| 目的 | 不是 |
|------|------|
| 找出系统和流程的薄弱环节 | 找出"谁做错了" |
| 提炼可执行的改进项 | 追究责任 |
| 学习经验教训 | 惩罚 |

## 24.3 复盘的四个关键原则

### 原则一：复盘不是追责会

**表现**：复盘时花大量时间讨论"是谁导致的"。

**后果**：参与复盘的人感到被指责，下次隐瞒信息。

**正确的做法**：聚焦在"系统和流程如何改进"，而非"谁做错了"。

### 原则二：接受"人为错误"是系统设计的一部分

**表现**：认为"如果某人不犯错，事故就不会发生"。

**后果**：只惩罚了人，系统和流程没有任何改进——下次换个人犯同样的错误。

**正确的做法**：思考"是什么让这个错误变得可能"，改进系统而不是惩罚人。

### 原则三：行动项要可执行

```
❌ "加强测试" → 太模糊，无法执行
✅ "为支付模块添加集成测试，覆盖余额不足、超时、重复支付三种异常场景"
```

### 原则四：行动项要闭环

每个行动项必须有：
- 明确的负责人
- 明确的截止日期
- 定期的跟踪进展

## 24.4 5 Whys 根因分析法

### 什么是 5 Whys？

通过连续追问"为什么"，逐步从表面症状深入到根本原因。

### 一个完整的 5 Whys 分析

**问题：** 支付服务宕机 45 分钟。

1. **为什么宕机？** → 数据库连接池耗尽
2. **为什么连接池耗尽？** → 某 API 调用失败后连接没有释放
3. **为什么连接没有释放？** → `finally` 块中没有包含释放连接的代码
4. **为什么代码审查没发现？** → 代码审查清单中不包含"检查资源释放"
5. **为什么清单中没有？** → 团队没有建立代码审查规范

**根因：** 团队缺乏代码审查规范，没有强制要求检查资源释放。

### 5 Whys 的注意事项

- **不要停在"人"身上**："因为某人没检查"不是根因，要继续追问"为什么他没检查"
- **根因通常是流程或系统问题**：95% 的根因是流程或系统问题，不是人的问题
- **可能有多个根因**：不是只有一个"为什么"的答案
