# 第 4 章 琐事（Toil）：SRE 最大的敌人

## 4.1 什么是琐事？

### 一个故事：运维的"日常"

小张是某公司的运维工程师。每天早上到公司的第一件事，就是查看监控系统——看看昨晚有没有出问题。然后处理前一天的工单——有人申请开通数据库权限，有人需要创建新的虚拟机，有人报告某个服务访问不了。

处理完这些，已经快中午了。下午开始处理告警——磁盘空间不足的、服务重启的、证书即将过期的。一天下来，小张发现自己什么"正事"都没干——没有写自动化脚本，没有优化系统架构，没有做任何能提升系统可靠性的工作。

**第二天，同样的事情重复一遍。**

这就是琐事（Toil）的典型表现。

### 琐事的定义

Google SRE 团队对琐事的定义是：**重复性的、手动的、可被自动化的、与系统长期价值无关的运维操作。**

琐事有以下几个特征：

| 特征 | 说明 | 例子 |
|------|------|------|
| **重复性** | 你反复做同样的事情 | 每周都要手动清理磁盘 |
| **手动性** | 需要人工操作，没有自动化 | 手动点击控制台创建资源 |
| **可自动化** | 理论上可以用代码完成 | 写个脚本自动清理过期数据 |
| **无长期价值** | 做完这次，下次还要做 | 重启服务只是临时缓解，没有修复根因 |
| **与规模线性相关** | 系统规模越大，琐事越多 | 100 台服务器比 10 台需要更多的重启操作 |

### 琐事 vs 工程工作

| 维度 | 琐事（Toil） | 工程工作（Engineering） |
|------|-------------|----------------------|
| 性质 | 重复性操作 | 创造性工作 |
| 价值 | 短期维持 | 长期提升 |
| 可扩展性 | 与规模线性相关 | 与规模无关（一次解决一类问题） |
| 成就感 | 低 | 高 |
| 学习价值 | 低 | 高 |

### 典型的琐事清单

**基础设施类：**
- 手动创建云资源（每次都要点很多次鼠标）
- 手动配置 DNS 记录
- 手动轮转证书
- 手动清理未挂载的磁盘
- 手动调整资源规格

**运维操作类：**
- 手动重启宕机的服务
- 手动清理磁盘空间
- 手动处理重复的告警
- 手动部署应用
- 手动回滚有问题的版本

**管理类：**
- 手动审批权限申请
- 手动更新文档
- 手动回复重复的咨询问题
- 手动整理账单和成本数据

## 4.2 琐事的量化

### 50% 黄金法则

Google SRE 团队提出的一个黄金法则是：

> **SRE 团队处理琐事的时间不应超过 50%。**

如果团队超过半数的精力都花在了琐事上，说明团队没有践行 SRE 的方法论，而是退回了传统运维的救火模式。

### 如何量化琐事？

**方法一：自我估算**

每周结束时，让团队每个成员估算自己花在琐事上的时间比例。持续跟踪几周，取平均值。

**示例：**

```
团队成员 A：本周 40% 琐事
团队成员 B：本周 55% 琐事
团队成员 C：本周 70% 琐事
团队平均：55% 琐事 → 超过 50% 警戒线
```

**方法二：时间日志**

花一周时间，让团队成员详细记录每天的工作内容，然后分类统计。

**琐事记录模板：**

```markdown
## 琐事日志 - 团队成员 A
### 周一
| 时间 | 活动 | 类型 | 耗时 |
|------|------|------|------|
| 09:00-09:30 | 查看监控告警 | 琐事 | 30min |
| 09:30-10:00 | 处理工单：开通数据库权限 | 琐事 | 30min |
| 10:00-11:30 | 编写自动扩容脚本 | 工程 | 90min |
| 11:30-12:00 | 手动重启宕机服务 | 琐事 | 30min |
| 14:00-15:00 | 代码审查 | 工程 | 60min |
| 15:00-15:30 | 处理告警：磁盘空间不足 | 琐事 | 30min |
| 15:30-17:00 | 架构设计评审 | 工程 | 90min |

**当日统计：琐事 2h / 工程 4h = 33% 琐事**
```

**方法三：告警统计**

分析告警系统的数据，统计需要人工介入的告警数量和耗时。

```
每周告警统计：
- 总告警数：150 条
- 需要人工处理的：45 条
- 平均处理时间：15 分钟/条
- 每周琐事时间：45 × 15 = 675 分钟 ≈ 11.25 小时
```

### 琐事量化后的行动

如果发现琐事比例超过 50%，团队需要制定一个消除琐事的计划。但要注意：**消除琐事并不意味着它能完全消失。** 琐事就像杂草——你永远无法根除，但可以通过持续的管理来控制和减少。

## 4.3 消除琐事的四步法

### 第一步：记录和分类

花一周时间，记录下团队做的每一件琐事。然后进行分类：

| 类别 | 说明 | 例子 |
|------|------|------|
| 系统性琐事 | 每次都要做的，可预测的 | 每次部署都要手动配置 |
| 偶发性琐事 | 偶尔出现的，不可预测的 | 某个服务偶尔需要重启 |
| 周期性琐事 | 按固定周期出现的 | 每月清理一次日志 |
| 被动性琐事 | 别人找上门来的 | 处理权限申请工单 |

### 第二步：评估自动化可行性

对每一类琐事，评估自动化的成本和收益。

**自动化 ROI 计算公式：**

```
自动化 ROI = (每周耗时 × 52周) / 预计开发时间
```

- ROI > 10：非常值得自动化
- ROI 5-10：值得自动化
- ROI 1-5：可以考虑，但优先级较低
- ROI < 1：不值得自动化

**示例：**

| 琐事 | 每周耗时 | 年耗时 | 预计开发时间 | ROI | 建议 |
|------|---------|-------|------------|-----|------|
| 手动清理磁盘 | 2 小时 | 104 小时 | 8 小时 | 13 | ✅ 立即做 |
| 手动重启服务 | 3 小时 | 156 小时 | 16 小时 | 9.75 | ✅ 立即做 |
| 手动创建 VM | 4 小时 | 208 小时 | 40 小时 | 5.2 | ✅ 做 |
| 手动配置 DNS | 1 小时 | 52 小时 | 40 小时 | 1.3 | ⚠️ 考虑 |
| 手动审批权限 | 0.5 小时 | 26 小时 | 80 小时 | 0.33 | ❌ 不做 |

### 第三步：制定消除计划

按优先顺序制定一个消除琐事的项目清单：

```
优先级 P0（ROI > 10）：本月完成
  - 磁盘自动清理脚本
  - 服务健康检查 + 自动重启

优先级 P1（ROI 5-10）：本季度完成
  - Terraform 模板化资源创建
  - CI/CD 流水线自动化部署

优先级 P2（ROI 1-5）：本年度完成
  - DNS 配置自动化
  - 证书自动轮换

优先级 P3（ROI < 1）：暂不处理
  - 权限审批自动化
```

### 第四步：持续迭代

琐事消除不是一次性的活动。建议：

- **每月**：检查琐事比例是否在 50% 以下
- **每季度**：重新评估琐事清单，更新自动化计划
- **每年**：全面审查琐事消除成果，制定下一年计划

## 4.4 一个完整场景：琐事消除实战

### 背景

某 SaaS 公司的 SRE 团队有 5 人，管理着 200+ 台服务器和 50+ 个微服务。团队感觉"每天都在忙，但不知道在忙什么"。

### 第一步：量化现状

团队花了一周时间记录琐事，结果如下：

| 琐事 | 每周总耗时 | 负责人 |
|------|----------|--------|
| 手动部署服务 | 20 小时 | 全员 |
| 处理磁盘告警 | 10 小时 | 小张 |
| 手动创建云资源 | 8 小时 | 小李 |
| 处理权限申请 | 5 小时 | 小王 |
| 手动重启服务 | 5 小时 | 全员 |
| 其他琐事 | 7 小时 | 全员 |
| **琐事总计** | **55 小时** | |
| **团队总工时** | **200 小时（5人×40h）** | |
| **琐事比例** | **27.5%** | |

27.5% 的琐事比例看起来不高，但团队的目标是降到 15% 以下。

### 第二步：制定自动化计划

团队评估了每项琐事的自动化方案：

| 琐事 | 自动化方案 | 开发时间 | ROI | 优先级 |
|------|-----------|---------|-----|--------|
| 手动部署 | CI/CD 流水线 | 40 小时 | 26 | P0 |
| 磁盘告警 | 自动清理 + 扩容策略 | 8 小时 | 65 | P0 |
| 手动创建资源 | Terraform 模板 | 40 小时 | 10.4 | P0 |
| 权限申请 | 自服务门户 | 80 小时 | 3.25 | P2 |
| 手动重启 | 健康检查 + 自动恢复 | 16 小时 | 16.25 | P0 |

### 第三步：执行

**第 1-2 周：** 完成磁盘自动清理脚本和自动扩容策略配置。磁盘告警从每周 10 小时降到了 1 小时。

**第 3-6 周：** 搭建 CI/CD 流水线。部署从手动操作变成了"提交代码 → 自动构建 → 自动部署"。部署时间从每周 20 小时降到了 2 小时（主要是审查和监控）。

**第 7-10 周：** 编写 Terraform 模板，将常用的资源创建流程模板化。资源创建从每周 8 小时降到了 1 小时。

**第 11-12 周：** 配置健康检查和自动恢复机制。服务重启从每周 5 小时降到了接近 0。

### 第四步：成果

3 个月后：

| 琐事 | 自动化前 | 自动化后 | 节省 |
|------|---------|---------|------|
| 手动部署 | 20 小时/周 | 2 小时/周 | 18 小时 |
| 磁盘告警 | 10 小时/周 | 1 小时/周 | 9 小时 |
| 手动创建资源 | 8 小时/周 | 1 小时/周 | 7 小时 |
| 手动重启 | 5 小时/周 | 0.5 小时/周 | 4.5 小时 |
| **总计** | **43 小时/周** | **4.5 小时/周** | **38.5 小时** |

琐事比例从 27.5% 降到了 **5% 以下**。团队释放出来的时间投入到了更有价值的工作中——性能优化、架构升级、安全加固。

## 4.5 一个具体的自动化脚本示例

### 场景：自动清理未挂载的磁盘

在 GCP 中，当虚拟机实例被删除时，其持久化磁盘往往没有被自动清理。这些"孤儿磁盘"会持续产生存储费用。

**Python 自动化脚本：**

```python
#!/usr/bin/env python3
"""
自动清理 GCP 中未挂载的磁盘（孤儿磁盘）
使用前请先通过 gcloud auth application-default login 认证
"""

import google.auth
from google.cloud import compute_v1

def list_unattached_disks(project_id):
    """列出所有未挂载到任何实例的磁盘"""
    disks_client = compute_v1.DisksClient()
    
    # 获取所有区域的所有磁盘
    request = compute_v1.AggregatedListDisksRequest()
    request.project = project_id
    
    unattached_disks = []
    
    for zone, disks_in_zone in disks_client.aggregated_list(request=request):
        if disks_in_zone.disks:
            for disk in disks_in_zone.disks:
                # 检查磁盘是否未挂载
                if not disk.users:
                    unattached_disks.append({
                        'name': disk.name,
                        'zone': zone.replace('zones/', ''),
                        'size_gb': disk.size_gb,
                        'type': disk.type,
                        'created': disk.creation_timestamp,
                    })
    
    return unattached_disks

def delete_disk(project_id, zone, disk_name, dry_run=True):
    """删除指定的磁盘"""
    if dry_run:
        print(f"[DRY RUN] 将删除磁盘: {disk_name} (区域: {zone})")
        return True
    
    disks_client = compute_v1.DisksClient()
    request = compute_v1.DeleteDiskRequest()
    request.project = project_id
    request.zone = zone
    request.disk = disk_name
    
    try:
        operation = disks_client.delete(request=request)
        operation.result()  # 等待操作完成
        print(f"✅ 已删除磁盘: {disk_name}")
        return True
    except Exception as e:
        print(f"❌ 删除磁盘失败 {disk_name}: {e}")
        return False

def main():
    project_id = "your-project-id"  # 替换为你的项目 ID
    
    print(f"正在扫描项目 {project_id} 中的未挂载磁盘...")
    unattached = list_unattached_disks(project_id)
    
    if not unattached:
        print("🎉 没有发现未挂载的磁盘！")
        return
    
    print(f"\n发现 {len(unattached)} 个未挂载的磁盘：")
    print(f"{'名称':<40} {'区域':<20} {'大小(GB)':<10} {'创建时间'}")
    print("-" * 80)
    
    total_size = 0
    for disk in unattached:
        print(f"{disk['name']:<40} {disk['zone']:<20} {disk['size_gb']:<10} {disk['created']}")
        total_size += disk['size_gb']
    
    print(f"\n总计可释放空间: {total_size} GB")
    
    # 确认后删除
    confirm = input(f"\n是否删除这 {len(unattached)} 个磁盘？(yes/no): ")
    if confirm.lower() == 'yes':
        for disk in unattached:
            delete_disk(project_id, disk['zone'], disk['name'], dry_run=False)
        print("清理完成！")
    else:
        print("已取消。")

if __name__ == "__main__":
    main()
```

**使用方式：**

```bash
# 安装依赖
pip install google-cloud-compute

# 先以 dry-run 模式运行，查看哪些磁盘会被清理
python cleanup_unattached_disks.py

# 确认无误后，修改脚本中的 dry_run=False 或直接删除 dry_run 参数
```

## 4.6 反模式：琐事管理中的常见错误

### 反模式一：琐事太多但不去自动化

**表现**：团队每天忙得不可开交，但就是"没时间"做自动化。"等忙完这阵子再写脚本"——但这阵子永远忙不完。

**后果**：琐事越来越多，团队越来越疲惫，系统越来越不稳定。陷入恶性循环。

**正确的做法**：**停下来，先做自动化。** 即使这意味着短期内琐事会堆积，但长期来看是值得的。记住：花 8 小时写一个脚本，可能为你节省每周 2 小时——一个月就回本了。

### 反模式二：追求完美的自动化

**表现**：团队花了很多时间开发一个"完美"的自动化工具，覆盖了所有可能的场景和异常情况。但这个工具开发了 3 个月还没上线。

**后果**：在工具开发期间，团队一直在手动处理琐事。如果先做一个"80% 完美"的工具，团队可以提前 2 个月开始受益。

**正确的做法**：**先做一个能用的版本，然后持续迭代。** 80% 的自动化比 100% 的手动操作好得多。

### 反模式三：自动化后就不管了

**表现**：团队写了一个自动化脚本，运行了几个月，效果很好。然后就没有然后了——没有人维护，没有人更新。半年后，环境变了，脚本跑不通了。

**后果**：自动化工具变成了"一次性工具"，团队又回到了手动操作的状态。

**正确的做法**：自动化工具也需要维护。把自动化脚本纳入版本管理，定期检查和更新。就像对待生产代码一样对待自动化工具。

### 反模式四：把琐事当作"学习机会"

**表现**：团队 leader 说："让新人手动操作几次，可以帮他们了解系统。"

**后果**：新人确实了解了系统，但也养成了手动操作的习惯。而且，如果手动操作是了解系统的唯一方式，说明系统的文档和可观测性做得不够好。

**正确的做法**：通过文档、架构图、演练环境来帮助新人了解系统，而不是通过手动操作生产环境。

## 4.7 速查总结

### 琐事识别速查表

| 问题 | 如果是"是"，就是琐事 |
|------|-------------------|
| 这个操作需要手动完成吗？ | ✅ 是 |
| 这个操作你做过 3 次以上了吗？ | ✅ 是 |
| 这个操作可以用代码完成吗？ | ✅ 是 |
| 做完这次，下次还要做吗？ | ✅ 是 |
| 这个操作有长期价值吗？ | ❌ 否 |

### 自动化 ROI 速查

| ROI | 建议 | 行动 |
|-----|------|------|
| > 10 | 非常值得 | 本月内完成 |
| 5 - 10 | 值得 | 本季度内完成 |
| 1 - 5 | 可以考虑 | 排入 backlog |
| < 1 | 不值得 | 暂不处理 |

### 每周琐事检查清单

- [ ] 本周琐事比例是否低于 50%？
- [ ] 是否有新的琐事出现？
- [ ] 是否有自动化工具需要维护或更新？
- [ ] 本周是否有琐事可以立即自动化？
- [ ] 团队成员的琐事负担是否均衡？
