# 第 2 章 用 SLI/SLO/SLA 量化可靠性

## 2.1 为什么需要量化可靠性？

### 一个常见的对话

想象一下，你是一家电商平台的 SRE 工程师。业务方跑来说：

> "最近网站好像有点慢，能不能提升一下性能？"

这时候你会遇到几个问题：

- **"慢"到底是什么意思？** 是指页面加载慢，还是下单流程慢？是所有人都慢，还是部分用户慢？
- **"有点"是多少？** 是 10% 的用户觉得慢，还是 1% 的用户？是比上周慢了 10%，还是慢了 100%？
- **要提升到什么程度才算"好"？** 是页面要在 1 秒内加载完，还是 3 秒以内就可以？

如果没有量化的指标，所有这些讨论都会变成"我觉得""我认为"的主观判断。SRE 的做法是：**用指标说话**。

### 一个类比：体检报告

想象你去医院做体检。医生不会说"你身体好像有点不太好"——他会给你一份体检报告，上面写着：

- 血压：120/80 mmHg（正常范围）
- 血糖：5.0 mmol/L（正常范围）
- 胆固醇：4.2 mmol/L（正常范围）

有了这些量化数据，你才知道自己的身体到底怎么样，哪些指标需要关注，哪些指标是正常的。

SLI、SLO、SLA 就是系统的"体检报告"。

## 2.2 SLI：服务水平的衡量指标

### 什么是 SLI？

SLI（Service Level Indicator，服务水平指标）是你用来度量服务质量的具体数字。它回答的问题是：**"我们现在服务得好不好？"**

SLI 必须是一个**可测量**的数值。如果你说"用户体验很好"，这不是 SLI。但如果你说"页面加载时间的 P99 是 200ms"，这就是 SLI。

### 常见的 SLI 类型

#### 可用性（Availability）

可用性是最基础也是最核心的 SLI。它衡量的是：**服务是否在正常工作？**

最简单的计算方式：

```
可用性 = 成功的请求数 / 总请求数 × 100%
```

**什么是"成功的请求"？** 这需要你自己定义。通常来说，HTTP 状态码在 200-499 范围内的请求被认为是成功的，500 以上的被认为是失败的。但有些情况下，即使返回了 200，内容可能是错误的（比如返回了空数据或错误信息），这也应该算作失败。

**一个具体的例子：**

某 API 服务在过去 24 小时内收到了 1,000,000 个请求，其中 998,500 个请求成功返回了正确的结果。那么：

```
可用性 = 998,500 / 1,000,000 × 100% = 99.85%
```

#### 延迟（Latency）

延迟衡量的是：**请求处理的速度有多快？**

延迟通常用**分位数**来衡量，而不是平均值。为什么不用平均值？来看一个例子：

假设有 100 个请求，它们的响应时间分别是：
- 99 个请求在 10ms 内完成
- 1 个请求花了 10,000ms（10 秒）

平均延迟 = (99 × 10 + 10,000) / 100 = 109.9ms

看起来还不错，对吧？但实际上，有 1% 的用户体验极差——他们等了 10 秒。

**分位数能更真实地反映用户体验：**

| 分位数 | 含义 | 上例中的值 |
|--------|------|-----------|
| P50（中位数） | 50% 的请求在这个时间内完成 | 10ms |
| P90 | 90% 的请求在这个时间内完成 | 10ms |
| P99 | 99% 的请求在这个时间内完成 | 10ms |
| P99.9 | 99.9% 的请求在这个时间内完成 | 10,000ms |

P99 延迟是 SRE 最常用的延迟指标——它告诉你"绝大多数用户的体验是好的，但最慢的那 1% 用户经历了什么"。

#### 吞吐量（Throughput）

吞吐量衡量的是：**系统单位时间内能处理多少请求？**

```
吞吐量 = 请求总数 / 时间窗口
```

吞吐量通常用于容量规划——你的系统能承受多大的流量？当吞吐量接近上限时，延迟通常会开始恶化。

#### 错误率（Error Rate）

错误率衡量的是：**请求失败的比例？**

```
错误率 = 失败的请求数 / 总请求数 × 100%
```

错误分为两种：
- **显式错误**：HTTP 5xx 状态码、连接超时、请求被拒绝
- **隐式错误**：HTTP 200 但返回的内容是错误的（比如返回了空白的搜索结果）

隐式错误更难检测，通常需要应用层面的监控来发现。

#### 饱和度（Saturation）

饱和度衡量的是：**系统资源被占用的程度？**

常见的饱和度指标包括：
- CPU 使用率
- 内存使用率
- 磁盘 I/O 使用率
- 网络带宽使用率
- 连接池占用率
- 队列深度

饱和度往往是其他指标恶化的**前兆**。当 CPU 使用率持续超过 80% 时，延迟通常开始上升；当连接池使用率达到 90% 时，新的连接请求可能开始被拒绝。

### SLI 的选择原则

**不要试图监控所有指标。** 选择 SLI 的原则是：**选择那些与用户体验直接相关的指标。**

一个好的做法是：针对每个**关键用户旅程**，选择 2-3 个 SLI。比如对于一个电商平台：

| 用户旅程 | SLI |
|---------|-----|
| 搜索商品 | 搜索 API 的可用性、P99 延迟 |
| 浏览详情 | 商品详情页的加载时间 |
| 加入购物车 | 购物车 API 的可用性、错误率 |
| 下单支付 | 下单 API 的可用性、P99 延迟、支付成功率 |

## 2.3 SLO：你承诺的目标值

### 什么是 SLO？

SLO（Service Level Objective，服务水平目标）是你给服务设定的一个**目标值**。它回答的问题是：**"我们希望服务好到什么程度？"**

一个典型的 SLO 长这样：

> 在 30 天的滚动窗口内，服务可用性不低于 **99.9%**，P99 延迟不超过 **200ms**。

### 如何制定 SLO？

#### 第一步：了解当前的基线

在制定 SLO 之前，先收集一段时间的实际数据，了解当前服务的真实表现。你需要回答：

- 当前的可用性是多少？
- 当前的 P99 延迟是多少？
- 当前的错误率是多少？
- 这些指标在高峰期和低峰期有什么变化？

**示例：** 你查看了过去三个月的监控数据，发现可用性在 99.95% 到 99.99% 之间波动，P99 延迟在 150ms 到 250ms 之间。

#### 第二步：与业务方沟通期望

SLO 不是 SRE 团队单方面决定的。你需要和业务方讨论：

- 用户对服务的期望是什么？
- 哪些功能对业务最关键？
- 可以接受的故障时间是多少？
- 可以接受的性能下降程度是多少？

**示例对话：**

> **SRE：** "我们目前可用性在 99.98% 左右，你们觉得什么样的目标比较合理？"
>
> **业务方：** "支付可不能出问题，能不能做到 99.999%？"
>
> **SRE：** "99.999% 意味着年不可用时间只有 5 分钟。要达到这个目标，我们需要做多活部署、跨区域冗余、实时故障切换——这些改造需要 6 个月以上，成本也很高。我建议先定 99.99%，年不可用时间约 52 分钟，这对支付服务来说已经是一个很高的保障级别了。同时我们内部目标设到 99.995%，给自己留出缓冲。"
>
> **业务方：** "52 分钟……可以接受。那就先按 99.99% 来。"

#### 第三步：设定 SLO

基于基线和业务期望，设定 SLO。几个关键原则：

**原则一：SLO 不是越多越好。** 一个服务有 2-3 个 SLO 就足够了。过多的 SLO 会分散团队的注意力。

**原则二：SLO 要有挑战性但可达。** 如果 SLO 定得太低（比如 99%），团队没有动力去改进。如果定得太高（比如 99.999%），团队会疲于奔命。一个好的 SLO 应该是"跳一跳够得着"的水平。

**原则三：SLO 要留出缓冲。** 你的内部目标（SLO）应该比你实际能做到的水平稍微宽松一些。比如你实际能做到 99.99%，那么 SLO 定在 99.95% 是比较合理的。这样即使出现一些意外情况，你仍然在 SLO 范围内。

#### 第四步：持续迭代

SLO 不是一成不变的。随着业务的发展和系统的演进，SLO 也需要定期审视和调整。建议每季度 review 一次 SLO。

### SLO 的常见目标值参考

| 可用性 | 年不可用时间 | 月不可用时间 | 适用场景 |
|--------|-------------|-------------|---------|
| 99%（两个九） | 87.6 小时 | 7.2 小时 | 内部工具、开发环境 |
| 99.9%（三个九） | 8.76 小时 | 43.2 分钟 | 大多数 Web 应用 |
| 99.99%（四个九） | 52.6 分钟 | 4.3 分钟 | 金融交易、在线支付 |
| 99.999%（五个九） | 5.26 分钟 | 25.9 秒 | 电信核心网、关键基础设施 |

**注意：** 每增加一个"九"，成本和复杂度都会大幅增加。从 99.9% 到 99.99%，你可能需要从单区域部署升级到多区域部署，成本可能翻倍甚至更多。

## 2.4 SLA：你对外承诺的合同

### 什么是 SLA？

SLA（Service Level Agreement，服务水平协议）是一个**法律层面的承诺**。当你的服务对外售卖时，合同中会写明：如果你没有达到某个 SLO，你需要向客户提供赔偿。

### SLI、SLO、SLA 三者的关系

用一个简单的图来表示：

```
SLI（实际测量值）→ 与 SLO（目标值）比较 → 是否触发 SLA（合同承诺）
```

**具体来说：**

- **SLI** 是实际测量到的值：比如"过去 30 天可用性测量结果是 99.95%"
- **SLO** 是你内部设定的目标值：比如"我们的目标是 99.99%"
- **SLA** 是你对外承诺的合同值：比如"如果没有达到 99.9%，我们赔偿 10% 的服务费"

### 一个重要的策略：SLA 应该比 SLO 更宽松

你的内部目标（SLO）要比对外承诺（SLA）更严格。这样即使你偶尔达不到 SLO，仍然在 SLA 的范围之内，不会触发赔偿。

**示例：**

| 层级 | 目标值 | 说明 |
|------|--------|------|
| 实际能力 | 99.99% | 系统实际能达到的水平 |
| SLO（内部目标） | 99.95% | 给自己留出缓冲 |
| SLA（对外承诺） | 99.9% | 法律层面的最低保障 |

这样设计的好处是：
- 即使系统出现了一些小问题，可用性从 99.99% 降到了 99.96%，你仍然在 SLO 范围内
- 即使出现了较大的问题，可用性降到了 99.92%，你仍然在 SLA 范围内，不会触发赔偿
- 只有出现严重故障，可用性低于 99.9% 时，才需要启动赔偿流程

## 2.5 一个完整场景：为支付服务制定 SLO

### 背景

你是某支付平台的 SRE 工程师，需要为"支付服务"制定 SLO。支付服务是公司的核心服务，每天处理约 50 万笔交易。

### 第一步：识别关键用户旅程

支付服务的关键用户旅程是：**用户发起支付 → 支付服务处理 → 返回支付结果**。

### 第二步：确定 SLI

针对这个用户旅程，你确定了三个 SLI：

| SLI | 测量方式 | 当前基线 |
|-----|---------|---------|
| 可用性 | 支付 API 成功响应的比例 | 99.98% |
| P99 延迟 | 从收到请求到返回结果的耗时 | 800ms |
| 支付成功率 | 支付成功完成的交易比例 | 99.5% |

### 第三步：与业务方协商

你约了产品经理和业务负责人开会。

**业务方：** "支付服务太重要了，可用性至少要做到 99.999%。"

**你：** "我理解支付的重要性。但 99.999% 意味着一年只能宕机 5 分钟。要达到这个目标，我们需要做多区域部署、实时数据同步、自动故障切换——这些改造至少需要 6 个月，成本也很高。我建议先定 99.99%，一年宕机不超过 52 分钟，这对支付来说已经是非常高的标准了。"

**业务方：** "52 分钟……那延迟呢？现在用户反馈有时候支付要等好几秒。"

**你：** "目前 P99 延迟是 800ms，我们建议 SLO 定在 2 秒。因为支付涉及到外部银行接口，有些银行的响应时间不可控。2 秒的 SLO 给了我们足够的缓冲，同时也能保证绝大多数用户的体验。"

**业务方：** "2 秒可以接受。那支付成功率呢？"

**你：** "目前支付成功率是 99.5%，我们建议 SLO 定在 99%。因为有些支付失败是用户自身的原因（余额不足、输错密码等），这些不是我们系统的问题。"

**业务方：** "同意。"

### 第四步：确定最终的 SLO

经过协商，最终的 SLO 如下：

| SLI | SLO | 说明 |
|-----|-----|------|
| 可用性 | ≥ 99.99%（30 天滚动窗口） | 月不可用时间不超过 4.3 分钟 |
| P99 延迟 | ≤ 2 秒（30 天滚动窗口） | 99% 的支付请求在 2 秒内完成 |
| 支付成功率 | ≥ 99%（30 天滚动窗口） | 排除用户自身原因导致的失败 |

### 第五步：配置监控和告警

SLO 制定完成后，你在 Cloud Monitoring 中配置了对应的告警：

- 当可用性低于 99.995% 时触发警告（提前预警）
- 当可用性低于 99.99% 时触发 P1 告警（SLO 即将违反）
- 当 P99 延迟超过 1.5 秒时触发警告
- 当 P99 延迟超过 2 秒时触发 P1 告警

## 2.6 反模式：SLO 实践中的常见错误

### 反模式一：SLO 定得太多

**表现**：为每个能想到的指标都设定了 SLO——CPU 使用率、磁盘 I/O、网络延迟、数据库连接数、缓存命中率……

**后果**：团队被大量的 SLO 监控淹没，无法聚焦在最关键的问题上。每个 SLO 都在告警，但团队不知道哪个最重要。

**正确的做法**：每个服务只设定 2-3 个与用户体验直接相关的 SLO。其他的指标作为辅助参考，不作为 SLO。

### 反模式二：SLO 定得太高

**表现**：团队把 SLO 定在 99.999%，但系统实际只能做到 99.9%。

**后果**：SLO 永远达不到，团队每天都在处理告警和故障，错误预算永远为负。团队士气低落，对 SLO 失去信心。

**正确的做法**：SLO 应该基于实际数据，设定一个"跳一跳够得着"的目标。从 99.9% 开始，逐步提升。

### 反模式三：SLO 定好就不管了

**表现**：团队花了很多精力制定了 SLO，然后就放在那里不管了。半年后，业务已经变了，系统已经改了，但 SLO 还是半年前的那个。

**后果**：SLO 与实际情况脱节，失去了指导意义。

**正确的做法**：每季度 review 一次 SLO，根据业务变化和系统演进进行调整。

### 反模式四：SLO 和 SLA 混为一谈

**表现**：团队把 SLO 当作 SLA 来用——"我们的 SLO 是 99.9%，达不到就要赔偿"。

**后果**：SLO 变得过于保守，团队不敢设定有挑战性的目标，因为怕达不到要赔偿。

**正确的做法**：SLO 是内部目标，SLA 是外部承诺。SLO 应该比 SLA 更严格。

## 2.7 速查总结

### SLI/SLO/SLA 速查表

| 概念 | 含义 | 回答的问题 | 示例 |
|------|------|-----------|------|
| SLI | 实际测量值 | 现在服务怎么样？ | 可用性 99.95% |
| SLO | 内部目标值 | 我们希望达到什么水平？ | 可用性 ≥ 99.9% |
| SLA | 对外承诺值 | 达不到怎么赔偿？ | 可用性 < 99.9% 赔偿 10% |

### 制定 SLO 的 5 步流程

```
1. 识别关键用户旅程 → 2. 确定 SLI → 3. 设定初始 SLO
→ 4. 与业务方达成一致 → 5. 持续迭代
```

### 常见 SLO 目标值参考

| 可用性 | 月不可用时间 | 适合场景 | 技术复杂度 |
|--------|-------------|---------|-----------|
| 99% | 7.2 小时 | 内部工具 | 低 |
| 99.9% | 43.2 分钟 | 大多数 Web 应用 | 中 |
| 99.99% | 4.3 分钟 | 金融交易 | 高 |
| 99.999% | 25.9 秒 | 关键基础设施 | 极高 |

### 每周 SLO 检查清单

- [ ] 所有核心服务的 SLO 是否都在达标范围内？
- [ ] 是否有 SLO 接近违反边界？
- [ ] 错误预算消耗速度是否正常？
- [ ] 本周是否有新的服务需要制定 SLO？
- [ ] 现有的 SLO 是否需要调整？
