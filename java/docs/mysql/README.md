# MySQL SQL 优化从入门到精通 — 书籍规划

> 从"为什么这条SQL这么慢"到"我知道怎么让它快100倍"，一本让你真正掌握MySQL SQL优化的实战指南

---

## 一、这本书是写给谁的？

### 目标读者

你是**后端开发工程师、DBA或技术负责人**。你可能已经写过几百条SQL，但当你面对以下场景时，还是会感到头疼：

- 系统刚上线时一切正常，三个月后用户量涨到10万，某个查询突然从50毫秒变成了5秒。你打开监控一看，数据库CPU飙到100%，但不知道是哪条SQL在"捣乱"。
- 你在`name`字段上建了索引，但`WHERE name LIKE '%张三%'`还是全表扫描。你不理解——明明有索引，为什么没用上？
- 面试官问你"如何优化一条慢SQL"，你只能回答"加索引"。但你知道这个答案太浅了，面试官追问"如果加了索引还是慢呢？"你就答不上来了。
- 同事写了一条三表JOIN的查询，跑了10秒。你隐约觉得可以优化，但不知道从哪下手——是改JOIN顺序？还是加索引？还是重写SQL？

**如果你有以上任何一个困惑，这本书就是为你写的。**

### 你需要什么基础

- 熟悉SQL基本语法（SELECT、JOIN、WHERE、GROUP BY）——你不需要是SQL专家，但至少写过几十条查询
- 了解基本的数据库概念（表、索引、事务）——知道索引是"让查询变快的东西"就够了
- **不需要**DBA经验——我们会从"一条SQL是怎么执行的"开始讲起，逐步深入到执行计划、索引原理、查询重写

### 学完这本书你能做什么

学完这本书，你不再是那个只会说"加索引"的开发。你将能够：

- **读懂EXPLAIN执行计划**：看到`type=ALL`就知道是全表扫描，看到`Using filesort`就知道需要优化排序。你能像医生看化验单一样，从EXPLAIN输出中诊断出查询的"病因"。
- **设计高效的索引**：不再盲目地给每个字段建索引。你知道什么时候该用联合索引、什么时候该用覆盖索引、为什么`(city, age)`和`(age, city)`是不同的索引。
- **重写低效SQL**：看到`WHERE YEAR(created_at) = 2024`就知道索引会失效，能把它改成范围查询。看到`OR`条件就知道该拆成`UNION ALL`。
- **优化JOIN和子查询**：理解"小表驱动大表"的原则，知道什么时候该用JOIN代替子查询，什么时候反过来。
- **解决深分页问题**：不再让`LIMIT 100000, 20`拖垮数据库，能用延迟关联或游标分页把查询从10秒降到10毫秒。
- **诊断和解决锁问题**：当系统出现死锁时，你能通过`SHOW ENGINE INNODB STATUS`找到原因，而不是重启数据库了事。
- **配置MySQL参数**：知道`innodb_buffer_pool_size`应该设为物理内存的50%-70%，知道`sort_buffer_size`不是越大越好。

## 三、全书章节详解

### 第1章：MySQL架构与查询执行流程

#### 🎯 为什么学这章？

很多开发人员优化SQL时只会"加索引"，但不知道为什么加了索引就快了。这章带你理解一条SQL从客户端发送到返回结果的**完整执行流程**——连接器、分析器、优化器、执行器、存储引擎各做了什么。理解了这些，你才能知道"优化"到底优化的是什么。

#### 📖 核心内容

| 项目 | 内容 |
|------|------|
| **MySQL架构** | Server层（连接器/分析器/优化器/执行器）+ 存储引擎层（InnoDB/MyISAM） |
| **查询执行流程** | 连接 → 解析 → 优化 → 执行 → 返回 |
| **优化器工作原理** | 成本估算、索引选择、JOIN顺序选择 |
| **存储引擎对比** | InnoDB vs MyISAM：事务、锁、索引结构 |
| **示例** | `01-architecture` — 启动MySQL，执行查询并观察执行流程 |

### 第2章：执行计划解读(EXPLAIN)

#### 🎯 为什么学这章？

EXPLAIN是MySQL优化的"显微镜"——它能告诉你查询是怎么执行的、用了哪个索引、扫描了多少行。不会读EXPLAIN，优化就是"盲人摸象"。这章教你读懂EXPLAIN的每个字段，知道什么情况下查询是"高效"的，什么情况下需要优化。

#### 📖 核心内容

| 项目 | 内容 |
|------|------|
| **EXPLAIN字段详解** | id、select_type、table、type、key、rows、Extra |
| **type字段解读** | system > const > eq_ref > ref > range > index > ALL |
| **Extra关键信息** | Using index、Using filesort、Using temporary、Using where |
| **EXPLAIN ANALYZE** | MySQL 8.0+ 的实际执行时间分析 |
| **示例** | `02-explain` — 创建测试表，对比不同查询的执行计划 |

## 四、典型问题处理手册

### 4.1 查询突然变慢

**真实案例**：小张的系统上线3个月后，用户列表查询从50ms变成了5秒。

**诊断步骤**：
```sql
-- 1. 查看执行计划
EXPLAIN SELECT * FROM users WHERE status = 1 ORDER BY created_at DESC LIMIT 20;

-- 2. 检查索引使用情况
SHOW INDEX FROM users;

-- 3. 检查表数据量
SELECT COUNT(*) FROM users;
```

**常见原因与解决**：

| 原因 | 诊断 | 解决 |
|------|------|------|
| 数据量增长，索引失效 | EXPLAIN看到type=ALL | 重建索引或优化查询 |
| 统计信息过期 | 执行计划与实际不符 | ANALYZE TABLE |
| 锁等待 | SHOW PROCESSLIST看到Waiting | 优化事务，减少锁持有时间 |
| 配置不合理 | 缓冲池太小 | 调整innodb_buffer_pool_size |

### 4.2 索引不生效

**真实案例**：小李在`name`字段上建了索引，但`WHERE name LIKE '%张三%'`还是全表扫描。

**常见索引失效场景**：

| 场景 | 错误写法 | 正确写法 |
|------|---------|---------|
| LIKE前置通配符 | `LIKE '%张三%'` | `LIKE '张三%'`（或全文索引） |
| 函数操作 | `WHERE DATE(created_at) = '2024-01-01'` | `WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02'` |
| 隐式类型转换 | `WHERE phone = 13800138000`（phone是VARCHAR） | `WHERE phone = '13800138000'` |
| OR条件 | `WHERE a = 1 OR b = 2` | 拆成UNION或建联合索引 |
| 不等于 | `WHERE status != 1` | 用IN替代（如果值有限） |

### 4.3 深分页性能问题

**真实案例**：小王的订单列表有100万条数据，翻到第5000页时查询需要10秒。

**解决方案对比**：

| 方案 | SQL | 性能 |
|------|-----|------|
| 原始分页 | `SELECT * FROM orders ORDER BY id LIMIT 100000, 20` | 10秒 |
| 延迟关联 | `SELECT * FROM orders o JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 20) t ON o.id = t.id` | 0.5秒 |
| 游标分页 | `SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20` | 0.01秒 |

### 4.4 死锁问题

**真实案例**：小陈的系统在高峰期频繁出现死锁，导致订单创建失败。

**诊断方法**：
```sql
-- 查看最近死锁
SHOW ENGINE INNODB STATUS\G

-- 查看当前锁等待
SELECT * FROM information_schema.INNODB_TRX;
SELECT * FROM information_schema.INNODB_LOCKS;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

**预防策略**：
- 按固定顺序访问资源（如按ID升序更新）
- 缩短事务时间
- 使用合适的事务隔离级别
- 合理设计索引，避免间隙锁范围过大
