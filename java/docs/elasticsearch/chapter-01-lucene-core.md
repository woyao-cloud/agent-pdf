# 第1章 搜索引擎的基石：Lucene 核心数据结构

## 本章导读

Elasticsearch 被很多人误解为"一个面向 JSON 的分布式 NoSQL 数据库"。这个理解不能说错，但忽略了 ES 最核心、最与众不同的能力——**搜索**。ES 能在一秒内从 10 亿条数据中找到匹配某个关键词的文档，不是因为它存储快（论存储它不如 Cassandra），也不是因为它计算快（论计算它不如 Spark），而是因为它的底层核心——**Apache Lucene**——用一系列极其精巧的数据结构，将"查找"这件事的复杂度从 O(N) 降低到了接近 O(1)。

想象一下，你在 1000 万条商品数据中搜索"苹果手机"。如果你是 MySQL，它会在 description 字段上用 `LIKE '%苹果%'` 做全表扫描。如果你是 ES，它的做法完全不同：**它提前"记住"了"苹果"这个词出现在哪些文档中**。搜索时，它只需要查一次"词典"，就能直接拿到包含"苹果"的所有文档 ID 列表。这个"词典"被称为**倒排索引**。

本章将深入 Lucene 的三大核心数据结构：倒排索引（为什么检索这么快？）、DocValues（为什么排序和聚合不依赖 _source？）、以及 BM25 评分算法（为什么从 TF-IDF 切换到 BM25？）。理解这些数据结构，你就理解了 ES 性能的天花板在哪里。

---

## 1.1 倒排索引（Inverted Index）

### 正向索引 vs 倒排索引——重新思考"查找"

首先要理解"正排"和"倒排"的视角差异。传统关系型数据库使用正向索引（如 B+ 树），解决的问题是：**根据文档 ID 快速找到文档内容**。而搜索引擎需要解决的问题恰恰相反：**根据内容（关键词）找到哪些文档包含它**。

```
正向索引（MySQL B+ Tree）：
  文档 ID → 文档内容
  ┌────────┬────────────────────────────┐
  │  Doc1  │ 苹果手机 15 Pro 最新款     │
  │  Doc2  │ 苹果笔记本 MacBook Pro     │
  │  Doc3  │ 华为手机 Mate 60           │
  │  Doc4  │ 苹果耳机 AirPods Pro       │
  └────────┴────────────────────────────┘

  搜索"苹果"：全表扫描 LIKE '%苹果%' → 遍历 4 条 → 找到 3 条
  搜索"手机"：全表扫描 LIKE '%手机%' → 遍历 4 条 → 找到 2 条
  搜索"苹果 手机"：两个 LIKE 的结果取交集
  → 在 1000 万条数据上，这就是灾难

倒排索引（Lucene）：
  关键词 → 文档 ID 列表
  ┌──────────┬─────────────────┐
  │  苹果     │  [Doc1, Doc2, Doc4]│
  │  手机     │  [Doc1, Doc3]     │
  │  15       │  [Doc1]           │
  │  Pro      │  [Doc1, Doc2]     │
  │  笔记本   │  [Doc2]           │
  │  华为     │  [Doc3]           │
  │  耳机     │  [Doc4]           │
  └──────────┴─────────────────┘

  搜索"苹果"：查倒排索引 → 直接拿到 [Doc1, Doc2, Doc4] → O(1)
  搜索"苹果 手机"：查两次倒排索引 → [Doc1,Doc2,Doc4] ∩ [Doc1,Doc3] = [Doc1]
  → 在 10 亿条数据上，速度和在 10 条上一样快！
```

**倒排索引是 ES/Lucene 性能的根基**。理解了这个核心差异，你就明白了为什么 ES 在"搜索"场景下能碾压 MySQL。

### 倒排索引的三层结构

Lucene 的倒排索引不是简单的"关键词 → 文档列表"，它由三个部分组成：

```
倒排索引的三层结构：

  第 1 层：Term Index（词条索引）
  ┌────────────────────────────────────────────┐
  │  为了在大规模词典中快速定位 Term            │
  │  使用 FST（有限状态转换器）数据结构          │
  │  存储在堆外内存（常驻 OS PageCache）        │
  │  极小的内存占用：1000 万个 Term 约 100MB    │
  │  功能：给定前缀，快速找到对应的 Term Dict   │
  └────────────────────────────────────────────┘
             │  （根据 "苹果" 快速定位到 "苹果" 在词典中的位置）
             ▼
  第 2 层：Term Dictionary（词条词典）
  ┌────────────────────────────────────────────┐
  │  所有 Term 按字典序排列                     │
  │  使用二分查找在块内搜索                     │
  │  每个块有一个起始偏移量                     │
  │  功能：精确查找到 Term 对应的 Posting List  │
  └────────────────────────────────────────────┘
             │  （"苹果" → 指向包含"苹果"的文档列表）
             ▼
  第 3 层：Posting List（倒排列表）
  ┌────────────────────────────────────────────┐
  │  包含该 Term 的文档 ID 列表                │
  │  使用 Roaring Bitmap（咆哮位图）存储        │
  │  自动在 3 种编码间切换以适应不同密度         │
  │  支持高效的 AND/OR/NOT 位运算               │
  │  功能：快速做交/并/差集运算                 │
  └────────────────────────────────────────────┘
```

#### Term Index：FST（Finite State Transducer）

FST 是 Lucene 最具独创性的数据结构，它用极其紧凑的方式存储了所有 Term 的前缀路径，使得你可以在百万级 Term 中实现**纳秒级**的前缀匹配：

```
FST 的存储原理：

  假设我们有 3 个 Term："cat"、"cap"、"dog"

  一个朴素的字典（HashMap 或 Trie）：
  ┌──────┐
  │ cat  │──→ Posting List for cat
  │ cap  │──→ Posting List for cap
  │ dog  │──→ Posting List for dog
  └──────┘
  存储了 "c","a","t","c","a","p","d","o","g" = 9 个字符
  （共享前缀 "ca" 被存了两次！）

  FST 的存储（共享前缀）：
  ┌──────────────────┐
  │  0 →[c]→ 1 →[a]→ 2 →[t]→ 3 (cat 结束)
  │                    →[p]→ 4 (cap 结束)
  │  0 →[d]→ 5 →[o]→ 6 →[g]→ 7 (dog 结束)
  └──────────────────┘
  只存储了 "c","a","t","p","d","o","g" = 7 个字符
  "c"+"a" 被共享了！→ 节省 22% 的空间

  在 Lucene 中，FST 管理着上亿个 Term：
  如 "苹果手机"、"苹果电脑"、"苹果耳机" 共享 "苹果" 前缀
  1000 万个 Term，共享前缀后，FST 的内存不到 100MB
  → 可以常驻 OS PageCache（操作系统的文件系统缓存）
  → 每次查词典 ≈ 从内存读一次，纳秒级
```

```
FST 的查询效率：

  给定前缀 "苹果"，在 FST 中查找：
  从 FST 的起始节点出发：
  → 走 "苹" 边 → 到达节点 A
  → 走 "果" 边 → 到达节点 B
  → 到达节点 B 时，我们知道所有以 "苹果" 开头的 Term
    都在节点 B 的子树中
  → 找到 Term Dictionary 中 "苹果" 对应的块
  → 在块中二分查找精确匹配的 Term
  → 拿到 Posting List 的指针

  整个路径：3 步 FST 遍历 + 1 次块内二分查找
  时间复杂度：O(len(查询词)) + O(log(块大小))
  对于查询词"苹果"：len=2，常数时间
```

#### Term Dictionary：带索引的有序数组

FST 定位到 Term 在词典中的大致位置后，还需要在 Term Dictionary 中做精确查找。Term Dictionary 是一个按字典序排列的数组，每 64 个或 128 个 Term 有一个索引块：

```
Term Dictionary 的结构：

  索引块（每隔 N 个 Term 存一个起始 Term）：
  ┌─────────────┬─────────────┬─────────────┐
  │  阿 (offset 0)│  不 (offset 64)│  吃 (offset 128)│  ...
  └─────────────┴─────────────┴─────────────┘
                ↑ 先查索引块找到区间
                │
  数据块（Term 数组，二分查找）：
  ┌────┬────┬────┬────┬────┬────┐
  │ 阿  │ 哎  │ 哀  │ 挨  │ 皑  │ 癌  │  ...
  └────┴────┴────┴────┴────┴────┘
                ↑ 在区间内二分查找精确匹配

  查找"苹果"：
  1. 在索引块中找到"苹"在"不"和"吃"之间 → 二分范围确定
  2. 在 64 个 Term 的块中二分查找 → 最多 6 次比较
  3. 找到 "苹果" → 读取其关联的 Posting List 指针
```

#### Posting List：Roaring Bitmap（咆哮位图）

Posting List 是倒排索引中最"重"的部分——它存储了包含某个 Term 的所有文档 ID。Lucene 使用 Roaring Bitmap 来存储 Posting List，它能够根据数据密度自动选择最优编码：

```
Roaring Bitmap 的三种编码模式：

  情况 A：稀疏数据（如 "苹果" 只出现在 100 个文档中）
  ┌────────────────────────────────────────────┐
  │  使用 Array Container：有序 short 数组      │
  │  [1024, 2048, 3072, 4096, ...] → 每个 ID 2 字节│
  │  100 个 ID → 200 字节                       │
  │  适合：低频词、罕见词                        │
  └────────────────────────────────────────────┘

  情况 B：密集数据（如 "的" 出现在 80% 的文档中）
  ┌────────────────────────────────────────────┐
  │  使用 Bitmap Container：位图               │
  │  65536 位 = 8KB（不管有多少个 1）           │
  │  65536 个 bit 正好存满一个 chunk            │
  │  适合：高频词、"的"、"是"、"在"             │
  └────────────────────────────────────────────┘

  情况 C：超密集数据（如 "我" 出现在几乎所有文档）
  ┌────────────────────────────────────────────┐
  │  使用 Run Container：运行长度编码（RLE）     │
  │  [0, 10000] → 表示文档 0 到 10000 都包含    │
  │  1 万个 ID → 只需要 2 个 int（4 字节）       │
  │  适合：几乎出现在所有文档中的词               │
  └────────────────────────────────────────────┘

  三种容器自动切换：
  Array Container 的元素超过 4096 个 → 切换为 Bitmap Container
  Bitmap Container 的可运行的片段很长 → 切换为 Run Container
  Run Container 拆分后变稀疏 → 切换为 Array Container
```

```
位运算的效率优势：

  假设我们搜索 "苹果 AND 手机 AND 最新款"：

  "苹果" 的 Posting List：[1, 100, 101, 102, 1000, 1001]
  "手机" 的 Posting List：[1, 2, 100, 200, 1000]
  "最新款" 的 Posting List：[1, 100, 1000, 2000]

  苹果 ∩ 手机 ∩ 最新款：
  
  传统方式（数组遍历）：
  i=0,j=0 → 苹果[1] vs 手机[1] → 相等！存起来
  i=1,j=1 → 苹果[100] vs 手机[2] → 不相等，移动较小的
  → 两两对比，时间复杂度 O(N+M)

  Roaring Bitmap 方式：
  → "苹果" Bitmap: 0010...
  → "手机" Bitmap: 0011...
  → "最新款" Bitmap: 0010...
  → AND: 0010... & 0011... & 0010... = 0010...
  → CPU 的一条 AND 指令同时处理 64 位
  → 一次运算处理 64 个文档的匹配结果
  → 比逐元素遍历快 64 倍！
```

## 1.2 正排索引与 DocValues

### 为什么不用 `_source` 做聚合？

在 ES 中，`_source` 字段存储的是原始的 JSON 文档内容。当你搜索到文档时，返回的 `_source` 就是这份数据。但如果你要做排序或聚合——比如"按价格排序"或"按分类统计数量"——用 `_source` 就灾难了：

```
行式存储的聚合灾难：
  
  _source 存储方式（行式存储——相邻行在磁盘上相邻）：

  磁盘上的 _source：
  ┌──────────────────────────────────────────────────────────────┐
  │  Doc1: { "name":"苹果手机","price":8999,"category":"手机"}   │
  │  Doc2: { "name":"华为手机","price":5999,"category":"手机"}   │
  │  Doc3: { "name":"苹果电脑","price":14999,"category":"电脑"}  │
  │  ...                                                        │
  │  Doc10000: { "name":"华为电脑","price":9999,"category":"电脑"} │
  └──────────────────────────────────────────────────────────────┘

  如果你要做 `SELECT SUM(price) FROM products GROUP BY category`：

  传统行式存储（MySQL 或 _source）：
  1. 读取所有文档的 _source（每个文档可能 1KB 以上）
  2. 解析 JSON，提取 price 和 category 字段
  3. 丢弃其他 20 个不需要的字段
  → I/O 浪费：你只需要 2 个字段，但读入了全部 20 个字段
  → 如果每个文档 1KB，10 亿文档 = 1TB 的 I/O！
```

### DocValues 的列式存储

DocValues 的解决方案是：**将每个字段单独存储为一个列文件**。聚合时，只需要读取这一个列文件，不读其他无关字段：

```
DocValues 列式存储：

  磁盘上的 DocValues（列式——相邻值在磁盘上相邻）：

  price 字段的列文件：
  ┌──────┬──────┬───────┬──────┬──────┐
  │ 8999 │ 5999 │ 14999 │ 9999 │ 4999 │  ...
  └──────┴──────┴───────┴──────┴──────┘
  ↑ 1 个 int = 4 字节
  只需要读 10 亿 × 4 = 4GB 的数据

  category 字段的列文件：
  ┌─────┬─────┬─────┬─────┬─────┐
  │ 手机 │ 手机 │ 电脑 │ 电脑 │ 手机 │  ...
  └─────┴─────┴─────┴─────┴─────┘
  ↑ 配合 Global Ordinals 优化

  SUM(price) GROUP BY category 的 I/O 对比：
  ┌──────────────────────────────┬──────────────────────────────┐
  │  使用 _source（行存储）        │  使用 DocValues（列存储）      │
  ├──────────────────────────────┼──────────────────────────────┤
  │  读取 10 亿条 _source         │  读取 2 个列文件              │
  │  每条 1KB → 1TB I/O         │  price: 4GB + category: 2GB  │
  │  解析 10 亿次 JSON           │  无解析开销                  │
  │  I/O 时间：≈ 1000 秒         │  I/O 时间：≈ 6 秒            │
  │  （SSD 读取速度 1GB/s）       │                              │
  └──────────────────────────────┴──────────────────────────────┘
```

### DocValues 的存储格式

Lucene 的 DocValues 字段在磁盘上有几种格式，根据数据类型使用不同的编码：

```java
// Lucene DocValues 的类型——对应 ES 中不同的字段类型
// 每个字段在索引时，ES 会创建一个对应的 DocValues 文件

// 1. NumericDocValues（数值类型）
//    用于 int、long、float、double 字段
//    存储：每个文档一个数值
//    → 文件格式：.dvd / .dvm（数据 + 元数据）
//    适用：price、age、count 等

// 2. SortedDocValues（有序字符串类型）
//    用于 keyword 字段
//    存储：Term ID（Ordinal）+ Term String
//    → 每个唯一值分配一个递增的 ID
//    → 文档中存 ID，词典中存 ID→字符串映射
//    适用：category、status、color 等

// 3. SortedSetDocValues（多值有序字符串）
//    用于数组类型的 keyword 字段
//    存储：每个文档多个 Term ID
//    适用：tags、roles 等

// 4. BinaryDocValues（二进制类型）
//    用于二进制字段
//    存储：完整值
//    适用：少量用，因为内存占用大
```

### Global Ordinals——字符串聚合的"秘密武器"

当对字符串（keyword）字段做 Terms 聚合时，Lucene 使用 Global Ordinals 来优化。这个机制非常巧妙——它把字符串比较变成了整数比较：

```
Global Ordinals 的工作原理：

  原始数据：category 字段有 3 个唯一值 ["手机", "电脑", "平板"]

  第 1 步：建立 Ordinal 映射（在每个分片中）
  ┌──────────┬────────┐
  │  String  │ Ordinal│
  ├──────────┼────────┤
  │  电脑    │   0    │
  │  平板    │   1    │
  │  手机    │   2    │
  └──────────┴────────┘

  第 2 步：文档只存储 Ordinal
  ┌──────┬──────────┬────────────┐
  │ Doc  │ category │ category   │
  │ ID   │ (原始)   │ (Ordinal)  │
  ├──────┼──────────┼────────────┤
  │  1   │ 手机     │     2      │
  │  2   │ 手机     │     2      │
  │  3   │ 电脑     │     0      │
  │  4   │ 平板     │     1      │
  │  5   │ 手机     │     2      │
  └──────┴──────────┴────────────┘

  第 3 步：聚合时
  GROUP BY category 变成：
  → 遍历 Ordinal 列
  → 对 Ordinal 做分组计数
  → 整数比较：if (ord == 2) count[2]++
  → 不需要字符串比较！

  性能提升：
  字符串比较：每次比较需要遍历字符，最坏 O(N) 字节
  整数比较：一次 CPU 指令，O(1)
  在百万级文档的聚合中，这可能是 100 倍的性能差距
```

> **💡 核心理解**：ES 的排序和聚合性能依赖 DocValues。如果对一个字段禁用了 DocValues（`"doc_values": false`），ES 就只能回退到从 `_source` 中提取数据——性能会下降 1-2 个数量级。所以生产环境中，**对需要排序和聚合的字段，永远不要禁用 DocValues**。

## 1.3 评分算法演进——从 TF-IDF 到 BM25

### 为什么需要相关性评分？

当搜索返回多条结果时，如何决定哪条结果排在最前面？这需要**相关性评分**（Relevance Scoring）。ES 的 `_score` 字段就代表了一个文档与查询的匹配程度。

### TF-IDF（ES 5.x 之前）

TF-IDF（Term Frequency-Inverse Document Frequency）是信息检索领域最经典的评分算法。它由两个部分相乘得到：

```
TF-IDF = TF（词频）× IDF（逆文档频率）

  TF（Term Frequency）——这个词在本文档中出现了多少次？
  公式：TF = sqrt(term_count)
  解释：一个词在一篇文档中出现次数越多，这篇文档越相关
        但用 sqrt 开方，防止重复次数导致的线性增长

  IDF（Inverse Document Frequency）——这个词在所有文档中常见吗？
  公式：IDF = 1 + ln(total_docs / (doc_freq + 1))
  解释：一个词如果在很多文档中都出现，它对区分"相关性"的贡献就低
        比如"的"字几乎出现在所有文档中——IDF 接近 0
        而"iPhone15Pro"只在少数文档中出现——IDF 很高

  TF-IDF 举例：
  搜索 "苹果手机"：
  Doc1 "苹果手机" 出现 5 次 → TF = sqrt(5) = 2.236
       "苹果" 在 10 万篇中出现 → IDF(苹果) = ln(100万/10万) = 2.30
       "手机" 在 5 万篇中出现 → IDF(手机) = ln(100万/5万) = 2.99
  Doc1 得分 = 2.236 × (2.30 + 2.99) = 11.83
```

**TF-IDF 的问题——长文本评分失真**：

```
TF-IDF 的致命缺陷：

  场景：搜索 "苹果"

  短文档 A（10 个字）：
  "苹果手机 15 Pro"                → "苹果" 出现 1 次
  TF = sqrt(1) = 1.0

  长文档 B（1000 个字）：
  "这是一篇关于手机发展史的文章...苹果...苹果...苹果..."
  → "苹果" 出现 3 次
  TF = sqrt(3) = 1.732

  在 TF-IDF 下：文档 B 的得分 > 文档 A 的得分
  但直觉上：文档 A 更相关（全文就是在讲苹果手机）
  这就是 TF-IDF 的"长文本偏差"——长文档有机会重复同一个词更多次
```

### BM25（ES 5.x+）

BM25（Best Matching 25）是对 TF-IDF 的改进，它引入了一个**饱和函数**来解决长文本偏差问题：

```
BM25 评分公式（简化版）：

  score = IDF × (TF × (k1 + 1)) / (TF + k1 × (1 - b + b × docLen / avgDocLen))

  参数说明：
  k1（默认 1.2）：控制 TF 的饱和速度
    → k1 越小，TF 饱和得越快（防止长文档靠词频取胜）
    → k1=0 → TF 不产生影响（只看 IDF）
    → k1 越大 → TF 的影响越大

  b（默认 0.75）：控制文档长度归一化的力度
    → b=0 → 不考虑文档长度
    → b=1 → 完全按文档长度归一化
    → 默认 0.75 表示：长的文档会被"惩罚"，但不是完全忽略

  docLen / avgDocLen：当前文档长度 / 所有文档的平均长度
    → 如果当前文档比平均长，这个值 > 1
    → 短的文档比平均短，这个值 < 1
    → 这修正了长文本偏差！
```

```
BM25 的饱和效应：

  假设 k1 = 1.2，TF 对得分的影响曲线：

  得分 │
       │
   1.0 │     ┌──────────────────────────────────
       │    /
   0.8 │   /
       │  /
   0.6 │ /
       │/
   0.4 │
       │
   0.2 │
       │
   0.0 └──────────────────────────────────── TF
       0   1   2   3   4   5   6   7   8

  关键：
  TF=0 → 得分=0
  TF=1 → 得分≈0.52  ← 第一次提及最关键
  TF=2 → 得分≈0.71  ← 第二次也有价值，但增益变小
  TF=3 → 得分≈0.81  ← 第三次还有收益，但更小了
  TF=4 → 得分≈0.87  ← 第四次几乎不影响
  TF=5 → 得分≈0.90  ← 第五次基本可以忽略

  → 在 BM25 中，一个词出现 2-3 次就"饱和"了
  → 长文档无法通过大量重复同一个词来获取高分
  → 这解决了 TF-IDF 的长文本偏差问题
```

## 本章总结

| 数据结构 | 解决的问题 | 核心原理 | 内存/磁盘占用 |
|---------|-----------|---------|-------------|
| **倒排索引（FST + Term Dict + Posting List）** | 根据关键词找到文档 | 词典存储词→文档列表的映射 | FST 内存常驻，Posting List 磁盘 |
| **FST** | 快速定位 Term | 共享前缀的有限状态机 | 1000 万 Term ≈ 100MB |
| **Roaring Bitmap** | 高效的位运算 | 自动切换 Array/Bitmap/Run | 根据数据密度自适应 |
| **DocValues** | 排序和聚合 | 列式存储，每个字段单独文件 | 每个字段磁盘占用 ≈ 字段值大小 |
| **Global Ordinals** | 字符串聚合优化 | 字符串→整数映射，比较变整数比较 | 唯一值数量 × 8 字节 |
| **BM25** | 相关性评分 | 饱和函数 + 长度归一化 | 无额外存储（计算时算的） |

**对 Java 开发者的启示**：
1. **ES 的快来自倒排索引，不是来自内存**——很多人以为 ES 快是因为"数据在内存中"。实际上 ES 的数据大部分在磁盘上，但倒排索引 + OS PageCache 的组合让大多数搜索操作只需要读很少的数据
2. **排序和聚合一定要用 DocValues**——不要依赖 `_source`，它是行式存储，对分析操作是灾难
3. **BM25 参数（k1, b）可以根据业务调整**——比如在搜索短标题的场景（电商），可以调高 k1 让词频发挥更大作用；在搜索长文章的场景（内容平台），可以调低 k1 让饱和更快
