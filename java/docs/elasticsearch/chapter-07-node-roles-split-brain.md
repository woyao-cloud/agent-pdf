# 第7章 节点角色、脑裂防范与分片策略

## 本章导读

2019 年，某公司的 ES 集群在深夜突然"挂了"——所有写入请求都返回错误，但集群似乎还在运行。运维人员登录 Kibana 看到：集群状态是 Red，所有索引都不可用。排查发现：Master 节点因为 GC 停顿了 10 秒，在这 10 秒内其他节点检测到 Master 无响应，触发了选举。由于没有配置 `discovery.zen.minimum_master_nodes`，两个节点各自选了自己为 Master——集群脑裂了。

脑裂之后，两个 Master 各自管理一部分索引和分片，而数据节点不知道该听谁的。更糟糕的是，两个 Master 同时接受了针对同一索引的写入——数据出现了不一致。最终只能通过快照恢复数据，丢失了约 15 分钟的数据。

ES 的分布式架构在提供高可用的同时，也带来了一系列配置陷阱。本章将系统讲解节点角色、脑裂防范和分片策略这三个在集群部署中必须理解的核心话题。

---

## 7.1 节点角色划分

### 四种核心节点类型

在 ES 7.x+ 中，节点可以分为以下几种角色。生产环境中，**不要让一个节点承担所有角色**——这就像不让同一个工程师同时写代码、做运维、管数据库、接客服电话一样，不专业也不稳定。

```
ES 节点的角色分工：

  ┌────────────────────────────────────────────────────────────┐
  │                     Master 节点                             │
  │  职责：管理集群元数据（Cluster State）                       │
  │  ├── 创建/删除索引                                         │
  │  ├── 分配分片到数据节点                                     │
  │  ├── 监控数据节点健康                                       │
  │  └── 发布 Cluster State 到所有节点                          │
  │                                                             │
  │  配置：node.roles: ["master"]                               │
  │  资源：CPU 中高、内存中高、磁盘低（不存数据）                  │
  │  建议：3 个 Master 节点（奇数，避免平局），独立部署            │
  └────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────┐
  │                     Data 节点                               │
  │  职责：存储数据、处理搜索和聚合请求                           │
  │  ├── 存储分片数据                                           │
  │  ├── 执行搜索和聚合操作                                     │
  │  └── 处理写入和读取请求                                     │
  │                                                             │
  │  配置：node.roles: ["data_hot", "data_content"]             │
  │  资源：CPU 高、内存高、磁盘大                                │
  │  建议：根据数据量横向扩展，至少 2 个节点                      │
  └────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────┐
  │                    Ingest 节点                               │
  │  职责：数据预处理（Ingest Pipeline）                          │
  │  ├── 执行 Pipeline 处理器                                   │
  │  ├── 字段转换、脱敏、GeoIP 解析等                            │
  │  └── 将处理后的数据转发到 Data 节点                          │
  │                                                             │
  │  配置：node.roles: ["ingest"]                               │
  │  资源：CPU 中（Pipeline 处理器消耗 CPU）、内存适中             │
  │  建议：如果 Ingest Pipeline 使用频繁，独立部署                │
  └────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────┐
  │                  Coordinating 节点                           │
  │  职责：负载均衡和请求路由                                    │
  │  ├── 接收客户端请求                                         │
  │  ├── 将请求广播到 Data 节点                                 │
  │  ├── 合并各 Data 节点的搜索结果                             │
  │  └── 将结果返回给客户端                                     │
  │                                                             │
  │  配置：node.roles: []（空 = 仅协调）                         │
  │  资源：CPU 中（合并结果需要 CPU）、网络带宽大                  │
  │  建议：高并发搜索场景可以在客户端前加一层协调节点              │
  └────────────────────────────────────────────────────────────┘
```

### 生产环境推荐的角色分配

```
小规模集群（3 台物理机，数据量 < 10TB）：
  Node 1: Master + Data + Ingest   ├── 混合部署节省资源
  Node 2: Master + Data + Ingest   │   但注意：Master 和 Data 混合
  Node 3: Master + Data + Ingest   │   当 Data 节点繁忙时，可能影响 Master 响应
  + 客户端直连（无独立的 Coordinating 节点）

中规模集群（6-10 台，数据量 10TB-100TB）：
  Node 1-3: Master only（3 台独立 Master）
  Node 4-8: Data only（5 台 Data 节点）
  Node 9-10: Coordinating only（2 台协调节点）
  → 角色隔离，互不影响

大规模集群（20+ 台，数据量 100TB+）：
  Node 1-3: Master only（3 台）
  Node 4-N: Data only（分 Hot/Warm/Cold）
  Node N+1-M: Coordinating only（2-4 台）
  + 独立的 Ingest 节点（可选）
```

## 7.2 脑裂（Split-Brain）防范

### 什么是脑裂？

脑裂是指在分布式集群中，由于网络分区或节点故障，集群被分裂为两个或多个"子集群"，每个子集群都认为自己是"合法的"独立集群。在 ES 中，脑裂会导致以下问题：

```
脑裂的过程：

  正常状态：3 个 Master 节点，Node-A 是当前 Master
  
  Node-A (Master) ──── Node-B (可选举)
       │
       └──── Node-C (可选举)

  网络分区发生：Node-A 与 Node-B、Node-C 断开

  ┌────────────────┐    ┌─────────────────────┐
  │  分区 1         │    │  分区 2              │
  │  Node-A         │    │  Node-B, Node-C      │
  │  (自认为是 Master)│    │  发现 Node-A 不可用    │
  │  │               │    │  选举 Node-B 为新 Master│
  │  │ 接受写入 A    │    │  │                    │
  │  │               │    │  接受写入 B           │
  └────────────────┘    └─────────────────────┘

  两个 Master 同时接受写入 → 数据不一致
  分区恢复后 → 不知道谁的元数据正确 → 数据丢失！
```

### ES 7.x+ 的自动 Quorum 机制

ES 6.x 及之前版本通过 `discovery.zen.minimum_master_nodes` 来防范脑裂，这是一个手动配置的值（通常= `(master 节点数/2) + 1`），但如果手动配错，仍然无法防范脑裂。

ES 7.x 引入了**基于 Voting Configuration（投票配置）**的自动 Quorum 机制：

```
ES 7.x+ 的脑裂防范：

  集群启动时（3 个 Master-eligible 节点）：
  ┌────────────────────────────────────────────┐
  │  Voting Configuration = [Node-A, Node-B, Node-C] │
  │  Quorum = (3 / 2) + 1 = 2 个投票          │
  │                                              │
  │  假设 Node-A 是当前 Master                  │
  │  Node-A 必须获得至少 2 个投票才能保持 Master  │
  └────────────────────────────────────────────┘

  Node-A 宕机：
  ┌────────────────────────────────────────────┐
  │  Node-B 和 Node-C 发现 Node-A 不可用        │
  │  检查：Voting Configuration 仍有 3 个节点    │
  │  当前在线投票数：2 < Quorum(2)？→ ≥ Quorum  │
  │  ✓ 可以选举！                               │
  │  选举 Node-B 为 Master                       │
  └────────────────────────────────────────────┘

  Node-A 网络分区（与 B、C 断开，但自我运行）：
  ┌────────────────────────────────────────────┐
  │  Node-A（分区侧）：只有自己 1 票             │
  │  Quorum = 2，但只有 1 票 < 2                │
  │  Node-A 认为自己失去了 Master 资格           │
  │  → 降级为候选节点，不再接受写入              │
  │  → 不会形成两个 Master！                    │
  │                                              │
  │  Node-B, Node-C（另一侧）：有 2 票 ≥ 2       │
  │  ✓ 可以继续运行                              │
  └────────────────────────────────────────────┘
```

**自动 Quorum 的核心优势**：当节点宕机后，Voting Configuration 会自动将宕机节点从投票配置中移除。比如 Node-A 宕机后，Voting Configuration 变为 `[Node-B, Node-C]`，新 Quorum = (2/2)+1 = 2 票——仍然是安全的。

```
自动 Quorum 的节点数建议：

  Master-eligible 节点数要求：
  ┌──────┬──────────┬─────────────────────────────┐
  │ 节点数 │ 容错能力 │ 说明                         │
  ├──────┼──────────┼─────────────────────────────┤
  │  1   │   0      │ 单点故障，不推荐               │
  │  2   │   0      │ 一个宕机后就剩 1 票 < 2        │
  │      │          │ 集群变成"不可用"但"未挂"状态    │
  │  3   │   1      │ ✅ 生产最低配置                │
  │  5   │   2      │ 超级大集群使用                 │
  └──────┴──────────┴─────────────────────────────┘
```

### Elastic Cloud 的最小脑裂配置

在 Docker 或 K8s 中部署时，需注意以下配置以防范脑裂：

```yaml
# elasticsearch.yml 配置（每个节点）
cluster.name: "es-docker-cluster"        # 集群名必须相同
node.name: "es-node1"                    # 节点名必须唯一
network.host: 0.0.0.0                    # 监听所有网络接口

# 发现和选举配置（7.x+ 关键配置）
discovery.seed_hosts:                    # 集群中其他节点的地址
  - es-node1
  - es-node2
  - es-node3

cluster.initial_master_nodes:            # 集群首次启动时的候选主节点
  - es-node1
  - es-node2
  - es-node3

# 注意：7.x 不需要配置 discovery.zen.minimum_master_nodes
# 自动 Quorum 机制已经内置了脑裂防范
```

## 7.3 分片数设计的黄金法则

### 分片不是越多越好

"分片多 = 并行度高 = 性能好"——这是最常见的一个误解。分片确实带来了并行能力，但过多的分片会带来前面提到的问题：Master 节点内存压力、搜索时需要打开的文件数太多。

```
分片数设计的核心原则：

  单个分片的最佳大小：10GB - 50GB
  也就是说：分片数 = 预估数据总量 / (10GB ~ 50GB)

  举例：
  场景 1：日志索引，每天 500GB 数据，保留 90 天
  → 总数据量 = 500GB × 90 = 45TB
  → 按天建索引，每天 500GB
  → 每天的分片数 = 500GB / 50GB = 10 个主分片
  → 每天复制 1 份（1 副本）→ 20 个分片
  → 90 天 × 20 = 1800 个分片 → 对 3 节点的集群来说合理

  场景 2：商品索引，总量 200GB，不经常变
  → 分片数 = 200GB / 50GB = 4 个主分片
  → 1 副本 → 8 个分片
  → 对 3 节点的集群来说非常健康

  场景 3：用户索引，只有 5GB
  → 分片数 = 5GB / 50GB ≈ 0.1
  → 最少设 1 个主分片（ES 要求至少 1 个）
  → 1 副本 → 2 个分片
  → 小索引完全没问题
```

### 分片数与节点数的关系

```
分片分布的影响：

  3 个 Data 节点，10 个主分片，1 副本 = 20 个分片：

  Node A: 分片 0(P), 分片 3(P), 分片 6(P), 分片 9(P), 分片 1(R), 分片 4(R), 分片 7(R)
  Node B: 分片 1(P), 分片 4(P), 分片 7(P), 分片 0(R), 分片 3(R), 分片 6(R), 分片 9(R)
  Node C: 分片 2(P), 分片 5(P), 分片 8(P), 分片 2(R), 分片 5(R), 分片 8(R)

  每个节点约 6-7 个分片，负载均衡

  但如果 3 个 Data 节点，100 个主分片，1 副本 = 200 个分片：
  每个节点约 66-67 个分片
  每个搜索请求要发到 100 个主分片（并行度太高不一定快）
  Master 节点的 Cluster State 膨胀
```

## 本章总结

| 概念 | 关键要点 | 生产建议 |
|------|---------|---------|
| **节点角色** | Master、Data、Ingest、Coordinating | 3 节点以上时分离 Master 和 Data 角色 |
| **脑裂防范** | 7.x 自动 Quorum = (master 数/2)+1 | 最少 3 个 Master-eligible 节点，奇数 |
| **分片大小** | 10GB-50GB 是最佳区间 | 按此公式计算分片数 |
| **分片数** | 创建后不可修改 | 提前规划，宁愿少不要多 |
| **副本数** | 保障高可用 | 至少 1 个副本，最多 2 个 |

**核心原则**：
1. **分离 Master 和 Data 角色**——这是生产环境最基本的要求。Master 节点不应该做数据存储和搜索，Data 节点不应该参与集群管理决策。3 台独立 Master + N 台 Data 是最小推荐配置
2. **7.x+ 的自动 Quorum 不需要手动配置**——但仍然需要确保 Master-eligible 节点数是奇数（3 或 5）。两个 Master 节点不防脑裂（一个宕机后另一个凑不够 Quorum）
3. **分片数 = 数据总量 / 50GB**——这是简单的估算公式。可以少分点（比如按 30GB 算），但不要多分。分片数只能增加（通过 Reindex），不能减少
