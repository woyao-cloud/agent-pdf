# 第2章 读写底层链路与"近实时（NRT）"的奥秘

## 本章导读

如果你往 ES 中写入一条数据，然后立刻搜索它——你会发现这条数据在大约 1 秒后才出现在搜索结果中。在数据库领域，这被称为"近实时"（Near Real-Time，NRT），而不是"实时"。

为什么不是实时？为什么是大约 1 秒？这个 1 秒来自哪里？更重要的是，如果这 1 秒你等不了怎么办？

在回答这些问题之前，我们先来看一个典型的"线上事故"：某电商平台在双 11 大促中，运营人员在后台新增了一个秒杀商品，然后立刻在前端搜索。结果——搜不到！明明已经写入成功了，但搜索就是不返回。运营人员试了 3 次、5 次、10 次……直到第 12 秒才看到商品出现在搜索结果中。为什么是 12 秒？因为 ES 节点的写入压力太大（每秒数万条订单数据写入），前面有 11 秒的写入拥堵，到第 12 秒才轮到这条商品数据的 refresh 周期。

这就是 NRT 的"Achilles Heel"——写入负载越高，refresh 间隔越不稳定。理解这个机制，你才能在 ES 的写入延迟和写入吞吐之间找到正确的平衡点。

---

## 2.1 写入链路全景解析

### 一次写入请求的完整旅程

一条文档写入 ES，经历了从客户端到协调节点、到主分片、到副本分片、最终可见的完整链路：

```
写入流程图：

  客户端               协调节点                主分片                副本分片
    │                    │                    │                    │
    │ POST /index/_doc   │                    │                    │
    │ ────────────────►  │                    │                    │
    │                    │ 路由 → 分片        │                    │
    │                    │ shard = hash(id) % │                    │
    │                    │ number_of_shards   │                    │
    │                    │ ────────────────►  │                    │
    │                    │                    │                    │
    │                    │                    │ 1. 写入内存缓冲区   │
    │                    │                    │ 2. 写入 Translog   │
    │                    │                    │    （事务日志）     │
    │                    │                    │                    │
    │                    │                    │ ─── 同步复制 ────► │
    │                    │                    │                    │
    │                    │                    │ ◄── 写入完成 ───── │
    │                    │                    │                    │
    │                    │ ◄── 返回成功 ──────│                    │
    │                    │                    │                    │
    │ ◄── 200 OK ───────│                    │                    │
    │                    │                    │                    │
    │   此时：数据在 Translog 中，不在搜索范围内                │
    │   要等到 Refresh 后，数据才会出现在搜索结果中              │
```

**为什么 Translog 先写？** 内存缓冲区在宕机会丢失，Translog 是"安全网"。ES 保证：只要 Translog 写成功了，即使节点宕机，重启后也能从 Translog 恢复数据。

### In-memory Buffer 与 Segment

写入 ES 的数据首先进入内存缓冲区（In-memory Buffer），此时数据**不可搜索**。直到 Refresh 发生后，缓冲区中的数据被写入一个新的 Segment，才进入搜索范围。

```
In-memory Buffer 和 Segment 的关系：

  ┌──────────────────────────────────────────────────────────┐
  │  In-memory Buffer（内存缓冲区）                            │
  │  ┌──────┬──────┬──────┬──────┬──────┬──────┐            │
  │  │ Doc1 │ Doc2 │ Doc3 │ Doc4 │ Doc5 │ ...  │            │
  │  └──────┴──────┴──────┴──────┴──────┴──────┘            │
  │  数据在缓冲区中：不可搜索                                  │
  │  │                                                        │
  │  │ Refresh 触发（默认 1 秒）                               │
  │  ▼                                                        │
  │  ┌──────────────────────────────────────────────────────┐ │
  │  │  Segment 1（磁盘上的新段）                              │ │
  │  │  ├── 倒排索引：{ "苹果": [Doc1, Doc3], "手机": [Doc1], ...}│ │
  │  │  ├── DocValues：{ price: [8999, 5999], ... }         │ │
  │  │  ├── _source 数据                                      │ │
  │  │  └── 该 Segment 现在可被搜索！                         │ │
  │  └──────────────────────────────────────────────────────┘ │
  │                                                            │
  │  此时 In-memory Buffer 清空，准备接收新的写入                │
  └──────────────────────────────────────────────────────────┘
```

**Segment 的不可变性**：一个 Segment 一旦写入磁盘，就**不会**再被修改。这意味着：
- 倒排索引不需要加锁（没有并发写）
- OS PageCache 可以缓存整个 Segment，不会被失效
- 后续的删除和更新，是通过"标记删除"和"增量写入新 Segment"来实现的

### Refresh 机制——近实时的"1 秒"从哪里来

```
Refresh 的触发条件：

  条件 1：定时触发（默认 1 秒间隔）
  ┌────────────────────────────────────────────┐
  │  index.refresh_interval: 1s                │
  │                                            │
  │  T0: 刷新 → 缓冲区清空 → Segment 生成      │
  │  T0+1s: 再次刷新 → 新 Segment 生成          │
  │  T0+2s: 再次刷新                            │
  │  → 平均延迟 0.5 秒，最大延迟 1 秒           │
  └────────────────────────────────────────────┘

  条件 2：主动触发
  ┌────────────────────────────────────────────┐
  │  POST /my_index/_refresh                   │
  │  立即生成 Segment，数据立即可搜索           │
  │  代价：频繁调用会产生大量小 Segment          │
  └────────────────────────────────────────────┘

  条件 3：缓冲区满（强制刷新）
  ┌────────────────────────────────────────────┐
  │  当 In-memory Buffer 满时（由 JVM 堆控制），│
  │  会自动触发 refresh                         │
  │  这不是常规路径，但高写入流量下常见         │
  └────────────────────────────────────────────┘
```

```json
// 调整 Refresh 间隔
// 场景 1：搜索为主，写入很少 → 可以用更短的 refresh 间隔
PUT my_search_index/_settings
{
  "index": {
    "refresh_interval": "500ms"  // 500 毫秒刷新一次
  }
}

// 场景 2：批量写入，不需要实时搜索 → 关掉 refresh，写完再开
PUT my_log_index/_settings
{
  "index": {
    "refresh_interval": "-1"  // 关闭自动 refresh
  }
}

// 批量写入完成后，手动刷新
POST my_log_index/_refresh

// 重置为默认
PUT my_log_index/_settings
{
  "index": {
    "refresh_interval": "1s"
  }
}
```

### Translog——数据不丢的最后防线

Translog（事务日志）是 ES 用于保证数据不丢的核心机制。在数据被写入内存缓冲区的同时，也会写入 Translog。

```
Translog 的工作原理：

  写入流程：
  ┌──────────────────────────────────────────────────────────┐
  │  1. 数据到达主分片                                        │
  │     ├── 写入 In-memory Buffer（内存，快，但易失）         │
  │     └── 写入 Translog（磁盘，慢，但持久）                  │
  │                                                            │
  │  2. 返回写入成功（只要 Translog 写成功了）                  │
  │                                                            │
  │  3. 定时 Refresh                                           │
  │     ├── Buffer 中的数据变成 Segment（可搜索）               │
  │     └── Buffer 清空                                        │
  │                                                            │
  │  4. Translog 持续增长，直到触发 Flush                      │
  │     ├── 所有 Buffer 中的数据 flush 到磁盘                  │
  │     ├── 生成新的 Commit Point                              │
  │     └── 旧的 Translog 被删除                               │
  └──────────────────────────────────────────────────────────┘

  宕机恢复流程：
  ┌──────────────────────────────────────────────────────────┐
  │  节点宕机后重启                                            │
  │  1. 从最后一个 Commit Point 恢复已 flush 的数据            │
  │  2. 重放 Translog 中未 flush 的写入操作                    │
  │  3. 数据完整恢复                                           │
  │                                                            │
  │  数据丢失的可能性：                                        │
  │  Translog 配置为每次请求 fsync（默认）：不丢失             │
  │  Translog 配置为异步 fsync：可能丢失最几秒的数据           │
  └──────────────────────────────────────────────────────────┘
```

### Flush——Translog 的"清理时刻"

Flush 与 Refresh 是 ES 中最容易被混淆的两个概念：

```
Refresh vs Flush 的区别：

  Refresh（轻量操作，每秒发生）：
  目的：让新数据可被搜索
  操作：将 In-memory Buffer 写入文件系统缓存（不是直接刷盘）
  代价：很小（一次文件写入）
  触发：默认每秒一次

  Flush（重量操作，每 30 分钟或 Translog 达 512MB 触发）：
  目的：将文件系统缓存中的数据刷到磁盘，清空 Translog
  操作：fsync 刷盘 + 更新 Commit Point + 删除旧 Translog
  代价：较大（磁盘 I/O）
  触发：Translog 大小达到上限或时间间隔
```

```
Flush 的触发条件：

  条件 1：Translog 大小超过上限（默认 512MB）
  ┌────────────────────────────────────────────┐
  │  PUT my_index/_settings                    │
  │  { "index": {                              │
  │    "translog": {                           │
  │      "flush_threshold_size": "1024mb"     │
  │    }                                       │
  │  } }                                       │
  │  增大此值 → 更少的 Flush → 更高的写入吞吐│
  │            但宕机后恢复时间更长            │
  └────────────────────────────────────────────┘

  条件 2：时间间隔（默认 30 分钟）
  ┌────────────────────────────────────────────┐
  │  即使 Translog 没到 512MB，每 30 分钟也会  │
  │  自动 flush 一次                           │
  └────────────────────────────────────────────┘
```

## 2.2 Segment 的不可变性与合并（Merge）

### 为什么 Segment 是不可变的？

Lucene 选择不可变 Segment（immutable segment）的设计，与操作系统的文件缓存机制密切相关：

```
不可变 Segment 的三大好处：

  好处 1：OS PageCache 缓存永不失效
  ┌────────────────────────────────────────────┐
  │  文件在磁盘上是不变的                        │
  │  OS PageCache 缓存了这个文件的内容           │
  │  下次读同一个文件 → 直接从内存读取           │
  │  因为是只读的 → 缓存永远不会被失效           │
  │                                            │
  │  对比：MySQL 的 B+ 树页如果被修改            │
  │  对应的 PageCache 缓存失效                  │
  │  下次读需要重新从磁盘加载                    │
  └────────────────────────────────────────────┘

  好处 2：没有锁竞争
  ┌────────────────────────────────────────────┐
  │  不需要读写锁                               │
  │  读操作直接读 Segment                       │
  │  写操作创建新的 Segment                     │
  │  读和写互不干扰                             │
  └────────────────────────────────────────────┘

  好处 3：缓存友好
  ┌────────────────────────────────────────────┐
  │  数据在内存中是连续的                        │
  │  CPU 缓存命中率高                           │
  │  遍历倒排索引时，按顺序读取内存              │
  └────────────────────────────────────────────┘
```

### 问题：小 Segment 太多会怎样？

每次 Refresh 产生一个 Segment，默认每秒一个。一小时后就有 3600 个 Segment。如果不合并，后果严重：

```
小 Segment 过多的问题：

  ┌──────────────────────────────────────────────────────────┐
  │  Segment 1  │  Segment 2  │  Segment 3  │  ...  3600 个  │
  └────────────┴────────────┴────────────┴──────────────────┘

  搜索一个词时：
  1. 打开 Segment 1 的倒排索引 → 查 → 有结果
  2. 打开 Segment 2 的倒排索引 → 查 → 有结果
  3. 打开 Segment 3 的倒排索引 → 查 → 无结果
  4. ... 打开 3600 个 Segment → 查 → 汇总结果

  一个搜索请求 → 打开 3600 个文件 → 每个文件都要查一次 → 文件句柄耗尽
  → 搜索越来越慢 → 最终 OOM
```

### 后台 Merge 线程

ES 的后台 Merge 线程在后台持续将小的 Segment 合并为大的 Segment：

```
Merge 的工作方式：

  合并前：
  ┌─────┐┌─────┐┌─────┐┌─────┐┌─────┐
  │  S1 ││  S2 ││  S3 ││  S4 ││  S5 │  ← 5 个小 Segment
  └─────┘└─────┘└─────┘└─────┘└─────┘
                              │
                         合并线程
                              │
                              ▼
  合并后：
  ┌─────────────────────┐┌─────┐
  │  合并 Segment M1    ││  S5 │  ← M1 包含 S1-S4 的数据
  │  (删除重复数据)      ││     │     S1-S4 标记为删除
  └─────────────────────┘└─────┘
                              │
                         合并线程（继续）
                              │
                              ▼
  最终：
  ┌────────────────────────────────────┐
  │  大 Segment M（合并所有小 Segment）  │
  │  （最理想状态）                      │
  └────────────────────────────────────┘
```

```
Merge 策略：

  ES 使用 Tiered Merge Policy（分层合并策略）：
  
  层级划分：
  层级 0：10MB 以下的 Segment
  层级 1：10MB - 50MB 的 Segment
  层级 2：50MB - 250MB 的 Segment
  层级 3：250MB - 1GB 的 Segment
  ...

  合并规则：
  每一层中的 Segment 数量超过阈值 → 触发合并
  同层合并 → 生成下一层大小的 Segment

  效果：
  刚 refresh 的小 Segment（10MB）会很快被合并
  大 Segment（几 GB）很少触发合并
  → 写入压力大的时候 Merge 线程也忙
  → 如果 Merge 赶不上 Refresh 的速度
  → Segment 数量持续增长 → 搜索变慢
```

### force_merge——手动强制合并

对于不再写入的索引（如日志索引归档），可以执行 `force_merge` 将所有 Segment 合并为 1 个（或指定数量）：

```json
// 对只读索引执行强制合并
// 适用场景：日志索引每天一个，昨天的索引不会再写入了

// 1. 将索引设为只读
PUT my_log_index_2024-01-01/_settings
{
  "index": {
    "blocks.write": true  // 禁止写入
  }
}

// 2. 强制合并为 1 个 Segment
POST my_log_index_2024-01-01/_forcemerge?max_num_segments=1

// 性能提升：
// 合并前：500 个 Segment → 搜索需要打开 500 个文件
// 合并后：1 个 Segment → 搜索只需要打开 1 个文件
// 搜索延迟：从 50ms 降到 5ms

// ⚠️ 注意：force_merge 是 I/O 密集型操作
// 建议在业务低峰期执行
// 对正在写入的索引执行 force_merge 是没有意义的
// （refresh 会不断产生新的 Segment）
```

## 2.3 分布式读写模型（Scatter-Gather）

### 写入路由——为什么主分片数不能改？

ES 将数据分布在多个分片中，每个文档的去向由路由公式决定：

```
路由公式：
  shard = hash(routing) % number_of_primary_shards

  例子：
  写入文档 _id = "doc_1001"
  hash("doc_1001") % 5 = 3
  → 这个文档属于分片 3

  为什么主分片数不能修改？
  如果创建索引时设了 5 个主分片，试图再改为 10 个：

  原来：hash("doc_1001") % 5 = 3 → 在分片 3
  如果改为 10：hash("doc_1001") % 10 = 8 → 在分片 8

  原来在分片 3 的数据，按新公式应该在分片 8
  但分片 8 没有这些数据！→ 搜索不到 doc_1001
  
  所以：主分片数一旦创建，永久不可修改。
  要重新分片，必须重建索引（Reindex）。
```

```
自定义路由：

  默认使用 _id 作为路由，但如果使用自定义路由（如 tenant_id）：

  PUT my_index/_doc/doc_1001?routing=tenant_42
  { "title": "test", "tenant_id": "tenant_42" }

  shard = hash("tenant_42") % number_of_primary_shards

  这样所有 tenant_42 的文档都落在同一个分片上
  → 按 tenant_id 搜索时，只需要查一个分片
  → 不需要广播到所有分片（Scatter-Gather 的优化）
```

### 读取两阶段：Query Phase + Fetch Phase

ES 的搜索请求分为两个阶段。理解这两个阶段，你就理解了为什么深度分页是灾难：

```
搜索的两阶段流程：

  客户端           协调节点              分片 1           分片 2           分片 3
    │                │                    │                │                │
    │  搜索请求       │                    │                │                │
    │ ────────────►  │                    │                │                │
    │                │                    │                │                │
    │                │  Query Phase       │                │                │
    │                │  广播到所有分片     │                │                │
    │                │ ─────────────────► │                │                │
    │                │ ─────────────────────────────────► │                │
    │                │ ────────────────────────────────────────────────► │
    │                │                    │                │                │
    │                │  每个分片在本地查询  │                │                │
    │                │  返回 (docId, score)│                │                │
    │                │ ◄────────────────── │                │                │
    │                │ ◄─────────────────────────────────── │                │
    │                │ ◄────────────────────────────────────────────────── │
    │                │                    │                │                │
    │                │  协调节点合并结果    │                │                │
    │                │  排序（全局 Top N） │                │                │
    │                │                    │                │                │
    │                │  Fetch Phase       │                │                │
    │                │  根据 docId 获取    │                │                │
    │                │  完整的 _source    │                │                │
    │                │ ─────────────────► │                │                │
    │                │ ─────────────────────────────────► │                │
    │                │ ────────────────────────────────────────────────► │
    │                │                    │                │                │
    │                │ ◄── _source ───────│                │                │
    │                │ ◄── _source ──────────────────────│                │
    │                │ ◄── _source ───────────────────────────────────── │
    │                │                    │                │                │
    │                │ 组装结果，返回       │                │                │
    │ ◄── 结果 ─────│                    │                │                │
```

```
深度分页的问题（from: 10000, size: 10）：

  Query Phase 时：
  每个分片（假设有 5 个）准备 10010 条 (docId, score)
  共 5 × 10010 = 50050 条数据返回给协调节点
  协调节点对 50050 条数据排序，取第 10000-10010 条
  → 50050 条数据的排序在大数据量下也能承受

  Fetch Phase 时：
  协调节点从每个分片取 10 条 _source
  5 个分片 × 10 条 = 50 条
  没问题！

  但如果 from: 1000000, size: 10：
  每个分片准备 1000010 条 (docId, score)
  5 × 1000010 = 5000050 条
  协调节点对 500 万条数据排序！
  内存占用：500 万 × (docId + score) ≈ 100MB
  如果是 10 个并发搜索 → 1GB → OOM！
```

## 本章总结

| 机制 | 作用 | 触发频率 | 性能影响 |
|------|------|---------|---------|
| **Refresh** | 使新数据可搜索 | 默认每秒一次 | 轻量，产生小 Segment |
| **Translog** | 保证数据不丢失 | 每次写入 | 每次写入写一次磁盘 |
| **Flush** | 清空 Translog | 每 30 分钟或 Translog 达 512MB | 较重，fsync 刷盘 |
| **Merge** | 合并小 Segment | 后台持续 | I/O 密集型，但必不可少 |
| **Query Phase** | 协调节点广播到所有分片 | 每次搜索 | 与分片数量成正比 |
| **Fetch Phase** | 根据 docId 取 _source | 每次搜索 | 与返回条数成正比 |

**核心原则**：
1. **ES 的 "近实时" 本质是 Refresh 延迟**——默认 1 秒。如果需要实时可见（如运营后台），可以手动 `_refresh`；如果不需要实时（如日志），可以关掉 refresh 获得更高写入吞吐
2. **主分片数一旦创建不可更改**——这是路由公式决定的。在创建索引前就要规划好分片数（通常按 10GB-50GB 每个分片估算）
3. **深度分页不要用 from/size**——协调节点需要在内存中排序所有分片返回的数据，from 越大越危险。用 `search_after` + PIT 替代
4. **Segment 是双刃剑**——Refresh 产生的小 Segment 太多会降低搜索性能，但 Merge 又是 I/O 密集型操作。在写入高峰时，Merge 可能成为瓶颈
