# 第14章：Agent 与子任务编排

## 章节概述

Claude Code 不仅仅是一个对话式的编码助手——它内置了强大的 Agent 系统，能够自主地将复杂任务分解为子任务，并按需创建子 Agent 并行执行。这是 Claude Code 区别于普通 AI 编码助手的核心能力之一。

本章将深入讲解 Agent 架构、类型选择、任务分解策略、并行编排模式以及常见的工作流设计模式。学完本章，你将能够设计并实施多 Agent 协作的工作流，显著提升处理大型复杂任务的效率。

## 学习目标

- 理解 Claude Code 的 Agent 架构和两种核心类型（Explore 与 General）
- 掌握任务分解的粒度控制和依赖关系管理
- 学会构建多 Agent 协作工作流（扇出/扇入、流水线等模式）
- 能够设计高效的并行执行策略并处理错误

## 核心知识点

### 1. Agent 类型与选择

Claude Code 的 Agent 系统基于 **Task 工具**实现，这是一种允许当前会话创建子 Agent 并将其委派执行子任务的机制。理解不同类型的 Agent 及其适用场景是编排工作的基础。

#### Agent 架构概览

Claude Code 的 Agent 系统采用分层架构：

```
主会话 (Main Session)
  ├── 子 Agent 1 (Explore)
  │    └── 子 Agent 1.1 (Explore)
  ├── 子 Agent 2 (General)
  └── 子 Agent 3 (General)
       └── 子 Agent 3.1 (Explore)
```

每个子 Agent 拥有独立的上下文窗口，可以访问文件系统、执行命令，并能创建自己的子 Agent。这种递归结构使得处理任意复杂度的任务成为可能。

#### Agent 类型概览

Claude Code 提供了两种核心 Agent 类型，通过 Task 工具的 `agent` 参数指定：

| 特性 | Explore | General |
|------|---------|---------|
| 行为模式 | 探索性、开放式 | 目标导向、指令跟随 |
| 最佳任务类型 | 研究、调查、分析 | 编码、实现、重构 |
| 自主程度 | 高（自主探索） | 中（按指令执行） |
| 输出一致性 | 较低 | 较高 |
| 上下文效率 | 可能发散 | 更聚焦 |

**Explore Agent**：当任务需要探索性工作、没有明确路径时使用。例如"调研这个项目的测试覆盖率状况"——Explore Agent 会自行决定查看哪些文件、运行哪些命令来收集信息。

**General Agent**：当任务有明确的输入输出规范时使用。例如"在 `src/utils/validate.ts` 中添加 email 验证函数"——General Agent 会精确执行指令，不进行超出范围的探索。

#### Agent 能力边界

理解 Agent 的能力边界对避免误用至关重要：

- **上下文限制**：每个子 Agent 有自己的上下文窗口（约 100K tokens），但不共享主会话的历史。意味着子 Agent 无法知道主会话中之前的对话内容，除非显式传递。
- **工具访问**：所有 Agent 都可以访问文件系统、执行命令等核心工具，但无法创建新的工具或修改工具权限。
- **递归深度**：Agent 可以递归创建子 Agent，但深度过深（超过 3-4 层）可能导致指令传递失真。

#### 自定义 Agent 配置

通过项目配置（`opencode.json` 或 `CLAUDE.md`），可以自定义 Agent 的默认行为：

```json
{
  "agent": {
    "defaultType": "general",
    "maxSubAgents": 5,
    "timeoutSeconds": 300
  }
}
```

在 CLAUDE.md 中可以定义特定类型任务的 Agent 行为偏好：

```
## 任务约定

对于代码生成任务，使用 General Agent，严格遵循项目现有的代码风格。
对于技术调研任务，使用 Explore Agent，需要输出调研报告的 Markdown 文件。
```

### 2. 任务分解策略

把一个大任务拆解成合适的子任务是 Agent 编排成功的关键。拆得太大，单个 Agent 无法高效处理；拆得太小，Agent 间通信和协调开销会抵消并行收益。

#### 任务粒度控制

判断粒度是否合适的经验法则：

| 粒度 | 子任务规模 | 适用场景 | 风险 |
|------|-----------|---------|------|
| 粗粒度 | 1 Agent 处理 1 个完整功能 | 功能间耦合度高 | Agent 上下文可能不足 |
| 中粒度 | 1 Agent 处理 1-2 个文件 | 标准 CRUD 开发 | 较优选择 |
| 细粒度 | 1 Agent 处理 1 个函数/方法 | 复杂算法实现 | Agent 间通信开销大 |

推荐的粒度是：**一个子任务应该在 30-60 分钟内完成**。如果预判超过这个时间，应该继续拆分。

#### 依赖关系分析

任务分解后，需要识别依赖关系。常用的依赖类型：

- **数据依赖**：子任务 B 需要子任务 A 的输出（如：先定义接口，再实现实现类）
- **资源依赖**：子任务 B 需要子任务 A 创建的资源（如：先建数据库表，再写 DAO 层）
- **知识依赖**：子任务 B 需要子任务 A 产生的决策（如：先确定设计模式，再编写具体代码）

示例：实现一个用户注册功能的任务依赖图

```
Task: 实现用户注册功能
├── T1: 定义 User 实体和数据库表 (无依赖)
├── T2: 实现 UserRepository 接口 (依赖 T1)
├── T3: 实现注册校验逻辑 (依赖 T1)
├── T4: 实现注册 Controller (依赖 T2, T3)
├── T5: 编写单元测试 (依赖 T2, T3, T4)
└── T6: 编写集成测试 (依赖 T4)
```

向 Claude Code 描述依赖：

```
请分析以下子任务的依赖关系：
- 定义 User 实体
- 实现 Repository
- 实现注册校验
- 实现 Controller
- 编写单元测试
输出一个拓扑排序后的执行顺序，并标注哪些任务可以并行。
```

#### 优先级排序

在资源有限的情况下（如 Agent 并发数限制），需要为任务排定优先级：

```
请对以下子任务进行 MoSCoW 优先级排序：
Must have: 核心功能（登录、注册、权限校验）
Should have: 密码重置、邮箱验证
Could have: 第三方登录（Google/GitHub）
Won't have: 社交账号关联、用户标签管理

为每个优先级的任务预估工作量（小时）。
```

#### 任务依赖图构建

Claude Code 可以基于你的描述生成可视化的依赖图（文本形式或 Mermaid 格式）：

```
根据之前的依赖分析，请生成 Mermaid 格式的甘特图，
展示任务的依赖关系和并行执行窗口。
```

### 3. 并行执行编排

并行执行是 Agent 编排的核心价值所在。Claude Code 的 Task 工具允许并发创建多个子 Agent，实现真正的并行处理。

#### 独立任务并行化

识别无依赖关系的子任务后，可以一次性提交并行执行：

```
请同时完成以下独立任务：
1. 创建 User 实体类（参考现有 User 实体写法）
2. 创建 Product 实体类（参考现有 Product 实体写法）
3. 创建 Order 实体类（参考现有 Order 实体写法）

每个实体的标准：JPA 注解、Lombok、validation 注解、统一继承 BaseEntity。
完成后将结果输出到对应文件。
```

Claude Code 会为每个独立任务创建一个子 Agent，所有子 Agent 并行工作。这意味着理论上 3 个实体可以同时生成，总时间 ≈ 单个实体生成时间。

#### 结果聚合策略

并行任务完成后，需要将结果聚合：

```
以上 3 个实体已经创建完毕。现在请执行以下聚合操作：
1. 检查 3 个文件的代码风格一致性（命名、注解使用、继承关系）
2. 检查它们之间的关联关系是否正确（如 Order 引用 User 和 Product）
3. 如果不一致，统一修复
4. 生成一个变更摘要
```

聚合 Agent 会依次检查每个子 Agent 的输出，进行交叉验证和一致性保证。这是多 Agent 编排中容易遗漏但至关重要的步骤。

#### 错误处理与重试

并行执行中的错误处理策略：

```
任务执行中可能会出错。请遵循以下错误处理策略：
- 如果某个子任务失败（如编译错误），记录错误日志但不要中止其他子任务
- 所有子任务完成后，汇总失败任务
- 对于失败任务，自动重试最多 2 次
- 如果重试仍然失败，生成详细的错误报告，包括：
  - 失败的具体文件位置
  - 错误类型（语法/逻辑/依赖缺失）
  - 建议的修复方案
```

#### 执行进度监控

对于长时间运行的多 Agent 工作流，需要进度可见性：

```
请执行以下步骤并每完成 20% 报告一次进度：
- 总任务：为整个微服务项目生成 CRUD 代码
- 进度报告格式：[x/5] 模块名 - 完成 - 耗时 xx 秒
- 最终输出：所有生成文件的索引清单
```

Claude Code 在执行过程中会定期输出进度报告，让你了解当前所处的阶段和剩余工作量。

### 4. 工作流设计模式

实践中总结出几种可复用的工作流模式，可以直接套用到不同的项目场景中。

#### 流水线模式

**适用场景**：任务有明确的阶段划分，前一阶段输出是后一阶段输入。

```
流水线：代码生成 → 代码审查 → 测试生成 → 测试执行

Stage 1: 生成 Controller 和 Service 层代码
Stage 2: 审查生成的代码，检查是否符合架构规范
Stage 3: 为生成的代码编写单元测试
Stage 4: 执行测试，输出覆盖率报告

每个阶段完成后自动进入下一阶段，只有当前阶段通过才继续。
```

这种模式适合 CI/CD 风格的自动化工作流，每个阶段的责任清晰，易于定位问题。

#### 扇出/扇入模式

**适用场景**：一个任务需要分解为多个独立子任务并行处理，最后汇总结果。

```
扇出（Fan-out）：
  主任务：实现用户管理模块
  ├── 子 Agent 1: 实现用户 CRUD Controller
  ├── 子 Agent 2: 实现用户 Service 层
  ├── 子 Agent 3: 实现用户 Repository 层
  └── 子 Agent 4: 实现用户数据校验

扇入（Fan-in）：
  汇总所有子 Agent 的输出：
  1. 检查 API 一致性
  2. 确保 Service 引用正确的 Repository
  3. 运行集成测试验证各层协作
  4. 生成最终的变更清单
```

这是最常用的模式，最大化并行度，适合模块化良好的项目。

#### 监督式协作

**适用场景**：一个 Agent 监督其他 Agent 的工作质量，适合代码审查和架构合规场景。

```
监督架构：
  主 Agent（架构师）：定义规范和质量标准
  ├── 子 Agent 1: 实现模块 A（Genera Agent）
  ├── 子 Agent 2: 实现模块 B（Genera Agent）
  └── 子 Agent 3: 实现模块 C（Genera Agent）
  
  质量 Gate：
  ├── 子 Agent 4（Explore Agent: 审查模块 A 是否符合架构规范）
  ├── 子 Agent 5（Explore Agent: 审查模块 B 是否符合架构规范）
  └── 子 Agent 6（Explore Agent: 审查模块 C 是否符合架构规范）
```

监督 Agent 与被监督 Agent 类型不同（Explore 审查 General 的输出），确保视角差异带来的检查深度。

#### 迭代优化循环

**适用场景**：需要多轮反馈和改进的任务，如代码重构、性能优化。

```
迭代循环：
Round 1: Explore Agent 分析当前代码的坏味道
Round 2: General Agent 根据分析结果进行重构
Round 3: Explore Agent 检查重构后的代码是否引入新问题
Round 4: General Agent 修复发现的问题

循环退出条件：
- 代码坏味道数量 < 3
- 测试通过率 = 100%
- 或达到最大迭代次数（5 轮）

每轮输出变更 diff 和检查结果。
```

循环模式适合需要"分析—执行—验证—修正"闭环的任务，如代码审查修复、性能调优等。

## 实战练习

**任务**：将一个复杂开发任务分解为多个子任务，使用 Agent 编排完成整个工作流。

**步骤**：

1. **定义主任务**
   向 Claude Code 描述：
   ```
   请在项目中添加用户通知模块，包括：
   - 数据库：通知表（通知 ID、用户 ID、类型、内容、是否已读、创建时间）
   - 后端：NotificationController、NotificationService、NotificationRepository
   - 支持的通知类型：系统通知、评论回复、@提及
   - 需要单元测试和集成测试
   ```

2. **任务分解**
   让 Claude Code 分析该任务的子任务划分（分析其输出的依赖图）

3. **选择 Agent 类型**
   - 为"数据库迁移脚本编写"使用 General Agent（指令明确）
   - 为"通知服务的错误边界设计"使用 Explore Agent（需要探索性思考）

4. **编排并行执行**
   命令示例：
   ```
   请使用 Task 工具并行执行以下子任务：
   
   子任务 1（General）：
   创建通知数据库迁移脚本，包括通知表和索引
   
   子任务 2（General）：
   创建 Notification 实体类，使用 JPA 注解
   
   子任务 3（General）：
   创建 NotificationRepository，继承 JpaRepository，添加按用户查询和按未读查询方法
   
   所有子任务完成后，汇总检查文件一致性并生成变更摘要。
   ```

5. **结果聚合与验证**
   所有子任务完成后，让主 Agent 检查：
   - Controller 是否正确引用 Service
   - Service 是否正确使用 Repository
   - API 路径是否一致
   - 测试是否能覆盖主要场景

6. **迭代优化**
   如果有测试失败或代码质量问题，进入迭代循环修复。

## 本章小结

1. Claude Code 的 Agent 系统通过 Task 工具实现递归子 Agent 创建，支持多层级任务分解结构。
2. Explore Agent 适合探索性工作（调研、分析、审查），General Agent 适合指令性工作（编码、实现、重构）。
3. 任务分解的黄金粒度是 30-60 分钟可完成，拆解过细会导致通信开销超过并行收益。
4. 依赖图分析是无环执行的保证，使用拓扑排序确定安全的执行顺序。
5. 扇出/扇入是最常用的并行模式，适用于模块化良好的代码库。
6. 监督式协作中，使用不同类型的 Agent（Explore 审查 General）可以获得更好的检查效果。
7. 迭代优化循环适合需要多轮反馈的任务，必须设置明确的退出条件避免无限循环。
8. 并行任务完成后必须执行结果聚合（一致性检查），这是多 Agent 编排中最易忽略但最关键的一步。

## 思考题

1. 什么类型的任务适合使用多 Agent 协作？
   *提示：适合的任务特征——可分解为独立的子任务、子任务间耦合度低、单 Agent 上下文无法容纳完整任务、需要不同类型的处理能力（如分析 + 执行）。不适合的任务特征——强依赖串行处理、子任务间需要频繁通信、决策路径高度不确定。*

2. Agent 编排中的错误处理策略有哪些？
   *提示：三种主要策略——快速失败（一个失败则整体中止，适用于依赖链紧密的任务）、优雅降级（失败子任务标记跳过，其余继续，适用于非关键辅助任务）、自动重试（有限次数重试后仍失败则升级为人工处理）。实践中建议组合使用：对关键路径用快速失败，对非关键路径用优雅降级。*

3. 如何衡量多 Agent 编排的效率提升？
   *提示：定义基线（单 Agent 串行执行的时间），对比多 Agent 并行的 wall-clock 时间。关注三个指标：并行加速比（串行时间/并行时间）、资源利用率（实际创建 Agent 数/最大允许数）、任务成功率（无错误完成的任务数/总任务数）。注意 Amdahl's Law——不可并行部分占比决定了理论上限。*
