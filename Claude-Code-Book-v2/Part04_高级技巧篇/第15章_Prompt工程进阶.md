# 第15章：Prompt 工程进阶

## 章节概述

Prompt 工程是与 AI 交互的核心技能。在 Claude Code 的上下文中，写好 Prompt 不仅关乎单次对话的质量，更关乎整个开发工作流的效率。一个精心设计的 Prompt 可以大幅减少来回对话的次数，让 Claude Code 第一次输出就接近你想要的答案。

本章将深入讲解结构化 Prompt 的设计方法、系统提示词（CLAUDE.md）的最佳实践、上下文优化策略以及一系列高级技巧。这些技术将帮助你从"能用"跨越到"精通"。

## 学习目标

- 掌握结构化 Prompt 的设计方法（角色、指令、格式、示例）
- 学会编写和维护高效的 CLAUDE.md 项目提示词
- 理解上下文窗口管理策略，最大化每次对话的信息密度
- 能够通过思维链、约束表达等高级技巧精确控制输出

## 核心知识点

### 1. 结构化 Prompt

好的 Prompt 像好的代码——结构清晰、层次分明、易于理解。结构化 Prompt 应该包含四个核心要素。

#### 角色设定

为 Claude Code 设定明确的角色可以帮助它选择适当的"知识框架"来理解问题：

```
你是一位资深的 Python 后端架构师，专注于构建高并发微服务系统。
你在 Django、FastAPI 和 Celery 方面有 10 年经验。
请从架构角度回答以下问题。
```

角色设定不是简单地"扮演"一个角色，而是激活模型中与特定领域相关的知识模式。你在 CLAUDE.md 中设定的项目级角色会在每次对话中自动生效。

不同角色的 Prompt 效果对比：

| 角色 | 输出风格 | 适合场景 |
|------|---------|---------|
| "资深架构师" | 系统性、考虑全局 | 架构设计、技术选型 |
| "安全专家" | 偏保守、关注攻击面 | 代码审查、安全审计 |
| "DBA" | 关注索引、查询计划 | SQL 优化、数据库设计 |
| "代码 Reviewer" | 挑剔、关注坏味道 | 代码质量检查 |
| "初级开发者" | 简单、逐步解释 | 教学、文档编写 |

#### 指令分层

复杂任务应该使用分层指令结构，从抽象到具体：

```
# 高层指令（WHAT）
实现用户注册的完整后端逻辑

# 中层约束（CONSTRAINTS）
- 使用 Spring Boot 3.x + MyBatis-Plus
- 遵循 RESTful API 设计规范
- 统一异常处理和返回格式

# 底层规格（HOW）
- Controller: POST /api/users/register
- 请求体: {username, password, email}
- 密码使用 BCrypt 加密存储
- 返回标准 Result<T> 包装
- 参数校验使用 JSR-303 注解
```

这种分层方式符合人类认知的"自上而下"模式，让 AI 先理解上下文再进入细节，比直接给细节指令更容易得到一致的结果。

#### 输出格式控制

精确指定输出格式可以节省大量的后处理时间：

```
请输出以下内容：

## 文件：UserController.java
```java
[代码内容]
```

## 文件：UserService.java
```java
[代码内容]
```

## 变更摘要
| 文件 | 操作 | 说明 |
|-----|------|------|
| ... | 新增 | ... |

## 测试验证
```bash
# 验证命令
```
```

对于需要解析的结构化输出（如 CI/CD 集成），要求 JSON 格式：

```
请以 JSON 格式输出，包含以下字段：
{
  "files": [{"path": "...", "action": "create|update|delete"}],
  "summary": "变更说明",
  "testCommand": "验证命令"
}
```

#### 示例引导（Few-shot）

提供输入输出示例可以显著提高输出质量，尤其对于复杂或非常规的任务：

```
我需要编写 API 文档。请参考以下示例格式：

示例输入：
POST /api/users
请求体: { "username": "abc", "email": "a@b.com" }

示例输出：
### POST /api/users
创建新用户

**请求体**
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| username | string | 是 | 用户名，3-20 字符 |
| email | string | 是 | 邮箱，需唯一 |

**响应**
201 Created: { "id": 1, "username": "abc" }
400 Bad Request: { "error": "邮箱已存在" }

---

现在请为以下接口生成文档：
PATCH /api/users/{id}
请求体: { "username?": "new_name", "email?": "new@email.com" }
```

2-3 个精心挑选的示例往往比冗长的文字说明更有效。

### 2. 系统提示词

系统提示词是每次对话中自动注入的"背景指令"。在 Claude Code 中，核心的系统提示词载体是 **CLAUDE.md** 文件。

#### CLAUDE.md 的使用

CLAUDE.md 是放置在项目根目录的 Markdown 文件，每次启动对话时都会被加载到系统提示中。它是全局提示词的最佳实现方式：

```markdown
# CLAUDE.md

## 项目概述
这是一个基于 Spring Boot 3.2 + Vue 3 的企业级 CRM 系统。
前后端分离，MySQL 数据库，Redis 缓存。

## 代码规范
- Java 包名: com.company.crm.*
- 所有 Controller 返回统一 Result<T> 格式
- Service 层必须写单元测试（JUnit 5 + Mockito）
- API 路径使用 RESTful 风格，复数名词

## 架构约定
- 分层架构: Controller → Service → Repository
- 禁止 Service 层直接返回 Entity，必须使用 DTO
- 异常使用全局 @RestControllerAdvice 处理

## 测试要求
- 单元测试覆盖率 > 80%
- 集成测试使用 Testcontainers
- Controller 测试使用 MockMvc
```

设置好 CLAUDE.md 后，每次对话 Claude Code 都会自动遵循这些约定，无需重复说明。

#### 项目级指令配置

除了 CLAUDE.md，还可以使用 `opencode.json` 配置文件设定粒度更细的指令：

```json
{
  "systemPrompt": "你是一位资深的全栈工程师，熟悉 Java、Vue、Docker 和 Kubernetes。",
  "ignorePatterns": ["node_modules", "target", "*.generated.*"],
  "customInstructions": {
    "formatting": {
      "lineLength": 100,
      "indentSize": 2
    }
  }
}
```

`opencode.json` 中的配置优先级高于 CLAUDE.md，适用于更技术性的设置（如路径忽略、格式化规则）。

#### 全局 vs 局部提示词

| 类型 | 载体 | 作用范围 | 示例 |
|------|------|---------|------|
| 全局提示词 | CLAUDE.md | 项目所有对话 | 编码规范、架构约定 |
| 对话提示词 | 用户消息 | 单次对话 | 本次任务的具体指令 |
| 临时提示词 | 单条消息 | 单次回复 | 当前问题的约束条件 |

CLAUDE.md 设定"不变"的规则，对话中设定"本次变化"的需求。好的分工是：CLAUDE.md 减少重复说同样的规则，对话 Prompt 专注于每次任务的独特要求。

#### 提示词版本管理

CLAUDE.md 应该纳入版本控制，并像代码一样进行 review：

```
# 变更记录
## 2025-01-15 - v2.1
- 新增：Dockerfile 必须使用多阶段构建
- 修改：MySQL 版本从 8.0 升级到 8.4
- 移除：已废弃的 Feign 客户端规范

## 2024-12-01 - v2.0
- 全面更新为 Spring Boot 3.x 规范
- 新增：Testcontainers 测试规范
```

将提示词变更与代码变更关联，确保任何开发者（和 AI）都能理解当前项目的工作方式。

### 3. 上下文优化

Claude Code 的上下文窗口虽然很大（约 100K tokens），但合理管理仍然是高效使用的关键。乱用上下文会导致回复变慢、质量下降。

#### 上下文窗口管理

理解上下文窗口的组成部分：

```
总上下文 = 系统提示词 (CLAUDE.md) + 历史消息 + 当前输入 + 工具输出
```

估算你的对话消耗：

```
CLAUDE.md: ~1K tokens
历史对话（20 轮）: ~10-20K tokens
当前输入: ~0.5-2K tokens
工具输出（文件读取）: ~1-50K tokens (取决于文件大小)
总计: ~12-73K tokens
```

当上下文接近窗口上限时，回复质量会下降。触发的标志包括：回复变慢、开始"遗忘"早期的约定、执行命令的结果不完整。

**上下文清理策略**：

```
请忽略之前的对话历史。这是新的开始。
当前上下文：
- 项目: CRM 系统
- 当前正在工作: UserController 的单元测试
- 已有知识: CLAUDE.md 中的项目规范
请基于以上信息，直接回答我的问题。
```

这相当于"软重置"——给 AI 一个重新聚焦的机会。

#### 关键信息优先策略

将最重要的信息放在消息的开头和结尾（AI 模型对首尾内容的注意力更高）：

```
关键约束（请优先处理）：
1. 不要修改现有的接口定义
2. 所有新代码测试覆盖率必须 > 90%
3. 兼容 Java 17 和 Java 21

以下是具体需求：
[详细描述...]
```

Claude Code 的注意力机制倾向于关注消息头部的指令。因此，"最重要的指令放最前面，细节放后面"是最佳策略。

#### 冗余信息过滤

提交任务时，避免大段无关上下文：

```
❌ 错误做法：
"我之前提到过 User 实体有 20 个字段，然后讨论了缓存策略，
还写过邮件通知功能……（省略 5000 字历史）现在请帮我改一个字段名。"

✅ 正确做法：
"请在 User 实体中将字段 'tel' 重命名为 'phone'。
User 实体路径: src/main/java/com/crm/entity/User.java
需要同步修改的地方: UserDTO、UserVO、Mapper XML。
之前关于缓存和通知的讨论与此无关，请忽略。
```

如果 Claud Code 需要读取文件了解上下文，明确指定文件路径，而不是在对话中粘贴大量内容。

#### 长对话保持一致性

随着对话增长，Claude Code 可能"忘记"早期的约定。重置策略：

```
在继续之前，请回顾当前进度：
1. 我们完成了哪些内容？（请列出已完成文件的列表）
2. 下一步计划是什么？
3. 有哪些还在进行中的决策？
```

这种"检查点"式的总结可以让双方对齐认知，避免"我以为你说过了但是实际上没有"的误解。

### 4. 高级技巧

#### 思维链提示（Chain-of-Thought）

对于复杂逻辑任务，要求 Claude Code 展示推理过程：

```
请使用思维链方式分析以下代码的性能瓶颈：

```java
public List<Order> getOrders(Long userId) {
    var user = userRepo.findById(userId);
    var orders = orderRepo.findByUser(user);
    for (var order : orders) {
        order.setItems(itemRepo.findByOrder(order));
        for (var item : order.getItems()) {
            item.setReviews(reviewRepo.findByItem(item));
        }
    }
    return orders;
}
```

请先逐步分析，再给出优化方案。
步骤：
1. 识别潜在的 N+1 查询
2. 估算当前复杂度
3. 提出优化方案
4. 给出优化后的代码
```

思维链不仅有助于获得更好的答案，还能让你看到 AI 的"推理路径"，便于发现和纠正错误。

#### 约束条件表达

使用结构化方式表达约束，而非自然语言：

```
// 好：结构化约束
约束列表：
- [硬性] 不能引入新的第三方依赖
- [硬性] 兼容现有的所有单元测试
- [软性] 优先使用 Stream API 而非 for 循环
- [度量] 性能不能低于当前实现的 90%

// 不好：散装约束
"尽量用简单的方法实现，不要用太多外部库，
要保证兼容现有测试，速度不能太慢。"
```

明确的约束表达让 AI 能在搜索解空间时快速剪枝，避免生成不符合要求的方案。

#### 多轮迭代策略

不要期望一次 Prompt 就拿到完美结果。采用迭代策略：

```
Round 1: "生成 UserController 的 CRUD 方法"
Round 2: "在 createUser 方法中添加邮箱唯一性校验"
Round 3: "将所有方法的返回值从 User 改为 UserDTO"
Round 4: "添加 Swagger 注解到所有接口"
```

每一轮聚焦一个关注点，避免在一轮中提出过多要求导致 AI "顾此失彼"。

#### 反馈循环设计

当 Claude Code 的输出不符合预期时，提供具体的反馈：

```
❌ 模糊反馈："这个代码不够好"

✅ 具体反馈：
"代码需要改进的地方：
1. 第 15 行：直接用字符串拼接 SQL 有注入风险，请改用参数化查询
2. 第 42 行：这个方法的圈复杂度超过 10，请拆分为更小的方法
3. 缺少异常处理：当数据库连接失败时应该有降级逻辑
请只修复以上问题，不要改动其他部分。"
```

具体反馈相当于 debug 指令，让 AI 精确理解问题所在，避免"修好了一个问题又引入新问题"的连锁反应。

## 实战练习

**任务**：为一个特定开发任务设计一套完整的 Prompt 体系

**场景**：你需要在 Spring Boot 项目中添加一个新的"评论审核"功能模块。

**步骤**：

1. **编写 CLAUDE.md 片段**
   为这个项目添加评论模块的专属规范：
   ```
   ## 评论审核模块规范
   - 审核状态枚举: PENDING, APPROVED, REJECTED, FLAGGED
   - 审核操作需要记录操作人和操作时间
   - 评论内容长度限制 1-2000 字符
   - 敏感词过滤在 Service 层实现
   - 所有审核操作需要有日志记录
   ```

2. **设计结构化 Prompt**
   编写一个包含角色、指令分层、输出格式控制的 Prompt：

   ```
   你是一位 Java 后端开发者，熟悉 Spring Boot 和 JPA。

   ## 任务
   实现评论审核的 Service 层逻辑

   ## 约束
   - 使用 Review Entity（已有），新增 status、reviewedBy、reviewedAt 字段
   - 审核操作：通过、拒绝、标记
   - 拒绝时需要提供拒绝原因
   - 通过后自动触发通知

   ## 输出
   ### 文件: ReviewService.java
   [具体代码]
   ### 文件: ReviewController.java  
   [具体代码]
   ```

3. **使用示例引导**
   在 Prompt 中加入一个已有的 Service 实现作为参考示例，确保风格一致。

4. **多轮迭代**
   - Round 1: 生成基础实现
   - Round 2: 要求添加事务管理
   - Round 3: 要求添加缓存（Redis）
   - Round 4: 要求添加性能监控（Micrometer）

5. **上下文优化**
   每轮开始前，手动清理无关的历史内容（"忽略上一轮的输出，我们专注于……"）

完成练习后，你应该能感受到：好的 Prompt + 迭代策略 vs 一次性 Complete Prompt 之间的效率差异。

## 本章小结

1. 结构化 Prompt 的四要素（角色、指令分层、格式控制、示例引导）缺一不可，组合使用效果远超单独使用。
2. CLAUDE.md 是 Claude Code 系统提示词的核心载体，应该像代码一样纳入版本管理、定期 review。
3. 全局提示词（CLAUDE.md）解决"不变"的约定，对话提示词解决"本次变化"的需求，两者分工协作。
4. 上下文管理的关键策略：重要信息放首尾、过滤冗余内容、适时软重置（清理历史）。
5. 思维链（Chain-of-Thought）适用于复杂逻辑任务，能显著提升输出质量和可追溯性。
6. 约束条件使用结构化表达（明确标注硬性 vs 软性）比自然语言描述效果更好。
7. 多轮迭代优于一次性 Prompt——每轮聚焦一个关注点，总输出的质量和一致性更好。
8. 反馈要具体（指出行号、具体问题），模糊反馈会导致 AI 做出不相关的修改。

## 思考题

1. Prompt 工程中最常见的错误是什么？
   *提示：最常见的三个错误——（1）过度追求"完美的一次性 Prompt"，实际上多轮迭代效果更好；（2）忽略 CLAUDE.md 的作用，每次对话重复相同的指令，既浪费上下文又容易遗漏；（3）反馈过于模糊（"不够好"、"改进一下"），没有指出具体问题位置和期望的修改方向。*

2. 如何评估和优化 Prompt 的效果？
   *提示：建立评估维度——输出与预期的一致率、平均迭代轮数（轮数越少说明 Prompt 越精确）、是否需要后处理（格式修正、内容校验）。优化方法：A/B 测试不同 Prompt 结构（如同等条件下对比"有角色设定 vs 无角色设定"的输出质量）、持续迭代 CLAUDE.md（每次发现 AI 在某个方面反复出错，就在 CLAUDE.md 中增加对应的规则）。*

3. 在什么场景下应该避免使用思维链提示？
   *提示：思维链适用于需要逐步推理的复杂任务（算法设计、性能分析、架构决策）。但在简单任务上使用思维链反而会增加 token 消耗并可能引入不必要的"噪音"——比如"这个文件路径是什么"就不需要 AI 展示思考过程。判断标准：如果一个人类开发者 30 秒内能完成的任务，就不要用思维链。*
