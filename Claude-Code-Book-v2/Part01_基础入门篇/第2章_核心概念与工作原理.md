# 第2章：核心概念与工作原理

## 章节概述

本章深入讲解 Claude Code 的核心概念和工作原理，包括对话模型架构、上下文管理机制、工具调用系统和安全模型。理解这些底层机制对于高效使用 Claude Code 至关重要——它解释了为什么 Claude Code 有时表现得"聪明"、何时会遇到"瓶颈"，以及如何通过调整使用策略来最大化其效能。本章将帮助你从"会用"进阶到"懂用"。

- 了解 Claude Code 的安全模型和权限控制体系

## 核心知识点

### 1. 对话模型架构

#### 大语言模型基础

Claude Code 的智能核心来自 Anthropic 的大语言模型（LLM）。要理解 Claude Code 的工作原理，首先需要了解 LLM 的基本运行机制。

LLM 本质上是基于 Transformer 架构的深度神经网络，经过海量文本数据的预训练，学会了理解和生成人类语言。当用户输入一段文本（称为"提示"或 Prompt）时，模型会将其分解为 Token，然后通过多层注意力机制计算每个 Token 之间的关系，逐步预测并生成最合理的后续 Token。

一个关键的认知是：**LLM 并不真正"理解"代码，而是在统计层面上预测最可能正确的输出**。然而，当训练数据足够庞大、模型参数足够多时，这种统计预测的效果可以达到令人惊叹的准确度。Claude 模型在代码数据上进行了专门训练，能够理解数十种编程语言的语法、惯用法和最佳实践。

Claude Code 并不直接在原始 LLM 上运行，而是在 LLM 之上叠加了多层工程架构：

```
用户输入（自然语言）
        ↓
  ┌─────────────────┐
  │  意图解析层      │ ← 理解用户想要什么
  ├─────────────────┤
  │  工具选择层      │ ← 决定使用哪些工具
  ├─────────────────┤
  │  工具执行层      │ ← 调用具体工具
  ├─────────────────┤
  │  结果综合层      │ ← 整合结果生成回复
  └─────────────────┘
        ↓
  ┌─────────────────┐
  │  Claude LLM      │ ← 底层语言模型
  └─────────────────┘
```

#### Claude 模型家族特点

Anthropic 的 Claude 模型系列经历了多次迭代，每个版本都有不同的特点和适用场景：

| 模型版本 | 发布年份 | 特点 | 在 Claude Code 中的表现 |
|---------|---------|------|----------------------|
| Claude 2 | 2023 | 基础版本，代码能力一般 | 已不再作为默认模型 |
| Claude 3 Haiku | 2024 | 轻量快速，低延迟 | 适合简单任务和快速迭代 |
| Claude 3 Sonnet | 2024 | 平衡速度与质量 | Claude Code 早期默认模型 |
| Claude 3.5 Sonnet | 2024 | 代码能力大幅提升 | 最受欢迎的编码模型 |
| Claude 3.5 Haiku | 2024 | 速度与质量的优化平衡 | 适合日常开发任务 |
| Claude 4 Sonnet | 2025 | 更强推理和工具使用能力 | 最新旗舰编码模型 |

Claude 模型在代码任务上的优势主要来源于：
- **长上下文窗口**：最高可达 200K Token，可以容纳整个中型项目的代码
- **多语言覆盖**：对 Python、JavaScript、TypeScript、Rust、Go 等主流语言均有出色表现
- **指令跟随能力**：能精确理解复杂的、多步骤的指令
- **工具使用（Tool Use）**：原生支持调用外部工具和函数

#### 对话历史管理

Claude Code 的对话管理采用多轮交互架构。每次用户输入和 AI 响应都会被记录到对话历史中，并作为后续请求的上下文发送给模型。

对话历史的组织方式：

```
会话 Session
  ├── 消息 1: 用户输入
  ├── 消息 2: AI 响应（可能包含工具调用）
  │     ├── 工具调用 1: 读文件
  │     ├── 工具调用 2: 写文件
  │     └── 工具调用 3: 执行命令
  ├── 消息 3: 用户输入
  ├── 消息 4: AI 响应
  └── ...
```

每次新的用户请求都会携带完整的对话历史（在上下文窗口允许的范围内）。这意味着：
- 越早的对话内容，对当前行为的影响可能越小（被后面的大量 Token "稀释"）
- 对话越长，每次请求的成本（Token 消耗）越高
- 当对话历史超过上下文窗口限制时，需要进行压缩或截断

### 2. 上下文管理

#### 上下文窗口的概念

上下文窗口是 LLM 在单次推理中能处理的 Token 数量上限。可以把它理解成模型的"工作记忆"——窗口越大，模型能同时"看到"的信息就越多。

Claude 3.5 Sonnet 和 Claude 4 系列模型支持 200K Token 的上下文窗口。这是什么概念？

```
200K Token ≈
  - 约 15 万英文单词
  - 约 10 万中文字符
  - 约 5000-8000 行代码
  - 约 3-5 个中型代码文件 + 完整对话历史
```

上下文窗口决定了 Claude Code 能"看到"多少项目代码。如果整个项目的代码量超出了上下文窗口，Claude Code 就需要有策略地选择哪些文件应该被包含在上下文中。

#### Token 计算方式

Token 是 LLM 处理文本的基本单位。不同模型使用不同的 Tokenizer（分词器），Claude 模型使用 SentencePiece 分词器。

**Token 计数估算：**
- 英文：约 1 Token ≈ 0.75 个英文单词
- 中文：约 1 Token ≈ 1.5 个中文字符
- 代码：约 1 Token ≈ 3-4 个字符（取决于语法密集度）

```python
# Token 计数示例（伪代码）
# Claude 的 Tokenizer 对代码的编码效率较高

text_english = "Hello, world! This is a simple example."
# Token 数 ≈ 7

text_chinese = "你好，世界！这是一个简单的例子。"
# Token 数 ≈ 13

code_python = """
def fibonacci(n):
    if n <= 1:
        return n
    return fibonacci(n-1) + fibonacci(n-2)
"""
# Token 数 ≈ 25
```

实际使用时，可以通过 `/cost` 命令查看当前会话的 Token 消耗：

```bash
# 在 Claude Code 会话中
/cost
# 输出：
# 输入 Token: 12,345
# 输出 Token: 4,567
# 总消耗: 16,912 Token
# 预计费用: $0.XX
```

#### 上下文压缩策略

当对话变长或项目变大时，上下文窗口可能不够用。Claude Code 采用多种策略来管理上下文空间：

**策略一：滑动窗口（对话历史管理）**
Claude Code 不会无限累积对话历史。当对话过长时，它会自动丢弃最早的轮次，保留最近的交互。这就像人类的短期记忆——你记得刚才讨论的内容，但不太记得一小时前的每句话。

**策略二：上下文压缩（/compact）**
`/compact` 命令会主动压缩当前会话的上下文，将之前的对话摘要为更短的表述：

```bash
# 当感觉 Claude Code "忘记"了早期内容时
/compact

# 压缩后的效果
# 原始 50 轮对话 → 摘要为 3-5 段的总结
```

压缩是一个"有损"过程——细节会丢失，但核心决策和关键信息会被保留。压缩后，Claude Code 的行为会基于摘要而非原始对话历史。

**策略三：选择性文件读取**
Claude Code 不会一次性读取仓库中的所有文件。它使用智能策略来决定哪些文件需要被包含在上下文中：

- 根据你的任务描述推测相关文件
- 优先读取入口文件、配置文件、关键模块
- 读取文件内容的摘要或头部注释来判断是否相关
- 在需要时才深入读取具体实现

#### 长会话处理

对于长时间、多轮次的开发会话，建议采取以下策略：

1. **定期压缩**：每 20-30 轮对话后执行 `/compact`
2. **适时开启新会话**：当任务主题发生根本性变化时，开启新会话
3. **保留关键决策记录**：在项目根目录维护一个 `DECISIONS.md` 文件，记录重要的技术决策
4. **分阶段工作**：将一个大型任务拆分为多个相对独立的子任务，分别处理

```bash
# 推荐的工作流
# 阶段一：架构设计
claude -p "设计用户管理模块的架构，记录到 DECISIONS.md"

# 阶段二：实现核心逻辑
claude -p "实现用户管理模块的核心逻辑"

# 阶段三：编写测试
claude -p "为用户管理模块编写单元测试"
```

### 3. 工具调用机制

工具调用（Tool Use / Function Calling）是 Claude Code 最核心的技术特性之一。它让 Claude 不仅能生成文本，还能实际操作系统资源。

#### 工具定义与注册

每个工具都有明确的定义，包括名称、描述、参数列表和返回类型。Claude Code 在启动时会注册一组内置工具，类似以下结构：

```json
{
  "tools": [
    {
      "name": "read_file",
      "description": "读取指定文件的内容",
      "parameters": {
        "type": "object",
        "properties": {
          "file_path": {
            "type": "string",
            "description": "文件的路径"
          }
        },
        "required": ["file_path"]
      }
    },
    {
      "name": "write_file",
      "description": "写入内容到指定文件",
      "parameters": {
        "type": "object",
        "properties": {
          "file_path": { "type": "string" },
          "content": { "type": "string" },
          "mode": { "type": "string", "enum": ["overwrite", "append"] }
        },
        "required": ["file_path", "content"]
      }
    },
    {
      "name": "execute_command",
      "description": "在终端中执行 shell 命令",
      "parameters": {
        "type": "object",
        "properties": {
          "command": { "type": "string" },
          "timeout": { "type": "number" }
        },
        "required": ["command"]
      }
    },
    {
      "name": "git_operation",
      "description": "执行 Git 操作",
      "parameters": {
        "type": "object",
        "properties": {
          "operation": { "type": "string", "enum": ["commit", "branch", "diff", "status", "log"] },
          "args": { "type": "array", "items": { "type": "string" } }
        },
        "required": ["operation"]
      }
    }
  ]
}
```

Claude Code 预置的主要工具类别：

| 工具类别 | 包含工具 | 用途 |
|---------|---------|------|
| 文件操作 | `read_file`, `write_file`, `edit_file`, `delete_file`, `list_files` | 文件系统的读写管理 |
| 命令执行 | `execute_command`, `execute_script` | 运行 shell 命令和脚本 |
| Git 操作 | `git_status`, `git_diff`, `git_commit`, `git_branch` | 版本控制 |
| 搜索 | `grep_search`, `file_search`, `glob_match` | 在代码库中搜索 |
| 诊断 | `run_tests`, `lint_check`, `type_check` | 代码质量验证 |
| 网络 | `fetch_url` | 获取网络资源 |

#### 工具选择策略

Claude Code 如何决定在某个时刻应该调用哪个工具？这个过程类似于一个多步推理：

1. **意图分析**：分析用户输入，理解目标
2. **任务分解**：将目标拆解为子任务
3. **工具匹配**：为每个子任务匹配合适的工具
4. **参数填充**：确定工具的调用参数
5. **执行排序**：确定工具调用的顺序

例如，当用户说"帮我创建一个 Express 服务器"时，Claude Code 的内部推理过程大致如下：

```
用户意图：创建一个 Express 服务器

任务分解：
  1. 检查 package.json 是否存在 → 使用 read_file
  2. 初始化 npm 项目 → 使用 execute_command
  3. 安装 Express 依赖 → 使用 execute_command
  4. 创建 index.js 入口文件 → 使用 write_file
  5. 创建基本路由 → 使用 write_file
  6. 验证服务器能启动 → 使用 execute_command
```

#### 工具执行流程

完整的工具调用生命周期如下：

```
用户输入
   ↓
① 意图解析 → Claude Code 理解用户需求
   ↓
② 规划生成 → 生成执行计划（调用序列）
   ↓
③ 逐工具调用 → 按计划调用工具
   ↓
④ 结果反馈 → 工具执行结果返回给模型
   ↓
⑤ 结果分析 → 模型分析工具输出
   ↓
⑥ 下一步决策 → 继续调用工具或生成最终回复
   ↓
最终回复 → 向用户展示结果
```

每一步都是模型的一次独立推理。这意味着，工具调用和推理是交替进行的——模型调用一个工具 → 等待结果 → 分析结果 → 决定下一步。

实际执行过程中，用户可以看到工具调用的实时反馈：

```
[Claude Code 正在执行...]
📁 读取文件: package.json (已存在)
📦 执行命令: npm init -y
📦 执行命令: npm install express
📝 创建文件: index.js
📝 创建文件: routes/index.js
✅ 命令执行成功: node index.js
```

#### 结果处理与反馈

工具执行的结果会以结构化的方式返回给模型：

```json
{
  "tool_call_id": "call_abc123",
  "tool_name": "execute_command",
  "result": {
    "exit_code": 0,
    "stdout": "Server running at http://localhost:3000",
    "stderr": "",
    "duration_ms": 1250
  }
}
```

基于工具的执行结果，模型会做出下一步决策：
- **成功**：继续执行计划的下一步
- **失败（exit code ≠ 0）**：分析错误输出，尝试修复后重试
- **意外结果**：根据新情况调整计划

这种"执行-反馈-调整"的循环是 Claude Code 能自主完成复杂任务的关键。

### 4. 安全模型

Claude Code 能直接操作文件系统和执行命令，安全性是至关重要的设计考量。Anthropic 在安全方面构建了多层次防护体系。

#### 权限控制

Claude Code 的权限控制分为三个层级：

**层级一：用户授权（资格审查）**
每次 Claude Code 要执行关键操作（修改文件、执行命令）时，会首先请求用户确认：

```
Claude Code: 我将执行以下操作：
  - 创建文件: src/server.js
  - 创建文件: src/routes.js
  - 执行命令: npm install express
  
是否继续？(Y/n)
```

用户可以选择：
- `Y` 或直接回车：批准全部操作
- `n`：拒绝全部操作
- `s`：选择性批准（逐项确认）

**层级二：配置权限（策略控制）**
在 `~/.claude/claude.json` 中，可以设置更细粒度的权限策略：

```json
{
  "permissions": {
    "fileOperations": true,
    "commandExecution": true,
    "gitOperations": true,
    "networkAccess": false,
    "allowedCommands": ["npm", "node", "git", "python", "cargo"],
    "blockedCommands": ["rm -rf", "sudo", "chmod"],
    "allowedPaths": ["/home/user/projects/*"],
    "blockedPaths": ["/etc", "/usr", "/home/user/.ssh"]
  }
}
```

**层级三：操作确认（高风险操作）**
对于高风险操作（如删除大量文件、安装未知包、修改系统配置），Claude Code 会要求二次确认：

```
⚠️ 高风险操作警告
操作: 执行命令 rm -rf node_modules
风险评估: 此操作将永久删除目录 node_modules 及其所有内容
是否继续？(y/N)
```

#### 文件系统访问策略

Claude Code 对文件系统的访问遵循"最小权限"原则：

1. **默认工作目录限制**：默认只能访问当前工作目录及其子目录中的文件
2. **路径解析安全**：阻止路径遍历攻击（如 `../../../etc/passwd`）
3. **敏感文件保护**：对 `.env`、`credentials.json`、`~/.ssh/` 等敏感文件和目录有特殊保护
4. **文件大小限制**：对大文件（通常 >1MB）会警告或截断读取

```bash
# 安全规则示例
# ✅ 允许：读写项目目录中的文件
claude  # CWD: /home/user/project
# 可以访问 /home/user/project/src/main.js

# ❌ 拒绝：读写项目目录外的敏感文件
# 尝试读取 ~/.ssh/id_rsa → 被拒绝
# 尝试读取 /etc/shadow → 被拒绝
```

#### 网络访问控制

默认情况下，Claude Code 的网络访问权限被严格控制：

| 网络操作 | 默认权限 | 说明 |
|---------|---------|------|
| 连接 Anthropic API | ✅ 允许 | 核心功能必需 |
| 下载 npm 包 | ✅ 允许 | 项目依赖必需 |
| 访问公共 API | ⚠️ 需确认 | 如 GitHub API、Docker Hub |
| 访问内网资源 | ❌ 禁止 | 除非显式配置 |
| 启动监听端口 | ⚠️ 需确认 | 如启动开发服务器 |

#### 数据隐私保障

Anthropic 对数据隐私采用了多层保障措施：

1. **数据传输加密**：所有 API 通信使用 TLS 1.3 加密
2. **数据不用于训练**：Anthropic 承诺不会将 API 调用数据用于模型训练（除非用户明确选择加入）
3. **会话隔离**：每个会话的数据在传输和处理过程中与其他用户隔离
4. **本地处理**：敏感操作（如 API Key 管理）完全在本地完成，不会发送到云端

需要注意的是，所有代码内容在被 Claude Code 处理时都会发送到 Anthropic 的服务器进行推理。如果项目包含高度敏感的代码，应评估使用 Claude Code 的风险，或咨询法务和技术安全团队。

## 本章小结

1. Claude Code 的智能来自底层 Claude LLM（大语言模型），但在其之上叠加了意图解析、工具选择、工具执行和结果综合等工程架构层，形成了 Agent 式的自主工作能力。

2. 上下文窗口是 Claude Code 的"工作记忆"上限（最高 200K Token），决定了它能同时处理的信息量。当对话变长或项目变大时，需要通过 `/compact` 命令压缩或开启新会话。

3. 工具调用机制（Tool Use）是 Claude Code 能主动执行操作的核心。它通过预注册的工具定义（文件操作、命令执行、Git 操作等），结合多步推理自主规划任务执行流程。

4. 安全模型采用三层防护：用户授权（操作前确认）→ 配置权限（策略控制）→ 风险确认（高危操作二次确认）。文件系统访问遵循最小权限原则，敏感文件和目录有特殊保护。

5. Token 消耗决定使用成本。英文约 0.75 词/Token，中文约 1.5 字符/Token，代码约 3-4 字符/Token。可通过 `/cost` 命令实时监控消耗。

6. 对话历史以多轮消息形式组织，每次请求携带完整上下文。长会话中推荐定期压缩、适时开启新会话、保留关键决策记录。

## 思考题

1. **上下文窗口大小对代码生成质量有什么影响？**
   > **提示**：从两个角度分析：① 上下文窗口过小时，Claude Code 可能"看不到"项目中相关的代码，导致生成的代码与现有代码风格不一致、接口不匹配或重复实现已有功能；② 上下文窗口足够大时，模型能同时理解项目结构、依赖关系、代码约定等全局信息，生成的代码更符合项目上下文。建议根据项目大小合理规划会话，必要时通过分阶段工作来充分利用上下文窗口。

2. **工具调用机制如何保证安全性？**
   > **提示**：从三个层面回答：① 用户授权层——每次关键操作前请求用户确认；② 配置策略层——通过配置文件设置允许/禁止的命令路径和文件路径；③ 运行时防护层——阻止路径遍历攻击、保护敏感文件（.env、~/.ssh/ 等）、限制文件访问范围到当前工作目录。此外，Anthropic 的 API 数据传输全程加密，且不会将用户代码用于模型训练。
